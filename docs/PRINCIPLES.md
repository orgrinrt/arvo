# arvo. Architecture Principles


## Topology
Five crates. `arvo-format`, `arvo-placement` and `arvo-strategy` chain by
dependency, and that direction carries the design. `arvo-format` declares what
values exist: the representable set as one affine predicate, the six rounding
modes, the overflow policies, the adaptation as the pair of those two, and the
map that applies one. It has no workspace dependency, so nothing in it can
name a machine carrier. `arvo-placement` depends on it and derives where the
bits sit, keyed on occupancy. `arvo-strategy` depends on both and binds a
name to a placement objective and an adaptation selection.

`arvo-numeral` is the fourth, and it builds on the first two without reaching
for the strategy binding. It holds a value, one member of a declared signature
alone in the carrier its placement derives. Its sum is computed in that
carrier and gives the slot the format's own sum gives, and comparison is its
own.

`arvo-bits` is the fifth and does not chain with the others: it depends
on nothing in this workspace and ships one type, `Bits<const N: u32>`, a
value at an exact declared width with no arithmetic and no sign. It answers a
different question from the rest, what bits are held and not what values exist
or where they sit, so it sits beside `arvo-format` rather than above or below
it.

There is no facade. A crate re-exporting the five would sit above all of them,
and nothing needs one yet.

The split is by what a consumer must depend on to say one thing. Declaring
formats needs `arvo-format` alone; placing them needs `arvo-placement`;
choosing between placements needs `arvo-strategy`; holding a value and
computing with it needs `arvo-numeral`; naming a value at an exact width needs
`arvo-bits` alone, not `arvo-format`, because the two answer different
questions.

Everything that can be answered before the program runs is answered there, in
plain `const fn`. No crate here enables a nightly feature as it builds by
default, and the toolchain pin is a workspace policy rather than something these
crates reach for. The one exception is opt in: a cargo feature of `arvo-numeral`
that implements another crate's const trait.

`generic_const_exprs` is ruled out, and `min_generic_const_args` is what there is,
so a quantity derived from a const parameter is expressed within that bound rather
than around it. `arvo-format`'s design carries the reasoning.

## No heap. Ever.

No ad-hoc allocations. Allocation is scheduler-managed, declared at
compile time, never runtime-fabricated. The `no_std` and `no_alloc`
attributes aren't crate attributes first; they're the universe. `Vec`, `Box`,
`Rc`, `Arc`, `HashMap`, `String`, and the `format` macro don't exist here.

If an API feels like it wants a runtime-growable container, the shape
is wrong: reshape toward a trait-bound emitter / iterator / bounded
store. The heap is not temporarily available; there is no "just for
this moment".

## No bare primitives. Anywhere.

`u8` through `u128`, `i8` through `i128`, `f32`, `f64`, `usize`,
`isize`, `bool`, `Option`, `Result`, `String`, non-static `&str`, **they do not exist in this stack.** Not in public signatures, not
in private fields, not in internal `let` bindings, not in cast
expressions, not in type aliases, not in `const`/`static`
declarations, not in trait method parameter types, not in `where`
clauses, not in tuple-struct fields.

The type of a const generic parameter is the one excepted position,
so `Signed<const BITS: u32>` passes and an associated constant beside
it does not. A literal suffix is a different matter: it is not
excepted and it is also not reached, because a line scan wants a
non-identifier byte on each side of the name and a suffix carries a
digit in front of it. `0u32` goes unreported, and closing that wants
the parse rather than the line.

Substitute vocabulary lives in arvo and notko (`Maybe` / `Outcome` /
`Just`), and hilavitkutin-str supplies `Str` for interned string
identity. What arvo offers today is the format layer's own vocabulary,
`Width` and `Bool` among it, the exact-width container `Bits<N>`, and
the value `Num` with its integer aliases, which holds integers and
fixed point; a float value is not there to reach for yet. The
`arvo-types-only`, `no-bare-numeric`, `no-bare-option`,
`no-bare-result`, `no-bare-string` and `no-public-raw-field` lints
scan the `.rs` files of every crate that does not itself introduce the
category a lint guards, and block the commit the moment a bare
primitive is physically written there. `arvo-format`, `arvo-bits` and
`arvo-numeral` are declared as introducing the numeric category, since
the host integers have to be named somewhere for everything else to
avoid them, so the numeric lints leave those three alone and reach
`arvo-placement` and `arvo-strategy`.

If a foreign crate's trait or an unavoidable language feature forces
a specific std primitive, the first question is: *can we implement
the foreign contract on an arvo type instead?* If yes, that's the
path. If no, the crate smells like ass and we drop it. The escape
hatch `// lint:allow(<rule>) reason: ...; tracked: #N` exists only
for the genuinely unavoidable boundary, always with a tracked
remediation task.

### No `.0` field-access on arvo primitives

The no-bare-primitives discipline extends to field-access on arvo
primitives. The types a consumer computes with in the tree today are
three: `Bool` in `arvo-format`, a truth value, `Bits<N>` in `arvo-bits`,
an exact-width bit container, and `Num` in `arvo-numeral`, the numeral.
The format layer's own coordinates and counts, `Width`, `Slot`,
`SlotCount`, `Exponent`, `Magnitude`, `MagnitudeCount`, `Radix` and
`Arity`, are newtypes over a host integer in the same way and fall
under the same discipline. Each of the three carries
its operations as inherent `const fn`s (`Bool::and`, `Bool::or`,
`Bool::not`, `Bits::masked`, `Bits::cast`, `Num::add`, `Num::cmp`) and
each has its declared door out, and consumer code goes through those
rather than through `.0` on the inner primitive.

The format points in `arvo-format`, `Integer`, `UFixed`, `Biased`,
`Floating`, and the platform-width `USize` and `ISize`, are zero-sized
markers that name a format and hold no value: `points::USize` is
`UFixed<{ ::core::primitive::usize::BITS }, 0>` and `points::ISize` is
`Integer<{ ::core::primitive::usize::BITS }>`. They have no constants,
no constructor, no arithmetic and no field to read, so a field typed as
one carries nothing. The value is `arvo-numeral`'s `Num`, one datum of
a declared signature held alone in the carrier its placement derives,
for the signatures it admits: integers and fixed point at a constant
exponent, under wrapping or saturation. Its aliases `Uint`, `Int`,
`USize` and `ISize` name the integer points, so `arvo_numeral::USize`
is a value where `arvo_format::points::USize` is a format. No float
value type exists, and `IFixed`, `FastFloat` and `StrictFloat` are not
in the tree. A datum of a format is one point of its ambient domain
(`ruling::a_format_datum_is_one_point_and_a_saturating_end_is_one_point`);
what a value is at a shared placement, and what a composition's datum
is, stay open under `question::what_a_datum_stands_for`.

`x.0` on an arvo primitive is a smell. The alternatives:

- For computing on one: the type's inherent `const fn`s and constants.
- For boundary unwrap to a raw primitive (FFI, `core::*` APIs that
  take a host integer directly): the type's declared unwrap door,
  `Bool::get()` for a `Bool` and `Bits::raw()` for a `Bits<N>`. A
  `Num` gives its `Slot` through `Num::slot()`, which is the coordinate
  the format is stated in and not a host integer. The host integer
  behind a coordinate is one door further, `Slot::index()`, and the two
  platform-width aliases have a door of their own, `USize::host()` and
  `ISize::host()`. Document the boundary use with an inline comment if
  it's not obvious.
- For literal construction: a tuple-struct constructor is fine; the
  ban is on read-side field-access in arithmetic contexts, not on
  construction.

A workspace lint forbidding `.0` field-access on arvo primitives
outside the implementing crate is filed as a follow-up; the inherent
`const fn`s and the declared doors are the typed access path such a
lint would enforce.

## Think in traits, not types

Signatures take trait bounds. The concrete type is whatever the
caller brings.

**The question isn't "what type goes here"; it's "what is the contract
this position represents".** Monomorphisation makes trait-generic
signatures compile to the same code as concrete ones. Inference at
call sites means no turbofish.

Patterns throughout the stack are instances of this single mental
model: arvo-format's `Format` and `Adaptation` contracts,
hilavitkutin-api's 22 access/context/platform traits, the workspace
"no Vec in trait signatures" rule. All the same rule.

**Decision test:** "Can I imagine two implementations with different
behavior?" If yes, it's a trait slot, not a concrete type.

## No `Vec` or `Box<[T]>` in trait signatures

Direct consequence of the two principles above. Trait return types
use `impl IntoIterator`, `AsRef<[T]>`, or associated types. Sink
positions take `&mut impl Collector<T>` / `&mut impl DiagnosticSink`
/ `&mut impl ByteEmitter`. Concrete collection types are
implementation choices, not contracts.

Collections never cross ecosystem API boundaries. They live below
the boundary, on the implementer's side. The boundary carries data
flow, not storage.

## No `dyn`, no `Box<dyn>`, no runtime dispatch

All dispatch goes through monomorphised trait bounds. `dyn Trait`
forces late binding, heap via `Box<dyn>`, and vtable layouts that
aren't stable across compilations or `dlopen` boundaries.

Where extension across an ABI boundary is required, use registered
traits + `repr(C)` descriptors (inventory pattern), not `dyn`.

## Type taxonomy

Every type anywhere in source, public or private, fn sig or field,
local or cast expression, falls into one of three categories:

| Category | When | Examples |
|----------|------|----------|
| **Trait** | Varying behavior, shared contract, extensible | arithmetic ops, sinks, platform providers |
| **Newtype** | Fixed representation, validation at construction | `Bool`, `Bits<N>`, strategy markers |
| **`repr(C)` enum** | Closed set, crosses ABI boundary | none in the tree yet |

There is no fourth "bare primitive" category. Raw `u8`..`u128`,
`i8`..`i128`, `f32`, `f64`, `usize`, `isize`, `bool` never appear in
source; every numeric identity flows through arvo's type system.

Decision test is the same as above: if two plausible implementations
could differ, it's a trait.

If you're asking "should this enum have room for plugin extensions?"
It shouldn't be an enum. It should be a trait.

## Sizes are const at type level

Every container's capacity lives at type level:
`Seq<T, N>`, `Map<K, V, N>`, with `N` a type-level parameter. That
parameter is the const generic position the primitive obligation
excepts from the stack's own types, and even there the bare form is
used only where the alternative is genuinely painful. What type spells
`N`, the host's `usize` under that exception or a type the stack owns,
is open: no ruling says, no capacity type is built here, and whether a
capacity is a case where the alternative is genuinely painful has not
been decided. No runtime resize, no runtime grow. If a consumer needs a
bigger container, they pick the bigger type.

This is what the "no heap" principle bottoms out in at the storage
layer: capacity is a compile-time choice the consumer makes once,
not a runtime allocation the callee fabricates.

## One mechanism, not two

If two subsystems solve the same problem differently, one must go.
No parallel versioning tables, no parallel serialization paths, no
"fast path" alongside a "slow path". One mechanism per concern.

## Registered traits over `repr(C)` enums

If a concept might need extension, it's a trait + `#[register]` (or
the stack's inventory equivalent), not a `repr(C)` enum. Enums are
for truly closed sets only.

## One name, one source of truth

Every registrable type has `const NAME: &'static str`. The
descriptor's name field is a const pointer to it. No duplication,
no copies, no parallel naming.

## ZST markers for discrimination

Schema kinds, events, settings domains, storage locations, access
levels, HTTP methods, all ZSTs. Marker types carry compile-time
identity without runtime footprint.

## Primitive vocabulary (the stack's own)

The rule is "no bare primitives anywhere" (section above); the table
here documents WHICH stack type replaces WHICH bare primitive. It is
not a "for public API only" table. Every mapping applies everywhere
the bare primitive might otherwise appear.

| Don't | Do | Lives in |
|-------|----|----------|
| `Option<T>` | `Maybe<T>` | `notko` |
| `Result<T, E>` | `Outcome<T, E>` | `notko` |
| `Vec<T>` return | `impl IntoIterator<Item=T>` / trait-bound sink | trait at the API boundary |
| `&mut Vec<T>` param | `&mut impl Collector<T>` | hilavitkutin-api contracts |
| `HashMap<K, V>` | `Map<K, V, N>` | hilavitkutin-api |
| `String` owned | `Str` | `hilavitkutin-str` |
| `&str` non-static | `&'static str` or `Str` | as above |
| `usize` / `isize` | domain newtype, or `arvo_numeral::USize` / `ISize` where the value is a platform-width integer; a const generic parameter is the excepted position, bare only where the alternative is genuinely painful | `arvo-numeral` for the value; `arvo-format`'s `points::USize` and `points::ISize` name the format and hold no value |
| `u8..u128` / `i8..i128` | `Uint<BITS, A>` / `Int<BITS, A>`, or `T: Boundable` / `T: NonZeroable` | `arvo-numeral` for the value, `notko` for the bounds; `Integer` and `UFixed` name formats and hold no value |
| `f32` / `f64` | no float value type exists yet; `Floating` names the format and holds no value | `arvo-numeral` admits no floating format |
| `bool` | `Bool` | `arvo-format` |

Escape hatches: std trait method impls whose signatures are fixed by
the language (`fn next() -> Option<Self::Item>`, `fn partial_cmp() ->
Option<Ordering>`, `fn fmt() -> fmt::Result`). Each one carries
`// lint:allow(<rule>) reason: std trait parity; tracked: #N`.
Everywhere else, the rule stands.

`lint:allow(...)` is NOT for skeleton convenience; it's for tracked
debt with a linked task id. If the suppression isn't traceable to a
specific follow-up, the design is wrong, not the rule.

*The following principles are specific to arvo.*

## arvo: the fixed-point arithmetic stack

arvo is a standalone `no_std` numeric primitive library family,
cross-project; consumed by hilavitkutin and downstream applications.
It is the exclusive numeric foundation for every consumer in the
stack.

Every numeric position in the stack is arvo's. What the tree has so
far is the format a numeral declares, `Integer`, `UFixed`, `Biased`,
`Floating` and any format another crate adds, each a zero-sized marker
holding no value. A datum of a format is one point of its ambient
domain (`ruling::a_format_datum_is_one_point_and_a_saturating_end_is_one_point`).
A type holding one at sole occupancy is what
`ruling::behaviour_is_stated_per_declared_signature_and_the_premise_dissolves`
and `ruling::the_derivation_is_a_placement_and_the_operation_set_is_an_admission_rule`
presuppose, and `arvo-numeral` holds the integer and fixed points that
way; that clause as a statement of its own has one cold read and is open. What a composition's datum is, and
what a value is at a shared placement, stay open under
`question::what_a_datum_stands_for`. Bare Rust primitives (`u8`, `u16`,
`u32`, `u64`, `u128`, `i8`, `i16`, `i32`, `i64`, `i128`, `f32`,
`f64`, `bool`, `usize`, `isize`) effectively do not exist in
arvo's universe. This is not a preference, not a default, not a
"usually use": it is the identity. Reach for a raw primitive and
you have forgotten what arvo is.

The discipline is enforced at commit by the `arvo-types-only` lint,
beside the others the section on bare primitives names, over the
crates that do not introduce the numeric category, as that section
says.

Algorithm crates, when they come, are generic over numeric trait bounds and
reflexively reach for arvo primitives. They do not accept or return bare
types at any boundary. None ships on the current base.

Strategy markers are type parameters, not runtime config. They embed
operational intent into the type system, and the caller is to pick the
tradeoff at the type level. `Hot`, `Warm`, `Cold` and `Precise` are
the presets that ship, as implementors of an open concept, so a fifth
needs no edit to anything already there. No value in the tree takes a
strategy yet: `Num` is parameterised by a declared signature and its
aliases by an adaptation, and `arvo-numeral` does not depend on
`arvo-strategy`.

`Bool`, `Bits<N>` and `Num`, and the format layer's coordinates and
counts beside them, are `repr(transparent)` over their host container,
and the format points are zero-sized, so each is laid out as the
container it holds and nothing more.

## no_std, no alloc

Every crate is `no_std` with no allocation. All collections are
const-sized. Consumers own allocation strategy; arvo never calls out.

## Strategy markers are load-bearing

A strategy is not decoration. As `arvo-strategy` has it today, it
binds a name to a placement objective, which is what the derivation in
`arvo-placement` is keyed on, and to an adaptation selection, so the
marker a type comes to carry says what it gives up and what for. It names no
implementation and owns none.

Default strategy is `Warm` unless called out, and every semantic
alias carries a default for its strategy parameter. The tree is short
of that today, since no alias takes a strategy at all, and which
adaptation the default names for integers is not settled.

## Monomorphisation is the dispatch

No `dyn`. No `TypeId`. No `std::any`. Sub-crates are generic over
trait bounds (`Format`, `Slots` and the other contracts in
`arvo-format`); consumers pick concrete instantiations at use site.

The monomorphised function IS the type identity. Compiler proves
devirtualisation; we never pay for dispatch.

## Contracts before concretes

- `arvo-format` declares what values exist and what an adaptation is.
- `arvo-placement` derives where the bits sit, and reads no adaptation.
- `arvo-strategy` binds a name to a choice between placements.
- `arvo-numeral` holds a value of a declared signature, with a sum in
  its carrier that gives the format's own result and a comparison of
  its own.
- `arvo-bits` ships one concrete with no contract behind it, because an
  exact-width value at a declared width has one shape rather than an open
  set of them for another crate to supply a second instance of.

Depending on the contracts rather than on the instances is what lets a
consumer change a placement without touching anything that declares a
format.

## Sizes are const

Every size lives at type level: `Bits<N>`, `Seq<T, N>`.
No runtime resize, no runtime grow. If a consumer needs a bigger
container, they pick the bigger type.

## Zero platform dep

arvo has no opinion about syscalls, threads, clocks, or filesystems.
Everything is pure compute on const-sized containers. Platform
concerns live in consumer crates (notably `hilavitkutin`).
