# arvo. Architecture Design

> Numeric primitives whose behaviour is the consumer's to select, through
> strategy markers at type level. `#![no_std]`, no alloc. Zero dependency
> on platform. Designed so every downstream consumer shares one
> numeric layer.

## Principles

The primitives are parameterised by strategy. A numeral's behaviour is to be
selected at type level by a strategy, without runtime dispatch. `Hot`, `Warm`, `Cold` and
`Precise` ship as presets and the set is open. No value in the tree takes a
strategy yet, since `Num` is parameterised by a declared signature and its
aliases by an adaptation.

Every crate is `no_std` with no allocation, and every size is const, so
consumers pre-allocate and arvo never calls into an allocator.

The crates are written against trait contracts and are generic over trait
bounds, so downstream code picks its own concrete instantiations.

Monomorphisation is the dispatch. There is no `dyn` and no `TypeId`, and the
monomorphised function is the type identity.

Everything answerable before the program runs is answered there, in plain
`const fn`. No crate enables an unstable feature as it builds by default, so no
trait here is a `const trait`, and the operations wanted in const context are
inherent `const fn`s on their types. One cargo feature of `arvo-numeral`, off
by default, enables `const_trait_impl` for its const impl of another crate's
trait, and a consumer of it needs no feature of the toolchain for that.

## Crate topology

Six crates. Four of them chain by dependency, and the dependency direction is
what enforces the design rather than a rule asking for it: `arvo-format` cannot
name a carrier because it does not depend on the crate that has one, which is
how "every operation is a function of the declared width and never of the
machine carrier" stays true under later edits. The fifth, `arvo-bits`, sits
parallel to `arvo-format` rather than in the chain, depending on nothing in
this workspace. The sixth, `arvo-digest`, sits on `arvo-bits`, whose door its bytes come
through and whose container holds its result, and on `arvo-numeral`, whose
wrapping product FNV-1a multiplies by.

The set is open at both ends it can be. A new numeral joins by implementing
`Format`, a new overflow policy by implementing `Overflow`, and a new strategy by
implementing `Strategy`, none of which edits anything that already exists. The
rounding vocabulary is the one closed enumeration, fixed at six names, so a
const predicate over it is exhaustive and a seventh mode is a different design
rather than a new row.

## Contracts and their instances

Every crate here is a small set of contracts plus the instances that ship with
them. `Format`, `Ambient`, `Quantum`, `Slots`, `Rounding`, `Overflow`,
`Adaptation`, `DeclaredSignature` and `Operation` are contracts; `Integer`,
`UFixed`, `Biased`, `Floating`, the six modes, the three policies and the
operations `Add`, `Neg`, `Sub`, `Mul`, `Div` and `Convert` are instances of
them. In `arvo-numeral`, `Sole`, `DebugCheck`, `NamesAdaptation` and `Identity`
are contracts, and `Abort`, `Quiet` and `Additive` are instances.

`Bits<const N: u32>` in `arvo-bits` is the one exception to that shape, and
naming it as one is worth a sentence rather than leaving it to look like an
oversight. There is no open contract behind it, because there is nothing for
an outside crate to implement: an exact-width value at a declared width has
one shape, and a second implementation would not be a new instance of a
concept, it would be a second definition of the same fact.

The reason the split falls this way is what a consumer has to depend on to say
one thing. Stating what values exist needs `arvo-format` and nothing else.
Stating where they sit needs `arvo-placement` on top of it. Choosing between
placements needs `arvo-strategy` on top of both. Holding a value and computing
with it needs `arvo-numeral`, which builds on the first two and not on the
strategy binding. Saying the same thing in an
industrial convention's own words is still stating what values exist, so it needs
`arvo-format` and nothing else, and the conventions ship there beside the
parameterisation points. A consumer that only declares formats never compiles a
carrier ladder. Naming a value at an exact width needs `arvo-bits` and nothing
else either, including not `arvo-format`: the two answer different questions
and a consumer wanting only one of them should not compile the other.

## Dependency direction

Strictly upward within the chain, and it carries a design constraint
rather than a convention. `arvo-format` has no workspace dependency, so nothing
in it can mention a carrier; `arvo-placement` depends on it and derives one;
`arvo-strategy` depends on both and binds a name to a choice between them.
`arvo-numeral` depends on the first two and holds a value in the carrier the
placement derives, reading the format for everything it computes.
`arvo-bits` depends on none of them: it sits beside `arvo-format` rather
than above or below it, because the value it holds and the format that would
describe a numeral's representable set are answers to different questions, and
a consumer of one should not be made to compile the other. `arvo-digest`
depends on `arvo-bits` for the bytes it reads, the container its result is held
in and the width a consumer narrows it to, on `arvo-numeral` for the
wrapping product and on `arvo-format` for the adaptation that product is taken
under, so it writes neither the walk's door nor its arithmetic. There is no facade today, and a
crate that re-exported the six would sit below all of them rather than above.

## Consumers

arvo is a library rather than a program, so how it gets used is not fully known
here. What it is built for is the algorithm crates every downstream repository
uses, and the contracts for things that compose into units bigger than numerals
alone. The numeral base has to work first, which is what the crates above are.

**The consumers named in earlier versions of this document, hilavitkutin and
vehje, used crates that no longer exist.** Those crates were removed on
2026-08-08 and the surfaces they offered have not been rebuilt on the current
base. A downstream repository pinning this branch gets the crates above and
nothing else, and that is the honest statement of what is available rather than
of what is planned. `arvo-numeral` is the first value type on the current base:
integers and the other constant-quantum points, with their sum, difference,
negation, product, quotient, conversion and comparison, and nothing yet of a
remainder. `arvo-bits` is new source written from the current canon,
not a restoration of anything removed, and it answers one piece of what those
removed crates used to answer, an exact-width container, rather than the rest
of it. Hashing is `arvo-digest`'s, new source
rather than restored from the removed hash crate, and string identity is not
shipped here.
