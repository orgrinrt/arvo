# arvo-spectral. Design

Spectral graph methods on fixed-capacity structures.
`#![no_std]`, no alloc. Operates on dense weighted matrices via
`arvo_tensor::Matrix<W, C>` and on CSR-shaped adjacency via the
`LinearOperator` trait. Small-N spectral methods fit in
stack-allocated dense arrays; larger-N consumers reach the same
algorithms through the operator trait without materialising a dense
N x N storage.

The crate depends on
`arvo-storage`, `arvo-bits-contracts`, `arvo-numeric-contracts`,
`arvo-tensor`, `arvo-bitmask`, `arvo-sparse`. The prior `arvo-bits`
direct dep is replaced by `arvo-bits-contracts`.

## Matrix wrapper

Dense square matrix storage uses `arvo_tensor::Matrix<W, C>`:
`#[repr(transparent)]` over the composition `C::Array<C::Array<W>>` with
`get(i: USize, j: USize) -> W` / `set(i: USize, j: USize, v: W)` /
`from_fn(|r, c| -> W)` / `diagonal()`. Previously shipped local to
arvo-spectral; promoted to arvo-tensor
(arvo-comb sweep) for shared use across the algorithm crates.
arvo-spectral re-exports:

```rust
pub use arvo_tensor::Matrix;
```

so existing consumers keep their `arvo_spectral::Matrix` import
paths.

Generic over numeric traits for weights and eigenvectors. Weight
matrices use trait-bounded types; eigenvectors use float-like types.
Weight-to-float conversion happens at the API boundary via `Into<F>`.
Consumer instantiates with concrete arvo types; this crate is library
code.

## Capacity

The capacity is a TYPE: `C: Capacity` (arvo-tensor's `Capacity`) in
place of the prior `const N: Cap`. Array storage is the associated
type `C::Array<X>`, so no `cap_size` sits in type position; a body
that needs the count as a value reads `cap_size(C::CAP)`.

Partition outputs use the `(USize, C::Array<USize>)` classification
shape, parallel to arvo-sparse Dulmage-Mendelsohn. The shape scales
with the consumer's chosen `C`; the optional 64-cap mask form is
recoverable via `arvo_sparse::classification_to_mask` for consumers
fitting in a single word.

Spectral methods are typically used at small N (about 30 iterations,
N around 32 in observed workloads), but the operator framing means
larger-N consumers reach the same algorithms without materialising a
dense `Matrix<W, C>`. The `SparseLaplacian` operator runs
power iteration and Fiedler directly off CSR adjacency in O(N + NNZ)
per `apply`.

## Laplacian construction

The Laplacian is an abstract operator (`L = D - A`) defined by its
action `L * x` rather than materialised storage. Two concrete
representations ship today: `Matrix<W, C>` (dense, the existing
materialised form) and `SparseLaplacian` (CSR-driven). Both
implement `LinearOperator<F, C>`. Spectral methods (power iteration,
Fiedler) accept any operator that satisfies the trait, so consumer
choice of representation is independent of algorithm choice.

## Linear operator contract

Spectral methods (power iteration, Fiedler) only ever ask the
operator one question: what is `L * x` for a vector `x`? The trait
names that interface; algorithms become generic over the operator.
Dense `Matrix<W, C>` keeps its existing impl by reading entries via
`get(i, j)` and accumulating into `out`; `SparseLaplacian`
adds a CSR-driven impl that computes `L * x` directly from sparse
adjacency in O(N + NNZ).

```rust
pub trait LinearOperator<F, C: Capacity> {
 fn apply(&self, x: &C::Array<F>, out: &mut C::Array<F>);
 fn live_dim(&self) -> USize;
}
```

The trait is plain (non-const). Power iteration and Fiedler run in
non-const contexts; the const-trait family is reserved for shapes
that benefit from const callability, which `apply` does not.

`live_dim` reports how many nodes the operator spans. A dense
`Matrix` returns `cap_size(C::CAP)`; a `SparseLaplacian` over a loose CSR
returns its live row count. The iterative methods iterate over
`live_dim()` rather than `cap_size(C::CAP)`, so a loose graph's empty
slack rows are excluded from the Fiedler iteration and the partition
budget. The method is required, not defaulted: every operator
declares its span, so a loose consumer cannot silently inherit a
full-capacity dimension.

## Sparse Laplacian

`SparseLaplacian` carries a borrow of a `T: SparseAdjacency<C>`
and the per-edge weight slice; it implements
`LinearOperator<F, C>` by computing `L * x = D * x - A * x` directly
from the adjacency without materialising L. Cost: O(N + NNZ) per
`apply`. Benefit: no dense `N * N` storage, no quadratic
re-materialisation from sparse input.

```rust
pub struct SparseLaplacian<'data, T, W>
where
 T: SparseAdjacency<C>,
{
 adjacency: &'data T,
 weights: &'data [W],
}
```

Constructor `SparseLaplacian::new(adjacency: &'data T, weights:
&'data [W]) -> Self` borrows both. Weight-to-float conversion happens
inside `apply` (`weights[edge_idx].into()`). Consumer supplies
integer weights (arvo fixed-point); algorithm body operates in float
(FastFloat / StrictFloat). The capacity `C` is carried by the
adjacency `T`'s `SparseAdjacency<C>` impl.

## Power iteration

Compute the dominant eigenvector of any `LinearOperator<F, C>` via
iterative `apply`. Capacity-typed stack-allocated: two `C::Array<F>`
buffers (input and output, ping-pong). Convergence
after a fixed iteration count, typically about 30 at pipeline scale.

Stack budget at N=64: two `C::Array<F>` eigenvector buffers, no
operator storage. The operator's storage is the operator's concern:
dense `Matrix<W, C>` carries `N * N * size_of(W)` bytes; sparse
`SparseLaplacian` borrows external storage and pays nothing
on the algorithm's stack frame. Microseconds at pipeline scale. Zero
heap.

## Fiedler vector

The eigenvector corresponding to the second-smallest eigenvalue of
the Laplacian. Computed via power iteration on the deflated
Laplacian (subtract the projection onto the constant eigenvector).
The deflation orthogonalises against the constant eigenvector at
each iteration; this is unchanged from the materialised-Matrix shape.

The Fiedler vector's sign partitions the graph: positive entries in
one group, negative in another. This bisection minimises the cut
weight, the total edge weight crossing the partition boundary.

## Spectral bisection

```rust
fn spectral_bisection<C: Capacity, F>(
 fiedler: &C::Array<F>,
) -> (USize, C::Array<USize>)
where
 F: TotalOrd + Copy + FromConstant,
```

Partition nodes into two groups by the sign of the Fiedler vector.
The output is a `(class_count, class_id_per_node)` classification array
with `class_count = 2` for a successful bisection. Class IDs: `0 =
positive`, `1 = non-positive`. The cut weight (sum of edge weights
between groups) is minimised by construction of the Fiedler vector.

Why spectral beats greedy: spectral considers the entire graph
structure globally. Greedy partitioning finds locally optimal
solutions that can miss the global minimum cut.

## Spectral bipartitioner

Problem-shaped trait family parallel to arvo-sparse's. Consumers
needing minimum-cut bipartition call the problem name; the named
impl is the default.

```rust
pub const trait SpectralBipartitioner<C: Capacity>:
 SparseAdjacency<C>
{
 fn bisect<F>(&self, iterations: USize)
 -> (USize, C::Array<USize>)
 where
 F: Add<Output = F>
 + Sub<Output = F>
 + Mul<Output = F>
 + Sqrt
 + Recip
 + TotalOrd
 + Copy
 + FromConstant;
}
```

Default impl runs Fiedler via `SparseLaplacian` wrapping `self`,
then `spectral_bisection` on the resulting eigenvector. Consumers
override when they ship a different bipartitioning strategy
(multilevel coarsening, ratio-cut variants, weighted balanced
bisection).

## k-way partitioning

```rust
fn k_way_partition<Op, C: Capacity, K: Capacity, F>(
 operator: &Op,
 iterations: USize,
) -> (USize, C::Array<USize>)
where
 Op: LinearOperator<F, C>,
 F: Add<Output = F>
 + Sub<Output = F>
 + Mul<Output = F>
 + Sqrt
 + Recip
 + TotalOrd
 + Copy
 + FromConstant,
```

For more than 2 groups: recursive bisection. Apply spectral bisection
to get 2 groups, then recursively bisect each group until K groups or
a group cannot be usefully split. Returns `(actual_partition_count,
partition_id_per_node)`; `actual_partition_count` may be less than the
`K` capacity.

Used when the consumer needs minimum-cut grouping of a weighted
graph at a scale where greedy bisection is insufficient. Researched
threshold: engage spectral when the grouping problem has more than
5 nodes; below that a single trunk suffices. Power iteration
converges in about 30 iterations at pipeline scale.

## Consumers

Typical usage: build a weighted graph where nodes are groupable
units and edge weights represent shared work or data volume between
them. Fiedler bisection cuts along the boundary with minimum total
shared work. Consumer supplies concrete numeric types: weights as
arvo fixed-point, eigenvectors as float (FastFloat / StrictFloat,
selected per build configuration).
