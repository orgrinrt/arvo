# Workflow

How a consumer uses arvo from a Rust project, what shape the dependency
takes, and how arvo evolves.

## Adding arvo to a project

```toml
[dependencies]
arvo = { version = "0.0", default-features = false }
```

arvo is `#![no_std]` and ships with no platform dependency. The crate
re-exports the public surface from the layered foundation crates
(`arvo-storage`, `arvo-strategy`, `arvo-bits-contracts`, ...); reaching
for `arvo` directly is the supported path. Only depend on a foundation
crate by name when an explicit dependency-size reduction is wanted.

## Picking primitives

Reach for the exact width: `Uint<3>`, `Uint<14>`, `Int<47>`. The
`Strategy` parameter defaults to `Warm`. Choose `Hot` for the fast
release path, `Precise` for saturating semantics, `Cold` for bitpacked
column-store layouts. The strategy marker is a type-level knob that
drives container width and codegen; it does not change at runtime.

Fixed-point arithmetic uses `UFixed<I, F, S>` and `IFixed<I, F, S>`,
where `I` is integer bit count and `F` is fractional bit count. Floats
use `FastFloat` and `StrictFloat`. Boolean values use `Bool`. Pointer-
width sizes use `USize` and the `Cap` newtype for type-level capacities.

## Pre-1.0 stability

arvo is in pre-1.0 design phase. Public surfaces stabilise at `0.0.x`;
expect breaking changes between minor versions. Consumers depending on
arvo today pin a specific version; once the surface stabilises and the
first `0.1` release ships, semver guarantees apply.

## Reporting issues

Issues and feature discussion happen on the GitHub repo. Patches arrive
as feature-branch PRs. The repository's CONTRIBUTING file (when shipped)
describes the local validation loop.
