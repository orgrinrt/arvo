# arvo-hash. Design

L2 hash-domain types and algorithm contracts. Ships a domain alias
over the `Bits` storage primitive (now in `arvo-storage`), generic
trait contracts for hash algorithms, and two concrete algorithms:
`XxHash3<const N: u16>` (default) and `Fnv1a<const N: u16>`
(option for known-good fits).

`#![no_std]`, no alloc.

Per (#314): arvo-hash takes a direct dep on `arvo-bits-contracts` for the new `NarrowFromU64<N, S, Sign>` trait used by the bounded-generic `Hasher` impl. Other deps unchanged: imports flow through the `arvo` facade for `Bits`, `Hot`, `BitsContainerFor`. The `arvo-bits-contracts` direct dep is added because `NarrowFromU64` is the contract surface the algorithm impls bind to; pulling it through the facade would loop the dep graph back through arvo.

Per (#316): the `Bits` const-generic and `Hasher<const N: u16>` are u16-typed; the `Width` newtype layer used in earlier rounds is gone. `width_u8` / `width_u16` const helpers are not used by hash crate code post-#316.

## Why this crate exists

Hashes (content hashes, name hashes, pass-key identity) are numeric algorithms on opaque bit-patterns. The stack needs one home for the runtime carriers. arvo provides the generic `Bits` container; arvo-hash provides the domain vocabulary (`ContentHash`), the algo contracts (`Hasher` for streaming, `ConstHash<N, S, Sign>` for one-shot const-callable construction) consumers parameterise over, and the canonical algorithms (`XxHash3`, `Fnv1a`).

Growth surface (additional concrete algorithms, cryptographic hashes
as a sibling crate, semantic aliases beyond ContentHash) is tracked
in BACKLOG.

## Types

### ContentHash

A type alias for `arvo::Bits<64, Hot>`. Carries the canonical
content-addressed hash identity for downstream consumers
(hilavitkutin-str interner, hilavitkutin-persistence
StringTableEntry, clause resolver pass-key identity, column-store
entity content addressing). Consumers that want a named type at
call sites bind `ContentHash` instead of the raw `Bits<64, Hot>`.

```rust
pub type ContentHash = arvo::Bits<64, Hot>;
```

The width widened from 28 to 64 in Pass B.2 of.
64 bits matches `XxHash3`'s natural output and reduces collision
probability to negligible levels for million-entity workloads (the
prior 28-bit identity carried meaningful collision risk past about
16k unique values; 64 bits clears the projected scale by orders of
magnitude).

A direct type alias rather than a newtype: the semantic domain is fully captured by the bit width; no additional invariants warrant a distinct type. Per (#316), the `Bits` const-generic is `u16`; `Hasher` / `Fnv1a` / `XxHash3` carry `const N: u16` directly.

## Algorithm contracts

### Hasher (canonical, streaming)

```rust
use arvo::{Bits, Hot};
use arvo::strategy::{BitsContainerFor, Unsigned};

pub trait Hasher<const N: u16>
where Hot: BitsContainerFor<N, Unsigned>
{
 fn update(&mut self, bytes: &[u8]);
 fn finalize(self) -> Bits<N, Hot>;
}
```

Streaming hash: feed bytes incrementally, finalise to an N-bit opaque pattern. Consumers implementing a hash algorithm implement this trait.

The `&[u8]` parameter is workspace-rule exception #4 (boundary input from raw bytes; canonical hash input shape).

Round 4 (#314) collapses the per-N macro paste in algorithm impls (`impl_fnv1a!` / `impl_xxhash3!`) into a single bounded-generic `impl<const N: u16> Hasher<N> for Fnv1a<N>` per algorithm. The width-dispatched narrowing step from `u64` algorithm state to the dispatched container lifts to `NarrowFromU64<N, S, Sign>` (declared in `arvo-bits-contracts`). Consumer-facing surface unchanged; impl-block count drops from 128 hand-written bodies to 2.

### ConstHash<N, S, Sign> (one-shot, const-callable)

The arvo's content-addressing surface for compile-time hash construction. `ConstHash<N, S, Sign>` mirrors the strategy-aware `BitsContainerFor<N, Sign>` cascade and produces a typed `Bits<N, S, Sign>` from a byte slice.

```rust
use arvo::{Bits};
use arvo::strategy::{BitsContainerFor, Strategy, Signedness};
use arvo_bits_contracts::NarrowFromU64;

pub const trait ConstHash<const N: u16, S: Strategy, Sign: Signedness>: Sized
where
 S: BitsContainerFor<N, Sign>,
 <S as BitsContainerFor<N, Sign>>::T: [const] NarrowFromU64<N, S, Sign>,
{
 fn hash_const(bytes: &[u8]) -> Bits<N, S, Sign>;
}
```

The `[const]` host-effect bound on the supertrait constraint is required for cross-crate const dispatch. Sketch 02 validates the chain `ConstHash → NarrowFromU64 → BitsContainerFor → Project` resolves at both compile time and runtime in a downstream crate.

Algorithms implement `ConstHash` once each, generic over `N, S, Sign`. Per-N `hash_const` inherent methods on `Fnv1a<N>` and `XxHash3<N>` are gone; consumers reach for `<Fnv1a<N> as ConstHash<N, Hot, Unsigned>>::hash_const(bytes)` (or import the trait and write `Fnv1a::<N>::hash_const(bytes)` resolved through trait associated-fn lookup).

The user-flagged discipline issue with per-N inherent methods is fixed: hash-as-const-construction is now a focused trait contract, not a per-N inherent bolted onto every algorithm implementor.

### HasherExt is removed

The `HasherExt<N>: Hasher<N>` blanket extension trait shipped before Round 4 to provide one-shot `.hash(bytes)` ergonomics. The cross-crate `.hash()` method dispatch over the const-impl + Pattern C blanket-impl chain failed on rustc nightly (recorded as #316 apply-time finding 2). With `ConstHash<N, S, Sign>` providing the one-shot `hash_const` form through Pattern C dispatch directly, `HasherExt` is no longer the right shape: it left consumers with two parallel APIs where one silently failed cross-crate.

Round 4 deletes `HasherExt` outright per `no-legacy-shims-pre-1.0` (no deprecation alias). Streaming `Hasher<N>` stays for incremental hashing; one-shot ergonomics ride on `ConstHash`.

## Default algorithm choice

`XxHash3<const N: u16>` is the default hash family. `Fnv1a<const N: u16>`
remains as an explicit option for known-good fits (small inputs in the
8-16 byte band where FNV-1a stays competitive on bandwidth, or
algorithm-locked test fixtures).

The choice between defaults considered the arvo's primary
consumer workload (16-128 byte entity content addressing, millions
of entities in flight). XxHash3 wins on bandwidth above the 32-byte
input mark; FNV-1a holds at 8-16 bytes. The default crosses the
break-even mark into the consumer's typical band.

Per the `arvo-toolbox-not-policer` workspace rule, both ship; the
consumer picks. `ContentHasher` is the trait; `XxHash3` and `Fnv1a`
are concrete strategies satisfying it.

## Concrete algorithm: XxHash3

```rust
use arvo::{Bits, Hot};
use arvo::strategy::{BitsContainerFor, Unsigned};

/// Streaming XxHash3 hasher with N-bit output.
///
/// `XxHash3<N>` produces an N-bit hash via masking from the
/// algorithm's natural 64-bit output. Bound: `N <= 64` (implicit
/// via `Hot: BitsContainerFor<N, Unsigned>` plus algorithm-state
/// width). For 128-bit output see the `XxHash3_128` BACKLOG entry.
pub struct XxHash3<const N: u16>
where Hot: BitsContainerFor<N, Unsigned>;

impl<const N: u16> Hasher<N> for XxHash3<N>
where Hot: BitsContainerFor<N, Unsigned>
{
 fn update(&mut self, bytes: &[u8]) { /* SRC */ }
 fn finalize(self) -> Bits<N, Hot> { /* SRC */ }
}

impl<const N: u16> const ConstHash<N, Hot, Unsigned> for XxHash3<N>
where
 Hot: BitsContainerFor<N, Unsigned>,
 <Hot as BitsContainerFor<N, Unsigned>>::T: [const] NarrowFromU64<N, Hot, Unsigned>,
{
 fn hash_const(bytes: &[u8]) -> Bits<N, Hot, Unsigned> { /* SRC */ }
}
```

The `Hasher<N>` impl is a single bounded-generic block (not 64 hand-written impls). Internal narrowing dispatches through `<Hot as BitsContainerFor<N, Unsigned>>::T as NarrowFromU64<N, Hot, Unsigned>>::narrow_u64`. Consumer-facing ergonomics are identical; the algorithmic difference is the body of `update` / `finalize` and the bandwidth profile.

The streaming `update` is bounded by a 256-byte stack buffer. Bytes beyond the buffer trigger `debug_assert!` in debug builds (silent in release; consumers who need a higher cap chunk explicitly or use `ConstHash::hash_const` directly with the full byte slice). The streaming surface fits the arvo's content-addressing band (16-128 bytes typical); above that, the one-shot `ConstHash` path is the recommended consumer surface.

The `ConstHash<N, Hot, Unsigned>` impl ships; non-Hot strategy impls are BACKLOG.

The width bound is enforced through `Hot: BitsContainerFor<N, Unsigned>`: `Hot` covers `1..=128` natively, but FNV-1a-64's 64-bit state caps practical use at `N <= 64`. ## Usage

Downstream code parameterises over the trait; swapping algorithm is a type-parameter change, not a call-site rewrite.

Streaming:

```rust
fn intern_chunks<H>(mut hasher: H, chunks: &[&[u8]]) -> ContentHash
where
 H: Hasher<64>,
{
 for chunk in chunks { hasher.update(chunk); }
 hasher.finalize()
}
```

One-shot, const-callable:

```rust
const HASH: ContentHash = <XxHash3<64> as ConstHash<64, Hot, Unsigned>>::hash_const(b"hello");
```

Or via trait-in-scope shorthand:

```rust
use arvo_hash::ConstHash;

const fn fingerprint(bytes: &[u8]) -> ContentHash {
 XxHash3::<64>::hash_const(bytes)
}
```

To swap algorithm, change the type the caller supplies. No site edits; the trait signatures stay put.

## Dependencies

- `arvo` (facade): re-exports the storage primitives `Bits<const N: u16, S, Sign>`, the strategy markers (`Hot`, `Warm`, `Cold`, `Precise`), the `Unsigned` / `Signed` Sign markers, and the unified `BitsContainerFor<N, Sign>` projection. arvo-hash imports these via the facade.
- `arvo-bits-contracts` (direct dep added): hosts the `NarrowFromU64<N, S, Sign>` const trait that the bounded-generic `Hasher` impl binds to. The bound `<S as BitsContainerFor<N, Sign>>::T: [const] NarrowFromU64<N, S, Sign>` is the arvo-level contract that lets one impl block cover all valid `(N, S, Sign)` combinations without per-N enumeration.

The previously declared `arvo-bits` dep was dropped and stays dropped.

## What this crate does NOT contain

- Cryptographic hashes (SHA, BLAKE); out of scope entirely. A
 sibling arvo-crypto crate covers cryptographic needs if they
 surface.
- Hash widths beyond 64 bits in `Fnv1a`; tracked as `Fnv1a128` in
 BACKLOG.
- Other non-cryptographic algorithms (xxHash, CRC32); tracked in
 BACKLOG.
- Semantic aliases beyond ContentHash; consumers that need
 NameHash, KeyHash, or similar start with their own local alias
 over ContentHash or `Bits<N, Hot>` and promote to arvo-hash once
 patterns stabilise.
- rkyv Archive impls; consumers define Archive at their boundary.
- Owned byte buffers; all hashing takes `&[u8]` input.

## Design rule

`#![no_std]`, no alloc. Trait-first: the contract is generic over
`Width`, the concrete algorithm (`Fnv1a`) is one implementor, more
land as additional implementors. Consumer code parameterises over
the trait, not the algorithm.
