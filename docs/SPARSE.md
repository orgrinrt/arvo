# arvo-sparse. Design

Sparse matrix representations and algorithms on const-generic
fixed-size structures. `#![no_std]`, no alloc. Operates on
arvo-bitmask types for small matrices and CSR for larger ones.

The crate depends on
`arvo-storage`, `arvo-bits-contracts`, `arvo-numeric-contracts`,
`arvo-tensor`, `arvo-bitmask`. The prior `arvo-bits` direct dep is
replaced by `arvo-bits-contracts`.

## Absence results

Absence is modelled with `notko::Maybe<T>`, not bare `Option<T>`,
per the workspace primitive-vocabulary discipline. Concretely:
`Csr::get` returns `Maybe<W>`; private rcm helpers (e.g.
`min_degree_unvisited`) return `Maybe<USize>`. Trait method impls
of std `Iterator::next` remain on `Option<T>` (std-trait escape
hatch).

## Capacity

Every public algorithm signature here is W-generic. The bitmask path
takes `&BitMatrix<W, C>` with `W: BitPrim`; the trait-driven path
takes any `&T` where `T: SparseAdjacency<C>`. A module-root default-W
type alias keeps the conventional 64-wide adjacency short:

```rust
pub type Adjacency<C: Capacity> =
    BitMatrix<Bits<64, Hot, Unsigned>, C>;
```

Consumers with the conventional 64-wide adjacency call the algorithms
through the short alias. Consumers picking other widths (256, 512 via
WideBits, or CSR-shaped adjacency from elsewhere in the workspace)
reach the same algorithm body through the W or trait parameter.

The capacity is a TYPE: `C: Capacity` / `R: Capacity` / `NNZ: Capacity`
in place of the prior `const N: Cap` / `const ROWS: Cap` / `const NNZ:
Cap`. Array storage is the associated type `C::Array<X>` (the GAT from
arvo-tensor's `Capacity`), so no `cap_size` expression sits in type
position and the crate no longer threads `generic_const_exprs` over
capacity arithmetic. Where a body needs the count as a value (a loop
bound), it reads `cap_size(C::CAP)` (or `as_ref().len()`); that is a
value-position const-fn call, not a type-position expression.

Generic over numeric trait bounds for matrix values. Does not import
UFixed or IFixed directly. CSR is generic over the value type.
Consumer instantiates with concrete arvo types; this crate is
library code.

Note: "row" and "column" in this document refer to matrix
rows/columns, not data records or data-storage columns.

## CSR

```rust
pub struct Csr<R: Capacity, NNZ: Capacity, W: Copy> {
 row_ptr: R::Array<USize>,
 col_idx: NNZ::Array<NodeId>,
 values: NNZ::Array<W>,
 live_rows: USize, // live node count; defaults to cap_size(R::CAP)
 live_nnz: USize,  // live edge count; defaults to cap_size(NNZ::CAP)
}
```

Compressed sparse row. Fixed-size capacity arrays, no heap. `R` and
`NNZ` are `Capacity` type parameters (the row capacity and the nnz
capacity). Row pointers and column indices use `NodeId` from
arvo-bitmask.

The matrix is packed by default: `new()` sets `live_rows` to `cap_size(R::CAP)`
and `live_nnz` to `cap_size(NNZ::CAP)`, so a freshly-constructed matrix behaves
exactly as a fully-packed CSR and existing consumers are unchanged. A
capacity-with-slack consumer (a fixed-capacity buffer with a runtime live
count, such as a pipeline scheduler's dependency graph) sets a smaller live
count. `row_end` of the last live row then returns `live_nnz` rather than
`cap_size(NNZ::CAP)`, so the slack tail of `col_idx` past `live_nnz` is never read.
Storage stays sized at the `R` and `NNZ` capacities; only the
iteration bounds follow the live counts.

Generic over the value type `W`. No numeric trait needed on W for
the structure itself, only for algorithms that compute on the
values.

`Csr<R, NNZ, W>` implements `SparseAdjacency<R>` directly.
Successors of row `i` walk `col_idx[row_ptr[i] .. row_ptr[i+1]]` as
a slice iterator. Predecessor queries cost O(N + NNZ) per query and
are not supported on `Csr` directly; consumers needing predecessors
construct `CsrBidirectional` instead.

## CsrBidirectional

`CsrBidirectional<R, NNZ, W>` carries the original CSR plus a
transpose CSR. Constructor `Csr::with_transpose(...)` returns a
`CsrBidirectional` by sweeping the input once to build the
transpose. Cost: 2x memory plus one construction sweep. Benefit:
O(out_degree) predecessor lookup.

`with_transpose` reads only the live range (the live rows, and the scatter
over the live edges) and carries the live counts through to the result, so
the transpose records no spurious predecessor from an unfilled tail.

Implements `BidirectionalSparseAdjacency<R>` (sub-trait of
`SparseAdjacency<R>`). Algorithms that need predecessor access
bound `T: BidirectionalSparseAdjacency<C>`; algorithms that only
need successors stay on `SparseAdjacency<C>`.

## Sparse matrix representations

**Bitmask matrix** (any `W: BitPrim`, supports up to W::WIDTH rows
per column-set): `BitMatrix<W, C>` from arvo-bitmask. One-instruction
operations for the W-wide column sets. The default-W form (`W =
Bits<64, Hot, Unsigned>`) is the typical small-DAG case; wider W
extends the same algorithms to 256-wide or 512-wide adjacency
without an algorithmic-shape change.

**CSR** (arbitrary `R` / `NNZ` capacities): fixed-size capacity arrays as
above. For graphs whose adjacency is not naturally bitmask-shaped
and whose row count exceeds practical W::WIDTH.

The API is uniform: every algorithm has both a bitmask-shaped
overload (`fn algo<W, C: Capacity>(adj: &BitMatrix<W, C>)`) and a
trait-driven overload (`fn algo_via<T, C: Capacity>(adj: &T)
where T: SparseAdjacency<C>`). Capacity-typed sizing means no heap
allocation regardless of representation.

## Sparse adjacency contract

Both `BitMatrix<W, C>` and `Csr<R, NNZ, W>` describe the same
abstract object, a directed graph over `0..N` nodes. Algorithms only
ask the same handful of questions: successor set, predecessor set,
degree, iteration over set bits, membership test. A sealed
`SparseAdjacency<C: Capacity>` trait names that interface;
algorithms become generic over `T: SparseAdjacency<C>`. Cost: one
trait layer per call. Benefit: any consumer that ships its own
adjacency representation implements the trait once and reuses every
algorithm.

```rust
pub const trait SparseAdjacency<C: Capacity> {
    type Successors<'a>: Iterator<Item = NodeId>
    where
        Self: 'a;
    fn successors<'a>(&'a self, node: NodeId)
        -> Self::Successors<'a>;
    fn node_count(&self) -> USize;
    fn successor_mask<W: BitPrim>(&self, node: NodeId) -> Mask<W>;
}

pub const trait BidirectionalSparseAdjacency<C: Capacity>:
    SparseAdjacency<C>
{
    type Predecessors<'a>: Iterator<Item = NodeId>
    where
        Self: 'a;
    fn predecessors<'a>(&'a self, node: NodeId)
        -> Self::Predecessors<'a>;
}
```

`successor_mask` has a default impl from the `successors` iterator
(collect into the mask). Impls override when they can answer the
bitmap question more cheaply than walking the iterator. For
example, `BitMatrix` returns the row mask directly.

`node_count()` returns the live node count. For `BitMatrix` and a packed
`Csr` it equals the cap (`cap_size(C::CAP)`), so existing behaviour is
unchanged; for a capacity-with-slack `Csr` it is the live row count. The
trait-driven algorithms visit node seeds over the range `0` to
`node_count()`, so a consumer with fewer live nodes than the cap never
visits the unfilled remainder.

The `pub const trait` declarations stay `const` across the
capacity-type migration; the impls are plain (non-const) impls
carrying the runtime graph-query bodies, so the const declaration is
orthogonal to the `C: Capacity` parameter. The sketch
`mock/research/sketches/202605301400_capacity-trait-migration/`
confirmed the `C: Capacity` form compiles with the const trait kept on
the pinned nightly; the exact remaining `#![feature(...)]` set is
finalised in the source phase.

| Type | Implements |
|---|---|
| `BitMatrix<W, C>` | `SparseAdjacency<C>` |
| `Csr<R, NNZ, W>` | `SparseAdjacency<R>` |
| `CsrBidirectional<R, NNZ, W>` | `SparseAdjacency<R>` + `BidirectionalSparseAdjacency<R>` |

## Problem-shaped trait family

Each structural-decomposition family ships as a problem-shaped trait
with the named algorithm as the canonical first impl. Consumers call
the problem name; alternate impls land alongside without renaming
consumer call sites. The trait is open, the default is documented,
no consumer choice is foreclosed.

```rust
pub const trait BandwidthReducer<C: Capacity>:
    SparseAdjacency<C>
{
    fn reduce(&self) -> C::Array<NodeId>;
}

pub const trait BlockPartitioner<C: Capacity>:
    SparseAdjacency<C>
{
    fn partition(&self) -> (USize, C::Array<USize>);
}

pub const trait BipartiteStructuralAnalysis<C: Capacity>:
    BidirectionalSparseAdjacency<C>
{
    fn analyse(&self) -> (USize, C::Array<USize>);
}
```

Default impls and their named algorithms:

- `BandwidthReducer`: default runs RCM via `arvo_sparse::rcm_reorder`.
- `BlockPartitioner`: default runs connected-components via
  `arvo_sparse::block_diagonal`.
- `BipartiteStructuralAnalysis`: default runs Dulmage-Mendelsohn via
  `arvo_sparse::dulmage_mendelsohn`.

## RCM reordering

Reverse Cuthill-McKee bandwidth minimisation. O(n + nnz).

```rust
fn rcm_reorder<W, C: Capacity>(
 adjacency: &BitMatrix<W, C>,
) -> C::Array<NodeId> // permutation: new position -> old NodeId
where
 W: BitPrim,
```

Trait-driven overload `rcm_reorder_via<T, C: Capacity>(adjacency:
&T) -> C::Array<NodeId> where T: SparseAdjacency<C>` accepts
any `SparseAdjacency` impl (CSR, future representations). The
default-W consumer call `rcm_reorder::<_, C>(adj)` over
`Adjacency<C>` stays short.

The `_via` overload visits the node range `0` to `node_count()` and sizes
its output and visited arrays at the `C` capacity; non-live node slots keep
their default and the consumer reads the live prefix.

Common applications:

**Row reordering (execution order):** reorders matrix rows so that
operations accessing similar column sets become adjacent. Better
grouping of subsequent batched work than naive ordering; most
impactful for wide DAGs with fan-out.

**Column reordering (memory layout):** reorders matrix columns so
that co-accessed entries have adjacent offsets. The hardware
prefetcher benefits from spatial locality.

Design intent: run unconditionally during planning when the consumer
is a pipeline scheduler.
Sub-microsecond at typical pipeline scale.

## Block diagonal detection

```rust
fn block_diagonal<W, C: Capacity>(
 adjacency: &BitMatrix<W, C>,
) -> (USize, C::Array<USize>) // (block_count, block_id_per_node)
where
 W: BitPrim,
```

Trait-driven overload `block_diagonal_via<T, C: Capacity>(adjacency:
&T) -> (USize, C::Array<USize>) where T: SparseAdjacency<C>`
accepts CSR-shaped adjacency directly. Used by hilavitkutin's
plan-stage `block_diagonalise` step.

Visits the node range `0` to `node_count()`; storage stays sized at the
`C` capacity as above.

Permute the access matrix to block diagonal form. Each block is an
independent sub-problem with no shared columns between blocks.

Build bipartite graph (WUs on one side, stores on other), find
connected components (delegates to arvo-graph or internal bitmask
DFS). Each component is a block. Permute matrix rows and columns
to group blocks along the diagonal.

Common application: align blocks with phases from waist detection
(arvo-graph). Also enables dead-column elimination via
Dulmage-Mendelsohn. Design intent for pipeline schedulers: run
unconditionally during planning ("block
diagonal always").

## Dulmage-Mendelsohn decomposition

```rust
pub struct DulmageMendelsohn<C: Capacity> {
 pub class_count: USize,
 pub class: C::Array<USize>, // per-node classification id
}

fn dulmage_mendelsohn<W, C: Capacity>(
 adjacency: &BitMatrix<W, C>,
) -> DulmageMendelsohn<C>
where
 W: BitPrim,
```

Class IDs: `0 = horizontal`, `1 = vertical`, `2 = square`.

Trait-driven overload `dulmage_mendelsohn_via<T, C: Capacity>(
adjacency: &T) -> DulmageMendelsohn<C> where T:
BidirectionalSparseAdjacency<C>`. The bound is the bidirectional
sub-trait; DM needs predecessor access. Used by hilavitkutin's
plan-stage when bipartite analysis becomes relevant.

Visits the node range `0` to `node_count()`; storage stays sized at the
`C` capacity as above.

Structural decomposition of a bipartite graph into fine and coarse
components. Refines block diagonal detection:

- **Horizontal components:** rows whose outputs are never read by
 any other row. Dead-end, their outputs can be eliminated unless a
 final consumer reads them.
- **Vertical components:** columns that are only inputs (read-only
 throughout the computation).
- **Square components:** matched row-column pairs where every output
 is consumed. The core of the computation.

Dead-component elimination reduces the working set in the consumer's
downstream grouping, which can directly improve cache behaviour.
