# arvo — Deep Dive: Deref on Primitive Newtypes

## Context

arvo wraps several Rust primitives in newtypes to enforce semantic
meaning and satisfy the arvo-types-only lint:

- `Bool(bool)` — control flow boolean, returned by predicates
- `USize(Bits<{cfg-platform-width}, Hot>)` — index and count type
- `IBits(Bits<7, Hot>)` — integer bit count for const generics
- `FBits(Bits<7, Hot>)` — fractional bit count for const generics
- `Width(Bits<7, Hot>)` — bit-width meta value for const generics

These newtypes are `repr(transparent)`. After compilation they are
identical to their inner type's underlying container. They exist
purely for compile-time type safety: you cannot accidentally pass a
`USize` where a `Bool` is expected, and you cannot swap an `IBits`
with an `FBits` even though both wrap the same `Bits<7, Hot>` shape.

The four ConstParamTy newtypes (`USize`, `IBits`, `FBits`, `Width`)
moved to wrapping `Bits` over wrapping a bare primitive in round
202604500000. The `Bits` storage primitive itself bottoms out at a
`u8` const-generic (workspace-rule exception #2 root); the
meta-newtypes lift above that root.

The question is how to access the inner value when you need it.

## The problem

Rust's `if` requires `bool`. Not a type that wraps `bool`, not a
type that can be converted to `bool` — exactly `bool`. Similarly,
array indexing requires `usize`. These are hard-wired into the
language with no trait-based extension point.

If `is_zero()` returns `Bool` (our newtype), `if val.is_zero()`
does not compile. If `trailing_zeros()` returns `USize` (our
newtype), `array[val.trailing_zeros()]` does not compile.

Three options exist to bridge this gap.

## Option 1: Explicit conversion method

Define a trait or inherent method for extraction:

```rust
pub trait AsBool {
    fn as_bool(&self) -> bool;
}

impl AsBool for Bool {
    fn as_bool(&self) -> bool { self.0 }
}
```

Usage: `if val.is_zero().as_bool() { ... }`

Advantages: explicit, no magic, follows Rust `As*` naming convention.
Disadvantages: 10 extra characters at every call site. In hot loop
code operating on arvo types, predicates and index operations appear
frequently. The verbosity adds up and obscures the actual logic.

## Option 2: Try trait (? operator)

`Bool` implements `Try` with an uninhabited residual:

```rust
impl Try for Bool {
    type Output = bool;
    type Residual = Infallible;
    fn branch(self) -> ControlFlow<Infallible, bool> {
        ControlFlow::Continue(self.0)
    }
    fn from_output(output: bool) -> Self { Bool(output) }
}
```

Usage: `if val.is_zero()? { ... }`

The `?` always takes the `Continue` path (the `Break` path is
uninhabited and unreachable). Zero runtime cost. One character.

Limitation: the enclosing function must return a type that implements
`FromResidual<Infallible>`. In hilavitkutin, all WU execute methods
return `Outcome<T>` which satisfies this. Outside WU code, the
function's return type must be one of hilavitkutin's result family
(`Outcome`, `Just`, `Maybe`, `Result`) or the `?` approach is not
available.

This is the preferred path in WU code, where it comes for free.

## Option 3: Deref

`Bool` implements `Deref<Target = bool>`:

```rust
impl Deref for Bool {
    type Target = bool;
    fn deref(&self) -> &bool { &self.0 }
}
```

Usage: `if *val.is_zero() { ... }`

One character (`*`). Works everywhere, no return type requirements.

## Why Deref is unconventional here

The Rust API guidelines recommend `Deref` for smart pointer types
(`Box`, `Rc`, `Arc`, `MutexGuard`), not for newtypes. The reasoning
behind this convention stems from three concrete concerns:

### 1. Method resolution opacity

When you call `val.method()`, Rust's auto-deref chain tries methods
on the outer type first, then on `*val`, then on `**val`, etc. If
`Bool` has a method `then()` and `bool` also has `then()`, the
`Bool` version wins. If `Bool` does not have `then()`, `bool`'s
version is found via auto-deref. Reading the code, you cannot tell
which type's method is being called without checking both.

### 2. Reference coercion at call boundaries

Deref coercion means `&Bool` silently becomes `&bool` when passed
to a function expecting `&bool`. The type boundary evaporates at
reference sites without any visible marker in the code.

### 3. Trait bound inconsistency

`bool` may implement traits that `Bool` does not. Deref does not
make the outer type satisfy the inner type's trait bounds. But deref
coercion does make `&Bool` usable where `&bool` is expected. This
means the inner type's capabilities sometimes leak through and
sometimes do not, depending on whether the context uses values,
references, or trait bounds.

## Why these concerns are acceptable for arvo

### Method resolution is bounded

`bool` has a small, well-known API: `then()`, `then_some()`, and
the boolean operators. `usize` has more methods but they are all
standard numeric/conversion methods with no surprising behaviour.
There is no realistic scenario where auto-deref to the inner type
produces unexpected method dispatch. If arvo adds a method with the
same name as a method on the inner type, it intentionally shadows
it.

### Reference coercion is correct behaviour

These newtypes are `repr(transparent)` wrappers. At the machine
level, `&Bool` and `&bool` are the same pointer to the same byte.
The deref coercion makes the language-level behaviour match the
machine-level reality. A function accepting `&bool` receiving a
`&Bool` is not a type safety violation — it is the intended
transparency.

### Trait bound inconsistency is a learnable quirk

The inconsistency ("this works with `&Bool` but not with `Bool`
directly for some trait bounds") is real but not a safety hazard.
It manifests as a compile error, not a runtime bug. Developers
learn the pattern once: explicit `*` when you need the inner value,
auto-deref when working with references. This is the same pattern
Rust developers already use with `String`/`&str` via Deref.

### The alternative is worse

Without Deref, every predicate check and index operation requires
either `.as_bool()` / `.as_usize()` or the `?` operator (which
constrains the function's return type). In performance-critical
code with many predicate checks and array accesses, the explicit
conversion noise obscures the actual algorithm. The cure is worse
than the disease.

## The three-path design

arvo provides three bridges from newtypes to primitives, each
suited to different contexts:

| Path | Syntax | Where it works |
|---|---|---|
| `?` (Try) | `if val.is_zero()? { ... }` | Functions returning Outcome/Just/Maybe/Result |
| `*` (Deref) | `if *val.is_zero() { ... }` | Everywhere |
| `.as_bool()` (AsBool) | `if val.is_zero().as_bool() { ... }` | Everywhere, explicit, compatible |

In WU code (the hot path): use `?`. It is the most ergonomic and
comes for free because `execute()` returns `Outcome`.

In general arvo-consuming code: use `*`. One character, no return
type constraints.

For library public APIs that must expose Rust-native types for
compatibility with non-arvo consumers: use `.as_bool()` or
`.as_usize()` via the `AsBool` / `AsUSize` traits. This is the
explicit escape hatch at the boundary between arvo's type system
and external Rust code.

## Which newtypes get Deref

| Type | Deref target | Rationale |
|---|---|---|
| `Bool` | `bool` | Predicate results used in `if`/`while` |
| `USize` | `usize` | Indices used in array access |
| `IBits` | no | Compile-time const generic, no runtime extraction needed |
| `FBits` | no | Compile-time const generic, no runtime extraction needed |

`IBits` and `FBits` are used exclusively as const generic parameters.
Their values are never accessed at runtime. They do not need Deref.

## DerefMut

None of these types implement `DerefMut`. Mutation goes through
arvo's own APIs, not through the inner primitive. If you need to
increment a `USize`, use arvo's `Add` implementation, not `*val += 1`.
This preserves the type boundary for writes while relaxing it for
reads.

## Summary

Using `Deref` on newtypes is unconventional. The convention exists
to prevent confusion in large public APIs consumed by developers
who may not understand the auto-deref mechanism. arvo is an internal
library with expert users, transparent `repr(transparent)` wrappers,
and bounded inner-type APIs. The concrete downsides (method
resolution opacity, reference coercion, trait bound inconsistency)
are minor for this use case. The ergonomic gain (single `*` instead
of `.as_bool()` at every predicate site) is significant. The design
is a deliberate choice, not an oversight.

# arvo. Deep Dive: The Strategy-Bound Trilemma

## Context

`UFixed<I, F, S>`, `IFixed<I, F, S>`, and `Bits<N, S, Sign>` carry a
`where S: BitsContainerFor<{ ufixed_bits(I, F) }>` bound (or its `IBits`-
parameterised analogue) on every type definition. Most consumer code
never sees this bound: monomorphic call sites, alias bodies, and
trait-first algorithm signatures all skip it. A specific class of code
hits it head-on: arvo-internal generic-over-bit-width algorithm code
inside `arvo-graph`, `arvo-sparse`, `arvo-spectral`, and `arvo-comb`,
plus any consumer that defines an API genuinely parameterised by I and F
const-generics.

This document explains why the bound exists, why no creative
reorganisation eliminates it on current rustc without compromising
substrate principles, and the three-layer discipline that keeps the
friction contained to arvo's own implementation.

The constraint is not arvo-specific. Any Rust library combining (a)
static validity checking via trait bounds on const-expressions over
generic params, (b) type-level layout determined by those bounds, and
(c) generic-over-the-const-param consumer code hits it.

## The intent

Three properties define arvo's numeric substrate.

1. **Static validity check.** Combinations of `(strategy, bit-width)`
   that do not make sense fail at compile time. `Uint64<Warm>` produces
   a `BitsContainerFor`-bound error pointing the consumer at strategy
   choice, not a runtime panic or a silent wrap. Warm caps at
   `I + F <= 32`; above that, no `BitsContainerFor<N>` impl exists for
   `Warm`, and the type fails to compile. The static check is the
   substrate's correctness story.

2. **Strategy-driven container width at the type level.** `Bits<8, Hot>`
   is one byte; `Bits<8, Warm>` is two; `Bits<8, Cold>` is bitpacked to
   N bits in column storage. The strategy marker chooses physical
   layout, not just arithmetic semantics. This is what gives Hot its L1
   density, Cold its archival density, Warm its 2x safety on single
   ops. Lose this and Strategy collapses from a layout-determining
   marker to an arithmetic-flavour tag.

3. **Ergonomic call sites for consumers.** `let n: Uint8 = ...;`
   `type Coord = Fixed<13, 3, Warm>;`. Without ergonomic call-site
   syntax the substrate becomes painful to consume.

The substrate's value comes from holding all three together. Drop any
one and the design erodes.

## The constraint

On current rustc (`adt_const_params` and `generic_const_exprs`
available, `implied_bounds` not), you can have any two of those three,
not all three.

The mechanism: `UFixed<const I: IBits, const F: FBits, S: Strategy>`'s
storage field is `<S as BitsContainerFor<{ ufixed_bits(I, F) }>>::T`. The
field type is a projection through a trait bound that depends on a
const-expression over the type's own generic parameters. For the type
to be well-formed (Sized, layout-known), rustc must verify the bound.
For consumer code that writes `Fixed<I, F, S>` while itself being
generic over `<const I: IBits, const F: FBits, S: Strategy>`, rustc
cannot verify the bound at the consumer's definition site without the
consumer restating it.

The relevant rustc feature that would erase this restatement is
`feature(implied_bounds)` (RFC 2089, tracking issue #44491). It would
let a struct's where-clause apply implicitly when the struct is named
in a consumer's signature. The feature has been open since September
2017 with open design questions on crate-local vs module-local scope
and type-inference interactions; not on a near-term stabilisation
track. Adopting it pre-stabilisation would be on the same risk class as
`feature(fundamental)` (explicitly "not intended to be stabilized
as-is" per its tracking issue), too uncertain to commit to.

## Why the alternatives compromise principle

Three alternative architectures eliminate the friction. Each costs one
of the three properties. Each was traced and rejected during the
foundations restructure round.

### Alternative A: drop static validity (uniform storage)

Make `UFixed`'s storage uniform `u64`, store width info as a phantom
tag, validate at construction only. Eliminates the bound on the struct
definition; consumer-generic code names the type freely.

Costs: every `Bits<8, Hot>` value pays 8 bytes instead of 1. Cold's
bit-density at the type level evaporates. The substrate's "L1-density
Hot vs archival Cold" story collapses to a runtime-checked variant
tag. Hot becomes "u64 with hot semantics" instead of "the smallest
aligned container that fits". This is the regression we explicitly
reject. Arvo's framing as a fixed-point-first stack rests on
strategy-driven layout being real, not nominal.

### Alternative B: drop strategy-driven layout (per-container types)

Mirror the `fixed` crate's approach: `pub struct UFixedI8<const F: u8>(i8);`
`UFixedI16<...>(i16);` and so on. The integer container is part of the
type's name; no projection needed; bounds are simple `where Self:
Sized`.

Costs: combinatorial explosion of types; generic-over-strategy code
becomes generic-over-container-type instead, which is awkward; the
whole `BitsContainerFor` table that maps `(S, BITS)` to a container
disappears, taking with it the codegen optimisation hooks (LLVM passes
that fire on `Bits<N, Hot>` would have to be reimplemented per
container). The strategy marker degrades from a layout director to an
arithmetic flag, which the substrate explicitly rejects (Strategy is
layout per `PRINCIPLES.md`).

### Alternative C: keep both, accept friction

The current design. Generic-over-width consumer code restates
`where S: BitsContainerFor<{ ufixed_bits(I, F) }>`. Monomorphic consumer
code (the dominant case) is unaffected. The friction is contained: it
lives in algorithm code internal to arvo (graph / sparse / spectral /
comb generic-over-width paths) and in occasional consumer code that
genuinely needs to be generic over bit width. The substrate principles
hold; the cost is a verbose where-clause at one specific kind of call
site.

This is the chosen path.

## Creative unsafe options that do not help

The following angles were traced and rejected during the foundations
restructure src execution. Each fails for the same root reason: the
field type is the projection, and `unsafe` lets us reinterpret memory
we already have but not elide the typecheck that determines what type
the memory should be.

1. **Sealed unsafe marker trait with always-true blanket impl**
   (`unsafe trait BoundProof<S, I, F>`): the trait bound on the struct
   still expands to the same const-expr in the where-clause, just one
   trait deeper.
2. **`MaybeUninit<projection-typed field>`**: same projection, just less
   initialised. The Sized / layout query still hits the bound.
3. **Union of all container types** (u8/u16/u32/u64/u128): would work,
   but max-size = u128 violates Cold's exact-bit-density principle.
   Reduces to alternative A.
4. **`[u8; size_of_container::<S, I, F>()]` field**: array length is a
   const-expr, still depends on generic params, same propagation issue.
5. **Phantom-only struct, storage moves off-type**: breaks per-value
   semantics. `let x: UFixed<I, F, S> = ...` requires storage on the
   type.
6. **Specialisation-based fallback**: `feature(specialization)` is
   famously incomplete and has known unsoundness in non-trivial uses.
   Worse than `implied_bounds`.
7. **Const-eval guard via `[(); 1 / valid()]:`** (the Fnv1a trick):
   same const-expr propagation issue when used inside generic-over-
   width caller code.

The pattern across all of these: the bound failure is intrinsic to "the
field's type depends on a const-expr derived from generic params".
`unsafe` is not a workaround for this class of problem.

## How to work within the constraint

Three layers of access, each with its own pattern. The friction is
concentrated in layer 3 by design.

### Layer 1: end-user code

End users (vehje, viola consumers, downstream Clause) write canonical-
width aliases (`Uint8`, `Int16`, `Bits<28, Hot>`) and domain aliases
their crate defines locally. They never see the bound. Their imports
reach `arvo::{Uint8, Int16, USize, Bits, ...}` and that is the
surface.

Code at this layer is monomorphic: every type is fully specified at
the use site. The bound is verified once at the alias definition's
instantiation, never at the consumer's signature.

### Layer 2: domain-author code

A consumer crate defining its own domain alias for an ad-hoc width.
Pattern:

```rust
use arvo::{Fixed, Signed};

pub type Angle = Fixed<9, 7, Warm>;
pub type Coord = Signed<15, 16, Warm>;
pub type Hash = arvo::Bits<28, arvo::Hot>;
```

`Fixed<I, F, S>` and `Signed<I, F, S>` are bare-`u8`-const-generic
aliases that forward to the `IBits` / `FBits`-wrapped form internally.
The alias body is the only place `{ ibits(...) }` machinery appears;
consumer call sites never see it. Like layer 1, code here is
monomorphic. `Fixed<13, 3, Warm>` substitutes concrete values.

### Layer 3: arvo-internal generic-over-width code

The friction's home. Code inside arvo's algorithm crates (`arvo-graph`,
`arvo-sparse`, `arvo-spectral`, `arvo-comb`) that is generic over
numeric trait bounds occasionally needs to be generic over bit width
specifically. When that happens, the explicit bound is restated:

```rust
fn process<const I: IBits, const F: FBits, S: Strategy>(x: UFixed<I, F, S>)
where
    S: BitsContainerFor<{ ufixed_bits(I, F) }>,
{ /* ... */ }
```

This is verbose. It is also internal: no consumer reads it; it lives
in arvo crate sources. The verbosity is the price of the static
guarantee.

## The discipline that keeps friction contained

Generic-over-bit-width APIs at consumer-facing surfaces are the smell
that drags layer-3 friction into layer 1 / layer 2. The discipline:

- **Public consumer APIs use trait-bound abstractions, not bit-width-
  generic abstractions.** Take `T: BitPresentation + Add + Mul` not
  `<const I: IBits, const F: FBits, S>`. Algorithms generic over
  numeric trait bounds (the existing `arvo-graph` / `arvo-sparse`
  pattern) are clean. Algorithms generic over the const-generic bit
  width are the smell.
- **Domain types are aliases, not generic over width.**
  `pub type Coord = Fixed<13, 3, Warm>` is right.
  `pub type Coord<const I: u8, const F: u8> = Fixed<I, F, Warm>` is the
  smell. It pushes the bound up to every Coord use site.
- **When a consumer is tempted to write `<const I: u8, const F: u8>`,
  redesign as `<T: SomeNumericBound>`.** The trait-first cookbook
  (`.claude/rules/cookbook.md`) is the existing workspace-level
  guidance; this constraint reinforces why it matters beyond
  aesthetics.

If discipline is followed, the friction never manifests at consumer
call sites. Layers 1 and 2 stay clean; layer 3 absorbs the verbosity in
the substrate's own implementation.

## Forward-looking: CrossStrategyOp and the diagnostic surface

Round 202604281000 Pass G shipped `CrossStrategyOp<S1, S2>` in
`arvo-strategy/src/cross_strategy.rs`. The marker trait's
`#[diagnostic::on_unimplemented]` message points consumers at explicit
cast sites when the substrate would otherwise resolve a cross-strategy
op silently:

```rust
#[diagnostic::on_unimplemented(
    message = "cross-strategy operation between `{S1}` and `{S2}` shifts arithmetic semantics",
    label = "this op resolves to `Resolve<{S1}, {S2}>::Out` and may adopt different overflow / container / layout semantics than either operand",
    note = "consumer choice: insert an explicit `.cast::<S>()` to make the strategy shift visible at the call site, or annotate the surrounding scope with `// lint:allow(cross-strategy-resolution)` to silence the warning",
)]
pub trait CrossStrategyOp<S1: Strategy, S2: Strategy> {}
```

Same-strategy pairs implement the trait. Mixed-strategy pairs do not;
the diagnostic fires when an op site would resolve via `Resolve<S1, S2>`
without an explicit cast.

The trait surface is the type-level surfacing of this DEEPDIVE's
discipline. It says: "if you find yourself relying on cross-strategy
silent resolution at a hot-path op, the design wants you to make that
choice visible." Layer 1 / layer 2 code rarely encounters cross-strategy
ops because their types are fully named at use sites; layer 3 code
encounters them often, and the diagnostic is the toolbox-not-policer
nudge that says "warn, but never refuse".

Wiring the trait into op sites (so the diagnostic actually fires at
arithmetic positions) is forward-looking. The trait surface ships now;
the op-site wiring is BACKLOG-tracked.

## Watch-item: implied_bounds

If `feature(implied_bounds)` reaches the same stability and usability
level as the features arvo already uses (`adt_const_params`,
`generic_const_exprs`, `try_trait_v2`, `macro_metavar_expr_concat`), a
follow-up round flips on the feature flag and the friction in layer 3
dissolves. Every where-clause on a struct definition becomes implicit
at use sites, and generic-over-width consumer code can name
`Fixed<I, F, S>` without restating the bound.

Until then: the design is correct on principle, the friction is real
but contained, and the rule is "trait-first, alias-first, never bit-
width-generic at the consumer surface".
