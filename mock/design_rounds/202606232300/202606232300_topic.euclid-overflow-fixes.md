## Two debug-panic overflows on legal inputs (round 202606232230 follow-up)

The euclid/split round shipped two overflow paths that panic in debug on legal inputs, missed because the
style-correct non-power-of-two test widths (`IFixed<13,16>` in an i32 container) have headroom the
full-container widths do not.

1. `even_split_parts` forms `base + 1` eagerly even when the remainder is zero and `base_plus` is never
   yielded. For `n == 1`, `base == a`; at a full-container width with `a == iN::MAX` / `uN::MAX`,
   `base + 1` overflows on the legal call `split_evenly(USize(1))`. Fix: only form `base + 1` when the
   remainder is non-zero (where `n >= 2`, so `base <= a/2` and `base + 1` cannot overflow).

2. `div_euclid_whole`'s `a.div_euclid(b) << FRAC` overflows when the `Self` divisor `b` is sub-unit
   (`|b| < 1.0`, i.e. `b_raw < 1 << FRAC`). The whole-number quotient `k = a_raw.div_euclid(b_raw)` can be
   far larger than the integer range allows once shifted back to a fixed value. The "division shrinks
   magnitude, no clamp needed" rationale holds for `ScalarEuclid` (integer count `>= 1`) but NOT for
   `EuclidDiv` (a `Self` divisor can be a fraction). Fix: saturate the shift (`saturating_mul` by
   `1 << FRAC`) so an out-of-range whole quotient clamps to the bound rather than panicking. Deterministic,
   no panic. Documented on `EuclidDiv`.

Minor: `split_evenly(USize(0))` yields an empty iterator (drops the value) while scalar div-by-zero returns
the numerator. The two are different operations (a 0-way split has no shares to carry the value into; a
div-by-0 has a numerator to pass through); documented on `split_evenly` so the convention is explicit.

## Tests (catalogue the edges)

Width-8 (`IFixed<7,0,Hot>` / `UFixed<8,0,Hot>`) `split_evenly(USize(1))` on the container MAX conserves and
does not panic; `EuclidDiv::div_euclid` with a fractional `rhs` saturates rather than panicking.
