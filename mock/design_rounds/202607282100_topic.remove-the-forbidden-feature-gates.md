# Topic: remove the forbidden feature gates

**Date:** 2026-07-28
**Phase:** TOPIC
**Scope:** migrate the Pattern C container projection off `generic_const_exprs`, remove every
remaining forbidden unstable-feature gate across arvo, and correct the vetting record that let them
survive.
**Rests on:** the sketch `mock/research/sketches/202607282100_container-projection-without-gce/`
(outcome WORKS, zero feature gates).

## How this surfaced

A prior-art research pass was framed on the claim that arvo depends on `generic_const_exprs`
pervasively. op stopped it: the workspace vetting forbids fundamentally unsound or unstable features,
sketches had already proven the stack does not need either `generic_const_exprs` or full
`specialization`, and op had been told at each turn that the forbidden features were fine and up to
date.

Checking the source rather than the documents found the opposite of what both the agent and op had
been working from.

## What is actually true

**Live gates, anchored on `^#![feature(...)]`, across arvo and hilavitkutin.**

| Feature | Live gates | Where |

| `specialization` (full) | **0** | removal completed |
| `generic_const_exprs` | **11** | 3 crate roots plus 8 test files |
| `min_generic_const_args` | 0 | used nowhere |

The three crate roots are `arvo-strategy/src/lib.rs:11`, `arvo/src/lib.rs:25`, and
`hilavitkutin/src/lib.rs:24`.

**The two features were treated differently by the same sweep.** The 2026-05-29 unstable-feature
soundness sweep states its own discipline in its opening: "Under the discipline, a feature known
unsound with no prospective fix is forbidden outright, with no carve-out." It applied that to
`specialization` and to `associated_type_defaults`, and both are gone. For `generic_const_exprs` it
deferred instead, to "arvo's resolution, same date", which returned WATCH. The vetting that fed that
resolution had itself flagged FORBID.

**The gate did not merely survive, it spread.** The sweep named hilavitkutin's GCE gates as
`hilavitkutin-api/src/lib.rs:16` and `hilavitkutin-str/src/lib.rs:10`, and found "no GCE-requiring
construct in either crate... both gates are unused and removable". Those two roots are clean today.
The engine root `hilavitkutin/src/lib.rs`, which the sweep never listed, now carries the gate, along
with eight test files.

**The justification on record names a construct that no longer exists.** The retained disposition
defends `cap_size(N)` array-length patterns. `cap_size` has zero live occurrences in `arvo-strategy`
or the facade; both grep hits are inside the vetting comment itself. `const N: Cap` parameters are at
zero across all three gated crates. The `Capacity` migration deleted that form, and
`arvo-comb/src/lib.rs:16` records it: "the capacity is a TYPE ... so no `cap_size` expression sits in
type position and no `Cap` const generic appears."

**What the gate actually protects is the container projection**, in `arvo-strategy/src/container.rs`.
Sixteen sites across four `BitsContainerFor` impls, all one shape: a const function call on a generic
parameter, in const-generic argument position.

## Decisions

Recorded as they are made. Nothing here is the agent's call.

### D1. `generic_const_exprs` is FORBIDDEN, and so is full `specialization`

**Decision (op, 2026-07-28).** The standing gate, which predates this workspace and was settled during
the loimu-era feature vetting, is that a feature is allowed only if it is **not proven unsound or
unstable**, **and**, absent a very strong reason, is **itself on the stabilisation or mainlining
path**. `generic_const_exprs` fails the second test on its own terms: `min_generic_const_args` is the
documented "deliberate sound, minimally-scoped successor... named the viable path to stabilisation".
GCE is what that successor replaces, exactly as `min_specialization` replaces `specialization`, which
is already forbidden.

The workspace rule `unstable-features.md` has been corrected: GCE moves into the forbidden table, and
the 2026-05-29 WATCH resolution is marked superseded rather than deleted, so the drift stays legible.

### D2. The container projection migrates to typestate

**Decision (op).** Same cure as `Capacity`. The sketch proves it and needs no feature gate at all.

The tag is an integer computed by a function today. It is a closed vocabulary of slots, so it becomes
an enum of types. Width becomes typestate, the direct analogue of `Dim<N>`. A width-to-bucket trait
carries the selection as an **associated type**, and the two tag functions become two families rather
than two functions. The projection's const arguments become paths, and nothing computes in type
position.

Before, requiring GCE:

```rust
Picker: Project<{ tag_hot_cold(N) }, Sign, { bytes_for_u16(N) }, Hot>
```

After, requiring nothing:

```rust
W: WidthFor<HotCold>,
Picker: Project<W::Bkt, Sign, Hot>,
```

The sketch verifies resolution rather than parsing: `Hot` at 13 bits resolves to `u16`, at 47 bits to
`u64`, signed at 7 bits to `i8`; `Warm` at 13 bits to `u32` and signed at 32 bits to `i64`, preserving
the 2x-logical rule. It also instantiates the caller-threads-its-own-generic case, which is the shape
recorded as having overflowed GCE under the old form.

**The cost is per-width impls**, one row per supported width per family, expanded by macro. That cost
is already licensed by `arvo-compile-time-last.md`, which names "per-N const-trait impls (4 strategies
x 64+ widths x 2 sign = hundreds of impls)" among the things the substrate is allowed to spend when
the alternative is a runtime container check. Nothing new is being argued for.

### D3. Every remaining forbidden gate goes, not just the one that was load-bearing

**Decision (op).** The removal covers all eleven live gates, not only `arvo-strategy`. Two of the
three roots look vestigial on inspection and each needs its own check rather than an assumption:

The `arvo` facade's only live GCE constructs are two static asserts of the form
`[(); 1 / is_fractional(F)]:`, at `ufixed.rs:274` and `ifixed.rs:308`. A stable `const { assert!(...) }`
block is the candidate replacement and needs no feature.

`hilavitkutin/src/lib.rs:24` carries 76 `cap_size` calls and zero `[(); ...]` bounds, every inspected
use sitting in value position (`cap_size(C::CAP) <= 64`, `let n = cap_size(...)`). Its own comment
describes the const-generic use as living in "min-const-generic positions". The empirical check is the
one the sweep already ran for the sibling crates: drop the gate, build, see.

The eight test-file gates follow their crates.

### D4. The vetting record itself is suspect, and gets audited

**Decision (op).** Trust in the rule corpus has dropped to zero. Whether the forbid was never written
down or was actively rewritten to WATCH, the outcome is the same: op was told at each turn that the
forbidden features were fine, and acted on that, while checking only the code and never the feature
declarations in the lib roots.

So the correction to `unstable-features.md` is necessary and not sufficient. A line-by-line audit of
every rule surface follows, covering `clause-dev/.claude/`, each repo's `mock/agent/`, and the
`.claude/` or `CLAUDE.md` of repos that do not run mockspace. Line by line, no greps, no skips,
reporting anything suspect, wrong, or stale. That audit is its own work and is not scoped by this
topic beyond naming it as required.

## What this round does not decide

Whether the width parameter's public spelling changes for consumers. The sketch uses `Wid<N>` as the
typestate carrier, which mirrors `Dim<N>`, but whether `Bits<N, S, Sign>` keeps a const parameter at
its public surface and lowers to the typestate internally, or whether the typestate surfaces, is a
consumer-facing question this topic leaves open.

Whether `is_fractional`'s static assert should become a `const { assert!(...) }` block or move onto a
sealed trait as an associated const. Both avoid the feature; the choice is a shape question.

Whether the per-width macro expansion covers the full 1 to 128 range plus wide, or a narrower set with
a documented cap.
