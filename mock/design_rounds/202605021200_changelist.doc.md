# Doc changelist 202605021200 - const-trait arithmetic on every arvo numeric

**Date:** 2026-05-02
**Phase:** DOC
**Source topics (both frozen):**
- `202605021200_topic.usize-const-arith.md`
- `202605021200_topic.expand-to-all-numerics.md`
**Source sketch:** `mock/research/sketches/usize-const-arith-202605021200/sketch.rs` (compiles clean on nightly with `feature(const_trait_impl)` + `feature(const_ops)`; FINDINGS.md captures validated facts)
**Tracking tasks:** umbrella #300, layer breakdown #301 (Round A), #302 (Round B), #303 (Round C).

This round consolidates the addendum's "every arvo numeric primitive" scope into a single mockspace round, single PR. Three layers ship together:

- **Layer A** (#301): USize + Cap full const-arith surface. Fresh inherent constants and `impl const` ops. Sketch validated.
- **Layer B** (#302): convert the 19 existing `core::ops::*` impls on UFixed, IFixed, FastFloat, StrictFloat, Bits, Mask64, Mask256, BitMatrix, Bitfield to `impl const`. Add inherent constants per type. Add `feature(const_ops)` to every crate root that authors `impl const` on `core::ops::*` traits.
- **Layer C** (#303): sweep ~50 `.0` field-access call sites in arvo source (arvo-bitmask/src/ops.rs, arvo-comb/src/{dp,greedy}.rs, arvo-bits-contracts/src/bits_impl.rs) to use the const-arith surface from layers A and B.

The fourth-pass review on hilavitkutin PR #46 raised the question of whether anticipatory layers belong in the same round as the load-bearing one. The decision: yes, because the sweep in Layer C IS the consumer for Layer B's const conversions. Layer A's hilavitkutin Depth caller is the load-bearing consumer for the round; B and C compound. Splitting would land a round-and-a-half later; consolidating ships every wall the substrate hits today.
