# Topic: what the review found in the identity round

**Date:** 2026-07-28
**Phase:** TOPIC
**Reviews:** PR #2 on `orgrinrt/arvo`, expert review of the closed round `202607270015`

The identity round closed green and a review then found two defects and a coverage gap in the exact shape
the round existed to remove. This records what it found, which findings are acted on here, and which are
not.

## The finding that matters

`SignedIdentity` is implemented on bare primitives and on nothing else. `IFixed` has no impl at any width,
and neither does `Bits<N, S, Signed>`. `<IFixed<{ibits(0)}, {fbits(7)}, Hot> as SignedIdentity>::NEG_ONE`
does not compile: the trait bound is not satisfied.

Four artifacts state otherwise. The trait's own doc comment says it is implemented for "substrate types that
wrap signed primitives (`IFixed`, `Bits<N, S, Signed>`)". `mock/crates/arvo/DESIGN.md.tmpl` says "IFixed
gains `SignedIdentity::MINUS_ONE` separately". The locked src changelist justifies dropping the `Identity`
supertrait on the grounds that `NEG_ONE` stays reachable on the purely fractional signed types. And
`identity_laws.rs` repeats the reasoning in a comment.

The reasoning is correct and the thing it protects does not exist. A signed purely fractional type does span
`[-1, 1)`, minus one is representable there as the container minimum, and one is not, so the asymmetry is
real. Dropping the supertrait was still right. But nothing was rescued by it, because there was nothing
there to rescue.

The claim predates the round: `IFixed` never implemented `SignedIdentity`, and the doc comment was already
false when the round started. What the round did was carry the false claim forward and then build on it,
adding two more artifacts asserting it. That is the failure the round was convened to fix, reproduced inside
the fix: a property asserted in prose in four places and expressible in none, surviving because nobody tried
to write the test.

The lesson generalises past this one trait. The round wrote a matrix for the laws it thought were at risk
and asserted nothing at all about the constant it had just spent four paragraphs justifying. A justification
is not a test, and the amount of prose defending a property is uncorrelated with whether the property holds.

## The second defect, which the round introduced

`Precise::i_div_fixed` returns the wrong sign at the container minimum.
`<Precise as IArith<64>>::i_div_fixed::<0>(i128::MIN, -1)` returns the minimum. Its sibling `i_div`, same
strategy and same input, returns the maximum.

The maximum is right. `MIN / -1` is mathematically `+2^63`, which saturates upward, and `i_div` reaches that
with `saturating_div`. The round replaced a panicking `/` with `wrapping_div` at every site uniformly, which
is correct for the wrapping strategies and wrong for the saturating one: `wrapping_div` yields the minimum,
and the clamp that follows reads it as already inside the logical bound and leaves it.

The mistake was making `Precise` consistent with `Hot` rather than with itself. A saturating strategy has one
answer at an extreme and it is the bound, not the wrap.

## Coverage the round's own thesis demanded and did not deliver

The round argued that a law asserted over a sample reports green and proves nothing about the rest. Three of
its own tests sample.

`never_panic_contract.rs` exercises `Hot` and `Cold` at 128 bits only. That width routes exclusively through
the 256-bit widening family, so the plain wrapping and native-widening families, where four of the six
division edits landed, are never entered. The changelist claims the contract for `Precise` too; no `Precise`
case is run at all, which is why the sign defect above survived the round that introduced it.

`identity_laws.rs` stops at 64 logical bits, described in a comment as keeping the matrix "square" across
strategies. Squareness is not a coverage argument, and the 65 to 128 band is a different implementation
family: the one carrying `i_mul_fixed_128`, which this round patched. Every probe in the matrix is also
non-negative, so neither law is asserted on a negative operand anywhere.

The compile-fail pin covers `UFixed<0, 8, Hot>` alone. The topic called the signed case the worst of the
four, and there is no compile-fail case for it, nor for `Warm`, `Cold` or `Precise`. Loosening the bound on
`IFixed` leaves the suite green, which the pin's own doc comment says must not be possible.

## Corrections to the closed round's record

Two claims in the locked changelists do not match what shipped. Locked changelists are frozen, so the
corrections live here rather than as edits to them.

The src changelist says `arith.rs` becomes four modules, one named `arith_impl.rs`. It became five, and the
module is `arith_impls.rs`.

The same changelist frames the git build-dependency as what makes publishing refused outright. Removing it
was necessary and did not clear the blocker: `notko` is still a git-sourced normal dependency of
`arvo-strategy`, so a publish still stops on a git source, one dependency later. What changed is that the
tooling no longer ships in the manifest of every crate. The release text should say that rather than imply
publishing is now possible.

## Not acted on here

Counter increments across `arvo-comb`, `arvo-sparse` and `arvo-graph` read
`count + <USize as Identity<Multiplicative>>::IDENTITY`, using the multiplicative identity as the literal
one. That is the conflation this arc set out to remove, and it couples every counter to a projection that
has nothing to do with counting. It is faithful to what the code said before the sweep, and correcting it
properly needs a unit constant that does not exist yet, which is a design question rather than a fix.
Tracked separately.
