# Topic: what arvo already ships toward N dimensions

**Date:** 2026-07-28
**Phase:** TOPIC
**Scope:** internal research. What exists today, what the rank-limited pieces are, and what would
have to port whichever way the design goes. No decisions, no work.
**Continues:** `202607281005_topic.arvo-shape-two-dimensional-primitives.md` and
`202607281052_topic.shapes-are-n-dimensional.md`.

## The finding that reframes the question

The preceding topic said `arvo-tensor` stops at rank 2 and would need generalising. That is true of
the **types**, and misleading about the **foundation**, which is already general.

`arvo-tensor` carries `Capacity`, a trait whose associated array type is a generic associated type,
and `Dim<const N: usize>` as its one implementing marker:

```rust
pub trait Capacity {
    type Array<T>: AsRef<[T]> + AsMut<[T]>;
    const CAP: Cap;
    fn filled<T: Copy>(v: T) -> Self::Array<T>;
    fn from_fn<T, F: FnMut(USize) -> T>(f: F) -> Self::Array<T>;
}

pub struct Dim<const N: usize>;
impl<const N: usize> Capacity for Dim<N> {
    type Array<T> = [T; N];
    const CAP: Cap = cap(N);
    // ...
}
```

And the design document already states the consequence, in the comment on the trait itself:

> the `AsRef`/`AsMut` bound gives slice access without a const-generic `Index` HKT, and **lets 2-D
> storage be the composition `R::Array<C::Array<T>>` with no separate trait.**

`Matrix<W, C>` is built exactly that way, and the document is explicit that rank 2 needed no new
mechanism:

> `#[repr(transparent)]` over the composition `C::Array<C::Array<W>>`. **The square shape is two
> nested capacity projections; no separate rank-2 type is needed.**

**So arvo can already express rank N.** `C::Array<C::Array<C::Array<T>>>` is rank 3 and nothing has to
be invented for it. What is missing is not the mechanism but a way to **name** a rank without writing
its nesting by hand, and a way for a function to be generic over rank at all.

That is a much smaller gap than "generalise the tensor crate", and it changes what the design round
is deciding.

## Why `Capacity` exists at all, which constrains anything built on it

`Capacity` was not introduced for elegance. It was introduced to get const expressions out of type
position:

> A `Cap`-parameterised container stores `[T; cap_size(N)]`, which places a const expression in type
> position and invokes nightly `generic_const_exprs`. That holds when the capacity is concrete at the
> use site, but **the round-trip `cap_size(cap(N))` overflows the well-formedness evaluator and ICEs
> the moment a generic consumer threads the capacity through its own generic code.** `Capacity`
> removes the const expression from type position entirely.

`Dim<N>::Array<T> = [T; N]` is plain min-const-generics. No `cap_size`, no `generic_const_exprs`.

**This is the hard constraint on any N-dimensional design.** Whatever expresses rank must not
reintroduce a const expression in type position, because the failure mode is not a compile error at
the definition, it is an internal compiler error at some downstream generic consumer. Any scheme that
computes a shape (a product of extents, a stride, a flattened length) as a const expression in a type
walks straight back into it.

The one bare `usize` in the whole convention is `Dim`'s own `const N`, and the document names it as
irreducible: array lengths are `usize` at the language level.

## The const sibling, which anything spatial will want

`ConstCapacity` is the const-callable analog, carrying `filled`, `get`, `set`, `slice`, `slice_mut`.
`Dim<N>` implements both, so a consumer needing both binds both.

The reason it is a sibling rather than an extension is worth carrying forward, because it will recur:

> `Capacity` itself cannot be a `const trait`. Its `from_fn` takes a `FnMut(USize) -> T` closure and
> calls `core::array::from_fn` in its body, neither const-callable, and `impl const Trait` must
> provide a const body for every method.

Anything spatial built here inherits that split. A point that can be constructed in a `const` context
and a point built from a closure are two surfaces over one storage, not one surface.

## The rank-limited pattern appears twice, not once

The preceding topic named `arvo-tensor` as the piece stopping at rank 2. The same stop exists a
second time, over bits:

| Crate | Rank 1 | Rank 2 |
|---|---|---|
| `arvo-tensor`, values | `Array<T, C: Capacity>` | `Matrix<W, C: Capacity>`, square |
| `arvo-bitmask`, bits | `Mask<W>` | `BitMatrix<W, C: Capacity>` |

Both already bind `C: Capacity` rather than a `Cap` const generic, so both already sit on the
general foundation and both stop at the same place for the same reason: nobody needed rank 3.

`arvo-tensor` states the division deliberately: bitmask is "fixed-shape bit containers, every slot is
a bit, ops are bitwise"; tensor is "fixed-shape value containers, every slot is a T, ops are
trait-generic over T". Whether a general rank abstraction spans both element domains or is expressed
once per domain is an open question and probably the most consequential one in the design.

## A limitation worth naming before anything is built on it

`Matrix<W, C>` is **square**: one capacity parameter serves both axes. A rank-2 shape with different
extents per axis is not expressible today.

That is fine for its current consumers, which are adjacency matrices and Laplacians, and it is fatal
for anything spatial, where a rectangle is exactly a shape with different extents per axis. Any
N-dimensional design has to carry **a capacity per axis**, not one capacity for all of them, and that
is a real departure from what exists rather than a generalisation of it.

## What consumes the rank-limited types today

Everything that would have to be re-read if the shapes change:

| Crate | Uses |
|---|---|
| `arvo-graph` | `BitMatrix` adjacency; topological sort, components, rank, critical path, waist detection |
| `arvo-sparse` | `Csr` over `C: Capacity`; RCM reordering, block diagonal, Dulmage-Mendelsohn |
| `arvo-spectral` | `Matrix`; Laplacian, power iteration, Fiedler vector, spectral bisection. Re-exports `Matrix` |
| `arvo-comb` | matrix chain DP, greedy interval grouping, bin packing |
| `arvo-bitmask` | `Mask<W>`, `BitMatrix<W, C>` |

Note that `arvo-spectral` re-exports `Matrix` from `arvo-tensor`, and `arvo-bitmask` and
`arvo-spectral` previously shipped local duplicates of `cap_size` that were consolidated into
`arvo-tensor`. The consolidation direction is established: this family converges on one home rather
than replicating.

## What `arvo-tensor` deliberately excludes

Recorded because an N-dimensional crate will be pushed toward every one of these, and the exclusions
are stated as identity rather than as backlog:

> - Arithmetic operations on tensors, consumer concern.
> - Sparse shapes: arvo-sparse's domain.
> - Bit-shaped tensors: arvo-bitmask's domain.
> - **ML-style broadcasting, reshaping, transpose chains, not aligned with arvo's role.** Consumers
>   that need those build them on top.
> - Heap-backed growable shapes: no. Sizes are const.

The fourth is the one to watch. "N-dimensional" is a phrase that pulls hard toward a tensor library,
and arvo has already refused to be one.

## What this leaves open

Stated as questions, not answers.

1. Does a rank abstraction live in `arvo-tensor`, or in a crate of its own that `arvo-tensor` then
   binds? The foundation is already in `arvo-tensor` and the consolidation precedent points there.
2. Does it span values and bits, or is it expressed once per element domain?
3. How is a per-axis capacity carried, given `Matrix`'s single-capacity square shape is the only
   worked example and is not the shape a rectangle needs?
4. How is rank named without a const expression in type position, given that is the exact failure
   `Capacity` exists to prevent?
5. Is rank a type-level list of capacities, a recursive nesting, or a capacity plus a rank marker?
   These have different consequences for the const surface.
6. What does the const half look like, given `Capacity` and `ConstCapacity` had to split?
