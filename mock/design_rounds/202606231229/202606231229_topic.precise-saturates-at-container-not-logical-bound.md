# Topic: Precise saturates at the container bound, not the logical bound

**Date:** 2026-06-23
**Phase:** TOPIC (open, standing)
**Scope:** arvo-strategy (all Precise arithmetic), arvo (IFixed/UFixed)
**Tracked:** task #3; catalogue test `i_mul_fixed_precise_should_saturate_to_logical_bound`

This topic is left open on purpose. It documents a known, shipped bug in arvo's `Precise` strategy. The next
person to work on arvo should fix this first, or fold it into their work. It is not parked silently: there is
a failing catalogue test pinning the correct behaviour, a source comment at the bug site, and this file.

## The bug

Every `Precise` arithmetic operation saturates at the **container** bound, not the **logical** bound.

`Precise` is the saturating strategy. The design contract (stated in the `IFixed` / `UFixed` doc comments)
is that `Precise` clamps to the logical range, the `i_MIN..i_MAX` (or `0..u_MAX`) defined by the logical
width `N = 1 + I + F` (signed) or `I + F` (unsigned). The shipped implementation does not. In
`arvo-strategy/src/arith.rs`, `impl_u_arith_saturating` and `impl_i_arith_saturating` implement every op
(`add`, `sub`, `mul`, `div`, and the fixed-point `u_mul_fixed` / `i_mul_fixed`) with the container's own
`saturating_add` / `saturating_mul` / `saturating_div` and `saturating_max()`. Those clamp at the container
maximum, which for `Precise` (a DoubleLogical strategy) is the 2x-width container, far wider than the logical
range.

The consequence: a result that exceeds the logical range but still fits the container is returned unclamped.
`Precise` silently fails to saturate exactly where saturation is the whole point of choosing `Precise`.

## Intended behaviour: logical max, and why it is the sound one

The design question is whether fixed-point saturation should clamp at the container bound or the logical
bound. The logical bound is the sound and expected behaviour, for four reasons:

1. The type's contract is its logical range. `IFixed<I, F, S>` advertises a logical value range; the
   container is an implementation detail the `Strategy` selects. If saturation clamps only at the container,
   a value of the type can hold a raw outside its own logical range, breaking the type's central invariant.
2. Saturation point must belong to the logical type, not the storage strategy. With container-bound
   clamping, `IFixed<8, 4, Precise>` (2x container) and `IFixed<8, 4, Hot>` saturate at different values
   despite being the same logical type. Saturation should be a property of what the type represents.
3. Soundness under conversion. If a `Precise` value can exceed its logical range, narrowing it to a
   same-logical-width `Hot` re-introduces the wrap that saturation existed to prevent. Logical-bound
   saturation keeps "value stays in logical range" invariant across strategy conversions.
4. It is what `Precise` users expect. Choosing the saturating strategy means clamp at the maximum the type
   declares (the logical max), not at a wider internal container the user never sees. This is the standard
   DSP / audio / graphics saturation semantic.

The container-gives-headroom argument is real but applies to the intermediate computation, not the stored
value: compute wide (exact, no precision loss), then saturate to the logical bound on output. Both are had
at once. So the fix is not "stop using the wide container", it is "clamp the final result at the logical
bound instead of the container bound".

## Worked example

`Precise` at logical width 8 dispatches to an `i16` container (DoubleLogical = 2x). The logical signed range
is 8-bit: max raw `127`. Take the fixed-point multiply at `FRAC = 4`:

```
i_mul_fixed::<4>(100, 100)   // raw 100 = value 6.25
```

The true product is `6.25 * 6.25 = 39.06`, which is far above the logical max (`~7.94`). Correct `Precise`
behaviour clamps to the logical max, raw `127`. The shipped code computes `saturating_mul(100, 100) = 10000`
(no `i16` overflow, so no saturation fires at all), then `>> 4 = 625`, and returns `625`: a value about five
times the logical maximum, unclamped.

The catalogue test `i_mul_fixed_precise_should_saturate_to_logical_bound` (in
`arvo/tests/fixed_point_mul.rs`, `#[ignore]`d) asserts the correct `127` and fails today with `left: 625`.

## Why it is arvo-wide, not specific to the multiply

The fixed-point multiply surfaced this, but the root is shared by all `Precise` ops. `add`, `sub`, `mul`,
and `div` all route through the same container-level saturating primitives and `saturating_max()`. Any
`Precise` result that overflows the logical range while fitting the container is affected. The fix belongs at
the strategy layer, not in one operation.

## The fix

Thread the logical bound into the `Precise` saturating bodies. The logical width `N` is the trait key
(`IArith<N>` / `UArith<N>`), so the logical `MIN` / `MAX` are derivable from `N` (signed: `MAX = (1 << (N-1))
- 1`, `MIN = -(1 << (N-1))`; unsigned: `MAX = (1 << N) - 1`, `MIN = 0`), computed in the container type.
After each op produces its (exact, for in-range) container result, clamp to `[logical_MIN, logical_MAX]`
instead of relying on the container's own saturation. For the fixed-point multiply specifically, the exact
product for in-range operands already fits the (2x) container, so the change is: replace
`saturating_mul(a, b) >> FRAC` with `(a.wrapping_mul(b) >> FRAC).clamp_to_logical(N)`. For the
`> 64`-bit-logical widths whose product needs a wider intermediate, this composes with the deferred WideBits
widen (the other half of task #3).

Out-of-range container inputs (values that already exceed the logical range before the op) are garbage-in per
`arvo-toolbox-not-policer.md`; the fix targets correct saturation for in-range operands whose result exceeds
the logical range, which is the contract `Precise` advertises.

## Boundary

Whether `Precise` should clamp at the logical bound (this topic's premise) versus document container-bound
saturation as the real contract was raised and decided: the logical bound is correct, the current behaviour
is the bug. The doc comments already promise the logical range; the implementation must match them.
