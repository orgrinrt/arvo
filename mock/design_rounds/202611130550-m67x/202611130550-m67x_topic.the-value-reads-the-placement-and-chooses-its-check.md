## The four, as this round resolves them

1. The carrier table. Which ladder container a slot family takes at sole occupancy is the placement's
   question, and `arvo-placement` answers it as a width, `derive_sole`. The value needs the answer as a
   type, so the placement gives it a second form, `SoleCarrier`, a row per slot family checked against
   `derive_sole` by an obligation every row forces. The value crate reads the container from there and
   adds only the host integer of the container's size, which is where host integers are named.
2. The debug abort. It becomes a parameter of the value, `DebugCheck`, defaulting to `Abort`, with
   `Quiet` beside it. A cargo feature was sketched beside it and refused: features unify across a
   build, so one crate's choice changes another's behaviour under a signature it never touched, and a
   consumer with no feature line cannot choose. `Wrap` and `Saturate` state the adaptation only, and
   the second spellings `Wrapping` and `Saturating` go, since with the abort on its own axis they would
   differ from the first in nothing.
3. The seals. `Sole`'s admission becomes a check over what a signature already declares, in the shape
   `arvo-format`'s own `Slots::ADMITTED` has, so a slot family, a policy or a mode of another crate is
   held on the shipped ones' terms. `ValuePolicy` and `ValueRounding` go. The one seal kept is on the
   host's machine integers, which the bit copy needs and which are not instances of a contract the
   canon opens.
4. The aliases. They read their adaptation through a projection, `NamesAdaptation`, which every
   `Adapt<R, O>` implements for itself. A strategy implements it later by its own selection, and the
   alias then gains `A = Warm` without breaking a consumer written today. The projection has to ship
   now: a consumer written against an alias without it is refused by the later one.
