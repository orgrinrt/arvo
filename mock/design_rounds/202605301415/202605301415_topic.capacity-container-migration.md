# Migrate the fixed-capacity surface from `const N: Cap` to `C: Capacity`

#650 shipped the `Capacity` trait and the `Dim<const N: usize>` marker into arvo-tensor: a fixed storage capacity expressed as a TYPE, with the backing array a GAT (`type Array<T>`) bound to a literal-length array in the concrete impl. The point of that foundation is that no const expression sits in type position, so `generic_const_exprs` never runs over capacity arithmetic and cannot overflow the well-formedness evaluator when a generic consumer threads the capacity through its own generic code. #650 proved the container shape in isolation. It did not change a single existing container.

This round uses the foundation. Every fixed-capacity container and every algorithm that today is parameterised by `const N: Cap` and stores or returns `[T; cap_size(N)]` migrates to a `C: Capacity` type parameter storing `C::Array<T>`. After the migration, the whole family is callable from fully-generic consumer code (the shape hilavitkutin's plan layer needs once it threads a `PlanDims` bundle of capacities, task #652) without the `cap_size(cap(N))` ICE that the round-trip produces today.

## Why the scope is the whole family, not just the named containers

The task names four principal targets: `Csr` (arvo-sparse), `Array` and `Matrix` (arvo-tensor), and conditionally `BitMatrix` (arvo-bitmask), plus the partition functions in arvo-spectral. The migration cannot stop there, and the reason is structural rather than discretionary.

Two cross-cutting traits couple the containers and their algorithm crates into one connected component. `SparseAdjacency<const N: Cap>` (a sealed trait with a GAT) is implemented for both `BitMatrix<W, N>` and `Csr<ROWS, NNZ, W>`. `LinearOperator<F, const N: Cap>` is implemented for both `Matrix<F, N>` and the `SparseLaplacian` that wraps a `Csr`. Migrating either trait's parameter forces both its impls in lockstep, and `Csr` is reached by both traits, so `Matrix`, `Csr`, `BitMatrix`, and their consumers (`arvo-graph`'s topo / rank / waist / components, `arvo-comb`'s dp / binpack / greedy, all of `arvo-spectral`) form a single web.

The no-legacy-shims rule forbids a transitional parallel definition (an old `const N: Cap` shape coexisting with the new `C: Capacity` shape), so the migration cannot be sliced into independently-green rounds. It is one atomic unit: one round, one PR, the workspace green at lock. There is also a second forcing reason: a function like `matrix_chain_dp<const N: Cap>` builds a `Matrix<W, N>` internally, and once `Matrix` takes a `Capacity` type it can no longer be built from a `Cap` value (Rust has no value-to-type lifting), so the function's own parameter must become `C: Capacity`. The cascade is mechanical and unavoidable.

The full surface is 60 `const _: Cap` parameter declarations across the six crates and roughly 327 `cap_size(N)` call sites.

## What the migration is, concretely

The change is mechanical parameter substitution plus a field and return-type rewrite. `const N: Cap` becomes `C: Capacity` on every declaration. A field or return typed `[T; cap_size(N)]` becomes `C::Array<T>`. A scratch array `[v; cap_size(N)]` becomes `C::filled(v)`; an indexed build becomes `C::from_fn(..)`. A value-position `cap_size(N)` (loop bound, comparison) becomes `cap_size(C::CAP)`. Two-dimensional storage (`Matrix`) becomes the composition `C::Array<C::Array<W>>`, no separate type, exactly as the foundation's design section anticipated.

The algorithms themselves do not change. The array sizes are identical (`[T; N]` and `[T; cap_size(cap(N))]` lower to the same array; an associated-const length and a const-fn length are the same to codegen), so the migration is bench-neutral by construction. Benches are rerun as verification, not because a regression is expected.

## Foundation extension: `Capacity::from_fn`

The shipped `Capacity` carries only `filled`. The containers expose `from_fn` (used by `Matrix::diagonal` and by several algorithms that build by index), so the trait gains a `from_fn<T, F: FnMut(USize) -> T>(f) -> Self::Array<T>` method alongside `filled`. The `Dim<N>` impl is `core::array::from_fn`. This is a foundation extension consistent with the locked #650 convention, not a change to its shape.

## Decisions settled by the sketch

The sketch at `mock/research/sketches/202605301400_capacity-trait-migration/` reproduces the real trait shapes (the sealed adjacency trait with its GAT, the sub-trait, the default-method problem-traits with blanket impls returning a capacity-sized array, the dual-impl `LinearOperator`, and a generic consumer that returns `C::Array<T>`) and compiles and runs clean on the pinned nightly. It settles four questions:

The trait family migrates as plain parameter substitution, GATs and all. The default-method problem-traits and their blanket impls type-check with `C::Array<_>` returns. The migration machinery needs no `generic_const_exprs`. The `pub const trait` qualifier on `SparseAdjacency` and `BidirectionalSparseAdjacency` survives the parameter-kind change, because their impls are plain (non-const) impls carrying ordinary runtime bodies; the `const` declaration is orthogonal to the parameter kind and stays as-is.

## A bonus: the GCE feature gate likely drops

Once `cap_size` leaves type position everywhere (replaced by `C::Array<T>` in fields and returns, and `C::filled` / `C::from_fn` for scratch), the only remaining `cap_size` uses are value-position const-fn calls in loop bounds, which need no `generic_const_exprs`. Each algorithm crate that has no other GCE use can drop its `#![feature(generic_const_exprs)]` gate. This is verified per crate during the source phase and is the outcome that obviates task #628 for these crates. Where some unrelated GCE use remains, the gate stays.

## Out of scope

The `BitMatrix<W, const N: Cap>` per-row bit width `W` (`Bits<64>` today, the column cap that bounds adjacency at 64 nodes) is a separate widening concern. Only the row-count `N` migrates here. Widening the column axis past 64 is tracked separately.

The deferred cross-variant bench decisions (#635, RCM bitmask-vs-CSR and spectral dense-vs-SparseLaplacian) are not part of this round; the migration preserves both variants as they stand.
