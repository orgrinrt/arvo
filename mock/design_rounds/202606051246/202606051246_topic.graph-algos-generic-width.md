# Topic: parameterize arvo-graph DAG algorithms over the adjacency row-width

**Date:** 2026-06-05
**Scope:** arvo-graph. The DAG algorithms (`waist_detect`, `components`, `topo_sort`, `upward_rank`, `longest_path`, and the spanning-tree path if it consumes the adjacency) currently hardcode `BitMatrix<Bits<64, Hot, Unsigned>, C>`. Generalize them over the row-bearing word.
**Source:** downstream hilavitkutin needs DAG analysis above 64 nodes (its `UnitId` addresses far more than 64 units); the engine just wired `compute_waists` to `waist_detect` at the 64-node fit and is blocked from wider plans by the hardcoded width. Fix the cap in the library, not in the consumer.

`BitMatrix<W, C>` is already generic over two independent axes: the row-count capacity `C` (a `Capacity` type) and the per-row bit-bearing word `W` (doc at `arvo-bitmask/src/matrix.rs`: "The per-row bit-width `W` is a separate axis from the row-count capacity `C`"). The `Mask<W>` chassis works uniformly across native-primitive backings (`Bits<8..=128>`) and the wide bucket (`Bits<129..=256>`) through the `BitPrim` impls on `WideBits`, per the `Mask` module doc. So the adjacency type and every bit operation the DAG algorithms use are already width-generic.

The cap is only in the algorithm signatures. Each one pins `Bits<64, Hot, Unsigned>` as the matrix word and the returned mask, even though its body uses nothing 64-specific: it calls `BitMatrix::predecessors` / `successors` (returning `Mask<W>`), `Mask::empty`, `Mask::insert`, `Mask::contains`, `Mask::iter_set_bits`, all of which are defined generically over `W: BitSequence + BitAccess + BitLogic + Copy + Default` (with `Identity` for `empty`). The scratch arrays (depth, width, visited, distance) are sized by the row-count capacity `C`, not by the word, so they are already width-independent.

Generalizing removes the pin: each algorithm takes a row-word type parameter (named to avoid colliding with the existing edge-weight `W` on `upward_rank` / `longest_path`), bounded `BitSequence + BitAccess + BitLogic + Copy + Default + Identity`, takes `BitMatrix<that, C>`, and returns `Mask<that>` where it returned a mask. A consumer then picks the word width that fits its node count: `Bits<64>` for up to 64 nodes, `Bits<128>` / `Bits<256>` for wider, any width the substrate's container projection supports. The container-width ceiling itself (how wide `Bits<N>` can go) is an orthogonal arvo-storage axis, not touched here; this round removes arvo-graph's artificial pin so the algorithms span whatever widths the storage layer offers.

This is the toolbox-not-policer shape: the library stops dictating a 64-node ceiling it has no reason to impose, and the consumer chooses the width its workload needs.

## Changes proposed

Add a row-word type parameter to each BitMatrix-consuming DAG algorithm, bounded on the bit-sequence traits the body already uses, replacing the hardcoded `Bits<64, Hot, Unsigned>` in the signature and return type. Bodies are unchanged (they are already generic over the mask word). Existing tests that instantiate at `Bits<64>` keep working unchanged (it is one valid word). A new test instantiates an algorithm at a wider word over a graph exceeding 64 nodes, proving the generalization is real and not just admitted by the type checker. Module and per-function docs drop the "over `Bits<64>`" phrasing for the generic statement.

## Out of scope

The container-width projection ceiling (whether `Bits<N>` supports N above the current wide-bucket range) is a separate arvo-storage / strategy axis. The engine-side consumption (hilavitkutin choosing a wider word and growing its plan dimensions past 64) is a separate hilavitkutin slice that follows this one.
