# Topic: correctness blockers found reviewing the release

**Date:** 2026-07-26
**Phase:** TOPIC
**Scope:** `arvo`, `arvo-strategy`, `arvo-bitmask`, `arvo-graph`, plus the toolchain pin

A review of the `dev` to `main` release PR found three defects that are wrong in shipped code rather than
wrong in a document, plus a toolchain pin that does not do what every artifact in the repo claims it does.
One round covers all of them: they are independent in mechanism but share a release, and splitting them
would mean four rounds gating one tag.

## The toolchain pin has never applied

`mock/rust-toolchain.toml` reads `channel = "nightly"`. Every command run inside `mock/`, which is the
entire Cargo workspace and where the whole test suite lives, resolves a floating nightly. `rustup show
active-toolchain` in `mock/` reports `nightly-aarch64-apple-darwin (overridden by
.../mock/rust-toolchain.toml)`, and resolves `cced03bfd` where the intended pin resolves `57d06900f`.

Worse, arvo has **no root `rust-toolchain.toml` at all**, so removing the `mock/` one is not sufficient:
it would leave the repo entirely unpinned. Both halves are needed, a root pin added and the `mock/` one
deleted, and rustup's upward search then makes `mock/` inherit the root.

This matters beyond tidiness. arvo is the one repo in the stack carrying `generic_const_exprs`, a feature
kept on a watch footing precisely because its behaviour can change under it. A floating channel is the one
thing that can roll past such a change silently, which is why the workspace policy rejects a floating
channel by name. Every claim of "verified on the pinned nightly" made about this repo, including the ones
in the release PR body, has been false.

The same shadowing exists in hilavitkutin, vehje, viola and mockspace, each with a pinned root and a
floating `mock/`. Those are their own repos and their own rounds; noted here so the pattern is on record
rather than rediscovered four more times. notko has the correct shape already: one pin at the root, no
file in a subdirectory.

## `Identity::ONE` is silently zero for a purely fractional type

`UFixed<0, 8, Hot>::ONE` has raw `0`. `UFixed<0, 8, Precise>::ONE` has raw `255`. Neither is one, and the
first means `x * ONE == 0` for every purely fractional `Hot` value: the multiplicative identity
annihilates instead.

The mechanism is in `ufixed_fixed_one`, which starts from the container's raw `1` and doubles `F` times to
build `1 << F`, the raw encoding of 1.0. That encoding needs a container wide enough to hold it. For
`UFixed<I, F>` the container is `I + F` bits, so `1 << F` fits exactly when `I >= 1`. At `I == 0` the
container is `F` bits and the final doubling carries off the top: `Hot` wraps to zero, `Precise` saturates
to the maximum.

The fix is not a better computation, because there is nothing to compute. `UFixed<0, F>` has logical range
`[0, 1)`, so **1.0 is not a value of the type**. Asking for its `ONE` is a category error, and the honest
answer is to make the compiler refuse it rather than hand back a plausible-looking number. `ZERO` is
unaffected and stays available at every width, since zero is representable everywhere.

### Refusing it in the type system rather than at const evaluation

A `const { assert!(I.raw() >= 1) }` inside the associated const would work, in the sense that
`<UFixed<0, 8, Hot> as Identity>::ONE` would stop compiling and could carry a decent message. It is worth
saying why that is the second-best answer.

A const assertion fires after monomorphisation. The impl still exists for `I == 0`, the type still claims
to be an `Identity`, and the contradiction only surfaces when someone reaches the constant. Any generic
code bounded on `T: Identity` accepts `UFixed<0, 8, Hot>` happily and breaks later, at a site that has
nothing to do with the mistake.

The bound belongs on the impl, so the impl genuinely does not exist:

```rust
pub struct Requires<const COND: bool>;

#[diagnostic::on_unimplemented(
    message = "`{Self}` names a constraint that does not hold",
    note = "UFixed<0, F> has logical range [0, 1), so 1.0 is not a value of the type \
            and it has no multiplicative identity. Use ZERO, or give the type at \
            least one integer bit."
)]
pub trait Satisfied {}
impl Satisfied for Requires<true> {}
```

and then the `Identity` impl carries `Requires<{ I.raw() >= 1 }>: Satisfied`. Now `UFixed<0, 8, Hot>` is
simply not an `Identity`, the failure is a trait-resolution error at the point of use, and the note says
what to do. This is the pattern the crate already uses for strategy selection, where `UContainerFor`
carries a `#[diagnostic::on_unimplemented]` that points a consumer at the right strategy when `Warm`
cannot reach a width; the machinery generalises to any const predicate, and `generic_const_exprs` is what
lets `{ I.raw() >= 1 }` sit in that position.

This is the substrate's own principle applied to itself. A state that cannot be correct should not be
constructible, and the current shape makes it constructible and wrong.

## Signed fixed-point multiply overflows at the container minimum

`<Hot as IArith<128>>::i_mul_fixed::<0>(i128::MIN, 1)` panics with "attempt to negate with overflow".

The negative branch computes an unsigned magnitude, casts it back with `let m = mag as i128`, and returns
`-m` or `-m - 1` depending on whether low bits were dropped. When the true result is the container
minimum, the magnitude is `2^127`, which casts to `i128::MIN`, and negating that overflows.

Two reasons this is a blocker rather than an edge case. `Hot` and `Cold` are the strategies that promise
never to panic, and a panic is exactly what they produce here. And it is a hard error under const
evaluation, so it fails a build rather than a run.

The container minimum needs handling before the negate, returning it directly rather than trying to
reach it by negating its own magnitude.

## Withdrawn: the bit matrix is not defective, its axis naming is

The review reported that `BitMatrix<Bits<64, Hot, Unsigned>, Dim<100>>` compiles while
`set_edge(nid(0), nid(70))` vanishes, and called it a silent wrong answer introduced by generalising over
the row word. Checked, and it does not hold.

That type is 64 columns by 100 rows, and says so: `rows: C::Array<Mask<W>>` is C rows each holding one
`Mask<W>`, and the doc comment states that "bit positions within a row cover up to
`<W as HasBitWidth>::WIDTH` column nodes" and that the two are "a separate axis". Column 70 does not exist
because nobody asked for it. Writing there is a caller indexing past a bound it declared itself, which is
the same class of mistake as running off the end of an array, not a type failing to hold its own shape.

Nor is it reachable in practice. Every instantiation in the tree is `Bits<64, Hot, Unsigned>` with row
counts of 1 to 6, so real usage is always wider on columns than on rows, never narrower.

The behaviour was checked rather than assumed, because there is a much worse failure in the
neighbourhood. Setting a bit is `1 << pos` on the container, and a native shift by 70 on a 64-bit word is
masked to `1 << 6` in release builds. Had that reached the container, `set_edge(0, 70)` would set column
**6**: not a vanished edge but a fabricated one, and every graph answer downstream quietly wrong. It does
not. `BitsBitPrim` declares "leaves self unchanged for `idx >= WIDTH`" and the implementation holds it:
after `set_edge(nid(0), nid(70))` on a 64-bit row the row is empty and column 6 is clear.

So the contract is correct and kept. What is missing is anything that keeps it that way. Nothing in the
suite pins the out-of-range case, so a future change to the bit-set path could start aliasing and every
existing test would still pass, since none of them addresses a column that does not exist. The src phase
adds that regression test. This is the catalogue discipline in its ordinary form: the case was found, so
it becomes a test, whether or not it is currently failing.

A compile-time refusal is not available here without changing the API. `set_edge` takes runtime `NodeId`
values, and a runtime index cannot be a compile error. Making it one would mean a const-generic column
position, which is a design change rather than a correction, and belongs with the axis-naming question
below rather than in a release fix.

What survives is smaller and is a follow-up rather than a blocker, but it is what made the report
plausible in the first place:

**The axes are named and declared asymmetrically.** Rows are chosen directly, as `Dim<100>`. Columns
arrive as a consequence of the row word's bit width, so a reader picks one axis on purpose and the other
by implication, and the signature gives no hint the two relate. And `Capacity`, as the name of the
parameter that means specifically the row count, tells a reader nothing about which axis it sizes. A
two-axis type wants both axes named for what they are, and if a non-conformal matrix is genuinely wanted
then columns deserve to be declared in their own right rather than smuggled in through the storage word.

Recorded here so the question is asked deliberately: is a non-conformal bit matrix a thing this crate
wants? If yes, name both axes. If adjacency is the only real consumer, squareness belongs in the type and
`arvo-graph` should not accept a shape it cannot correctly consume. Neither answer changes shipped
behaviour, so neither gates this release.

## Honesty items in the same pass

**The divide is known wrong above 64-bit logical width**, recorded as a catalogued red test with a tracked
task. That is the correct state for an unbuilt case, and it is fine to ship. What is not fine is a release
description saying "fixed-point multiply and divide" with no qualifier, so a reader concludes the
arithmetic is complete. The release text names the limit.

**Raw values escape the declared logical range** on `Hot` and `Cold`, because wrapping happens at the
container width rather than the logical width: a `u_mul_fixed::<6>` at logical 12 returns 57408 against a
logical maximum of 4095. This is pre-existing and reaches further now that multiply exists. The strategy
overview documents only that `Precise` clamps; it should state the `Hot` and `Cold` consequence too, since
a consumer choosing a never-panic strategy is choosing this.

**Hygiene**: nine declared-but-unused feature gates, four private-in-public warnings, unused imports, and
31 em-dashes remaining in crate sources against a rule of zero.

## What this round does not do

It does not migrate `generic_const_exprs`, redesign the capacity model, or build the wide divide. Each is
its own arc. This round makes what already shipped correct, and makes the pin real so the next
verification means what it says.
