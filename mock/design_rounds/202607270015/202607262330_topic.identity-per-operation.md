# Topic: an identity belongs to an operation

**Date:** 2026-07-26
**Phase:** TOPIC
**Supersedes on the Identity question:** `202607262200_topic.release-blockers.md`, whose framing of the
`Identity` fix (a bound saying "at least one integer bit") was wrong and is corrected here. Its findings on
the toolchain pin, the signed multiply, and the withdrawn bit-matrix report stand.

This started as a release blocker and turned into a design correction, so the reasoning is recorded in full
rather than compressed into the change it produced.

## What was actually broken

Four constants, none of them one:

| type | `ONE` raw | consequence |
|---|---|---|
| `UFixed<0, 8, Hot>` | 0 | `x * ONE == 0`, the identity annihilates |
| `UFixed<0, 8, Precise>` | 255 | 255/256, so `x * ONE` shrinks slightly, every time |
| `IFixed<0, 7, Hot>` | -128 | the container minimum, so `x * ONE` flips sign |
| `IFixed<0, 7, Precise>` | 127 | 127/128, shrinks |

Each was reproduced against the pinned toolchain rather than taken on report. The signed case is the worst
and was not in the original review at all.

The mechanism is one line of arithmetic. The raw encoding of 1.0 is `1 << F`, and the container is `I + F`
bits wide, so the encoding fits exactly when there is at least one integer bit to hold it. At `I == 0` the
final doubling in `ufixed_fixed_one` carries off the top of the container: the wrapping strategies wrap it
to zero or to the minimum, and the saturating one clamps it to the maximum.

The wrapping failures are obvious once seen. The saturating ones are worse, because `x * ONE` returns
something plausible and slightly smaller and an error compounds quietly instead of announcing itself.

**401 tests passed throughout.** Every one of them named a width where the constant happened to come out
right.

## Why the first two fixes were wrong

**A bound saying `I >= 1`.** This is what the previous topic proposed. It states a numeric fact about a
parameter rather than the property that actually matters, and it reads as a patch on a symptom. It also
removes `ZERO` along with `ONE`, because both live on the same trait, and zero is representable at every
width.

**Inherent `ZERO` on the concrete types.** The next attempt kept `Identity` bounded and re-exposed `ZERO`
as an inherent constant on `UFixed` and `IFixed`. That leaks a trait's own details onto every downstream
type that happens to need one of them, and duplicates a const that already has a home. Rejected on sight,
correctly.

## The actual shape

An identity is always an identity **with respect to an operation**. There is one concept, not two
constants named after their values:

```rust
pub struct Additive;
pub struct Multiplicative;

pub const trait Identity<Op>: Sized {
    const IDENTITY: Self;
}
```

`UFixed<0, F, S>` implements `Identity<Additive>` and no `Identity<Multiplicative>`. The absence is the
statement. Naming the multiplicative identity of a type that has none fails to resolve, with no predicate,
no assertion inside a constant, and nothing removed that was correct.

It also generalises where the hardcoded pair could not. `Identity<Min>`, `Identity<Max>`, `Identity<BitOr>`
each have their own correct element and fall out of the same declaration, rather than waiting for someone
to bolt on a third and fourth constant.

And it separates two things the old trait conflated. `Bits<N, S>::ONE` is a bit pattern; `UFixed<I, F>::ONE`
is the number 1.0 at raw `1 << F`. `ufixed_fixed_one` exists precisely to convert between them, which is
the tell that they were never the same constant.

### Why the operation contracts cannot carry the condition

The natural next thought is to hang the identity off the op traits arvo already has, so the bound comes
from the operation itself. It does not work, and the reason is worth writing down because it is not
obvious.

`UFixed<0, F>` genuinely has multiplication. `[0, 1)` is closed under it: `0.5 * 0.5 = 0.25` is in range.
So `Mul` is correctly implemented for exactly the type that must be rejected, and any bound of the form
"this type can multiply" is satisfied by it. The operation is present and only the element is missing.

`UArith<N>` and `IArith<N>` do not help either: they are implemented on **strategies**, keyed on container
width, operating on raw container values. They say a strategy can multiply 14-bit values. They say nothing
about whether a value type contains a one.

So multiplication and its identity are independent facts here, and the condition has to come from
representability instead.

### The mechanism already exists, and it is not a boolean

The condition is the general law that **an identity element must be a value of the type it is an identity
for**. Not a fixed-point quirk, and the same law would govern any operation added later.

An invented `Requires<const COND: bool>` witness with a `Satisfied` marker was written, then deleted, because
arvo already does this and spells it as a projection rather than a boolean. From `container.rs:106`:

> Absence of a `Project` impl for a given `(TAG, Sign, S)` triple is how `Uint<100, Warm>` (N=100, no
> native u256) becomes a compile error pointing at the `#[diagnostic::on_unimplemented]` note below.

That is the identical mechanism, already load-bearing: a sealed table with a single implementor, where the
missing impl **is** the refusal and the diagnostic attribute carries the explanation. `Project` is sealed
via `crate::sealed::Sealed`, so downstream cannot add impls.

It scales past a handful of cases because `BitsContainerFor` runs a const fn that **compresses a large const
space into a small enumerated tag set**, then enumerates impls over the tags. The same trick applies here:
compress `(width, frac)` into the two-element space "one is representable" and "one is not", seal a marker
over the tag, and implement it only for the first.

So no new primitive, and notko needs no change. The pattern was already in the crate; it was missed because
a search for the vocabulary (`Requires`, `Satisfied`, `<const C: bool>`) does not find a projection table.

### What `MINUS_ONE` shows

A signed purely fractional type spans `[-1, 1)`. Minus one **is** representable there, as the container
minimum, while one is not. So the condition must not be copied onto `SignedIdentity::NEG_ONE` on the
assumption that the two are symmetric. They are not, and the asymmetry is real rather than an oversight.

## The other two defects, both verified and one already fixed

**The signed multiply overflowed at the container minimum.**
`<Hot as IArith<128>>::i_mul_fixed::<0>(i128::MIN, 1)` panicked at `arith.rs:541`. The negative branch
reached its result by negating an unsigned magnitude, and at the minimum that magnitude is `2^127`, which
casts to `i128::MIN`, and negating that overflows. `Hot` and `Cold` are the strategies that promise not to
panic, and under const evaluation it is a hard error that fails a build rather than a run.

Fixed with `wrapping_neg`, which is identical for every other input and yields the minimum itself there,
the correct two's-complement answer. `never_panic_contract.rs` went red to green off that change.

**The toolchain pin had never applied.** `mock/rust-toolchain.toml` read `channel = "nightly"`, floating,
and shadowed the root for the entire Cargo workspace, which is where every test runs. arvo also had **no
root pin at all**, so deleting the `mock/` one alone would have left the repo unpinned. Both halves fixed:
root pin added, `mock/` one deleted, and `rustup show active-toolchain` in `mock/` now names
`nightly-2026-05-28` citing the root file. Every prior claim of verification on the pinned nightly, in this
repo, had been false.

The same shadowing exists in hilavitkutin, vehje, viola and mockspace. Their own repos, their own rounds.

## Withdrawn: the bit matrix is not defective

The review reported that `BitMatrix<Bits<64, Hot, Unsigned>, Dim<100>>` compiles while
`set_edge(nid(0), nid(70))` vanishes. Checked, and it does not hold.

That type is 64 columns by 100 rows and says so: `rows: C::Array<Mask<W>>` is C rows each holding one
`Mask<W>`, and the doc states the column count comes from the row word's width and that the two are "a
separate axis". Column 70 does not exist because nobody asked for it. Every instantiation in the tree is
`Bits<64>` with row counts of 1 to 6, so real usage is always wider on columns than on rows.

It was checked rather than assumed because a much worse failure sits next door: setting a bit is a shift by
the position, and a native shift by 70 on a 64-bit word masks to `1 << 6` in release. Had that reached the
container, `set_edge(0, 70)` would have set column **6**, a fabricated edge rather than a missing one, and
every graph answer downstream quietly wrong. It does not. `BitsBitPrim` declares "leaves self unchanged for
`idx >= WIDTH`" and the implementation holds it.

Nothing pins that, so the src phase adds the regression test. A compile-time refusal is not available
without changing the API, since `set_edge` takes runtime `NodeId` values.

What survives is a naming question, not a defect: rows are chosen directly as `Dim<100>` while columns
arrive as a consequence of the row word, so one axis is picked on purpose and the other by implication. And
`Capacity`, as the name of the parameter meaning specifically the row count, says nothing about which axis
it sizes. Worth settling on its own; it changes no shipped behaviour and does not gate this release.

## Why none of this was caught

arvo was never properly initialised under mockspace. That is why an 843-line `arith.rs` and an 814-line
`traits.rs` sat unchallenged against a configured limit of 500 at error on every gate.

Initialising it surfaced a second reason, which was fixed upstream during this round: `file-size` measured
only `ctx.source`, the crate root, and never `ctx.all_sources`. Since a crate root declares modules and the
code lives in siblings, every crate was being measured by its smallest file. arvo's roots are around 100
lines, so it reported clean. Fixed in mockspace and merged to its `dev`; arvo now reports both files.

A byline and advert audit ran over the whole history while mockspace was not watching: commits, tree files,
and every PR body. **Clean.** The only matches are the policy text stating the rule and quoting the
forbidden strings. No rehousing needed.

## What the tests must do

The old suite had 401 passing tests and did not assert that multiplying by the identity returns the operand.
The replacement asserts the laws over the **whole** matrix of signedness, strategy and width split, not a
sample, because a law asserted only where it already holds reports green and proves nothing about the rest.

One row of that matrix does not compile, and it stays that way:

```
error: this arithmetic operation will overflow
94 | identity_laws!(u_0_8_hot, Fixed<0, 8, Hot>, 1 << 8, ...);
   |                                             ^^^^^^ attempt to shift left by 8
```

The expected raw for one is `1 << F`, and at `I == 0` the container is `F` bits, so **the expected value
cannot be written down**. That is the strongest evidence in the investigation: not a wrong value, but a
property with no expressible form. It must not be restructured away, and once the fix lands the error
should change from an arithmetic overflow in a test literal to an unsatisfied trait bound in the type,
carrying the diagnostic note. Same colour, opposite meaning.

## Scope

In: the `Identity<Op>` redesign and its impls across the ten crates that reference it, the sealed tag
projection carrying representability, the identity-law matrix, the out-of-range column regression test,
splitting `arith.rs` and `traits.rs` under the now-enforced file-size limit, and the warning sweep (nine
unused feature gates, an unused import).

Out: migrating `generic_const_exprs`, the capacity and axis-naming question, the wide divide above 64-bit
logical width, which stays a catalogued red with its tracked task. The release text names that limit rather
than describing the arithmetic as complete.
