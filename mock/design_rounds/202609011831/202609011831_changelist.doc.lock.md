# Doc changelist: the law about a test over a declaration names both failures

**Date:** 2026-09-01
**Round:** the shipped tests narrate the process that wrote them
**Scope:** `mock/crates/arvo-format/DESIGN.md.tmpl`

Two changes, both corrections to sentences the round before this one wrote. The comment sweep this
round also carries needs no design sentence: taking a process noun out of a comment adds nothing to
the code, and what a shipped surface may say is a workspace writing rule rather than this crate's
contract. Restating it here would be a second copy of a rule that already exists, which is the shape
this design refuses elsewhere in the same section.

## CHANGE: the declaration law FROM one failure described as two arms TO the two failures it actually was
File: `mock/crates/arvo-format/DESIGN.md.tmpl`
Verification: `grep -c "asserted a constant against the literal its own definition sets"
mock/crates/arvo-format/DESIGN.md.tmpl` returns zero, and the section carries two paragraphs, one per
failure, each naming its own repair.

The law as written said two arms once asserted a constant against the literal its own definition sets.
That is accurate about the overflow inventory arm, whose `DeclaredBound` was declared four lines above
it and existed for nothing else, and inaccurate about the declared-width arm, which wrote its own
literals against a macro elsewhere in the crate and would have failed against a macro writing
something else.

**The second failed for a different reason and the law should carry it**, because a reader holding one
description applies the wrong repair. **No construction this crate ships can separate a width that is
read from one recovered by counting**, since the declaration and the bounds agree on every one of
them, so that arm could not establish the property in its own name whatever it asserted.

So the law states both: an assertion that reaches a declaration and stops, and an assertion whose
whole set of constructions answers the same way under either implementation. The first is repaired by
running the declaration through the machinery that reads it, the second by finding a construction on
which the two answers differ, and a design that named only the first would send a reader to the wrong
one of those.

## CHANGE: the separating construction FROM a range no function can reach TO the one the test uses
File: `mock/crates/arvo-format/DESIGN.md.tmpl`
Verification: the paragraph names a range running from zero to three and declaring thirteen bits, which
is `WiderThanItsSpan`, and `crate::slots::is_admissible::<WiderThanItsSpan>()` is asserted true.

The same round wrote that a declaration running from zero to a thousand and stating four bits reads
back as four bits. **That range is `WidthTooNarrow` and it is inadmissible**: four bits cannot address
a thousand slots, so the obligation refuses it and `declared_slot_width` cannot be called on it at all.
The sentence described a check nothing can run.

The construction that does separate the two answers runs the other way. A declaration wider than its
span is coherent and admitted, its bounds imply two bits, it states thirteen, and the function returns
thirteen. **The asymmetry is the point and the design now names the side that works**: a width that
cannot address its range is refused, and one wider than its range is not.
