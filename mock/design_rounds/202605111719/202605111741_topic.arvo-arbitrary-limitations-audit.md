# Arvo arbitrary-limitations audit

The trigger: while opening round 202605111719 to ship CSR-driven sparse + spectral algorithms for hilavitkutin, the topic-file framing accepted a "Capacity cap at 64 nodes" as if it were a substrate property. It is not. arvo-bitmask's chassis (`BitMatrix<W, N>`, `Mask<W>`) is already generic over the word type W. The cap exists because algorithms in arvo-graph, arvo-sparse, and arvo-spectral arbitrarily hardcode `Bits<64, Hot, Unsigned>` in their public signatures, throwing away the W-genericity the L2 layer provides. That is a code smell: the algorithm chose a width that has no theoretical justification at the algorithm level; it chose `Hot` strategy that has no algorithm-level justification; it chose `Unsigned` sign that has zero meaning at the adjacency level.

This round catalogs the pattern across the arvo codebase. The goal is a comprehensive list of every signature, type, alias, and const value that bakes in an arbitrary choice when the substrate already provides the generic surface to let the consumer choose. Each identified smell drives a follow-up round in its respective layer, with the corrected shape replacing the hardcoded literal. The catalog is the artefact; the per-layer fixes are tracked tasks.

The principle this round formalises: **the substrate ships generic surfaces and named defaults, never hardcoded literals masquerading as substrate properties.** Consumers choose width, strategy, and sign per workload, exactly as `arvo-toolbox-not-policer` says. This round audits the deviations from that principle.

## What "arbitrary" means here

An arbitrary choice is one that:

1. Is not derived from the layer's role (e.g. `BitMatrix<W, N>` taking N from the consumer is theory-forced; the structure IS the adjacency cap of N nodes).
2. Is not driven by a specific hardware constraint named in the design (e.g. `AlignedWideBits16` requiring `align(16)` for SSE2/NEON SIMD baseline is theory-forced).
3. Could be lifted to a generic parameter without changing the algorithm body's semantics.
4. Is mechanically substitutable: the consumer's choice flows through the same body code without per-choice branching at the L2 level.

A justified choice, by contrast, is:

1. Theory-forced (algorithm requires this exact shape, e.g. `Hot` strategy when the algorithm body genuinely depends on `u64` containers via `core::arch::*` intrinsics).
2. Naming the meaning (e.g. `Byte = Bits<8, S>` where the alias name IS the width).
3. A documented default in a type alias with no underlying generic restriction (e.g. `Adjacency<N> = BitMatrix<Bits<64, Hot, Unsigned>, N>` as a short-form default the consumer can opt out of by using the underlying generic directly).

The audit's job is to draw that line at every site and call out each violation.

## Survey results, 2026-05-11

A `grep -rn "Bits<64, Hot, Unsigned>" mock/crates/*/src/*.rs` returns 36 hits across signatures. A `grep -rn "Hot, Unsigned"` returns 79 hits total. An `N <= 64` runtime gate appears in arvo-spectral fiedler.rs and partition.rs. Five categories emerge.

### Category 1: algorithm signatures with hardcoded W

Every public function in arvo-graph, arvo-sparse, arvo-spectral that takes a `BitMatrix<...>` or returns a `Mask<...>` hardcodes `Bits<64, Hot, Unsigned>`. The chassis is generic; the algorithm throws it away. List:

| Crate | File | Function / type |
|---|---|---|
| arvo-graph | rank.rs | `upward_rank<N, W>`, `downward_rank<N, W>` |
| arvo-graph | topo.rs | `topo_sort<N>` |
| arvo-graph | path.rs | `longest_path<N, W>` |
| arvo-graph | waist.rs | `waist_detect<N>` |
| arvo-graph | components.rs | `components<N>` |
| arvo-graph | spanning.rs | `SpanningTree<N>` struct fields + `spanning_tree<N, W>` |
| arvo-sparse | rcm.rs | `rcm_reorder<N>` + private helpers |
| arvo-sparse | block.rs | `block_diagonal<N>` |
| arvo-sparse | dm.rs | `DulmageMendelsohn<N>` struct fields + `dulmage_mendelsohn<N>` |
| arvo-spectral | partition.rs | `spectral_bisection<N, F>`, `k_way_partition<N, K, W, F>` |
| arvo-spectral | fiedler.rs | (returns `Mask<Bits<64, Hot, Unsigned>>` implicitly) |

Fix: every such signature becomes generic over `W: BitPrim`. Mask returns flow through as `Mask<W>`. Default-W type aliases at module roots preserve the consumer ergonomics. Round 202605111719's corrected scope addresses arvo-sparse + arvo-spectral; a separate follow-up round handles arvo-graph (also blocked on hilavitkutin needs; the engine uses these too).

### Category 2: typed aliases hardcoding width

`arvo-hash::ContentHash = Bits<64, Hot>` is one specific instance. Consumers who want 128-bit content hashes for very large content sets are forced to abandon the semantic alias. Fix: `pub type ContentHash<const N: u16 = 64> = Bits<N, Hot>;` (with `Hot` justified by the hash impl's reliance on specific intrinsic dispatch, or made generic if not). The default keeps the short consumer form. Same audit applies to any other semantic alias that hardcodes width without theory motivation; the named-width aliases (`Byte`, `Word`, etc.) are theory-forced and stay literal.

### Category 3: runtime gates on hardcoded widths

`arvo-spectral::fiedler.rs` line 72 panics with "fiedler_vector requires N <= 64 (Mask<Bits<64, Hot, Unsigned>> partition surface)". `arvo-spectral::partition.rs` line 36 documents "Requires N <= 64 at call site". `arvo-hash::fnv1a.rs` and `arvo-hash::xxhash3.rs` document "1 <= N <= 64". These gates are downstream of the hardcoded mask-width choice. With W-generic mask returns, the gates either disappear (Category 1) or move from runtime panics to typed where-clauses bound on `W: BitPrim` (Category 4 below).

### Category 4: runtime assertions that should be where-clauses

Where a constraint is genuinely required (e.g. an algorithm body that does require a specific bit-width relationship), it should appear as a const where-clause bound checked at monomorphisation time, not as a runtime `assert!`. Convert every `assert!(n <= some_bound)` in arvo to a `where { const_assert!(N <= some_bound) }` or `where [(); some_const_expr]:` form. The compile-time form gives consumers immediate diagnostic feedback at the call site instead of a runtime panic.

Sites surveyed:
- `arvo-spectral/src/fiedler.rs:72` — `assert!(n <= 64, ...)`. Disappears with W-generic returns.
- `arvo-strategy/src/width.rs:127` — `else if n <= 64`. This is a const-eval branch in `Project<TAG, ...>` dispatch; theory-forced (matches the BitPrim allowlist). Stays.
- `arvo-strategy/src/container.rs:68`, `:86` — same as above. Stays.

### Category 5: hardcoded strategy markers in algorithm bodies

The 79 `Hot, Unsigned` paired literals across arvo source mostly come from Category 1. Some are in bench code or internal helpers; those need per-site review. The principle: an algorithm body that uses `BitAccess` / `BitLogic` / `BitSequence` trait methods is strategy-agnostic and should not name `Hot` literally; an algorithm body that calls `core::arch::*` intrinsics is theory-forced to whatever `Hot` lowers to on the target and should document the dependency.

## Why this is a separate round, not absorbed into 202605111719

Three reasons:

1. **Scope.** 202605111719 ships graph + spectral algorithms for hilavitkutin's Pass 3. Adding "audit + fix every arvo crate for arbitrary monomorphisation" turns a tractable round into a multi-week sweep. Keep it focused.

2. **Per-crate review burden.** Each follow-up round touches a different crate (arvo-graph, arvo-hash, arvo-spectral as separate sweeps). Per-crate reviews catch per-crate corner cases. A single mega-round risks one reviewer eyeballing 200+ signature changes.

3. **The catalog is the artefact.** The round-202605111741 doc CL writes the catalog into `mock/PRINCIPLES.md.tmpl` or a dedicated `mock/research/arbitrary-limitations-2026-05.md`. The catalog stays as the audit-trail reference; the per-category fixes happen in their own rounds with the catalog cited at SRC-CL time.

## Sub-questions deferred to per-crate rounds

- Does W-generic monomorphisation produce too many instantiations at the consumer level? (Per-crate bench follow-up. The substrate's existing strategy-axes work already validates broad monomorphisation; this should be fine.)
- Are there cases where `Hot` is genuinely theory-forced because the algorithm body invokes `core::arch::*` intrinsics on a specific container type? (Per-site review during the per-crate round.)
- Does the `Mask<W>` return shape interact poorly with hilavitkutin's existing call sites? (hilavitkutin consumer round, after 202605111719 closes.)

## Workspace-rule candidate

If the per-category sweeps land successfully, a workspace lint catches future drift. Provisional shape:

```text
forbid: a `pub fn` or `pub struct` field in arvo-graph / arvo-sparse / arvo-spectral that names `Bits<{literal}, Hot, Unsigned>` as a concrete type. Require either:
  - A generic parameter `W: BitPrim` with the type abstracted.
  - A `lint:allow(hardcoded-substrate-width) reason: <theory justification> tracked: #<task>` comment with linked task.
```

Lives in `mockspace-hilavitkutin-stack-lints` if shipped; the rule is broader than this stack (workspace-wide), so it likely lands in mockspace built-ins.
