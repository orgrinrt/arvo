# Genericity correction for round 202605111719

The prior topic file (`202605111719_topic.graph-spectral-for-hilavitkutin.md`) is committed and frozen. This sister topic corrects a framing error in it before the doc CL locks. Per the design-round skill, multiple topic files in one round are allowed during TOPIC phase. This one supersedes the prior topic's Subtopic A and B framings without rewriting them; the prior topic stays as audit-trail per workspace discipline.

## The error in the prior framing

The prior topic file describes "Capacity cap at 64 nodes" as the first impedance gap and frames algorithms as needing CSR drivers to scale past it. That framing accepts the bad-design smell as a substrate property. It is not.

`arvo-bitmask::BitMatrix<W, const N: Cap>` and `arvo-bitmask::Mask<W>` are **already generic over W** in their declarations. The algorithms in arvo-graph, arvo-sparse, and arvo-spectral arbitrarily monomorphise to `BitMatrix<Bits<64, Hot, Unsigned>, N>` and `Mask<Bits<64, Hot, Unsigned>>` in their public signatures. There is nothing in the algorithm bodies that requires a 64-bit word; the substrate provides `Bits<W, S, Sign>` for any `W` up to 256 (and beyond with `WideBits`), and `Mask<W>` and `BitMatrix<W, N>` accept any of those. The 64-bit choice is a literal in the signature, not a derivation.

The same applies to `Hot, Unsigned` paired literals (79 occurrences across arvo source). `Hot` is the consumer-facing strategy default; baking it into the algorithm signature forecloses the consumer choice that arvo-toolbox-not-policer says belongs to the consumer.

## The corrected framing

Every algorithm in arvo-graph, arvo-sparse, and arvo-spectral becomes generic over `W: BitPrim` (the word type) and over the strategy / sign axes wherever the body does not actually require a specific instantiation. The default-generic parameter takes the existing `Bits<64, Hot, Unsigned>` as the default value (preserving consumer ergonomics; the consumer can write the short form when they want the default). Consumers that need wider adjacency (256-node, 512-node via `WideBits`, etc.) pass `Bits<256, Hot, Unsigned>` or any other valid container.

Concretely, signatures change from:

```rust
pub fn rcm_reorder<const N: Cap>(
    adjacency: &BitMatrix<Bits<64, Hot, Unsigned>, N>,
) -> [NodeId; cap_size(N)]
```

to:

```rust
pub fn rcm_reorder<W, const N: Cap>(
    adjacency: &BitMatrix<W, N>,
) -> [NodeId; cap_size(N)]
where
    W: BitPrim,
    [(); cap_size(N)]:,
```

The same shape applies to `block_diagonal`, `dulmage_mendelsohn`, `topo_sort`, `upward_rank`, `downward_rank`, `longest_path`, `components`, `waist_detect`, `spanning_tree`, `laplacian`, `fiedler_vector`, `power_iteration`, `spectral_bisection`, `k_way_partition`. Wherever a function takes `&BitMatrix<...>` it becomes `&BitMatrix<W, N>` plus `W: BitPrim` bound. Wherever a function returns `Mask<...>` it returns `Mask<W>` (the input W). Bodies that operate on bits use the trait methods on `W`; no body should reference `Bits<64, Hot, Unsigned>` as a literal.

The `N <= 64` runtime assertions in `arvo-spectral::fiedler_vector` and `arvo-spectral::partition` go away. They exist only because the return type is `Mask<Bits<64, Hot, Unsigned>>`. With `Mask<W>` returns, the consumer's chosen W defines the cap; the algorithm has nothing to assert.

## Relationship to the CSR work

The prior topic's Subtopic A introduces a `SparseAdjacency` trait so non-bitmask representations (CSR) can drive the same algorithms. That decision stands. The two angles compose:

- **W-generic over BitMatrix:** consumers with bitmask-shaped adjacency scale to whatever W they pick. 256 nodes via `Bits<256>`. 512 nodes via `WideBits`. The substrate already supports both.
- **CSR-driven via `SparseAdjacency`:** consumers with edge-list / CSR adjacency drive algorithms through the trait, scaling to whatever `MAX_UNITS` / `NNZ` they declare.

Algorithm bodies that hold for both representations are written against `SparseAdjacency` (per the prior topic). Body parts that are specifically efficient over bitmask-style adjacency keep a BitMatrix-W-generic specialisation. Both routes scale; neither caps at 64.

The hilavitkutin consumer reaches for the CSR route because its `DependencyGraph` is CSR-shaped. A future consumer with bitmask-shaped data at `Bits<256>` instantiates the W-generic BitMatrix overload directly. Both routes co-exist; the consumer chooses the representation, the algorithm is the same.

## Subtopic G. Default-W ergonomics

Defaults on generic parameters keep the short consumer-call form. Rust does not allow defaults on function-generic parameters today, only on struct/trait/type-alias-generic parameters. Resolution: ship type aliases at module roots that pin the conventional default, and document that the underlying functions take `W` generically.

```rust
// arvo-sparse module root
pub type Adjacency<const N: Cap> = BitMatrix<Bits<64, Hot, Unsigned>, N>;

// Consumer call (short form):
let perm = rcm_reorder::<_, N>(adjacency_64);

// Consumer call (explicit form for wider W):
let perm = rcm_reorder::<Bits<256, Hot, Unsigned>, N>(adjacency_256);
```

The `Mask` returns flow the same way: `Mask<W>` for the input W. Consumers that want the `Mask<Bits<64, Hot, Unsigned>>` shape get it for free when they use the default; consumers picking `Bits<256>` get `Mask<Bits<256, Hot, Unsigned>>`.

## Subtopic H. Sign-axis genericity

`Unsigned` baked into every adjacency literal is harder to motivate than `Hot`. Adjacency matrices are bit-set membership questions; there is no signed-vs-unsigned semantic at the adjacency level. The right thing is `W: BitPrim` with whatever sign W happens to be; the algorithm body uses the bit-level operations that are sign-agnostic. Resolution: drop `Unsigned` from every adjacency / mask signature; the W type carries whatever sign it has.

`Hot` baked into every adjacency literal is similarly soft. The strategy markers select container width and lowering; algorithm bodies that operate via `BitAccess` / `BitLogic` trait methods get whatever those traits do for the consumer's W. Resolution: drop `Hot` from every adjacency / mask signature; let the consumer's W carry the strategy.

## Subtopic I. ContentHash and other typed hardcodings

`arvo-hash::ContentHash = Bits<64, Hot>` is the same smell at a different layer. A consumer who wants 128-bit content hashes (collision-resistant for very large content sets) is forced to abandon `ContentHash` and use `Bits<128, Hot>` directly, losing the semantic alias. Resolution: ship `ContentHash<const N: u16 = 64>` as a generic alias defaulting to 64 bits. Consumers that need wider hashes pass `ContentHash<128>` and get the same semantic alias at their chosen width.

Similar audit applies to the `Bit / Nibble / Byte / Word / DWord / QWord` aliases in arvo-bits. Those are documented as specific-width aliases (1 / 4 / 8 / 16 / 32 / 64 bits respectively); the names ARE the meaning, so the widths are theory-forced and stay literal. No change needed at that layer.
