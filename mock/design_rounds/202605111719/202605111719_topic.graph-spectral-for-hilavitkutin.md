# Graph + spectral algorithms for hilavitkutin's plan-stage

hilavitkutin's plan-stage chain has three steps that currently ship as `always TRUE` / passthrough stubs in `mock/crates/hilavitkutin/src/plan/steps.rs`: `rcm_reorder`, `block_diagonalise`, `spectral_partition`. Pass 3 (dispatch codegen) needs real algorithm outputs to compile a non-trivial schedule. This round closes the cross-repo gap by extending arvo-sparse + arvo-spectral so hilavitkutin can call real algorithms with its own data shape.

The named algorithms (Reverse Cuthill-McKee, Dulmage-Mendelsohn, Laplacian-Fiedler bipartition) are one impl each of three well-defined structural problems. Each problem has multiple known impls with different bench profiles. The round commits to problem-shaped API surface with the named algorithm as the default impl; alternate impls land under the same surface when bench evidence motivates them.

## What is already shipped vs what is missing

arvo-sparse has working bodies for `rcm_reorder`, `block_diagonal`, `dulmage_mendelsohn`. arvo-spectral has working bodies for `laplacian`, `fiedler_vector`, `power_iteration`, `spectral_bisection`, `k_way_partition`. None of these compile against hilavitkutin's data shape today. Three impedance gaps:

1. **Capacity cap at 64 nodes.** Every arvo-sparse algorithm takes `BitMatrix<Bits<64, Hot, Unsigned>, N>` and returns `Mask<Bits<64, Hot, Unsigned>>`. The canonical 64-bit container caps usable N at 64. hilavitkutin's `MAX_UNITS` runs to thousands per realistic schedule.

2. **Representation impedance.** arvo-sparse algorithms consume dense bit-adjacency. hilavitkutin's `DependencyGraph<MAX_UNITS, MAX_EDGES>` is CSR: `row_offsets: [USize; MAX_UNITS]` plus `col_indices: [UnitId; MAX_EDGES]`. There is no path from one to the other without quadratic re-materialisation.

3. **Spectral input shape.** arvo-spectral consumes dense `Matrix<W, N>`. For a sparse DAG with average out-degree two to five, `Matrix<W, N>` is mostly zeros; building it from CSR costs O(N^2) memory at a scale hilavitkutin cannot afford.

The round closes all three. The work is not "implement the algorithms" (already done); it is "land scalable CSR-driven impls of the same problems alongside the bit-matrix-driven ones, with bench-validated parameter choices".

## Subtopic A. Sparse-adjacency contract

The two representations (BitMatrix and Csr) describe the same abstract object: a directed graph over `0..N` nodes. The algorithms only ever ask the same handful of questions: successor set of a node, predecessor set, degree, iteration over set bits, membership test.

This round introduces a sealed contract trait in arvo-sparse (working name `SparseAdjacency`) that both representations implement. Algorithms become generic over `T: SparseAdjacency`. Returns the trade-off back to compile-time monomorphisation; the runtime path through the algorithm is unchanged. Cost: one extra trait layer per crate. Benefit: any consumer that ships its own adjacency representation (hilavitkutin's `DependencyGraph`, future viola/vehje shapes) can implement the trait once and reuse every algorithm.

Decision: trait-shaped. Generic over `T: SparseAdjacency<N>` with `N: Cap`. Both `BitMatrix<Bits<64, Hot, Unsigned>, N>` and a new `Csr<...>` impl land in this round.

Open axis: whether `SparseAdjacency::successors` returns an iterator (associated type) or fills a caller-provided scratch `Mask`. The iterator form is cleaner, but the Mask form lets the body amortise allocation against the bitmap and is what the current arvo-sparse bodies already use internally. Resolution: associated `type Successors<'a>: Iterator<Item = NodeId>` and provide a default `successor_mask(&self, node) -> Mask<Self::Word>` for impls that can answer the bitmap question cheaply. Algorithm bodies pick whichever form fits the access pattern.

## Subtopic B. Wider return types

Every classification mask currently returned is `Mask<Bits<64, Hot, Unsigned>>`, capping the algorithm at 64 nodes regardless of input adjacency type. The fix:

For `DulmageMendelsohn` and `spectral_bisection`, switch from masks to `[USize; cap_size(N)]` classification arrays. Output is `(USize, [USize; cap_size(N)])` with the same shape as `block_diagonal`. Node `i`'s classification is `class[i]`, where class IDs are `0 = horizontal`, `1 = vertical`, `2 = square` for DM, and `0 = positive`, `1 = negative` for bipartition.

This is a breaking change to two function signatures. arvo is pre-1.0, so per workspace `no-legacy-shims-pre-1.0` we drop the old mask-returning shape outright; no deprecation alias. The current arvo-sparse and arvo-spectral test files migrate to the new shape in this round's src CL.

A 64-node fast-path is still useful for downstream consumers that know they fit. Resolution: ship the array form as canonical; provide a `pack_to_mask(&self) -> Maybe<Mask<W>>` helper on the returned array struct when `N <= W::WIDTH`. Pack returns `Maybe::Isnt` past the cap. This is a small free function on the result type, not a function-signature divergence.

## Subtopic C. CSR sparse-adjacency impl

arvo-sparse already declares `Csr<ROWS, NNZ, W>`. This round adds `impl<...> SparseAdjacency<ROWS> for Csr<ROWS, NNZ, W>`. The successor iterator walks `col_indices[row_ptr[i] .. row_ptr[i+1]]` directly; the predecessor iterator is more expensive (must scan all rows to find back-edges).

Predecessor cost is the design tension. Two options:

Option C1: build the transpose at construction. `Csr::with_transpose(...) -> CsrBidirectional<...>` carries the original CSR plus a transpose CSR. Cost: 2x memory, one extra construction sweep. Benefit: O(out_degree) predecessor lookup. Recommended for the algorithms in this round (RCM and DM both need predecessors).

Option C2: predecessor scan on demand. Cheaper memory, O(N + NNZ) per predecessor query. Acceptable for small N or rare predecessor queries. Not acceptable for RCM (predecessor query per BFS step).

Resolution: ship both. Constructor `Csr::new(...)` for forward-only; constructor `Csr::with_transpose(...)` returns a `CsrBidirectional<ROWS, NNZ, W>` that implements `SparseAdjacency` with cheap predecessor access. Algorithms that need predecessors bound `T: BidirectionalSparseAdjacency`; one-way ones stay on `SparseAdjacency`.

## Subtopic D. Spectral methods over sparse Laplacian

arvo-spectral's `laplacian` builds a dense `Matrix<W, N>` from a dense weight matrix. For sparse adjacency this is wasteful and bounded by the wrong cap.

The Laplacian of a graph is `L = D - A`, where `D` is the diagonal degree matrix and `A` is the adjacency matrix. For SpMV / power iteration / Fiedler, we never need `L` materialised; we only need `L * x` for a vector `x`. `L * x` factors into `D * x - A * x`, both computable from a CSR-shaped adjacency in O(N + NNZ).

Resolution: introduce a `SparseLaplacian<T: SparseAdjacency<N>, W>` wrapper struct in arvo-spectral. It carries a borrow of the adjacency and the per-edge weight slice; its `apply(&self, x: &[F; cap_size(N)], out: &mut [F; cap_size(N)])` method computes `L * x` directly. Power iteration and Fiedler get a generic-over-operator overload that takes any `T: LinearOperator<F, N>` (sealed trait with one method `apply`). The dense `Matrix<W, N>` keeps its existing impl of `LinearOperator`; `SparseLaplacian` implements it from CSR.

Deflation (orthogonalising against the constant vector) is the existing pattern from `fiedler_vector`. Works unchanged because deflation only consumes the eigenvector estimate, not the operator.

## Subtopic E. Problem-shaped naming with named-impl defaults

Per the user's framing nudge: ship problem-shaped trait or free-fn names with the named algorithm as the canonical first impl. Future impls land alongside without renaming the consumer's call site.

The cleanest shape is a trait with default-impl free functions:

```text
trait BandwidthReducer<const N: Cap>: SparseAdjacency<N> { fn reorder(&self) -> [NodeId; cap_size(N)]; }
trait BlockPartitioner<const N: Cap>: SparseAdjacency<N> { fn block_diagonal(&self) -> (USize, [USize; cap_size(N)]); }
trait BipartiteStructuralAnalysis<const N: Cap>: BidirectionalSparseAdjacency<N> { fn dulmage_mendelsohn(&self) -> (USize, [USize; cap_size(N)]); }
trait SpectralBipartitioner<const N: Cap>: SparseAdjacency<N> { fn spectral_bisect<F: ...>(&self, iterations: USize) -> (USize, [USize; cap_size(N)]); }
```

Default impls run the named algorithm (RCM / connected-components / DM / Fiedler). Consumers override when they ship a different strategy. The named impls also exist as free functions in their respective modules; the trait sits on top.

This adds one trait layer per algorithm-family. It is not policer-shaped: the trait is open, the default is documented, no consumer choice is foreclosed. Aligns with `arvo-toolbox-not-policer`.

## Subtopic F. Bench scope

Before locking the doc CL, sketches and benches characterise the parameter space. Bench shape lives under `mock/benches/` per the established pattern (variant binaries + bench.toml). Two bench bundles:

**Bundle 1: structural-decomposition (RCM + block-diag + DM).** Inputs: random DAGs at N in {32, 128, 512, 2048}, average out-degree in {2, 5, 20}, plus three structured shapes (linear chain, full fan-out, layered with width 8). For RCM: bandwidth before/after, runtime. For block-diag: number of components found vs ground truth, runtime. For DM: classification stability under permutation, runtime. Cross-comparison: BitMatrix-driven vs CSR-driven where N <= 64.

**Bundle 2: spectral-bisection.** Inputs: same DAG shapes as Bundle 1, plus weighted variants with weights drawn from {uniform, exponential} distributions. For each: iterations to converge (eigenvalue gap), final cut quality (number of edges crossing the partition), runtime. Comparison: dense `Matrix<W, N>` Laplacian vs sparse `SparseLaplacian` operator across N where both fit.

Sketches under `mock/research/sketches/202605111719_graph_spectral/` characterise the bench parameter space before benches are written. Sketches walk through the algorithm bodies probing the rustc + trait-solver behaviour at the trait-bound shapes proposed in Subtopic A and E. Specific probes:

- S1. `SparseAdjacency` trait with associated `Successors<'a>` iterator type. Verify `pub const trait` viability under the current rustc toolchain.
- S2. Generic-over-`T: SparseAdjacency` algorithm body for `block_diagonal`. Verify monomorphisation does the right thing under `-Znext-solver`.
- S3. `LinearOperator` trait + `SparseLaplacian` impl. Verify dispatch generates the expected SpMV inner loop without extra indirection.
- S4. Wider return shape: `(USize, [USize; cap_size(N)])` instead of `Mask<...>` for DM. Verify const-generic boundary handles cap_size correctly.

## Out of scope

- Wider adjacency containers beyond 64-node BitMatrix. The existing `BitMatrix<W, N>` chassis is generic over `W`; instantiating with `Bits<256, Hot, Unsigned>` extends to 256 nodes without algorithm change. Currently tracked in arvo-sparse BACKLOG as ergonomic helpers; this round does not promote them.
- Specialised restricted-Laplacian variant (per-component eigen, used by `k_way_partition`). The current full-graph re-compute remains; a follow-up round optimises if benches show it on a hot path.
- Asm microkernels or SIMD lowering of SpMV. Lands when bench evidence motivates; out of this round.
