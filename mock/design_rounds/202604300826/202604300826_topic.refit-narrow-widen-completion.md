# Topic: refit-narrow-widen completion

**Date:** 2026-04-30
**Phase:** TOPIC
**Scope:** Complete the bit-width refit trait family. Add same-container
Narrow impls, declare and impl `Widen<T>` as Narrow's counterpart, ship
cross-domain primitive↔Bits direct impls, add ergonomic Bits constructors
`from_narrowed` / `from_widened`, rename `arvo-narrow` to `arvo-refit`
as the combined re-export crate.
**Source topics:** Round 202604271346 Q-C (arvo-narrow as facade-pulled
re-export); round 202604280034 (Narrow trait declaration moved into
arvo-bits-contracts post-arvo-narrow-contracts merge); round 202604281000
Pass B.4 (cross-primitive Narrow impl tables); round 202604280500

the gaps via four lint:allow sites tracked: #290.
**Tasks:** #290.

## Why

The Narrow side of the bit-width refit family shipped during the audit
chain (rounds 202604271346 → 202604281000) but four shapes are missing
that consumers hit immediately when adopting Bits beyond the
power-of-two carrier widths:

1. **Same-container Narrow impls** are not implemented, so any
   cross-Bits narrow within one container range fails to compile.
   Hilavitkutin's `Bits<32, Hot>` → `Bits<28, Hot>` (both u32-backed)
   needs `u32: Narrow<u32>`, which is missing. The cross-Bits forwarder
   can't satisfy its where-clause `<S as BitsContainerFor<M>>::T:
   Narrow<<S as BitsContainerFor<N>>::T>` when M and N project to the
   same carrier.

2. **No `Widen<T>` trait** for bit-width widening exists at all.
   `arvo-strategy::UWidenFrom` / `IWidenFrom` are *strategy* widening
   (Hot → Warm container promotion), a different concept. Consumers
   reach for bare `as u64` casts with `lint:allow(no-bare-numeric,
   arvo-types-only)` to push through, exactly the pattern `Narrow`
   was added to replace on the truncate side.

3. **No cross-domain primitive↔Bits direct impls.** Consumers wanting
   `u64` → `Bits<28, Hot, Unsigned>` go through `Bits::from_raw` plus
   an explicit cross-Bits narrow, two steps when one would do. The
   current `Bits::from_raw` constructor is the only entry point and
   it takes the exact carrier type, no narrowing or widening.

4. **No ergonomic Bits constructors.** `Bits::<28, Hot>::from_raw((wide
   as u32))` is the current shape, with the `as` cast lint:allow'd.
   What consumers want is `Bits::<28, Hot>::from_truncated_or_widened
   (src)` resolving the bit-width fit from the source's type.

5. **`arvo-narrow` crate naming** is single-purpose. With Widen
   landing in the same domain, the crate ought to name the domain
   (bit-width refit) rather than one of the two operations.

The design space here is small, the consumer pull (hilavitkutin PR #45's
four lint:allow sites + future consumers) is concrete, and the round
chains naturally on the audit chain that produced Narrow.

## Current state

**Narrow trait** (`arvo-bits-contracts` since round 202604280034):

```rust
pub const trait Narrow<T> {
    fn narrow_to<const N: u16>(self) -> T where Self: Sized;
    fn narrow_to_unmasked<const N: u16>(self) -> T where Self: Sized;
}

pub type Narrowed<const N: u16, T> = T;
```

**Cross-primitive Narrow impls** (`arvo-bits-contracts`, round
202604281000 Pass B.4):

- Unsigned: `u16 → u8`, `u32 → {u8, u16}`, `u64 → {u8, u16, u32}`,
  `u128 → {u8, u16, u32, u64}`.
- Signed: `i16 → i8`, `i32 → {i8, i16}`, `i64 → {i8, i16, i32}`,
  `i128 → {i8, i16, i32, i64}`.

**Cross-Bits Narrow impl** (forwards through carrier):

```rust
impl<const M: u16, const N: u16, S: Strategy, Sign: Signedness>
    const Narrow<Bits<N, S, Sign>> for Bits<M, S, Sign>
where
    S: BitsContainerFor<M, Sign>,
    S: BitsContainerFor<N, Sign>,
    <S as BitsContainerFor<M, Sign>>::T:
        ~const Narrow<<S as BitsContainerFor<N, Sign>>::T>,
{ ... }
```

**arvo-narrow crate** is a one-line re-export:

```rust
pub use arvo_bits_contracts::{Narrow, Narrowed};
```

**Bits constructors** (`arvo-storage`): only `from_raw(raw: <S as
BitsContainerFor<N, Sign>>::T) -> Self` and `to_raw(self) -> <...>`.

**arvo facade**: re-exports Bits and the bit traits via `arvo-bits`.
Does NOT re-export `Narrow` or `Narrowed`.

**Widen on bit-width axis**: does not exist.

## Decisions

### A. Widen<T> trait shape

`Widen<T>` drops the const-N parameter that Narrow carries. Asymmetric
trait shape:

```rust
pub const trait Widen<T> {
    fn widen_to(self) -> T where Self: Sized;
    fn widen_to_unmasked(self) -> T where Self: Sized;
}

pub type Widened<T> = T;
```

The asymmetry is principled. Narrow's const-N is the destination logical
width, load-bearing for the mask: `wide_u32.narrow_to::<13>()` masks to
13 bits, the same wide_u32 can narrow to any logical width in 0..32. Widen
does not have an analogous degree of freedom: each `Widen<T>` impl widens
from a fixed source type to a fixed target type, and the source bit-width
is determined by the impl context (carrier `BITS` for primitives, `M` for
`Bits<M, S, Sign>`). A const parameter on `widen_to` would be informational
at best and misleading at worst (callers might expect it to drive sign-
extension behaviour, but the impl context already determines that).

This decision was reached after considering three alternatives:

1. Keep const-N on Widen with a "source width" meaning, requiring a
   `HasLogicalBits` trait so constructors can read the source's logical
   width. Rejected: extra trait surface for a parameter that the per-impl
   context already provides.

2. Keep const-N as informational only. Rejected: const params that
   never drive behaviour are documentation pretending to be enforcement,
   and read as load-bearing at the call site.

3. Drop const-N. Chosen: cleanest shape, ergonomic constructors fall out
   naturally, no auxiliary trait needed. Documents the asymmetry with
   Narrow as a deliberate semantic-driven choice in the doc CL.

### B. Cross-domain primitive↔Bits direct impls

Ship them. Generate `Pri: Narrow<Bits<N, S, Sign>>` for every primitive
Pri the existing matrix covers, where Pri's BITS >= the carrier of
`Bits<N, S, Sign>`. Symmetric: ship `Bits<N, S, Sign>: Widen<Pri>` for
every primitive Pri the existing widen matrix covers.

The macro shape mirrors the existing cross-primitive macros; impls are
~3 lines each (delegate to carrier-side `narrow_to` / `widen_to` then
wrap or unwrap as appropriate). Combinatorial impl count is bounded by
the (5 unsigned + 5 signed) × (logical widths the strategy table covers
under each carrier) matrix, which the macros emit in one pass per
strategy.

The cross-domain direct impls let the ergonomic constructors (decision C)
have a one-line body without intermediate `Bits::from_raw` wrappers,
and let consumers that want to skip the constructor and call the trait
method directly do so without manually wrapping into Bits first.

### C. Bits ergonomic constructors

Add to the inherent `Bits<N, S, Sign>` impl in `arvo-storage`:

```rust
impl<const N: u16, S: Strategy, Sign: Signedness> Bits<N, S, Sign>
where S: BitsContainerFor<N, Sign>,
{
    pub const fn from_narrowed<Src>(src: Src) -> Self
    where Src: ~const Narrow<<S as BitsContainerFor<N, Sign>>::T>,
    {
        Self::from_raw(src.narrow_to::<N>())
    }

    pub const fn from_widened<Src>(src: Src) -> Self
    where Src: ~const Widen<<S as BitsContainerFor<N, Sign>>::T>,
    {
        Self::from_raw(src.widen_to())
    }
}
```

Source type `Src` is inferred from the value at the call site. No
turbofish. Constructor names match trait names (`from_narrowed` ←
`Narrow`, `from_widened` ← `Widen`); verb-style consistent with the
existing `from_raw`. Naming considered:

- `from_narrowed` / `from_widened`: chosen. Trait-name aligned, reads
  cleanly with `from_raw` family.
- `from_truncated` / `from_widened`: marginal idiom edge for `truncate`
  in cast contexts (LLVM's `trunc` instruction), but breaks verb-family
  consistency with the `Narrow` trait name.
- `truncating_from` / `widening_from`: more `From`-style, but breaks
  symmetry with the existing `from_raw`.
- `narrowed` / `widened` (no `from_`): rejected, ambiguous with
  instance-method action verbs; unprecedented in std (`String::from_utf8`,
  `Vec::from_iter`, `i32::from_le_bytes` all carry `from_`).

### D. arvo-narrow → arvo-refit rename

Combined narrow + widen re-export crate. Single-purpose `arvo-narrow`
becomes domain-named `arvo-refit`: bit-width refitting via `Narrow` and
`Widen`. The crate body is an extended one-liner:

```rust
pub use arvo_bits_contracts::{Narrow, Narrowed, Widen, Widened};
```

Naming considered (rejected after second pass):

- `arvo-resize`: right concept but the word "resize" reads awkwardly
  for bit-width operations.
- `arvo-rewidth`: explicit but verbose.
- `arvo-shape`: too vague.
- `arvo-bitfit`: candidate but `arvo-refit` reads more natural.
- `arvo-fit`, `arvo-bridge`, `arvo-cast`: rejected for vagueness or
  Rust-keyword overlap.

Chosen `arvo-refit` reads as both verb and crate name: "refit a value
to a different bit-width" via Narrow (down) or Widen (up).

### E. Same-container Narrow impls

Add `u8: Narrow<u8>`, `u16: Narrow<u16>`, ..., `u128: Narrow<u128>`,
plus signed counterparts. The existing macro body's `if (N as u32) >=
<$src>::BITS { return self as $dst; }` short-circuit handles the
same-width case correctly; the macro just needs an extra invocation
per row.

This unblocks any cross-Bits Narrow within one container range. The
fix is mechanical; it could have shipped in round 202604281000 had the
matrix been written as a closed cross-product instead of a strict-
narrowing matrix. The omission was a thinko, not a design choice.

## Out of scope

- **Cross-strategy Narrow / Widen** (Hot → Warm logical widening with
  bit-width change). Consumers cast strategy first via existing
  Conversion / arvo-strategy paths, then refit. Same scoping rationale
  as round 202604280034 used for cross-strategy Narrow.

- **Lossy widen variants.** All Widen impls preserve the source value
  exactly (zero-extend for unsigned, sign-extend for signed). No
  truncating-widen or saturating-widen. Consumers needing those compose
  Narrow + Widen explicitly.

- **Generalised Refit<T> trait.** A unifying trait that resolves to
  Narrow or Widen based on source vs target widths is tempting but
  would need const-bounded dispatch (`if M > N then Narrow else Widen`)
  that const traits don't yet express cleanly. Two separate traits
  with parallel ergonomics on Bits constructors covers the consumer
  ergonomics without the bound-resolution complexity.

- **`arvo-narrow-contracts` revival.** The contracts crate was merged
  into `arvo-bits-contracts` in round 202604280034 and stays there.
