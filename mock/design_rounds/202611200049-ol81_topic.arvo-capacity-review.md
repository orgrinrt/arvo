**Date:** 2026-11-20

The first review of the capacity crate found it short of the consumer it was written for. hilavitkutin
builds arrays of elements that are not `Copy` from a capacity it is generic over, at
`mock/research/sketches/202611152312_derived-context-monomorphic/engine/src/dispatch/core_dispatch.rs:41`
(`<C as Capacity>::from_fn(|_| FiberDispatch::new())`) and in its scheduler builder and defaults, and the
crate offers only `filled<T: Copy>`. The same gap is what left the consumer to state a `Copy` bound on a
nested inner array. The review also found a compile-fail pair that tests the language rather than the
crate, a design naming the mutant cfg wrongly, a test comment overclaiming what the mutant turns red,
the count sampled under one adaptation only, and a seal whose refusal names nothing a reader can act on.

## What the canon says, and where it is silent

`obligation::a_count_fixed_at_build_that_sizes_arrays_from_generic_code` is still the row, still a
proposal asked of op. Its need is a real array sized from generic code; an array a generic caller can
only fill with a copied value serves part of that need. No row says how an array is built, so how the
constructor is spelled is design.

## D1. A constructor that takes a closure

`Capacity` gains `filled_with<T, F: FnMut() -> T>(f: F) -> Self::Array<T>`, the array with every element
the next value `f` returns, in order from the first. It needs no `T: Copy`.

Options it was chosen among:

1. `from_fn<T, F: FnMut(usize) -> T>`, the shape of `core::array::from_fn` and of hilavitkutin's old
   spelling. Rejected: the index is a bare `usize` at a public position.
2. `from_fn` with the index as `USize<A, K>`, `A` and `K` generic on the method. Rejected: every call
   site writes `|_|` and the index's adaptation cannot be inferred from it, so each call names an
   adaptation it does not use; and choosing one for the consumer is policy the crate does not own.
3. `filled_with` with no index. Taken. Every use site hilavitkutin has ignores the index, and a
   consumer that wants one counts in the closure, under the adaptation it picks.

With it, a nested array is built as `Outer::filled_with(|| Inner::filled(v))`, and the `Copy` residue the
first round documented is gone from the consumer. The paragraph naming it goes.

## D2. `filled` and `filled_with` are not `const`

They are trait methods, and a trait method is `const` only under `const_trait_impl`, which the stack has
not vetted for this crate. The design says so. A const arm is a follow-up, ticketed.

## D3. The seal says what it is

The seal carries `#[diagnostic::on_unimplemented]` naming `Dim<N>` as the one capacity and the open
question it is sealed under, so the refusal an outside implementor meets says what to do instead.

## D4. Tests

The pair refusing a `Dim` sized by a run-time value goes: the refusal is rustc's for any generic
argument read from a local, whatever `Dim` is, so it cannot fail for anything this crate does. Its twin
duplicated the outside-use twin of the seal pair.

The count is asserted at zero, one and the host's largest `usize` under every rounding mode and every
overflow policy `arvo-format` names, under both checks, where each combination admits `USize`.

`filled_with` is asserted to call its closure once per element, in order, with an element type that is
not `Copy`.

The agreement test's comment says what the mutant turns red: the tests that read the count. The
committed mutant run is redone over the new tests.

The consumer builds its nested array with `filled_with` and drops its `Copy` bound; its live count is a
`USize`. Its lockfile pins the notko the workspace builds.

The copy of `arvo-numeral`'s consumer harness drops its self-test, which `arvo-numeral` runs already.
Extracting the harness to one place is ticketed, since it touches `arvo-numeral`.
