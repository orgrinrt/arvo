**Phase:** TOPIC
**Scope:** arvo-spectral live-node-count awareness for loose-CSR Laplacians
**Source topics:** follow-on to round 202605291759 (arvo-sparse loose CSR, #634)

## Problem

arvo-spectral's iterative algorithms (`power_iteration`, `fiedler_vector`, `k_way_partition`, `spectral_bisection`) operate over the full const-generic dimension `cap_size(N)`. Every loop, every sum, every normalisation, and the Fiedler deflation against the all-ones direction run from `0` to `cap_size(N)`.

That was correct while every CSR was packed (live rows equal to the capacity). Round 202605291759 introduced loose CSR: a `Csr<ROWS, NNZ, W>` may carry `live_rows < cap_size(ROWS)`, with rows `[live_rows, cap_size(ROWS))` empty, and `node_count()` returning the live count through the `SparseAdjacency` trait. A `SparseLaplacian` wrapping a loose CSR now has a slack tail of empty rows.

In a graph Laplacian, an empty row is a degree-0 isolated node. Each isolated node is its own connected component, and the algebraic multiplicity of the Laplacian's zero eigenvalue equals the number of connected components. A loose graph with many slack rows therefore has a high-multiplicity zero eigenvalue, which makes the Fiedler vector (the eigenvector of the second-smallest eigenvalue) degenerate: the iteration latches onto a trivial isolated-node direction instead of separating the real graph. Two concrete failures follow:

1. `fiedler_vector` deflates against the all-ones vector with a mean taken over all `cap_size(N)` entries. The slack tail dilutes that mean and corrupts the deflation step regardless of whether the slack rows contribute to the matvec.
2. `k_way_partition` counts slack nodes toward each partition's `active_count`, so it spends its `K` budget bisecting meaningless isolated nodes and emits partition ids for rows that are not real graph nodes.

The consumer that forces this now is the hilavitkutin engine (Phase C, task #642): its `spectral_partition` step wraps a `CsrBidirectional` whose `unit_count` is typically far below `MAX_UNITS`, then calls `k_way_partition`. Today the engine discards the spectral output, so the corruption is harmless; the moment the engine consumes it (C1d-3) a non-full pipeline silently mispartitions.

## Resolution

The algorithms must iterate over the live node count, not `cap_size(N)`. The live count is a derived property of the graph, and the operator already owns the graph: `SparseLaplacian` wraps a `Csr` that knows its `live_rows` and exposes `node_count()`. The fix puts the knowledge where the data lives.

`LinearOperator<F, N>` gains a default method `fn live_dim(&self) -> USize { cap_size(N) }`. Dense `Matrix<F, N>` and any consumer operator that is always fully packed inherit the default and behave exactly as before (no slack concept, no edits, no test churn). `SparseLaplacian` overrides `live_dim()` to delegate to `self.csr.node_count()`. The three operator-driven algorithms read `operator.live_dim()` once and iterate `[0, live_dim())` everywhere they used `cap_size(N)`; the slack tail stays zeroed. `spectral_bisection` takes an explicit `live_n` argument because it receives a precomputed eigenvector array rather than an operator.

This shape was chosen over threading an explicit `live_n` parameter through every function because the caller-supplied-count path carries a silent-reinstatement risk: a caller who passes the handy `cap_size(N)` constant literally would reintroduce the exact bug. Encoding the live count on the operator follows the pattern arvo uses elsewhere, the type that holds the data exposes the derived property. The shape was validated by an independent architect review against both alternatives.

## Downstream coordination

The hilavitkutin engine's `SymmetricLaplacian` also implements `LinearOperator`; under the default method it keeps its current full-cap behaviour until C1d-3 adds a one-line `live_dim()` override delegating to its `CsrBidirectional::node_count()`. No engine break lands with this round; the engine adapts when it bumps its arvo dependency.
