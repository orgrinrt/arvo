# Add `cap`, the usize to Cap const constructor

`arvo-tensor` ships `cap_size(Cap) -> usize`, the canonical projection used in
`generic_const_exprs` array-length position. Its inverse does not exist: there
is no `usize -> Cap` const constructor anywhere in arvo. Consumers that need to
form a `Cap`-parameterised type (for example `Csr<{..}, {..}, W>`) from a
`usize` const-param cannot, because the literal constructor `Cap(USize(n))` is
rejected in const-generic position ("struct/enum construction is not supported
in generic constants"); a named `const fn` is the only accepted form, exactly as
`cap_size` already documents for the other direction.

## Current state

`cap_size(c: Cap) -> usize` (`arvo-tensor/src/cap.rs`) returns `c.0.0`. No
`cap`/`cap_of` inverse exists. `Cap(pub USize)` and `USize(pub usize)` are public
tuple newtypes, so the construction is trivial; it just needs to live behind a
named `const fn` to be usable in const-generic position.

## Changes proposed

Add `pub const fn cap(n: usize) -> Cap { Cap(USize(n)) }` to `arvo-tensor/src/cap.rs`,
the canonical inverse of `cap_size`, and export it from the crate root next to
`cap_size`. The `usize` parameter is the definition-site primitive boundary (same
justification as `cap_size`'s `usize` return), carried under a `lint:allow` with
the existing `#121` tracking reason. This is the substrate completion that lets
the hilavitkutin Phase C adapter name `Csr<{cap(MAX_UNITS)}, {cap(MAX_EDGES)}, W>`
with `[(); cap_size(cap(MAX_UNITS))]:` bounds, verified feasible by the
hilavitkutin sketch `202605290245_usize-to-cap-const-bridge.md`.
