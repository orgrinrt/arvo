# a-value-as-the-count-of-a-type-level-list

**Date:** 2026-11-13
**Round:** 202611132111-ew52, the fifth of track T3 on `work/arvo-values`. Ticket
`arvo_implements_notko_hlist_s_cardinal_for_usize`.

## What the round is for

`notko-hlist` is the workspace's type-level list. It counts a list's cells in a number type of the
consumer's own, through a trait of two items, a zero and a successor, and it says in its own text that
the number belongs to whichever crate owns the numerics. hilavitkutin's api adopted the list and kept
its own recursion for one length, because the count it wants is arvo's platform-sized integer and the
orphan rule gives that impl to one of two crates, the list's or the value's, and it is neither of
them. The list has no dependency and should have none. So the impl is the value's to carry.

This round implements the list's count trait for a value.

## What the canon says, asked before anything was written

The registry was searched for a row on counting, on a list, on a foreign trait and on a length. It
has none, and it has no reason to: a count is a member of an integer format, and what a value of one
does is already stated. The rows that bear on the round are these.

`ruling::the_format_spine_is_canon`: a value's operations are the format's own. A successor is a sum
with the format's one, so it is `add`, with the completion and the debug check `add` has. Nothing new
is stated about a number.

`obligation::a_platform_sized_unsigned_integer_at_an_api_position`: hilavitkutin carries arvo's
platform-sized integer at public positions, which is why its length is wanted in that type.

`obligation::the_unstable_machinery_does_not_reach_a_consumer`: a consumer naming arvo's types needs no
unstable feature and no gate of its own, whatever arvo uses internally. This is the row the round has
to be careful with, below.

`proposal::a_missing_identity_is_refused_as_a_failed_constant`, at one expert and provisional: the
shape both identities take, which the count reads.

`proposal::a_value_is_the_sole_occupancy_placement_of_a_declared_signature`, on a provisional stamp:
built on as provisional and not cited as ratified.

## For which values

The ticket names the platform-sized integer. The impl is written for every value: the count of
nothing is the additive identity, and one more is the sum with the multiplicative identity. A value
whose format has no one, a format of multiples of eight or a one-bit signed integer, has no count, and
is refused by the identity's own failed constant with its own message. A fixed-point value counts in
whole members, at its one.

Narrowing it to the platform-sized alias would be a second impl the first time a consumer counts in a
byte, and choosing unsigned only would be this crate deciding what a consumer may count in. The
consumer picks the count type at the bound, as the list intends.

A count past the range is the signature's sum: completed by the overflow policy, and under the
default check aborted on in a debug build. Where the length is read as a constant the abort is in
constant evaluation, so a list too long for its count type under `Abort` does not build. That is the
right refusal and it costs nothing to get.

## The const path, and the first optional gate in the tree

The list's length is a constant only where its count trait is a const trait, which is the unstable
`const_trait_impl`, and hilavitkutin wants the constant. A plain impl would compile against the const
trait and give no constant. So there are two paths, as the list has two:

`hlist` implements the trait plainly. The list is taken without its `const` feature, nothing in the
build is unstable, and a length is a call.

`hlist-const` implements it as a const impl and enables `const_trait_impl` in this crate, for that
one impl. A length is a constant.

Both are cargo features, off by default, so a consumer that does not ask sees the crate as it was,
with no new dependency and no gate. This is the first unstable feature any arvo crate can enable, and
the round says so where the root design says none is enabled.

It is inside what the canon allows. The obligation is on the consumer's side, and a consumer reading
a length as a constant writes no gate: the const call is made inside the list's own impl. A test
target that reads lengths as constants with no feature attribute is the proof of that. The workspace's
feature rule lists `const_trait_impl` as sound, with rough edges that are implementation gaps, and
`notko` enables it by default already, so the stack below this crate has it on today.

What it is not is a licence for the rest. No trait of arvo's becomes a const trait in this round, and
the operations stay inherent `const fn`s. Whether arvo's own traits should be const traits is a larger
call that is not made here, and a question ticket to op records that this optional gate now exists.

## What is proved

Lengths of lists of zero to four cells, and indices of positions, in the platform-sized integer, a
byte, a signed integer and a fixed-point value, on both paths off one shared module. Counts past the
range under wrapping and under saturation. On the const path, lengths as constants, one of them as an
array's length. The debug check: a call past the range aborts in a debug build on the plain path, and
on the const path it is a compile-fail pair, with a second pair for a format without a one.

`mutant-count` stops a count at one, and turns both targets red.

The consumer crate names no feature, so it does not reach the impl, and the two targets stand in for
it: each is written as a consumer would write it, with bounds on the list's traits and no gate.

## What the round leaves

hilavitkutin's api reading the shared length is its own round, in its repository. The targets run
only when their feature is named, so the default test run does not reach them.
