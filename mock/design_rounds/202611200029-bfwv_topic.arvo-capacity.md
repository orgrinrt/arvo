hilavitkutin sizes nearly everything it holds by a count fixed when it builds, and names the arvo
spelling of that count more than anything else of arvo's but the value type itself. arvo has had no
capacity since the canon work emptied the tree. This round writes the crate that carries one, against
the obligation row written for it on this branch, in the spelling the sketch on this branch found to
work from an outside consumer with no feature line.

## What the canon says, and where it is silent

`obligation::a_count_fixed_at_build_that_sizes_arrays_from_generic_code` is the row the crate answers.
It is a proposal for op to ratify, asked as `does_the_capacity_obligation_row_stand_as_arvo_s_need`,
and this round builds on it meanwhile. Its need asks for five things: a count fixed at the consumer's
build and carried as a type that sizes a real array from code generic over it; many such counts as the
associated types of one parameter; one count's array nested in another's with no product computed;
the count readable in a constant; none of it needing a feature line in the consumer.

`proposal::the_old_tensor_crate_returns_as_the_capacity_crate` (one expert) says the crate returns as a
count as typestate with its array projection and a const count. `proposal::the_old_storage_crate_is_gone`
moves the old `Cap` here. Neither is canon. hilavitkutin's own registry ratified the shape from its
side: one marker generic over the count implementing a non-generic capacity trait, the rung ladder
dropped (`fixed_capacity_is_one_generic_dimension_marker_implementing_the_capacity_trait_and_the_macro_rung_ladder_is_dropped`
in hilavitkutin's registry). arvo's canon is silent on the crate's place and on sealing.

The retirements this round must not repeat: `retirement::dl_capacity_unification_naive_spelling`,
`retirement::dl_feasibility_probe_compiled_the_load_bearing_path` (an earlier probe sized phantoms,
not arrays, so every arm here sizes a real array) and `retirement::dl_capacity_checked_at_the_one_construction_door`
(a capacity is never constructed, so no door sees a count that disagrees with its array).

The sketch `mock/research/sketches/202611200010_capacity-spellings/` measured three spellings from an
outside consumer. A count as a type works, bundled and nested. A count as a value of an adt const
parameter needs `min_adt_const_params` in the consumer to declare the parameter and
`generic_const_exprs` to size an array from it. A bare `usize` parameter works per parameter and
cannot be bundled. With the trait open, an outside implementor reports a count its array does not
have, and the build accepts it.

## D1. The crate

`arvo-capacity`, above `arvo-numeral`, depending on `arvo-format` and `arvo-numeral` and nothing else.
`#![no_std]`, no allocation, no feature of its own and no unstable gate.

## D2. The trait

`Capacity` carries a count as typestate. Its associated type `Array<T>` is an array of exactly the
count's length, bounded by `AsRef<[T]>` and `AsMut<[T]>` so generic code walks it as a slice, which is
the slice bridge hilavitkutin's `ConstCapacity` spells. `filled(value)` gives the array with every
element `value`, for `T: Copy`. Nesting is a projection inside a projection,
`<Outer as Capacity>::Array<<Inner as Capacity>::Array<T>>`, and no product is computed.

The trait is sealed to `Dim<N>`. That is the stand-in while `is_arvo_s_capacity_trait_sealed_to_its_one_marker`
is open, and the seal carries a `FIXME` naming it: sealed, the array and the count come from the one
`N` and cannot disagree; open, they can (`out/open_a_count_disagrees.txt` in the sketch). Unsealing
later breaks no consumer; sealing later would.

One residue stays with the consumer and is documented, not hidden: an array of a `Copy` element is
`Copy`, but the trait cannot say so for every capacity, so generic code that copies a nested inner
array states `<Inner as Capacity>::Array<T>: Copy` where it does. hilavitkutin states the same bound
today.

## D3. The marker

`Dim<const N: usize>` is the one capacity, for every exact count. `N` is the one bare integer in the
surface, at a const generic parameter, which the no-bare-primitives rule admits there; a consumer
declares its budget once, as `type Units = Dim<256>`.

## D4. The count

The count reads in a constant through `count::<C, A, K>()`, a `const fn` giving
`arvo_numeral::USize<A, K>`: the platform-sized integer under the adaptation and the check the
consumer names. The crate picks no adaptation for it, since how the count is completed in later
arithmetic is the consumer's to say. The length behind it is an associated constant of the seal's
supertrait, unreachable outside the crate, so no bare integer is public. A count that is not a
constant cannot be written, since `N` is a const parameter.

## D5. Tests

An outside consumer crate under `tests/consumer`, with no feature line, written the way hilavitkutin
uses a capacity: a bundle of dimensions as associated types of one parameter, a plan whose fields are
projections and a nested projection, filled and walked in generic code, and every count read in a
constant and checked against the array's length at build. Compile-fail pairs, each with a twin that
builds: an implementation of `Capacity` from outside refused beside `Dim<N>` used from outside; a
`Dim` sized by a value known only at run time refused beside one sized by a constant. The agreement
between the array and the count is tested over a spread of counts, and a committed mutant run, the
count one past the array under `--cfg capacity_mutant`, shows it red.
