# Topic: the width bound, and an objective that selects nothing

**Date:** 2026-08-31
**Phase:** TOPIC
**Scope:** the slot range's representable bound, the derivation's objective, and the two tests that
claimed to cover what they did not
**Status:** all four reproduced; two are the binding-time shape and the canon decides both

## What I reproduced before touching anything

**Finding one, exactly.** Transcribing the shipped definitions and running them: width 8 gives count
256, width 32 gives 4294967296, width 62 gives 4611686018427387904, and **width 63 gives count
-9223372036854775808 and a derived width of 0**. The count wraps negative, `declared_width`'s loop
never enters because `1 < count` is false against a negative, and a declared 63-bit numeral derives a
placement of zero bits. Width 64 fails const evaluation with `error[E0080]: attempt to negate
i64::MIN`, which is an arithmetic error rather than a statement about widths.

**Finding three, exactly.** Both arms of the match in `derive_sole` and `derive_shared` are the same
expression, and nothing else in either function reads `objective`. It is a dead parameter, which is
why 38 derivations across 19 widths at both occupancies come back identical.

**Findings two and four by reading.** The sweeps stop at 32 while the ladder reaches 64 and the file
claims to run every width the slot ranges admit. `the_objective_is_a_coordinate_of_the_derivation`
asserts both occupancies are `Sole` and that two enum variants differ, and never compares the two
derivations it took.

## Finding one is not a parked question, and here is the canon that decides it

The reviewer suggested deciding what carries a slot range wider than `i64` may be op's. **It is not,
and the canon says so in two places.**

`question::arbitrary_width_demands_in_the_canon` asks whether the **canon** should speak of arbitrary
const-width demands at all, and its second option is "leaving width families to design". So under
either answer the width family is the design's to choose: under option two explicitly, and under
option one the canon has not spoken. **Choosing the supported range is a design call.**

`ruling::never_a_runtime_check_and_one_lowered_path` is ratified and is what makes the current
behaviour wrong whatever range is chosen: "invalids are caught at compile time and unused paths are
cleared when lowered." **A width the representation cannot carry is an invalid**, and deriving zero
bits from it in release is the wrong answer produced at runtime where a compile-time refusal belongs.

`ruling::the_overflow_panic_is_permitted_and_bounded` reaches the same place from the other side: the
panic is for what cannot be caught at compile time through the typestate. This can be, so the debug
panic is not the remedy either.

**So the question splits and only one half was ever open.** How wide arvo should ultimately go is the
open one and this round does not answer it. What happens at a width the representation cannot carry is
closed by I15, and the answer is a named refusal at compile time.

## The binding-time defect underneath, which is the more interesting half

`declared_width` computes the count of slots and then takes its base-two logarithm by looping. **The
width it recovers that way is the width the declaration already stated.** `Signed<13>` knows it is
thirteen bits; the code derives thirteen by counting to 8192 and halving back.

That round trip is where the overflow lives. The count is the only quantity in the chain that does not
fit, and nothing needs it: **`Slots` should carry the declared width as an associated const and
`declared_width` should read it.** No count is formed, no loop runs, and the entire zero-bits class
disappears rather than being guarded against.

The refusal is still owed on `MIN` and `MAX`, which genuinely cannot be represented above a bound, and
that bound is now the only thing the range limit is about.

## Finding three: what the objective is supposed to select

`ruling::cold_is_for_cold_paths_and_cold_storage` is ratified: the storage-minimising strategy
"aggressively minimises and bitpacks". `ruling::the_derivation_is_a_placement_and_the_operation_set_is_an_admission_rule`
is ratified and gives three outputs at shared occupancy: the carrier, the access width and the stride.

**Bitpacking is what the footprint objective does and what the access objective does not.** At shared
occupancy the footprint arm packs, so the stride is the declared width and a read has to reach wider
because an element can straddle a carrier boundary. The access arm does not pack: one element per
carrier, stride and access both the carrier, padding rather than straddling.

**At sole occupancy they genuinely coincide**, because the value owns its allocation and there is
nothing to trade. That is a real result rather than a collapse, and it gets asserted as one instead of
being left to look like the same defect.

## The objective is a const the design was passing at runtime

`Objective` arrives as a function argument while the typestate holds it as a const, which is the
second half of I15: branching should be const-time and erased by monomorphisation. `adt_const_params`
is on the allowed feature list, so the objective becomes a const generic parameter and the branch goes
away at monomorphisation rather than being a match on a runtime value.

**That also makes finding three's fix real rather than cosmetic.** Two objectives producing two
placements is only worth having if the selection happens where an arm can be gated on it.

## What lands

`Slots` gains the declared width and loses the count round trip. `MIN` and `MAX` gain a named refusal
above what they can represent. The objective becomes a const parameter and selects a genuinely
different placement at shared occupancy. The sweeps run the range the design actually admits, and the
objective test compares the two derivations it takes.

The two bench manifests that cannot parse get a marker saying so, which is the thing that was missing
rather than the fix.
