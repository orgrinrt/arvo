# Topic: expand round 202605021200 scope to every arvo numeric primitive

**Date:** 2026-05-02
**Phase:** TOPIC (addendum to `202605021200_topic.usize-const-arith.md`, which is frozen)
**Scope:** Supersedes the "USize and Cap only" framing of the original topic. The round now covers every arvo numeric primitive that has (or should have) `core::ops::*` impls. The previous topic's open decisions (overflow semantics, mixed-arity policy, sweep audit, lint follow-up) all stand and apply uniformly across the expanded surface.

**Driver:** User direction after the original topic landed: "not only USize or Cap, all of the arvo prims that share those impls, which is, all the numerics." The principle (no field-access on arvo primitives in const contexts) applies uniformly. The original topic's narrow framing was a scoping mistake; consumers will hit the same wall on UFixed, IFixed, Bits, Mask64, etc. as soon as they need const arithmetic, and patching one type at a time is exactly the kind of incremental drift the round is meant to prevent.

# What the audit shows

A grep over `mock/crates/arvo*/src/` for `^impl.*Add\|^impl.*Sub\|^impl.*Mul\|^impl.*Div\|^impl const` returns 73 impl blocks on arvo numerics. Of those, 19 are arithmetic ops (`Add` / `Sub` / `Mul` / `Div` / shifts / bitops / cmp), and **none of those 19 are currently `impl const`**. The strategy-marker trait impls (`impl const Strategy for Hot`, etc.) are the only `impl const` blocks in the substrate today.

That matches the user's framing: const traits are now a reality (the infrastructure is in `arvo-transparent` already), and the only thing standing between the substrate and "no field-access on arvo primitives anywhere" is converting the existing ops impls and filling the ones that don't exist yet (USize, Cap, plus possibly Mask shifts and Bits arithmetic shims).

A second grep for `\.\b0\b\|\.0\)` patterns on USize / Cap returns ~50 field-access call sites in arvo's own source, primarily in `arvo-bitmask/src/ops.rs` (bit-position arithmetic), `arvo-comb/src/{dp,greedy}.rs` (loop counters), and `arvo-bits-contracts/src/bits_impl.rs` (bit-count computation). All of these are arithmetic in shape; once the const-trait surface is wired, every site has a mechanical migration.

# Expanded scope

Three layers of work, ordered by dependency:

## Layer A. Add inherent constants and const-trait arithmetic where missing

**`USize` (arvo-storage)**:

- Inherent constants: `pub const ZERO: USize = USize(0);` `pub const ONE: USize = USize(1);` `pub const MAX: USize = USize(usize::MAX);`.
- Const-trait impls: `impl const Add<USize>`, `impl const Sub<USize>`, `impl const Mul<USize>`, `impl const Div<USize>`, `impl const Rem<USize>`, `impl const Shl<USize>`, `impl const Shr<USize>`, `impl const BitAnd<USize>`, `impl const BitOr<USize>`, `impl const BitXor<USize>`, `impl const Not`.
- Comparison: `impl const PartialOrd<USize>` and `impl const Ord` (currently derived as non-const PartialEq/Eq via `derive`; PartialOrd/Ord need fresh impls).
- Rationale: USize covers the arithmetic load-bearing for every cons-list-counting trait the workspace will write (`Depth`, plan-stage counters, capacity computations).

**`Cap` (arvo-storage)**: same surface as USize, body delegates to the wrapped USize. `Cap::ZERO = Cap(USize::ZERO)` etc.

## Layer B. Convert existing non-const ops to const-trait ops

**`UFixed<I, F, S>` (arvo)**: lines 153, 167, 181, 195 of `mock/crates/arvo/src/ufixed.rs` already carry `impl<...> Add/Sub/Mul/Div for UFixed<...>`. Convert each to `impl const`. Add `pub const ZERO: UFixed<I, F, S> = ...;` and `pub const ONE: UFixed<I, F, S> = ...;` inherent constants per type instantiation (or as inherent associated consts on the generic struct, depending on what nightly accepts today; sketch validates the form).

**`IFixed<I, F, S>` (arvo)**: lines 142, 156, 170, 184 of `mock/crates/arvo/src/ifixed.rs`. Same conversion. ZERO / ONE / `MINUS_ONE` inherent constants.

**`FastFloat<F>` and `StrictFloat<F>` (arvo)**: shipped via task #52. Locate the existing ops impls (audit during DOC), convert to `impl const`. ZERO / ONE inherent constants.

**`Bits<N, S, Sign>` (arvo-storage)**: bit-storage primitive. Existing impls (BitAnd / BitOr / BitXor / Not / Shl / Shr from `arvo-bits-contracts::BitLogic` and friends) need const conversion. No arithmetic ops on Bits per design; bit-ops only.

**`Mask64`, `Mask256`, `BitMatrix` (arvo-bitmask)**: bit-ops (BitAnd / BitOr / Not). Convert to const.

**`Bitfield<...>` (arvo)**: any ops on Bitfield convert to const if they exist. Bitfield is recent (round 202604200055-ish per task #127); audit during DOC.

**`IBits`, `FBits`, `Width`, `BitWidth` (arvo-storage)**: meta-bit newtypes wrapping `UFixed<7, 0, Hot>` or similar. Their ops come through UFixed's impls; once UFixed is const, these inherit. Verify during sketch.

**`StoreId`, `AccessMask`, etc. in hilavitkutin-api**: out of scope (those are hilavitkutin's, not arvo's). Hilavitkutin's adoption follows in its own follow-up round once arvo lands.

## Layer C. Sweep field-access call sites

Migrate every `.0` access on an arvo numeric in arvo's own source to use the new const-trait surface. Three flavours:

1. **Arithmetic** (the majority): `USize(x.0 + y.0)` → `x + y`. `USize(R::D.0 + 1)` → `R::D + USize::ONE`. `USize(pos.0 >> 6)` → `pos >> USize(6)` (or `pos >> USize::const_from(6)` if a constructor helper is added). `USize(63 - lz.0)` → `USize(63) - lz`.

2. **Boundary unwrap to raw `usize`**: where consumer code needs the inner `usize` for an FFI / `core::*` API, use `*x` (the existing `Deref` impl) instead of `x.0`. Document in inline comment if the boundary use is non-obvious.

3. **Construction from a literal `usize`**: `USize(5)` is fine (constructor on a tuple struct is the canonical way). The `.0` ban is on read-side field-access in const-context arithmetic, not on construction.

The sweep covers every `arvo-*` crate. Estimated 50-80 sites based on the grep.

# Sketch

Write a small sketch under `mock/research/sketches/usize-const-arith-202605021200/` validating:

1. `impl const Add<USize> for USize` compiles on nightly with the existing `feature(const_trait_impl)`.
2. `<R as Depth>::D + USize::ONE` shape compiles in a const context (the load-bearing hilavitkutin case).
3. UFixed's existing ops convert to `impl const` without const-eval errors. If a primitive op (e.g. saturating mul on a fixed-point) is not const-callable on the underlying integer, document the gap and either ship a const-callable shim or file as follow-up per type.
4. The full `+`, `-`, `*`, `/`, `<<`, `>>`, `&`, `|`, `^`, `!` matrix on USize all const-evaluates.
5. Mixed-arity ops are absent: `USize + 1u32` does not compile, only `USize + USize::ONE` or `USize + USize(1)`.

The sketch is the validation gate before DOC commits, per the workspace process recommendation surfaced in PR #46's fourth-pass review ("sketches must include a stress instance"). Stress in this case: every primitive in the audit list compiles at const time through every op the audit shows it carries today.
