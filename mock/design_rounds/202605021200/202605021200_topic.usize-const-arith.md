# Topic: const arithmetic on USize, eliminate field-access on arvo primitives

**Date:** 2026-05-02
**Phase:** TOPIC
**Scope:** `arvo-storage` (USize, Cap arithmetic surface). Audit other `repr(transparent)` numeric wrappers (Bool excluded; not arithmetic) for field-access in const contexts. Tracks #300.

# Current state

`arvo-storage::USize` is `pub struct USize(pub usize)` with `Copy`, `Eq`, `Deref<Target = usize>`, and `ConstParamTy`. It carries no inherent constants and no arithmetic surface (neither inherent const fns nor `core::ops` impls). Consumers that compute on USize values at const time fall back to direct field access on the `pub usize` field:

```rust
const D: USize = USize(R::D.0 + 1);
```

This is the recurring shape every cons-list trait that counts elements at the type level needs. `hilavitkutin-api::Depth::D` (PR #46, round 202605011500) is the first concrete instance; the planned plan-stage WUs in hilavitkutin's domain 23 will compound it. Field access through `.0` is mechanically correct (the field is `pub`) but locally violates the no-bare-primitives spirit: the consumer is doing `usize` arithmetic dressed up as USize ceremony at the boundary.

`arvo-storage::Cap` wraps `USize`. `Cap` is positioned as the const-generic capacity newtype (used wherever a const generic sizes an array), so it does not need a full arithmetic surface, but it should derive its const constants and a small arithmetic shim from USize where capacity-math at const time is realistic (e.g. `Cap(N) + Cap(M)` for combined-region sizing).

`arvo-storage::Bool` is not arithmetic and is out of scope. It already ships `Bool::TRUE` and `Bool::FALSE` as inherent constants; the precedent is good.

`UFixed`, `IFixed`, `Bits` carry their own arithmetic via L0.5 contracts (`arvo-numeric-contracts`) and are not affected by this round. The audit below confirms: those types do not have public field-access escape hatches; their internal const-context arithmetic uses arvo facades.

The substrate already enables `feature(const_trait_impl)` in `arvo-transparent` (sibling L0 crate). The infrastructure for `impl const Add` is in place. Stable-channel const-trait impls are not yet a thing; this round commits to the same nightly path the rest of arvo runs on.

# Changes proposed

## 1. USize gains inherent constants and const-trait arithmetic

```rust
impl USize {
    pub const ZERO: USize = USize(0);
    pub const ONE: USize = USize(1);
    pub const MAX: USize = USize(usize::MAX);
}

impl const core::ops::Add<USize> for USize {
    type Output = USize;
    fn add(self, rhs: USize) -> USize { USize(self.0 + rhs.0) }
}
impl const core::ops::Sub<USize> for USize { /* checked or saturating: see decision below */ }
impl const core::ops::Mul<USize> for USize { /* same */ }
impl const core::ops::Div<USize> for USize { /* same */ }
```

Open decisions for the doc CL:

- **Overflow semantics**: USize is platform-pointer-width; overflow at `usize::MAX` is the underlying primitive's contract. Three options: (a) inherit primitive wrap/panic via direct `+` on `.0` (current de-facto), (b) explicit `checked_add` returning `Option<USize>` (poor fit for arvo's no-bare-Option discipline; would return `Maybe<USize>` from notko), (c) saturating. **Recommendation**: option (a), match primitive. This is "USize is the typed surface for `usize`; arithmetic semantics are `usize`'s." Document explicitly.
- **Mixed-arity ops**: should `USize + usize` work, or only `USize + USize`? **Recommendation**: only `USize + USize`. Mixed forms invite drift back to bare-primitive use; the const constants `USize::ZERO` / `USize::ONE` cover the common literal cases.
- **Inherent const fns versus const trait impls**: both? Only one? **Recommendation**: ship the const trait impls; inherent `const fn const_add(self, rhs: USize) -> USize { *self + rhs }` shims may be added if a real call site needs them, but defer until pulled. Const trait impls cover every `+` / `-` / `*` / `/` use site naturally.

## 2. Cap gains the same surface, derived from USize

```rust
impl Cap {
    pub const ZERO: Cap = Cap(USize::ZERO);
    pub const ONE: Cap = Cap(USize::ONE);
}

impl const core::ops::Add<Cap> for Cap {
    type Output = Cap;
    fn add(self, rhs: Cap) -> Cap { Cap(self.0 + rhs.0) }
}
// Sub / Mul / Div same shape.
```

`Cap` is `pub struct Cap(pub USize)`, so the bodies use `self.0 + rhs.0` where the `+` resolves to `USize::add` (the new const trait impl). No raw `usize` arithmetic. Field access on `Cap` (`.0`) is access to `USize`, which is itself an arvo primitive; this is the typed-surface composition we want.

## 3. ISize audit

`arvo-storage` does not currently ship `ISize`. The CLAUDE.md mentions "platform-binding wrappers and control-flow primitives" and `USize` covers the unsigned half. Signed platform-pointer-width values are rare in arvo's substrate (the sign axis is on `IFixed` / `IBits`, not on platform sizes). Decision: ship `USize` and `Cap` first. If a consumer surfaces `ISize` need, follow up.

## 4. Audit existing field-access usage

Sweep `arvo` source for `.0` on `USize` / `Cap` and migrate each site to use the new arithmetic surface. The migration is mechanical: `x.0 + y.0` becomes `x + y`, `USize(R::D.0 + 1)` becomes `R::D + USize::ONE`. Sites where the inner `usize` is genuinely needed (e.g. interfacing with a `core::*` API that takes `usize` directly) keep `*x` (the existing `Deref` impl) instead of `.0` for clarity, or are documented as boundary call sites with a `lint:allow` if any rule fires.

## 5. Lint rule: forbid `.0` field-access on arvo primitives outside the implementing crate

Add a workspace-shared lint rule (in `mockspace-hilavitkutin-stack-lints` or a new arvo-side rule) flagging `.0` on `USize`, `Cap`, `Bool`, `UFixed`, `IFixed`, `Bits` (and aliases) outside their implementing crates. The bound is "use the typed surface (`+`, `-`, `*`, `/`, `Deref`, inherent methods, `Transparent::raw()`) instead of accessing the inner field." Severity: warn at first, error after one sweep round confirms the lint catches no false positives.

This is the core principle (no bare primitives, even via field-access escape hatch) made enforceable. Filing as out-of-scope-for-this-round if the lint requires non-trivial implementation effort; the lint can land in a follow-up round once #300 ships.

# Open questions

The doc CL phase resolves these. Surfaced here for the user's call:

1. **Saturating-vs-wrap-vs-checked semantics** on USize arithmetic. Recommended: match primitive `usize` (wrap on debug-debug-assert, undefined behaviour on release if overflow; in practice the ops panic on debug-mode debug-assertions and wrap on release per Rust's default integer-overflow contract). Document explicitly.
2. **Should `USize::MAX` exist as an inherent const?** Recommended: yes. Cheap, useful, and matches `usize::MAX` semantics exposure.
3. **Cap arithmetic at all?** `Cap` carries semantic distinction (capacity, not arbitrary index). Adding `Cap + Cap` means consumers can write `Cap(A_CAP) + Cap(B_CAP)` for combined-region sizing. Recommendation: yes, ship the same surface as USize. The semantic boundary stays visible because `Cap + USize` does not compile (no cross-type op).
4. **What about other newtype wrappers (`IBits`, `FBits`, `Width`, `BitWidth`) ?** These carry meta-bit counts (bit positions, widths). They're already small `UFixed<N, 0, Hot>` aliases inside `Uint7` / `Uint8` shapes. Their arithmetic comes from the `UFixed` `core::ops` impls already shipped. Out of scope for this round.
