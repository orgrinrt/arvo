## 2. `DESIGN.md.tmpl:813`'s bound, checked rather than corrected as asked

The review's finding 2 states the bound is false and should read `(-2^126 - 2^62, 2^126 + 2^62)`, from
"`sum_is_carried` allows `2*max + ceiling <= i128::MAX`", with a phase of `(i64::MIN, 1)` pushing `max`
to `2^126 + 2^62 - 1`.

Checked against `addition.rs:191-195`, `doubled_plus`:

```rust
const fn doubled_plus(slot: i128, offset: i128) -> Bool {
    match slot.checked_mul(2) {
        Some(twice) => Bool::of(twice.checked_add(offset).is_some()),
        None => Bool::FALSE,
    }
}
```

`slot.checked_mul(2)` is evaluated and gated *before* `offset` (the phase's `whole` or `ceiling`) is
ever added. `2 * max` alone has to fit `i128` regardless of the phase, which caps `max` at
`i128::MAX / 2 = 2^126 - 1` and `min` at `i128::MIN / 2 = -2^126`, exactly the bound DESIGN already
states. A compiled probe confirms it: `max = 2^126 - 1` doubles to `Some(...)`, `max = 2^126` doubles to
`None`, independent of what is added after. `is_addable` on a format built at the review's own claimed
extreme (`max = 2^126 + 2^62 - 1`, phase `(i64::MIN, 1)`) is measured `false`, not `true`. The existing
`NearTheTop` test already pins the tight boundary at phase zero (`i128::MAX / 2`, admitted at ceiling 0
and 1, refused at ceiling 2), which is the same number the review's premise would have to move past and
does not.

So the sentence at `DESIGN.md.tmpl:813` is correct as written, and finding 2 rests on a reading of
`sum_is_carried` that treats it as one combined inequality rather than the two sequential checked
operations `doubled_plus` actually performs. This round leaves the bound as it is and adds
`no_phase_admits_a_range_past_the_doubling_bound_itself`, a test pinning that no phase moves either edge
outward, which is the artifact a later reader can check instead of re-deriving this by hand.

## 4. The width lint, the aliases, and the shadowing hole

`usize::BITS` resolves through whatever is in scope; a module or item literally named `usize` in the
same file would shadow the primitive type at that bare path. `core::primitive::usize::BITS` is the
language's own answer and cannot be shadowed. Checked by compiling `mock/crates/arvo-format` with the
aliases spelled that way: it builds clean at the host's 64-bit pointer width. Fix: spell both `USize`
and `ISize` over `core::primitive::usize::BITS` in `lib.rs`, update the lint's expected right-hand side
to match, and add a lint test proving a bare `usize::BITS` declaration still fires even where a `mod
usize` sits in the same source, which is the regression the widened spelling closes.
