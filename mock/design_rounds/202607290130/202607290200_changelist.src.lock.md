**Date:** 2026-07-29

**Source topic:** `202607290100_topic.the-round-repeated-its-own-defect.md`

Every claim below was checked by reading the file after the edit, not by trusting that the edit applied.
The previous round's three false claims were all edits whose success was assumed.

## CHANGE: `Precise` division CLAMPS by the sign of the numerator on a zero divisor

File: `mock/crates/arvo-strategy/src/arith_macros.rs`, the signed saturating `i_div` and `i_div_fixed`

Both returned the logical maximum whatever the numerator's sign, so `i_div(-5, 0)` was positive and the `lo`
bound computed on the line above was unreachable from that branch. A saturating strategy's answer at an
extreme is a bound, and which bound follows the direction the quotient heads: `lo` for a negative numerator,
`hi` otherwise.

The unsigned bodies keep `hi` unconditionally, which is correct there because an unsigned quotient has no
negative side.

Verification: `<Precise as IArith<64>>::i_div(-5, 0)` and `i_div_fixed::<0>(-5, 0)` both return the logical
minimum; the non-negative cases still return the maximum.

## CHANGE: the div-by-zero doc comments STATE what the code does

File: `mock/crates/arvo-strategy/src/arith.rs`

`u_div` and `i_div` carry "Div-by-zero: wrapping strategies use `wrapping_div` (panic convention); Precise
clamps to max." Both halves are false. No wrapping impl calls `wrapping_div` on a zero divisor; each guards
`b == 0` and returns the numerator, which the module header three lines above states correctly, so the crate
contradicted itself. And "clamps to max" describes only the non-negative case.

Both are rewritten to the per-strategy contract the design now carries.

Verification: `grep "panic convention" mock/crates/arvo-strategy/src/arith.rs` returns nothing.

File: `mock/crates/arvo-strategy/src/arith_macros.rs`, `impl_u_arith_saturating::u_div_fixed`

## CHANGE: the law matrix asserts what the last changelist said it did

File: `mock/crates/arvo/tests/identity_laws.rs`

Three claims made and not delivered, now delivered.

The constant assertion becomes `one.to_raw() == 1 << $f`. It read `>> $f == 1`, which accepts any raw in
`[1 << F, 2 << F)`, the exact looseness the previous changelist claimed to have removed. The replacement
that would have done it matched nothing and the failure was silent.

The signed rows gain negative probes, including the container minimum, so `x + ZERO == x` and `x * ONE == x`
are asserted on negative operands. Until now no probe anywhere in the file was negative, which means the
negative branch of the 256-bit multiply, the branch `wrapping_neg` was added for, was never entered by the
law matrix at all.

`NEG_ONE`'s magnitude is pinned at zero integer bits via `neg_one.to_raw() >> ($f - 1) == -2`. The previous
round asserted only that it was below zero, which raw `-1` satisfies, and claimed in a comment that the
encoding had no expressible form there. That claim was wrong: the literal `-(1 << F)` does not compile,
because the positive intermediate is unrepresentable, but the shifted comparison does and distinguishes the
right value from `-1`.

Verification: each assertion read back from the file after editing, and the matrix re-run against a
deliberately wrong constant to confirm it fails.

## CHANGE: `warm_bound_negative` is REMOVED, because its premise has no true instance

Files: `mock/crates/arvo/tests/warm_bound_negative.rs`, `tests/ui/warm_bound_negative.rs` and its `.stderr`

It exists to prove `UFixed<I, F, Warm>` does not compile past the Warm container's reach, and it has been
failing on `E0425: cannot find function ibits` since it was written, because it imports `IBits` and `FBits`
rather than the helper functions. The snapshot baked the wrong error in, so it passed while asserting
nothing.

Repairing the imports did not produce the test it was meant to be. It produced a finding: **`Warm` does not
drop off the container table at 65 bits.** `tag_warm_precise` sends everything above 64 to the wide bucket,
so `<Warm as BitsContainerFor<65, Unsigned>>::T` resolves to `WideBits<9>`. There is no width at which the
premise holds, so there is no correct version of this test to write.

Removed rather than repaired. A compile-fail test whose premise has no true instance cannot be fixed into a
useful one, and leaving it occupies the space where a real pin would be noticed missing.

What it uncovered is a design-versus-source conflict that this round does not resolve. Both the design
document and the `#[diagnostic::on_unimplemented]` note on `BitsContainerFor` say `Warm` and `Precise` cover
1 to 64 and have no bucket for 65 to 128, and that only above 128 do all four strategies reach `WideBits`.
The projection disagrees with both. Design is the oracle, so the projection is the thing that drifted, but
correcting it stops `Warm` and `Precise` compiling at 65 to 128, which is a consumer-visible behaviour change
well outside an identity round. Tracked for op.
