# Topic: the correction round repeated the defect it was correcting

**Date:** 2026-07-29
**Phase:** TOPIC
**Review:** second independent review of PR #2, over the closed rounds `202607270015` and `202607280130`

The first round asserted a property in four artifacts and implemented it nowhere. The second round was
convened to fix that, and shipped a locked changelist containing three claims that are false against the
source it shipped, plus a fourth wrong comment inside the change that was correcting two wrong comments.

That is the same failure three times on one branch, and the third instance is the worst, because it was made
by the round whose entire argument is that prose asserting a property is not the property.

## The three false claims

All in `202607280130/202607280200_changelist.src.lock.md`, all verified against the source at the commit it
locked.

It says the signed rows gain negative probes, including the container minimum. They did not.
`identity_laws.rs` probes `[0, 1, one.to_raw(), one.to_raw() | 1]`, every one of them non-negative, and the
container minimum appears nowhere in the file.

It says the constant assertion tightens from `one.to_raw() >> F == 1` to `== 1 << F`. It did not. The line
still reads `>> $f`, which accepts any raw in `[1 << F, 2 << F)`, which is the exact looseness the changelist
claims to have removed.

It says the law matrix asserts the `NEG_ONE` raw at every shape. It does not. `neg_one_law!` asserts only
that the value is below zero.

The file also carries a comment naming a `negatives` binding that does not exist. So the round wrote the
comment describing the probes, wrote the changelist describing the probes, and never wrote the probes. The
edit that would have tightened the assertion silently matched nothing and was never checked.

## How it happened, since the mechanism matters more than the instance

Every one of the three was a text edit whose success was assumed rather than observed. The claims were
written from the intent of the edit, not from the file after it. A string replacement that matches nothing
is silent, the suite stayed green because the weaker assertions still passed, and nothing in the process
compares a changelist's claims against the tree.

The lesson is narrow and mechanical: a `## CHANGE:` claim is a statement about source, and the only way to
know it is true is to read the source after the edit. `cl-claim-sketch-discipline.md` already says a locked
changelist is a claim about source state and that claims must match reality at lock time. The gap is that
nothing enforces it, and intent reads as fact when you are the one who formed the intent.

## The live defect, two lines from the one the last round fixed

`Precise::i_div` and `Precise::i_div_fixed` return the logical maximum on a zero divisor whatever the sign
of the numerator. `<Precise as IArith<64>>::i_div(-5, 0)` returns the maximum. The `lo` bound is computed on
the line above and that branch never reaches it.

This is the previous round's own finding restated: a saturating strategy has one answer at an extreme and it
is the bound, meaning the bound on the side the value is heading toward. Dividing a negative numerator by
zero heads toward negative infinity and owes `lo`. The round fixed that reasoning for `MIN / -1` and left the
identical error two lines above, in a branch it rewrote.

## The public contract documents it wrongly, and wrongly in both halves

`arith.rs` tells consumers "Div-by-zero: wrapping strategies use `wrapping_div` (panic convention); Precise
clamps to max."

Both halves are false. The wrapping strategies do not call `wrapping_div` on a zero divisor at all; they
guard `b == 0` and return the numerator, which the module header states correctly three lines earlier, so
the crate contradicts itself. And "clamps to max" describes the defect rather than the intent.

A wrong doc comment on a public trait method is worse than a wrong comment in a body: it is the contract a
consumer codes against, and it is the artifact least likely to be checked against behaviour.

## The sampling criticism, turned around

The second round criticised the first for asserting laws over the shapes where they already held. Three of
its own additions do the same.

No probe in the law matrix is negative, so `x * ONE == x` is asserted on a negative operand nowhere, and the
negative branch of the 256-bit multiply, the branch `wrapping_neg` exists for, is never entered by the
matrix. At zero integer bits the `NEG_ONE` magnitude is unpinned: the assertion is that it is below zero,
which raw `-1` would satisfy. The round's own comment claims the encoding has no expressible form there,
which is wrong; `neg_one.to_raw() >> (F - 1) == -2` distinguishes it, and the impl is in fact correct, so
this is a weak test rather than a broken value. And the compile-fail pin covers five of eight impl-strategy
cells while every one of its files claims to pin per impl and per strategy.

## Two older things the review surfaced

`warm_bound_negative.rs` is vacuous. It is meant to prove that `UFixed<I, F, Warm>` fails to compile past the
Warm container's reach, and it fails on `E0425: cannot find function ibits` instead, because it imports
`IBits` and `FBits` rather than the helper functions. The `.stderr` snapshot bakes that in, so the test has
been passing on the wrong error since it was written and asserts nothing about the container table.

The `traits.rs` split carried em-dashes into files it created. Those files were new, so the split was the
one moment the ban was free to enforce.
