# 202607281005 arvo-shape, the two-dimensional primitives

Origin: the first design round of hokkeli (the application shell), which needed shapes and found arvo
has none. No work done in this topic; scope is naming the crate and what it owns.

arvo has no two-dimensional geometry at all: no `Point`, `Extent`, `Rect`, `Size`, or `Affine`
anywhere in the workspace, confirmed rather than assumed. Three named consumers want them (a
primitive with no named consumer is called a guess): hokkeli (pixel space), kolli (kolli-layout,
integer terminal cells, "terminal geometry is arithmetic: it computes positions and never draws"), and
ikiuni-renderer (its -ui crate, screen space).

Reasoning for placing this in arvo rather than a new crate: arvo is already free of hardcoded scalars,
works over integers, fixed point, and its own float abstractions (an integer is fixed point with
F = 0). A shape declared over arvo's ops abstractions is usable in pixels, fixed point, or terminal
cells without the definition naming a scalar. Contrasted against two ecosystem alternatives: `kurbo`
welds f64 into `Point` and its only float abstraction is a sealed trait choosing between std and libm
f64 impls, unusable for any other scalar; `taffy` has generic-looking `Size<T>`/`Rect<T>` but hardcodes
f32 through every algorithm site. Neither serves a terminal-cell consumer.

What the crate owns: fundamental contracts for shapes, primitive contracts, and concretes where
needed. Numeric and primitive side only: points, extents, rectangles, affine transforms, and the curve
primitives a themed interface needs for a rounded corner. Declared over arvo's ops abstractions
throughout, naming no scalar.

What the crate does not own: layout (arranging things relative to each other, adapting across device
classes, constraint and flow models) lives in a separate crate, `lato`, built on arvo and notko. Stated
split: arvo declares the shapes for use; lato declares the things that use them. Layout is called
policy over shapes rather than arithmetic on them, a different axis from everything arvo holds today,
and named as the axis along which arvo would become a monolith if it absorbed layout.

Status at close of this topic: named, not scheduled. Work begins when hokkeli and lato need it; this
topic exists so naming and boundary are settled before either improvises a local version.

# 202607281052 shapes are N-dimensional, and the rank-limited pieces port onto them

Corrects and widens the preceding topic (`202607281005`). Supersedes it in part: the crate name
`arvo-shape` and the two-dimensional scope from that topic are overturned here; everything else in
that topic stands (arvo owns shapes for its scalar-freedom; layout stays in lato; arvo declares what
a shape is, lato declares what uses them).

The correction: scoping to 2D was wrong because it was driven by one consumer (an application shell).
There is no reason to limit to 2D; N-dimensional abstractions are the right form. The abstractions must
serve theoretical mathematics as readily as concrete spatial arithmetic: a point in a 17-dimensional
parameter space and a point on a screen are the same construction at different ranks. Rank becomes a
parameter, the way width already is across arvo. The two-dimensional case an application shell needs is
one arity of a general form, not the form itself.

What already exists and needs to port onto the new abstraction: `arvo-tensor`, described in its own
docs as "fixed-shape tensor wrappers with type-level capacity: `Array<T, N>` (rank-1), `Matrix<W, N>`
(rank-2)", two ranks as separate types with no general rank between or above them. This is called a
thing to generalise, not a thing to sit beside: once the N-dimensional abstraction exists, `Array` and
`Matrix` become its rank-1 and rank-2 instantiations. `arvo-comb`, `arvo-spectral`, and `arvo-graph` are
flagged as worth re-reading for the same const-generic-over-arvo-numerics pattern once the abstraction
settles; the topic explicitly does not claim they need porting, only that nobody has checked.

Naming is left open: whether the N-dimensional form keeps the name `arvo-shape` or the shape crate
becomes the spatial instantiation of a separately named general abstraction is unsettled and does not
need resolving until work is scheduled.

Status: named, not scheduled, same as the preceding topic. Both topics exist so the boundary and
dimensionality are settled before hokkeli or lato improvise a local version, and so arvo-tensor's two
ranks are understood as an instance of the general form rather than as the design itself.

# 202607281126 what arvo already ships toward N dimensions

Internal research, no decisions, no work. Continues the two preceding topics (`202607281005`,
`202607281052`).

Reframing finding: the earlier claim that `arvo-tensor` "stops at rank 2 and needs generalising" is
true of the types but misleading about the foundation, which the file states is already general.
`arvo-tensor` carries `Capacity`, a trait with a generic associated type `type Array<T>: AsRef<[T]> +
AsMut<[T]>` plus `const CAP: Cap`, `filled`, `from_fn`, and `Dim<const N: usize>` as its one
implementing marker (`type Array<T> = [T; N]`, `const CAP: Cap = cap(N)`). The design document's own
comment on `Capacity` states the `AsRef`/`AsMut` bound "lets 2-D storage be the composition
`R::Array<C::Array<T>>` with no separate trait", and `Matrix<W, C>` is built exactly that way, needing
no new mechanism for rank 2. Conclusion drawn: `C::Array<C::Array<C::Array<T>>>` is rank 3 and nothing
new is required for it; arvo can already express rank N. What is missing is a way to name a rank
without hand-writing the nesting, and a way for a function to be generic over rank. This is called a
much smaller gap than "generalise the tensor crate."

`Capacity` exists specifically to keep const expressions out of type position: a `Cap`-parameterised
`[T; cap_size(N)]` container invokes nightly `generic_const_exprs`, and the round trip
`cap_size(cap(N))` "overflows the well-formedness evaluator and ICEs the moment a generic consumer
threads the capacity through its own generic code" (quoted from the design document).
`Dim<N>::Array<T> = [T; N]` avoids this entirely, using plain min-const-generics. Stated as the hard
constraint on any N-dimensional design: whatever expresses rank must not reintroduce a const
expression in type position, because the failure surfaces as an ICE downstream rather than a compile
error at definition. The one irreducible bare `usize` in the convention is `Dim`'s own `const N`
(array lengths are `usize` at the language level).

`ConstCapacity` is a separate const-callable sibling trait (`filled`, `get`, `set`, `slice`,
`slice_mut`), not an extension of `Capacity`, because `Capacity::from_fn` takes a non-const-callable
`FnMut(USize) -> T` closure and `impl const Trait` requires a const body for every method. `Dim<N>`
implements both. Noted as a pattern that will recur: anything spatial built on this foundation
inherits the split between a const-constructible surface and a closure-built surface over one storage.

The rank-limited stop appears twice, not once: `arvo-tensor` (values: `Array<T, C>` rank 1,
`Matrix<W, C>` square rank 2) and `arvo-bitmask` (bits: `Mask<W>` rank 1, `BitMatrix<W, C>` rank 2).
Both already bind `C: Capacity` rather than a bare `Cap` const generic, so both sit on the general
foundation already and both stop at rank 2 because nobody needed rank 3. `arvo-tensor`'s own docs
state the domain split deliberately: bitmask is "fixed-shape bit containers, every slot is a bit, ops
are bitwise"; tensor is "fixed-shape value containers, every slot is a T, ops are trait-generic over
T". Whether a general rank abstraction should span both element domains or be expressed once per
domain is flagged as open and probably the most consequential open question in the design.

Limitation named before anything is built on it: `Matrix<W, C>` is square, one capacity parameter
serving both axes. Fine for its current consumers (adjacency matrices, Laplacians); fatal for anything
spatial, where a rectangle needs different extents per axis. Any N-dimensional design needs a capacity
per axis, called a real departure from what exists, not a generalisation of it.

Consumers of the rank-limited types today, all of which would need re-reading if the shapes change:
arvo-graph (`BitMatrix` adjacency; topo sort, components, rank, critical path, waist detection),
arvo-sparse (`Csr` over `C: Capacity`; RCM reordering, block diagonal, Dulmage-Mendelsohn),
arvo-spectral (`Matrix`; Laplacian, power iteration, Fiedler vector, spectral bisection; re-exports
`Matrix` from arvo-tensor), arvo-comb (matrix chain DP, greedy interval grouping, bin packing),
arvo-bitmask (`Mask<W>`, `BitMatrix<W, C>`). Notes that arvo-bitmask and arvo-spectral previously
shipped local duplicates of `cap_size` that were consolidated into arvo-tensor, cited as a precedent
that this family converges on one home rather than replicating.

`arvo-tensor`'s stated deliberate exclusions, recorded because an N-dimensional crate will be pushed
toward all of them: arithmetic operations on tensors (consumer concern), sparse shapes (arvo-sparse's
domain), bit-shaped tensors (arvo-bitmask's domain), ML-style broadcasting/reshaping/transpose chains
("not aligned with arvo's role"), heap-backed growable shapes (no, sizes are const). The file flags the
fourth exclusion as the one to watch: "N-dimensional" pulls toward a tensor library, which arvo has
already refused to be.

Six open questions, stated as questions, not decisions:

1. Does a rank abstraction live in `arvo-tensor` or in a separate crate that `arvo-tensor` then binds?
   (Foundation already in arvo-tensor; consolidation precedent points there.)
2. Does it span values and bits, or is it expressed once per element domain?
3. How is per-axis capacity carried, given `Matrix`'s single-capacity square shape is the only worked
   example and does not fit a rectangle?
4. How is rank named without a const expression in type position?
5. Is rank a type-level list of capacities, a recursive nesting, or a capacity plus a rank marker?
   (Different consequences for the const surface.)
6. What does the const half look like, given `Capacity` and `ConstCapacity` already had to split?

Points forward to the companion topic `202607281127_topic.arvo-ndim-and-shape.md` for op's steer on
the crate split.

# 202607281127 arvo-ndim and arvo-shape, the split and what each would contain

Working through op's proposed split. No decisions beyond op's own steer; no work. Companion to
`202607281126`, the research this rests on.

Op's steer, quoted directly: "perhaps add an `arvo-ndim` crate along with shape, and reserve shape for
things using the `arvo-ndim` to express spatials (`Point<N: Dim>`, `Rect<X: Into<Point<2>>, Y:
Into<Point<2>>>` or something like that etc. more whatever makes sense)", and separately, on what the
abstractions must serve: "They should work for theoretical math as well as real spatial concrete
ariths." Marked explicitly: where the steer is under-determined, alternatives are laid out rather than
resolved, reserved for the talk.

The split as drawn from the steer: `arvo-ndim` owns dimensionality as such (rank as a parameter,
per-axis capacity, naming a shape without a const expression in type position), nothing spatial.
`arvo-shape` owns the spatial reading (semantic aliases, renderer/layout types, operations meaningful
only when axes are space), uses `arvo-ndim`, adds no dimensional machinery of its own. Compared to the
D10 relationship between arvo and lato (one crate declares vocabulary, the next declares things that
use it), and to how geometry crates split from numeric libraries elsewhere in the ecosystem.

What `arvo-ndim` would have to contain:

Per-axis capacity, called the single most consequential gap (`Matrix<W, C>` is square, wrong for a
rectangle). Three candidate shapes laid out, none chosen: a type-level list of capacities (cons-list
shape, e.g. `Cons<Dim<3>, Cons<Dim<4>, Nil>>`; matches the shape hilavitkutin already uses for access
sets; carries rank implicitly as list length; most verbose at call site, needs a length-fold to
recover rank as a number); recursive nesting as today (`C::Array<C::Array<T>>` extended by induction,
no new concept, but a function generic over rank cannot easily be written against it); a capacity plus
a rank marker (simple when every axis has the same extent, covers an N-dimensional point but not a
rectangle, likely fails the spatial case).

A way to be generic over rank: stated as the concrete missing piece, a const fn or trait method
working for rank 1, 2, 3 without three separate implementations, with no worked example anywhere in
arvo.

A const half: `Capacity`/`ConstCapacity` already split because `from_fn` takes a non-const closure; any
rank abstraction inherits this, and whether it stays one trait pair or avoids the split is open.

And nothing else: explicitly not broadcasting, reshaping, or transpose chains, which arvo-tensor
already refuses. Noted that naming rank makes those temptations easier to reach for, which is exactly
why the refusal needs restating here.

What `arvo-shape` would have to contain:

Semantic aliases, recorded as prior art from loimu rather than proposed fresh, over these exact arvo
primitives: `Coord` = `IFixed<16, 16>` (spatial coordinate, signed, sub-pixel), `Dimension` =
`UFixed<16, 16>` (extent, unsigned), `Factor` = `IFixed<2, 14>` (scale/opacity/blend, range -2 to 2),
`Angle` = `IFixed<16, 16>` (rotation in radians), `ColorChannel` = `UFixed<0, 8>` (colour component, 0
to 1), `GradientPosition` = `UFixed<0, 16>` (position along a gradient axis). Two warnings attached:
`ColorChannel` as `UFixed<0, 8>` is purely fractional, the exact configuration where arvo's own
`Identity` cannot represent one (raw encoding of one is `1 << F`, and at `I == 0` the container is
exactly `F` bits wide). And loimu abandoned this whole table in favour of `kurbo` and `peniko` with no
recorded reason, flagged as the open question in hokkeli's research at
`mock/research/202607281058_loimu_research/03-geometry-already-designed.md`.

Spatial types: `Point`, an extent, an axis-aligned box, a transform. Over `arvo-ndim`, a point in N
dimensions is a rank-1 shape of `Coord`, a box is two points or a point and an extent. The steer's
`Rect<X: Into<Point<2>>, Y: Into<Point<2>>>` is noted as reading like a rectangle constructible from
anything convertible to its corners; the same construction at rank N is an axis-aligned bounding box,
and naming it `Rect` fixes it at rank 2 in the reader's mind while the type does not. Whether rank 2
gets its own name over a general box, or the general name is used throughout, left for the talk.

What is genuinely spatial and not dimensional: rotation is the sharp example (a scalar at rank 2, a
three-component thing at rank 3, a bivector in general). Anything behaving like that belongs in
arvo-shape because axes stop being interchangeable there.

Colour flagged as the boundary case: loimu put `Color` and `GradientStop` in its geometry crate;
colour is a bounded vector space, nothing spatial about it, and whether it belongs in arvo-shape, a
crate of its own, or nowhere in arvo is called a genuine open question.

What has to port either way, restating the table from `202607281126` with relationship-to-rank-
abstraction noted per crate: arvo-tensor (Array rank-1, Matrix rank-2 square: the instantiations, port
onto the general form), arvo-bitmask (Mask<W> rank-1, BitMatrix<W,C> rank-2: same stop over bits,
whether it shares the abstraction is open), arvo-sparse (Csr<C>: rank-2 sparse, probably unaffected,
worth checking), arvo-spectral (consumes and re-exports Matrix: follows arvo-tensor), arvo-graph
(consumes BitMatrix: follows arvo-bitmask), arvo-comb (const-generic structures: follows whichever it
binds). Consolidation precedent restated: cap_size duplication in arvo-bitmask and arvo-spectral was
pulled into arvo-tensor as the single home.

Governing constraint restated verbatim from the prior topic: "the round-trip `cap_size(cap(N))`
overflows the well-formedness evaluator and ICEs the moment a generic consumer threads the capacity
through its own generic code." Any scheme computing a shape (product of extents, stride, flattened
length) in type position walks back into this.

Seven open questions for the talk: (1) is arvo-ndim a new crate or is this what arvo-tensor becomes,
with the foundation already in arvo-tensor and consolidation precedent pointing there; (2) does the
rank abstraction span values and bits or is it stated once per element domain; (3) which per-axis
capacity shape (cons-list, recursive nesting, capacity plus rank); (4) does arvo-shape keep the `Rect`
name at rank 2 or name the general box; (5) does colour belong in arvo-shape at all; (6) is loimu's
alias table adopted, and what was the reason it was abandoned there; (7) what is the const surface,
given `Capacity`/`ConstCapacity` already split. The file marks question 6 as the one research cannot
answer and worth asking first.

## The taxonomy walk

Op asked for the whole arvo taxonomy before placing the shape crates; the walk found the shape
question is the second structural problem, not the first.

The facade is load-bearing though arvo's own rules forbid it: every `forbidden-imports` rule in
mockspace.toml from arvo-transparent through arvo-hash lists `arvo::*` as forbidden, meaning the
declared design is that the facade is terminal and nothing depends on it. Eight crates carry a Cargo
dependency on arvo anyway: arvo-bits, arvo-tensor, arvo-bitmask, arvo-hash, arvo-sparse, arvo-comb,
arvo-graph, arvo-spectral. Cause: the lints only ever read `src/lib.rs`, so `use arvo::USize;` in
module files was invisible, accounting for most of the 52 forbidden-imports findings recorded in the
first topic file of this round.

One rule is unsatisfiable as written, not only drift: arvo-tensor's rule forbids `arvo::*` and claims
it depends only on arvo-storage, arvo-bits-contracts, arvo-numeric-contracts, but `Capacity::CAP` is a
`Cap`, which at the time of this topic lived in the facade, so the layer rule and the type placement
could not both hold. Algorithm crates inherit the same problem through UFixed and IFixed. Op's
recorded reading: arvo has worked fine in practice so the wrong shape is mostly benign, but it remains
a soundness issue and a design contradiction the lints existed to prevent, and the "if mockspace allows
it, it's fine" vibe check was resting on a gate that could not see. The fix is stated to self-heal once
crate purposes hold and the facade becomes the leaf downstream of everything.

Correction to an earlier claim in this same round: arvo-bitmask depending on arvo-tensor was called
accidental above; it is not, bitmask's rule explicitly permits arvo-tensor with a stated reason. What
remains true is why the edge exists: `BitMatrix<W, C: Capacity>` needs the capacity system, which
lives in the value-container crate.

The anomaly explaining the whole thing: arvo's convention is a contracts crate plus a concrete sibling
(arvo-bits-contracts to arvo-bits, arvo-mask-contracts to arvo-bitmask). arvo-numeric-contracts has no
sibling; its own README says "default impl bodies live in the arvo facade." Conclusion: the facade
became load-bearing standing in for a crate that was never created; creating it completes an existing
pattern rather than inventing one.

## Addendum: research pass findings, added after the decisions below

Added after the decisions were recorded, before the talk resumed. Six external passes, two in-stack
audits, one sketch. Full documents at `mock/research/202607281616_prior_art/`, synthesised in
`99_synthesis.md` there; sibling syntheses in `kirjo/`, `lato/`, `hökkeli/` at the same path cited
where they bear on arvo. The file explicitly instructs reading the coverage caveat before weighting any
of this: the baseline handed to these passes was wrong about generic_const_exprs (two passes revised),
and a session-wide search budget ran out partway through the arc.

Five passes independently found: the mathematics this round wants to build has no fixed-point
literature. No geometric-algebra source in fixed point (two adjacent bodies separated out to avoid
confusion). No fixed-point treatment of clothoid or Fresnel curve evaluation. No fixed-point
implementation of any surveyed nonlinear-algebra algorithm and no compile-time rank formulation for any
decomposition family. No fixed-point-plus-shape-typing precedent. No general-purpose fully-integer
colour pipeline in the sibling repo's survey; every perceptual-space/gamut-mapping paper assumes float.

The sixth pass found the opposite, and the contrast is itself the finding: fixed point is the default
in digital signal processing, safety-critical embedded control, blockchain-deterministic arithmetic and
constant-time cryptography. Examples cited: ARM CMSIS-DSP ships saturating multiply-accumulate as a
first-class instruction; Ethereum has no float instruction at all; Uniswap V3 picked Q64.96 so
sqrt(price) fits exactly. Framing given: fixed point is alive in engineering, absent from mathematics,
and arvo sits at the join; expect to derive rather than adopt in geometry, curve, algebra and
decomposition work.

D11's research lead resolved two passes pointed opposite ways: the curves pass found no located
connection between the recalled lead and curve representation; the nonlinear-algebra pass surfaced a
candidate not on the original list, Rida Farouki's Pythagorean-hodograph curves (via quaternion
algebra, carrying a literal optimal-approximation-order bound). The curves pass separately cites the
same family a third time (Juttler and Sir on biarc-to-PH-quintic offsets) without recognising it. On
the name itself: Eckart (Eckart-Young-Mirsky) ranked strongest literal match for "bounded optimal
approximation"; Sturmfels fits "central figure in nonlinear algebra" but not the phrasing; Mirsky and
the Kolmogorov n-width added as alternates. Marked still op's to resolve.

D10 (rotors/PGA) picks a side in a live fork without saying so: projective geometric algebra has an
unresolved split between the bivector.net convention (Gunn, de Keninck, Dorst, Roelfs) and Eric
Lengyel's rigid geometric algebra, differing on dimensional assignment, wedge/antiwedge meaning, and
normalisation. D10 cites "Gunn's plane-based PGA, with Dorst and Lasenby", landing on one side of a
fork the round does not appear to know exists. Correction noted: no feud exists between Dorst and
Lasenby, they diverge in emphasis, and Dorst sits on the PGA side via a 2022 paper with de Keninck.
D10's stated compile-time-fold fallback is novel, not conventional: no library found deriving the
bivector basis as a compile-time type-level fold over an axis list; the three strategies in actual use
are baking at generation time, generating per signature at build time, or deferring to a runtime JIT on
input sparsity. Rotor drift/renormalisation is structurally identical to quaternion behaviour in 3D;
the state of the art for the general-dimension case is de Keninck and Dorst's 2022
exponential-logarithm-normalisation paper, called recent rather than settled. The real open requirement
for interpolation is ScLERP for motors, reducing to the same machinery.

D13's algebraic-laws gap (referenced from `202607281547`, a later topic file) has a shape nobody has
solved: the algebra pass derived a counterexample against shipped code, that signed Saturating addition
is not associative under two-sided clamping while Wrapping addition is a full abelian group, both being
`OverflowPolicy` instances sealed at `arvo-strategy/src/axes.rs:38`. So whether `Combine<Op>` satisfies
its law depends on a second type-level axis (the strategy), not only the operation marker
`Identity<Op>` is parameterised by. No literature found on laws conditional on a second type-level
parameter, across Haskell, Scala, Rust, or Agda. Two data points say do not climb the algebraic ladder
far: NumHask collapsed Ring, Field, Distributive and Module to type synonyms; the three Rust attempts
(`alga` used the operation-marker shape arvo has chosen and was succeeded by narrower `simba` with no

**D1. The dimensional foundation is lifted out from under the container crates.** Decision (op). It
becomes its own crate below arvo-tensor and arvo-bitmask rather than staying inside arvo-tensor or
moving into arvo-storage, so the container crates become peers over one foundation.

**D2. Four new crates, and the facade becomes a leaf.** Decision (op). New crates: `arvo-capacity`
(`Cap`, `Capacity`, `ConstCapacity`, `Dim<N>`, `cap`, `cap_size`), `arvo-shape` (rank, per-axis extent
sequences, generic over rank), `arvo-numeric` (`UFixed`, `IFixed`, `Int`, `Uint`, `FastFloat`,
`StrictFloat`, default contract impls), `arvo-geom` (`Point`, extent, box, `Affine`, semantic
aliases). `arvo` becomes terminal, re-exports only. Reasoning: `Cap` goes to arvo-capacity (not
arvo-storage) because Cap is the value form of a capacity, Capacity the type form, Dim<N> the marker,
cap/cap_size the bridges, and placing Cap with the const-generic carriers in arvo-storage would
separate it from the traits giving it meaning. Capacity and shape stay separate crates: a single axis
extent is a workaround for a compiler limitation, a sequence of them is a real concept, and merging
them would leave the workaround with no boundary (Array<T, C> already demonstrates a consumer wanting
capacity with no notion of rank). arvo-capacity does not depend on arvo-numeric (needs only USize), so
it is a sibling of arvo-bits-contracts, and the two new middle crates are independent of each other.
`Enumerator` leaves arvo-tensor (a blanket trait over IntoIterator is not a container concern); where
it lands is not settled here.

**D3. Naming, settled by the bunching.** Decision (op), implied by D2 and recorded explicitly.
`arvo-shape` is the rank and extent system (what shape means in both mathematics and computing). The
spatial crate is `arvo-geom` (the standard name for that job, and the one loimu used). This reverses
the working assumption carried from `202607281127`, where arvo-shape was to be the spatial crate and
the foundation was to be called arvo-ndim. arvo-ndim is dropped: it abbreviates where no other arvo
crate does, and the crate it named holds capacity as much as dimensionality.

The resulting dependency graph (from notko down): notko to arvo-transparent to arvo-strategy to
arvo-storage, which splits into arvo-bits-contracts (feeding arvo-bits, arvo-numeric-contracts which
feeds new arvo-numeric, and arvo-mask-contracts) and new arvo-capacity (feeding new arvo-shape, which
feeds arvo-tensor, arvo-bitmask, and arvo-sparse, which feeds arvo-graph/arvo-comb/arvo-spectral and
new arvo-geom). `arvo` sits as terminal facade, re-exports only, nothing depends on it.

**D4. A shape is a cons-list of capacities.** Decision (op). Rank and per-axis extents are carried by
a type-level cons-list whose elements are capacities: `Nil::Array<E> = E` (rank 0 is a scalar),
`Cons<H, T>::Array<E> = H::Array<T::Array<E>>` (one more axis). It survives the constraint ruling out
alternatives because rank and element count are associated consts, so arithmetic stays in value
position and no const expression reaches type position, avoiding the exact ICE-triggering failure
Capacity exists to prevent. Beyond rank, op notes the cons-list also carries membership and
satisfaction checks and later supports inferring things a naive typestate cannot represent, which is
why op chose it over tuples (rank is called the smallest thing it does). Existing types become
instantiations rather than migrations: `Matrix<W, C>` is already `C::Array<C::Array<W>>`, which is
`Cons<C, Cons<C, Nil>>::Array<W>`; per-axis extents come free where Matrix's single squared capacity
could not express a rectangle. Rejected: a tuple of capacities (needs impls generated per arity, caps
rank at whatever is written); a capacity plus a rank marker (forces every axis to share an extent,
cannot express a rectangle, the original limitation); bare recursive nesting as-is (leaves a function
generic over rank unwritable, the actual missing piece).

**D5. The cons-list is extracted to notko, as its own crate.** Decision (op). The pattern is
reinvented per repository today and about to be reinvented a third time, so it is formalised once in
notko. Cited duplication: `hilavitkutin/mock/crates/hilavitkutin-api/src/access.rs:50` and
`kolli/mock/crates/kolli-api/src/lib.rs:143` both declare byte-identical `pub struct Empty;` and `pub
struct Cons<H, T>(core::marker::PhantomData<(H, T)>);`, then each regrew the same operations under
different names (hilavitkutin: `AccessSet`/`Contains`/`ContainsAll`/`Concat`; kolli: `CommandSet` with
`LEN`/`each`/`find`). Length is parameterised rather than dropped or hardcoded, because notko cannot
name arvo's USize (arvo depends on notko), and a finding while checking is what makes this the only
workable shape: a separate counting crate in arvo is blocked by the orphan rule (if notko declares both
trait and list types, an impl in arvo has two foreign items and cannot be written; only notko can
implement a notko trait for notko types). So the count parameterises in notko via a `Cardinal` trait
(`const ZERO: Self; fn succ(self) -> Self;`) and a `Length<N: Cardinal>` trait with a blanket fold
impl on `Cons`; each consumer implements `Cardinal` for its own type (legal, since the type is
theirs). One crate, no orphan problem, count type stays consumer's choice; cost is the successor must
be const-callable, so `Cardinal` is a const trait and notko gates `const_trait_impl` as arvo already
does. Recorded because it has no home yet: notko has no `mock/` directory and does not run mockspace,
so this decision has no design round on the notko side; it is recorded here where the talk happened.

**D6. The trait a count type implements is `Cardinal`.** Decision (op). Not `Countable` (the -able
suffix means "can be counted"; this type IS the count, so the suffix inverts the meaning). Not
`Sized` (core rather than std, means "known size" rather than "can stand for the size of something
else"). Not `Natural` either, and the reason is a placement argument rather than naming: zero and
successor are the Peano constructors, so Natural is exactly precise, which is the problem, since it
claims a mathematical primitive that is arvo's territory rather than notko's. notko's existing traits
are properties (`Boundable`, `NonZeroable`); `Cardinal` joins that family. This also leaves `Natural`
available to arvo, which op noted is where it would sound at home alongside arvo's existing semantic
aliases and consts.

**D7. Each domain aliases the cell and the leaf to its own semantics.** Decision (op). The shared
crate ships `Cons` and the leaf; every consumer aliases both to domain-fitting words so the pattern
reads as what it models rather than as a list. Table: arvo-shape uses `Axis<H, T>` / `Scalar` ("an
axis of 3, then an axis of 4, then a scalar"); hilavitkutin uses `Access<H, T>` / `Deny` (op: "or
whatever is the opposite best"); kolli uses `Command<H, T>` / `EmptyInvoke` (op: "or whatever").
Example: `type Vec3 = Axis<Dim<3>, Scalar>; type Rect2 = Axis<Dim<3>, Axis<Dim<4>, Scalar>>;`. Rank 0
being `Scalar` stated as not a pun: a shape with no axes is a scalar. The hilavitkutin and kolli leaf
names are op's sketches, not settled; each repository confirms its own pair on adoption. What is
settled is that domains alias rather than use the generic names directly.

**D8. Bits are not forced onto the shape abstraction.** Decision (op). Where the shape fits the bit
containers, they alias it; where it does not, they do what fits instead. Reuse is not forced. Reason:
storage projections differ per element domain (a dense value shape composes to a nested array `[[T;
4]; 3]`; a bit shape wants the innermost axis packed into words, `[Mask<4>; 3]`, not `[[bool; 4]; 3]`;
`Csr` cannot be a nested array at all since sparse storage's point is not mirroring the shape). A
projection that has to be contorted to fit is called evidence the fit is wrong, not a problem to
engineer around.

**D9. The crate is `notko-hlist`, and prose still says cons-list.** Decision (op). No amendment to
`vocabulary.md` is needed, because a crate name is an identifier rather than prose and the rule is a
documentation rule unifying prose terminology, not a naming rule. On term prevalence: `HList` is the
established name for this specific heterogeneous, type-level structure (Kiselyov, Lammel and Schupke
2004, carried by frunk in Rust, shapeless in Scala, Haskell's HList library). `cons-list` is older and
broader, Lisp-derived, denoting any singly-linked list of cons cells without implying heterogeneity or
type-level residence. Noted for the prose side: in Rust specifically "cons list" is the Rust book's
term for a runtime linked list (the heap-allocated `enum List { Cons(i32, Box<List>), Nil }` example),
close to the opposite of what this crate ships; the ambiguity is recorded, the rule stands as op's
call. Rejected names: `notko-cons` (names the cell/verb, not the structure), `notko-cons-list` (too
verbose), `notko-typelist` (op read as hype), `notko-chain`/`notko-spine`/`notko-row` (none say
heterogeneous and type-level as directly).

**D10. Rotation is grounded on rotors, extending to motors.** Decision (op). Rotation is expressed as
rotors from geometric algebra, not quaternions, not matrices, with motors from projective geometric
algebra extending to rigid motion. ikiuni needs the same machinery, so this is not a geom-only call.
Quaternions rejected as the grounding because they do not generalise (a four-dimensional algebra
special to 3D, unit quaternions double-cover SO(3)); what generalises is the matrix they convert to,
and a matrix is a poor general form (N-squared components for n(n-1)/2 degrees of freedom, drifts under
repeated composition). Rotors are the general form: at rank 2 the even subalgebra of the Clifford
algebra is the complex numbers (one angle); at rank 3 it is the quaternions; at rank N a rotor carries
a scalar plus n(n-1)/2 bivector components, exactly the degrees of freedom a rotation has. Motors
extend to rigid motion (rotation plus translation in one composable object); the dual quaternion is the
3D motor already used industry-wide for skinning, and a motor is its general form; `Affine` is a rigid
motion plus scale, directly what geom wants. Lineage cited: Gunn's plane-based projective geometric
algebra, with Dorst and Lasenby (this citation is the one flagged in the addendum above as landing on
one side of an unacknowledged fork). Component-count concern (a rotor's 1 + n(n-1)/2 components is a
computed extent, a potential const-expression hazard) addressed by op: the toolchain is nightly with
vetted unstable features, not the wall the agent described; the fallback in any case is the hlist
itself, since a bivector basis is the set of 2-subsets of the axes and is derivable by a type-level
fold rather than arithmetic in type position.

**D11. Curves are arvo's, and the direction is a bench matrix rather than a pick.** Decision (op).
Curves are unambiguously arvo territory (mathematics). Representation is not chosen up front: candidates
are benched, the winner per workload is selected statically so LLVM erases alternatives (arvo-strategy's
existing job, applied one level up). Candidates to bench: Euler spirals and clothoids, biarcs and
piecewise-circular, implicit distance fields, classical Beziers. Workloads named and differ: rounded
corners want exact arcs (a Bezier only approximates); ikiuni needs fixed-point rotations first class for
heavy simulation; a terrain editor wants splines, and op's read that Bezier is not best even there is
called well founded since a Bezier's control points do not lie on the curve. A research lead is
unidentified: op has a hunch about unconventional wins from the nonlinear-algebra side, from a name not
yet recalled. Candidates offered and rejected as not it: Hackbusch (hierarchical matrices and tensor
formats), Heckbert (adaptive subdivision and flatness testing), Hausdorff (the curve-approximation-error
metric). Further unconfirmed candidates for the research pass: Eckart (Eckart-Young-Mirsky), Sturmfels,
Hankel, Higham, Householder. Recorded because the next step for arvo is research before committing.

**D12. Colour is not geometry. Packing stays in arvo; an imaging domain takes the rest.** Decision (op).
Bit-level packing, encoding and representation are already arvo's (arvo-bits, arvo-bitmask, arvo-hash;
a pixel format is a bit layout). Colour as a perceptual domain is not numerics with a colour flavour and
does not belong in arvo-geom. The bundle around colour is called imaging: a grid of samples, what a
sample means, how samples are laid out, how geometry becomes samples, expanding incrementally rather
than needing to be whole at once. Linebender is cited as converging on the same grouping and name.
Compression is called a third question, closer to arvo-comb's neighbourhood than colour's, not settled
here. `lato` was considered and rejected as a home (layout and relativity have no relationship to
colour).

**D13. Algebraic structure: the gap, and where the pieces already live.** Raised by op. arvo lacks
first-class monoids, monads, folding in general, and folding across ranks (cascades); placement
question is whether that is one new crate or falls across crates by domain. Most pieces have homes
already, recorded so the remaining gap is visible: type-level folds are already in the hlist (Length,
Concat, ContainsAll are folds; a general Fold belongs in notko-hlist and needs no numerics); the monad
half already exists in notko (Maybe, Outcome, ConstTry machinery; arvo need not restate it); functor
over containers is shape-preserving map, lives with the containers; cascades need the shape (reducing
along an axis requires knowing which axis, so they belong to arvo-shape and arvo-tensor); flattening a
nested container is Concat on its shape (the monadic operation at value level is the type-level concat
at shape level, one operation seen from two heights). The genuine gap is the algebraic contracts
themselves, Semigroup, Monoid, and whatever of the ladder is wanted; arvo-numeric-contracts is
operations (Abs, Recip, Sqrt, TotalOrd), a different thing from algebraic structure, so these have no
home today. One mechanism noted as already idiomatic to arvo: a type can be a monoid more than once
(under addition, under multiplication) and a type may carry only one impl of a trait; Haskell wraps in
Sum/Product newtypes, but arvo already parameterises by ZST marker (Hot, Warm, Cold, Precise), so
Monoid<Add> and Monoid<Mul> follow the existing pattern with no wrapper types needed. Where the
contracts crate sits, and whether it is one crate or an extension of an existing one, is not settled.

The correction: D13 recorded arvo as lacking first-class monoids and proposed parameterising by ZST

provenance rule."

Reasoning given: `Bounded` is algebra. `MIN` and `MAX` are not merely representational limits, they are
identity elements: for the lattice operations, `max(x, MIN) == x` and `min(x, MAX) == x`, so MIN is the
identity of max and MAX is the identity of min. A type with a least and greatest element is a bounded
lattice, its bounds are precisely its two identities, so Bounded moves to arvo-algebra-contracts
alongside Identity. Finding this exposes: `202607281547` records why `Identity<Op>` has one constant
with the operation as a parameter (quoted: "The earlier shape carried ZERO and ONE together, which
named two instances of one concept after their values and forced a type to have both or neither.").

forced to arrive together, where they are two instances of one concept under different operations. The
same crate already anticipates the replacement, quoted: "Identity<Min>, Identity<Max> and
Identity<BitOr> each have their own correct element and arrive as new impls rather than as a third and
fourth constant on this trait." Conclusion drawn: Bounded is Identity<Max> and Identity<Min> wearing
one name, and the argument that produced Identity<Op> applies verbatim; dissolving it would buy the
absence property the same way, a type with no least element simply having no Identity<Max> impl rather
than a Bounded impl carrying a wrong MIN.

Why recorded as a candidate rather than done: Bounded has a second, non-algebraic reading, saturating
arithmetic clamps to the representational limits of the container, a fact about representation rather
than about a lattice. For every arvo numeric type the two coincide, which is why the conflation
survived. Whether the saturating path should name Identity<Min>/Identity<Max>, or whether a separate
representational-limits contract is owed, is called a real question, not settled here. Stated as
standing regardless of that resolution: Bounded is algebra and moves with Identity; whether it survives
as its own trait afterward is the follow-up.

# 202607291300 Bounded is sugar over two identities

One op call, refining D24 of `202607291200`.

**D26. `Bounded` is not a bespoke trait; it is two `Identity` impls with a name.** Decision (op,
2026-07-29). D24 moved Bounded to the algebra crates and left "does it dissolve entirely" as a
follow-up; op closes that here: it is a convenience over the two identities and should say so in its

rather than returning something plausible. Today Bounded forces a type to have both constants or
neither, the exact complaint `202607281547` records against the ZERO/ONE shape Identity<Op> replaced.

Bounded that read through to the two identities, so no call site changes; Bounded becomes the sugar it
always was instead of a second source of the same values.

Left open, not settled here: Bounded's second, non-algebraic reading, that saturating arithmetic
clamps to the representational limits of the container, a fact about storage rather than a lattice. For
every arvo numeric type the two coincide, which is why the conflation went unnoticed. If the saturating

# 202607291900 arvo-num-systems, and proving membership rather than asserting it

Op's call on the crate, contents, and dependency direction. The literature grounding and one
consequence about arvo's own types are the agent's, sourced inline. `Natural` entered the round as a
leftover: D6 declined it for notko (claims a mathematical primitive), left it "available to arvo," and

**D38. arvo gets a crate for number-system membership.** Decision (op, 2026-07-29). Not just Natural,
the whole family: `Real`, `Surreal`, and the rest worth having, in a new crate `arvo-num-systems`.
Reasoning: the sets serve as generic bounds across all mathematical work, mattering more here than in
most codebases because the stack leans explicitly on typestate and generics; with the sets available as
bounds, code can diverge on established mathematical facts rather than ad-hoc predicates, and
expressing centuries-settled distinctions as bounds costs nothing at runtime. Op's call, explicitly the
opposite of the anti-speculation default applied elsewhere in this round for a stated specific reason:
they ship even if nothing uses them yet, because the vocabulary is fixed by mathematics rather than
invented here, so it cannot be got wrong in a way that later needs undoing, and having them exist now is
cheaper than retrofitting once consumers improvise around the absence.

What the literature calls this: "number systems" is the standard mathematical phrase, matching op's
name. The computing term for the same structure is the numerical tower (Scheme and Common Lisp,
defined as "a set of data types that represent numbers and a logic for their hierarchical
organisation," ordering Number superset Complex superset Real superset Rational superset Integer).
Noted: that tower has no Natural at its base, called a gap in the borrowed structure rather than a
reason to avoid the term; arvo's version starts one rung lower than Scheme's. Members table given:
Natural (N, below the Scheme tower's base), Integer (Z), Rational (Q), Real (R), Complex (C),
Quaternion (H, Cayley-Dickson from C), Octonion (O, Cayley-Dickson from H), Surreal (No, Conway; "op's
word was exactly the English one"), Hyperreal (*R, Robinson, non-standard analysis), p-adic (Q_p).
Algebraic and transcendental are noted to cut across R rather than nesting under it, a separate axis
rather than more rungs.

**D39. Membership is defined in terms of algebraic structure.** Decision (op, 2026-07-29).
arvo-num-systems depends on arvo-algebra-contracts, and the sets are defined through the structures
rather than as opaque markers: R is a complete ordered field, Z is an integral domain, each membership
bound saying so. Called the mathematically honest arrangement, with real content (a consumer bounding
on Real gets the field operations because that is what being real means, not because a separate bound
was also written). Sequencing consequence: the algebra ladder has to be defined before the sets can be,
so arvo-algebra-contracts is upstream work rather than a sibling; the changelist orders them
accordingly.

The harder half, called the actual work: op's framing, recorded because it makes the crate non-trivial.
Contracts without proofs would be marker traits a consumer could implement wrongly; the interesting
part is the const assertions and typestate machinery that statically prove membership holds, so an impl
exists only for types genuinely satisfying it, described as not obvious and where the design effort
goes. One precision noted from the start: the predicate is inhabits, not equals. Natural asserts every
value of the type is a natural number, not that the type represents all of N. `UFixed<8, 0, S>` holds 0
through 255, a finite subset, and is Natural under the inhabits reading and nothing under the equals
reading; inhabits is also called the reading that makes the bound decidable and composable and gives
the diverging-logic idea its teeth.

Agent finding, sourced inline: applying the inhabits test to arvo's existing primitives produces a
sharper answer than expected, decidable from the type parameters alone. A `UFixed<I, F, S>` is an
integer over 2^F, so every value is a fraction with a power-of-two denominator, the dyadic rationals,
ring Z[1/2], a proper subset of Q. Floats are stated the same, quoting sources: "for most
floating-point representations, the representable numbers are a subset of the dyadic rationals," and
fixed-point "use powers of two implicitly in the majority of cases." Table: `UFixed<I, 0, S>` inhabits N
(integers, non-negative, bounded); `IFixed<I, 0, S>` inhabits Z (integers, signed, bounded);
`UFixed<I, F, S>` with F > 0 inhabits Z[1/2] (numerator over 2^F); `IFixed<I, F, S>` with F > 0
inhabits Z[1/2] (same, signed); `FastFloat`/`StrictFloat` inhabit Z[1/2] plus specials (infinities and
NaN outside any of these sets). Conclusion: no arvo type is Real, none is Rational in full; Real becomes
a bound nothing in the crate satisfies, which op already accepted in advance ("even if nothing uses
them, they are there"), called information rather than a gap, stating precisely what the substrate
cannot promise so a consumer needing R learns it at the bound rather than after a rounding surprise. The
float row is connected to `202607291710`: NaN and infinities are exactly the values breaking

# 202607300300 proposal, arvo's primitives become named compositions over a formalization

Agent's full proposal, put point by point for op's agreement. Nothing decided. Rests on
`202607300200_research.the-strategy-axes-against-the-field.md` and on D38, D39, D47.

Core observation: Flocq (the Coq formalization underlying CompCert's float reasoning) treats fixed point
and floating point as one subject via a single predicate `generic_format β fexp`, where a real number is
in the format when unchanged by truncating the significand at its canonical exponent
(`cexp β fexp x = fexp (mag β x)`). The four standard formats (`FIX` constant exponent, `FLX = e -
prec`, `FLT = max(e - prec, emin)`, `FTZ` flush-to-zero) are four choices of the exponent function, so
fixed point versus IEEE float is one function parameter's value. Rounding is the same shape: a function
`rnd : ℝ → ℤ` (`Ztrunc`, `Zfloor`, `Zceil`, `ZnearestE`) whose lawfulness is carried by a `Valid_rnd`
typeclass. States this is the function-plus-law-typeclass mechanism arvo already believes in, arrived at
independently by formalists.

Proposes five layers, each depending only on layers below:

Layer 0, number systems: already settled as `arvo-num-systems` by D38, depending on the algebra
contracts by D39 (both prior-round decisions, not made here). Sets a value inhabits: ℕ, ℤ, ℚ, ℝ, ℂ, ℍ,
𝕆, surreal, hyperreal, p-adic.

Layer 1, algebraic structure: `arvo-algebra-contracts` per D22, populated to whatever depth per D47.
Two kinds of declaration kept separate: structures (Magma, Semigroup, Monoid, Group, AbelianGroup, Ring,
Field, FiniteField, Lattice, BoundedLattice, MV-algebra) and laws as separate markers (Associative,
Commutative, Monotone, Idempotent, Distributive, Invertible).

Layer 2, the format (new, called the heart of the proposal): a `Format` names which values of a number
system are representable, parameterised by radix, signedness, and an exponent function. Instances:
`Fix<F>` (constant exponent), `Flx<PREC>`, `Flt<PREC, EMIN>`, `Ftz<..>`, and any consumer-written
exponent function. States this collapses arvo's current four separate families into one concept.

Layer 3, landing policies (how an exact result too precise or too large maps back into the format,
called one shape not two subjects): `Rounding` (too precise; instances Trunc, Floor, Ceil, NearestEven,
NearestAway, Convergent, Stochastic), `Overflow` (too large; instances Wrap, Saturate, SaturateSym,
SaturateZero, WrapSignMagnitude, Trap), `Growth` (intermediate room; instances FullPrecision, KeepLsb,
KeepMsb, Specify). States `Rounding` is the axis arvo currently lacks entirely, `Overflow` is the axis
with two of the field's five values, `Growth` is the axis buried in the strategy markers that D34
already had to prise out by necessity.

Layer 4, composition with laws derived rather than declared per type. A concrete type composes a number
system, a format, a signedness, a rounding, an overflow, a growth; law markers are computed from the
composition. A table gives four compositions and their derived structure/laws: Wrap (any signedness) is
ℤ/2ⁿℤ, an abelian group and commutative ring, laws associative/commutative/invertible; Saturate
(unsigned) is truncated addition, a commutative monoid, laws associative/commutative/monotone; Saturate
(unsigned, UNORM encoding) is a finite MV-chain (standard Łukasiewicz structure), same laws plus MV
operations; Saturate (signed, two-sided) is a monotone commutative unital magma on a bounded lattice,
laws commutative/monotone/**not associative**. States `Monoid<Add>` resolves for the first three and not
the fourth, so a fold over a two-sided saturating type fails to compile rather than silently returning a
grouping-dependent answer, called a guarantee no industrial fixed-point system offers.

The MV-chain row is highlighted as resolving something the round had left open: the standard MV-algebra
is `[0,1]` with `¬x = 1-x`, `x ⊕ y = min(1, x+y)`, finite Łukasiewicz chains its finite forms. arvo's
`UFixed<0, F>` under the UNORM encoding (dividing by `2^F - 1` so all-ones lands exactly on one) is such
a chain; under arvo's own `2^F` encoding it is not, since one is not representable. Names D36 (an
earlier round) as the place that recorded the identity impl as incomplete with the encoding an unnamed
parameter, and states this proposal names what the two encodings actually are (one a named structure
with literature, the other a half-open interval without one).

Layer 5, semantic names: `UFixed<I, F, S>` / `IFixed<I, F, S>` become aliases for `Fix` compositions,
`FastFloat` / `StrictFloat` become aliases for `Flt` compositions, `Hot`/`Warm`/`Cold`/`Precise` are
documented as presets over (growth, overflow, container) per what the research already showed. Per D48
(`202607292300`) the public spelling is unaffected: `UFixed<13, 3, Warm>` keeps reading the same, the
composition it expands to stays internal.

States five ways this goes beyond the industrial standards, the explicit ask: law survival tracked in
the type (SystemC hands consumers `SC_SAT` with no associativity guarantee; this refuses the fold
instead); IEEE 754 standardises one format while `generic_format` covers a family, so arvo ships FIX/
FLX/FLT/FTZ plus any unstandardised exponent function; rounding as an open trait admits stochastic
rounding (a current research staple, absent from all four industrial systems); number-system membership
as a bound (dyadic-rational or MV-chain membership, decidable from type parameters, named in no other
numeric library); the composition itself is nameable, letting a consumer construct an unstandardised
numeric system and still get computed laws.

Three risks, called load-bearing:

1. Contradicts D29 (a prior-round decision creating `arvo-float` two days earlier on the reasoning that
   fixed point and IEEE float are different kinds of thing): Flocq says they are one thing at different
   exponent functions. States the crate split could survive as packaging (floats carry hardware concerns:
   infinities, NaN, specials that break membership) even if the mathematical claim behind the split does
   not. Explicitly flagged as op's to rule on and named as the reason this is a proposal rather than a
   plan.
2. The exponent function must not reach type position: `fexp` computing a canonical exponent at compile
   time is exactly the shape `generic_const_exprs` was forbidden for (per `unstable-features.md`'s
   FORBIDDEN classification). Must be an associated type or value-position computation per the cure D2
   (prior round) settled and the sketch at `202607282100_container-projection-without-gce`. States this
   needs its own sketch before anything is built; if not expressible gate-free, the proposal changes
   shape.
3. The composition is a product of six axes: `arvo-compile-time-last.md` licenses the cost explicitly,
   and D47 requires each rung sketched and benched rather than assumed. Mitigation offered (unverified,
   itself a sketch question): the composition is a type and law markers are blanket impls over it, so
   nothing enumerates the product combinatorially.

Sequencing the agent recommends (not decided): land the current restructure first, since it is mostly
crate movement, nearly fully decided, and creates `arvo-num-systems`, `arvo-algebra-contracts` and
`arvo-container`, the crates this proposal would fill; folding the two rounds together doubles the blast
radius of a round already spanning sixteen crates. This proposal opens as the next round, starting with
the `fexp` sketch, since the whole proposal rests on that being expressible.

fall out of; format unification makes underflow real for the first time.
