# Capacity Trait and Dim Marker, the GCE-free Fixed-Capacity Foundation

**Date:** 2026-05-30
**Phase:** TOPIC
**Scope:** arvo-tensor (L2). Ships two new items: the `Capacity` trait and the `Dim<const N: usize>` marker. Does NOT migrate existing containers (that is the follow-on round, task #651) and does NOT touch the engine (task #652).
**Source topics:** numeric-position convention design talk (hilavitkutin `mock/research/202605301130_numeric-position-convention.md`, decision T13) plus the validated sketch `hilavitkutin/mock/research/sketches/202605301145_capacity-as-type/`.
**Tasks:** #650 (this round), under gate #649. Unblocks #651 (container migration) and #652 (engine adoption).

## Why this round exists

arvo's fixed-shape containers bind a `Cap` const generic and store `[T; cap_size(N)]`, gated by a `where [(); cap_size(N)]:` clause on every impl. `Array<T, const N: Cap>` is the canonical shape (`array.rs`), and `Matrix`, `arvo-sparse::Csr`, and `arvo-bitmask::BitMatrix` follow the same pattern. The clause works when the capacity is a concrete `Cap` at the use site. It breaks when a generic consumer threads the capacity through its own generic code: the round-trip `cap_size(cap(N))` overflows rustc's `generic_const_exprs` well-formedness evaluator and ICEs. The hilavitkutin scheduler hit this three distinct ways while trying to thread plan dimensions through a generic `build()`.

The root cause is structural, not a tuning problem. `Cap` is a newtype over `USize` over `usize`; array lengths must be a bare `usize` at the language grammar level; so a `Cap`-parameterised container is forced to write `[T; cap_size(N)]`, which invokes `generic_const_exprs`, which is incomplete and overflows when the length expression is itself built from a generic parameter. No const-generics feature on the pinned nightly fixes this for the `cap_size(cap(N))` shape (`min_generic_const_args` cannot express it; `generic_const_args` needs `-Znext-solver=globally` and an all-or-nothing rewrite). The full reasoning is in the convention design talk and the two sketches it cites.

The decision (T13, locked with op, reviewed by a code-architect) is to stop putting a const generic in capacity position at all. A capacity becomes a TYPE. The array length becomes a literal inside a concrete impl. Then no const expression is evaluated in type position, `generic_const_exprs` never runs over capacity arithmetic, and the storage constructs, fills, indexes, and walks from fully-generic code with no ICE possible by construction. This is the same escape arvo already uses for bit widths: `BitsContainerFor` dispatches `(strategy, width, sign)` to a container TYPE rather than computing a length. T13 generalises that move from "pick a scalar container" to "pick an array type".

## What ships in this round

Two items in arvo-tensor, validated to compile with zero `#![feature(...)]` gates in the sketch.

A non-generic trait that names a fixed capacity as a type:

```rust
pub trait Capacity {
    type Array<T>: AsRef<[T]> + AsMut<[T]>;
    const CAP: Cap;
    const N: usize;
    fn empty<T: Copy>(fill: T) -> Self::Array<T>;
    fn as_slice<T>(a: &Self::Array<T>) -> &[T];
    fn as_mut_slice<T>(a: &mut Self::Array<T>) -> &mut [T];
}
```

The `AsRef<[T]> + AsMut<[T]>` bound (stable, no const evaluation) gives slice access and iteration without a const-generic `Index` HKT. It also lets a two-dimensional container be the composition `R::Array<C::Array<T>>` with no separate trait, which resolved the architect's one objection (the engine is predominantly multi-dimensional). `CAP` is the typed surface capacity (an `arvo::Cap`); `N` is the runtime length used only as a loop bound, never as an array length in generic code.

One generic marker that implements it for any exact size:

```rust
pub struct Dim<const DIM: usize>;
impl<const DIM: usize> Capacity for Dim<DIM> {
    type Array<T> = [T; DIM];
    const CAP: Cap = cap(DIM);
    const N: usize = DIM;
    fn empty<T: Copy>(fill: T) -> [T; DIM] { [fill; DIM] }
    fn as_slice<T>(a: &[T; DIM]) -> &[T] { a }
    fn as_mut_slice<T>(a: &mut [T; DIM]) -> &mut [T] { a }
}
```

The implementing TYPE is generic over `const DIM: usize`; the `Capacity` TRAIT stays non-generic, so consumers bind `C: Capacity` with no const parameter and keep the type-dispatch property. `[T; DIM]` is plain min-const-generics: no `cap_size`, no `generic_const_exprs`. `cap(DIM)` appears only in the associated-const VALUE position, never in type position, which is the one bit the sketch proved beyond the prior arvo experience.

Two-dimensional storage is the composition of two capacities, no new trait:

```rust
struct Matrix2<R: Capacity, C: Capacity, T> { rows: R::Array<C::Array<T>> }
```

The only residue is a `where <C as Capacity>::Array<T>: Copy` bound on two-dimensional constructors (the outer `empty([inner; R])` needs the inner row to be Copy). It is trivially satisfied for every POD element type and discharges at each concrete use; it just has to be stated on nested constructors. This round does not ship `Matrix2`; it is shown here because the two-dimensional story is what the migration round (#651) will lean on, and the `Capacity` shape has to support it.

Tests follow the TDD discipline: the SRC phase writes the strict generic-build-and-walk test first (the exact shape that ICE'd under the `Cap`-const-generic form, asserting it now compiles and runs), watches it fail against the absent trait, then ships the trait to pass it. The sketch is essentially that test already, against a toy `Cap`; the port swaps in arvo's real `Cap` and `cap`.

## What this round does NOT do

The existing `Array<T, const N: Cap>`, `Matrix<W, N>`, `Csr`, and `BitMatrix` are untouched. They keep their `Cap` const generics and their `cap_size(N)` bounds. The migration of those containers onto `Capacity` is task #651, a separate round, because it has to preserve each container's algorithms and bench characteristics and is the bulk of the arvo-side work. The engine `PlanDims` bundling trait and the `Scheduler` adoption are hilavitkutin-side (task #652). `cap` and `cap_size` stay exactly where they are; #650 adds to arvo-tensor, it does not remove from it.

## Home crate

arvo-tensor. The trait's return types are `arvo::Cap` (defined in arvo-storage, L0) plus plain arrays (no dependency), so the bridge-home rule would permit a home as low as arvo-storage. That option was considered and rejected: every consumer of array-length capacities is L2 or higher (Csr, Array, Matrix, BitMatrix, the engine plan dims), L0 and L1 numeric types use the type-dispatch path over `BitWidth` rather than array lengths, and arvo-tensor is already the home of `cap`, `cap_size`, and the `Cap`-shaped capacity machinery. Placing `Capacity` lower would buy reuse no current or planned consumer needs and would pull the `cap` const fn down with it. arvo-tensor keeps the capacity concepts together.

## Open questions for the DOC phase

The final name of the marker. `Dim<const N: usize>` is the working name; `Cap` is taken by the value newtype. `Dim` reads well for a dimension, but the trait it implements is `Capacity`, so `Cap`-adjacent names (`CapDim`, `Capacity` + `Sized<N>`) are worth one pass. Naming is a DOC topic, not a blocker.

Whether `Capacity` needs more than slice access. The sketch uses `as_slice` / `as_mut_slice` free functions on the trait. The migrated containers may want `Index` / `IndexMut` bounds, typed `USize` indexing (matching `Array::get(USize)`), or iterator adapters. The minimal trait ships this round; richer access can be additive in #651 when the real container access patterns drive it.

Whether `empty` stays `T: Copy` only. The engine's plan arrays are all Copy (`UnitMeta`, masks, ids), so the Copy constructor covers the known need. A non-Copy element type would need a `MaybeUninit`-based constructor on `Capacity`. Deferred until a non-Copy consumer appears.

Module placement inside arvo-tensor. A new `capacity.rs` alongside `cap.rs` is the obvious shape; the DOC CL settles it.
