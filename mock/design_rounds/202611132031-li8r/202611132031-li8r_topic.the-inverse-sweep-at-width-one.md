# the-inverse-sweep-at-width-one

**Date:** 2026-11-13

**Tickets:** `arvo_dev_is_red_the_inverse_round_trip_test_underflows_at_wi`,

## What is wrong

`law::the_multiplicative_inverse_round_trip` holds over unsigned wrapping multiplication at every width
from one to 65. The test that carries it in this crate,
`multiplication::tests::the_inverse_round_trip::the_inverse_of_three_round_trips_at_every_unsigned_width_from_one_to_63`,
panics before its first assertion. Its own sampler, `members`, writes the probe list as
`[0, 1, 2, 3, top / 3, top / 3 + 1, top - 2, top - 1, top]`, and at width one `top` is one, so
`top - 2` underflows in a debug build. The red is in the instrument and says nothing about the product,
and the width-one cell of the law has never been checked here. Every width from two up passes once the
sweep reaches it.

It is the one red `cargo test -p arvo-format --lib` reports on `work/arvo-standards` at `f0eeb2e3`: 297
passed, 1 failed.

## What changes

The two entries below the top are built by a saturating step, so at width one they fall to zero and one,
which the filter keeps, and the sweep runs at width one and two as the law states. Nothing in the code
under test moves.

The planted arm, the inverse plus two, cannot break at width one, since every odd constant is the inverse
of three modulo two, and the test already skips it there. So width one gets a planted arm of its own that
holds at every width: zero is no inverse of anything, so `(x * 3) * 0 == x` has to break at every width
from one up, at `x = 1` if nowhere else. That is the case that has to fail at the width the fix opens.

The design is silent on the test's sampler and says nothing that changes, so the doc changelist carries
no template edit.
