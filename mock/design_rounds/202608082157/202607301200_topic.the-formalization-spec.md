## What changed, in one paragraph

arvo's four numeric families become one type. `UFixed`, `IFixed`, `FastFloat` and `StrictFloat` are
four names for four compositions of `Number<N: Numeral, S: Policy + Lowering>`, and what
differentiates them is where their exponent lives. The strategy markers stop being an opaque bundle
and become named points across ten axes, five of which arvo did not previously name at all. Every
mathematical fact about a composition, from which number system its values inhabit to whether its
addition is associative, is derived by blanket implementation over the axes rather than asserted per
type. The public spelling does not change.

## The three contracts

The axes divide by what moving them does. This is D54, and it is the test that sorts any axis added
later: change it, and ask whether the set of representable values changed. If it did, the axis is
identity. If the same values are still representable and only the arithmetic differs, it is policy. If
neither changed and only the cost did, it is lowering.

```rust
/// What the number IS: which values are representable at all.
pub const trait Numeral {
    type ExponentForm: ExponentForm;
    type Adjustment:   Adjustment;
    type Bias:         Bias;
    type Sign:         Signedness;
    type LogicalWidth: Width;
}

/// What is returned when a result does not land in the numeral.
pub const trait Policy {
    type Quantisation: Quantisation;
    type Growth:       Growth;
}

/// What it costs to hold and to compute. Changes no answer.
pub const trait Lowering {
    type StoredWidth: StoredWidth;
    type Widening:    Widening;
    type Layout:      StorageLayout;
}

pub struct Number<N: Numeral, S>(..) where S: Policy + Lowering;
```

The split between the second and third is the one the round found hardest and is worth restating: a
`Policy` member changes the answer and therefore participates in the law derivation, while a
`Lowering` member changes only the emitted code and the bytes held, and conditioning a law on one
would be conditioning correctness on a storage choice. `Cold` is the shipped proof they are
independent, storing at minimum width and computing at double.

The three-way division is IEEE 754's own. The standard separates a format, which values are
representable, from its encoding, how those values are laid out in bits, and keeps rounding-direction
attributes separate from both as properties governing operations. Decimal is the proof case: IEEE
specifies two encodings, binary integer decimal and densely packed decimal, for one format, so
`decimal64` under either represents the same values with unrelated bit layouts. One numeral, two
lowerings. (D58.)

## The ten axes

### Identity, on `Numeral`

**`ExponentForm`** decides where the exponent lives, and everything else about the spacing follows
from it. This is the primitive that distinguishes fixed point from floating point, and stating it this
way rather than as a property of the spacing is what makes precision and minimum exponent stop being
parameters: both derive from the exponent field's width, which is how IEEE defines its interchange
formats. (D65.)

```rust
/// The exponent is a property of the type, so it is the same for every
/// value and the spacing is constant.
pub struct Implicit<const EXPONENT: Exponent>;

/// The exponent is stored in the value, in a field of this width, so it
/// varies per value and the spacing varies with magnitude. Only a stored
/// exponent has a range it can fall out of, which is where underflow acts.
pub struct Stored<const BITS: Width, U: Underflow>;
```

`Underflow` is nested rather than a top-level axis, because a constant exponent has no bottom to fall
off and would have to carry a value meaning the axis does not apply. Its instances are the three Flocq
distinguishes: `Unbounded` (no floor, no subnormals, FLX), `Gradual` (subnormals, IEEE 754's choice,
FLT) and `Flushed` (abrupt, flush to zero, FTZ). Underflow is identity rather than policy despite its
name pairing with overflow: changing it changes which values are representable, which is why Flocq
treats the three as three formats rather than one format with three behaviours.

**`Adjustment`** is the quantum's departure from a pure power of the radix. The quantum of a value is
`Adjustment * radix^exponent`, which is MATLAB's decomposition of a slope into an adjustment factor in
`[1, 2)` times a power of two. `Unit` is every ordinary numeral. `FullRange<F>`, being
`radix^F / (radix^F - 1)`, is what makes UNORM expressible, since its quantum `1/255` is not a power
of two and no exponent function produces it. (D61.)

**`Bias`** is where the origin sits. The value of a stored integer `k` is
`Adjustment * radix^exponent * k + Bias`, which is MATLAB's general scaling in full. `Zero` for every
ordinary numeral. A bias cannot be expressed by an adjustment or the reverse, since one moves the
origin and the other changes the spacing, and an affine map is not determined by either half. (D68.)

**`Sign`** is `Unsigned` or `Signed`, unchanged from what ships.

**`LogicalWidth`** is the total, from which the significand derives by subtracting the exponent field
and the sign bit. It is primitive and not derivable: the other identity members fix the spacing and
the origin and say nothing about the extent, and deriving it from `Lowering` is circular because
`DoubleLogical` is defined as twice it. (D69.)

### Semantics, on `Policy`

**`Quantisation`** is the map from an exact value onto the representable set, including at the ends of
the range. Rounding and overflow are not two axes; they are the in-range and out-of-range halves of
one map, which is what `202607300300`'s Layer 3 already said and what the field means by a quantizer.
An analogue-to-digital converter quantizes and clips, and both are quantization. (D64.)

There are five situations an exact value can be in, and the vocabulary differs only where the
situation does. Between two representable neighbours every rule is a choice between them, which is a
direction. Past either end one neighbour does not exist, so a rule has three further options: take the
neighbour that does exist, which is clamping and is still a direction; produce something unrelated to
where the value was; or decline.

```rust
pub const trait Resolution {}
pub const trait Direction: [const] Resolution {}

// Direction and Resolution
pub struct TowardNegative;  pub struct TowardPositive;
pub struct TowardZero;      pub struct AwayFromZero;
pub struct ToEven;          pub struct ToOdd;

// Resolution only: meaningless where a neighbour exists
pub struct ReduceModulo;    pub struct SubstituteZero;
pub struct Refuse;

pub const trait Quantisation {
    type UnderMidpoint: Direction;
    type OnMidpoint:    Direction;
    type OverMidpoint:  Direction;
    type OverRange:     Resolution;
    type UnderRange:    Resolution;
    /// `Just<T>` for total rules, `Outcome<T, _>` where `Refuse` appears.
    type Fallibility<T>: notko::ConstTry<Output = T>;
}
```

Clamping needs no name of its own: clamping above the range is `TowardNegative`, the marker rounding
already uses. Saturation is therefore `(TowardNegative, TowardPositive)` at the range members, which
says what saturation is rather than asserting it. The combinations no standard names are the
non-monotone ones, and monotonicity is derived rather than forbidden, so they exist and cannot be used
where the law is required. `ReduceModulo` at a midpoint position does not compile, because it is not a
`Direction` and there is no modulus to reduce by between adjacent representable values. (D63.)

**`Growth`** decides how much of an exact intermediate is kept before quantisation returns it. The
exact result of combining two values is itself a numeral, wider and with a finer quantum, and anything
narrower must drop bits from one end: dropping the low ones coarsens the quantum, dropping the high
ones shrinks the range.

```rust
/// Keep everything. Widths add, quanta multiply, nothing is dropped, so
/// there is no end to anchor to.
pub struct Exact;

/// Keep `W` bits anchored at one end.
pub struct Narrowed<W: IntermediateWidth, A: Anchor>;
```

### Cost, on `Lowering`

**`StoredWidth`** is `Minimum` or `DoubleLogical`. **`Widening`** is `None`, `InContainer` or
`PerOperation`, naming where intermediate headroom comes from. **`Layout`** is `Dense` or `Bitpacked`.
All three are as arvo ships them, with `None` added to `Widening` because `Hot` needs no intermediate
room and `InContainer` was the wrong word for having none. (D71.)

## What is derived rather than declared

This is the part that distinguishes the design from an enumeration, and the rule behind it is D16: a
property computed from the thing itself cannot lie and is a safe implementation, while a property
asserted about it is a promise and would be an `unsafe impl` carrying a contract. Everything below is
in the first category.

**Number-system membership.** `202607291900` derived a table of which set each arvo type inhabits, one
row per type, by hand. With the quantum in the numeral the rows become blanket implementations
conditioned on structure: an empty fractional part with an unsigned domain inhabits the naturals, the
same signed inhabits the integers, a power-of-two quantum with no bias inhabits the dyadic rationals,
any other exact quantum inhabits the rationals, and a floating numeral adds the specials that inhabit
nothing. The dyadic condition is `Adjustment = Unit`, an associated-type equality bound, so `FullRange`
cannot satisfy it and nothing had to gatekeep that. (D61.)

**Algebraic laws.** The `(Overflow, Signedness)` table the law sketch wrote out becomes two
implementations conditioned on one primitive property. A recovery is *faithful* when it leaves the
operation the operation of an algebraic structure on the representable set; modular reduction is,
since wrapping addition is the group operation of `ℤ/2ⁿℤ`, and clamping, substituting and refusing are
not.

```rust
// unsigned addition can only leave the range above, so one end is
// unreachable and the rule is truncated addition whatever it does there
impl<A: Resolution, B: Resolution> AddAssoc for ((A, B), Unsigned) {}

// signed addition reaches both ends, so neither may deviate
impl<A: Faithful, B: Faithful> AddAssoc for ((A, B), Signed) {}
```

Checked: signed saturation has neither end faithful and gets no implementation, which is the sketch's
refusal derived rather than arranged. Symmetric saturation likewise, confirming by construction what
the sketch confirmed by experiment. Signed trapping also fails, correctly, since `(127 + 1) + (-1)`
refuses while `127 + (1 - 1)` returns 127. Hybrids such as clamping above and wrapping below fail too,
which no hand-written table would have predicted because nobody would have written the row.

**The type-family markers.** `IntegerLike`, `FractionLike` and `FloatLike` become blanket
implementations conditioned on the exponent form. Because "fractional" means a negative exponent and
an inequality in a bound needs const-expression bounds, which are forbidden, integrality is declared
on the `Implicit` markers by a macro-expanded table so the bound is an equality rather than a
comparison. `BoolLike` leaves the family: `Bool` has no numeral and is not a `Number`. (D73.)

**The representable range.** Derived from the logical width, the sign and the quantum. D45's contract
is not declared, and what it was protecting survives more sharply: the numeral's range is identity,
the carrier's range is lowering, and they differ exactly when the stored width is doubled. (D73.)

**`Deterministic`.** A blanket implementation keyed on the composition, which makes D49's prose
qualification structural. The property holds for a composition rather than for arvo, so the claim a
consumer can rely on is exactly the claim their type makes. (D70.)

**`ConstantTime`.** The same shape. It reports rather than requests: a consumer can check whether the
composition they chose is constant-time and cannot demand it, so an internals change adding a
data-dependent early exit would withdraw the property silently. That is the accepted trade, recorded
so it is not reopened as an oversight. (D74.)

## The presets

Pre-1.0 nobody depends on the current meanings, so each is derived from what its name promises. Op's
statement of the four intents: `Hot` is as fast as possible, `Cold` stores as small as possible,
`Precise` is the most precise at the price of both storage and compute, `Warm` is the compromise that
suits most default cases and behaves intuitively. (D71.)

| | `Hot` | `Cold` | `Warm` | `Precise` |
|---|---|---|---|---|
| in-range | truncate | nearest, ties to even | nearest, ties to even | nearest, ties to even |
| out-of-range | reduce modulo | clamp | clamp | refuse |
| growth | narrowed to operand | exact | exact | exact |
| stored width | minimum | minimum | doubled | doubled |
| widening | none | per operation | in container | per operation |
| layout | dense | bitpacked | dense | dense |

Three consequences follow that a reader should meet here rather than discover.

*Only `Hot` folds for signed values.* Clamping and refusing are both unfaithful, so `AddAssoc` holds
for `Hot` alone once the operands are signed. The marker chosen for speed is the only one whose signed
folds are permitted, which reads backwards until wrapping is recognised as exactly the arithmetic of a
group and the others as deviations from one.

*`Cold` pays a compare and select on every store.* Taken deliberately: a bitpacked column that wraps
silently corrupts a stored value rather than an intermediate.

*`Precise` is fallible.* Its arithmetic returns through the refusing branch of the fallibility
projection, so call sites unwrap. That is the price of its stated intent, in the type rather than in a
comment.

## Conventions

Every established convention ships as an optional feature containing type aliases over the abstraction
and nothing else: `conv-ieee754`, `conv-systemc`, `conv-matlab`, `conv-amd-vitis`, `conv-flocq`, each
off by default. Per `arvo-toolbox-not-policer.md` arvo ships one structure and does not decide which
vocabulary a consumer arrives thinking in. (D66, D67.)

The second half is the load-bearing one: **if a convention's mode cannot be written as an alias, the
abstraction is not general enough.** That is a falsifiable test, runnable per standard before anything
ships. It has already found one gap and closed it, MATLAB's slope-and-bias scaling being inexpressible
until `Bias` was added.

The alias sets are also checkable documentation. Writing MATLAB's `Nearest`, `Round` and `Convergent`
out in terms of tie direction makes visible that only the third matches IEEE's default, a trap that
otherwise surfaces at runtime for anyone porting.

## Crates

One crate per contract, with the strategy crate holding only the four presets. (D72.)

| Crate | Holds |
|---|---|
| `arvo-numeral` | `Numeral`, `ExponentForm`, `Adjustment`, `Bias`, `Underflow`, and their markers |
| `arvo-policy` | `Policy`, `Quantisation`, `Resolution`, `Direction`, `Growth`, and their markers |
| `arvo-lowering` | `Lowering`, `StoredWidth`, `Widening`, `StorageLayout`, and their markers |
| `arvo-strategy` | `Hot`, `Cold`, `Warm`, `Precise`, and nothing else |
| `arvo-numeric` | `Number<N, S>`, the semantic aliases, the `conv-*` sets |
| `arvo-algebra-contracts` | the ladder and the law markers |

`arvo-strategy` keeps its name and loses everything that had accumulated in it. Its name was never
wrong; what was wrong was the container projection, the arithmetic dispatch, identity and widening all
living inside the crate named for four markers. D23 and D27 had already started moving pieces out.

The algebra ladder is declared to the depth the theory goes rather than the depth arvo's numerals
reach, on D38's reasoning that a vocabulary fixed by mathematics cannot be got wrong in a way that
later needs undoing. `Combine<Op>` is dropped for `Magma<Op>`, the exact name for a set with a binary
operation and no law claimed, with laws as separate markers so a structure is a magma plus the laws it
satisfies. D47's sketch-and-bench obligation attaches to implementations, which are claims about arvo,
not to declarations, which are not. (D75.)

## What does not change

`UFixed<13, 3, Warm>` reads as itself. `Uint<13>` reads as itself. `Bits<13, Hot>` reads as itself.
The composition is what the aliases expand to and stays internal to them, per D48 and D31, and the
relationship is the one D40 already established for `Rect` over `Orthotope` and D52 made the default
documented path.

What does change for an existing consumer is behaviour, not spelling: the presets are redefined, so
`Hot` stops truncating toward zero on divide and `Warm`, `Cold` and `Precise` stop truncating at all.

## Sketch obligations before any of this is implemented

Neither prior sketch validates the shape as it now stands, both predating the three contracts. The
following are open and gate the source changelist rather than the doc changelist.

1. The spine resolves. `Numeral`, `Policy`, `Lowering` and `Number` with all ten axes, a composition
   reaching a concrete carrier, and a function generic over a numeral threading the bound through its
   own generic code.
2. The quantisation triple and pair resolve with `Direction` as a subtrait of `Resolution`, and the
   refusal is real: `ReduceModulo` at a midpoint position must fail to compile.
3. The faithfulness derivation produces the same refusal the law sketch produced, for the four cases
   it tested and the three it could not.
4. The macro-expanded integrality table works at the scale of the width range, and the derived family
   markers resolve through it.
5. The fallibility projection type-checks as a generic associated type bounded on `notko::ConstTry`,
   with `Just<T>` and `Outcome<T, _>` both satisfying it.
6. The meta-newtypes compose at these positions. Both prior sketches used `i32` and bare primitives
   throughout, deliberately, which leaves E4 unanswered: whether `Exponent`, `Width` and their
   siblings sit cleanly where the probes put plain integers.

Nothing here is a bench question. The compile-time cost of the per-width and per-exponent impl tables
is, and belongs in `mock/benches/` per `bench-and-sketch-discipline.md`.
