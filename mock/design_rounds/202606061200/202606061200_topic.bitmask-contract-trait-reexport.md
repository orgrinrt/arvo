# Re-export the bit-contract traits through arvo-bitmask

`BitMatrix<W, C>` and `Mask<W>` are arvo-bitmask's public chassis types,
generic over a row word `W`. The bound on `W` is
`BitSequence + BitAccess + BitLogic + Copy + Default`, where the three
contract traits are declared in `arvo-bits-contracts` (L0.5). A consumer
that names a `BitMatrix<W, C>` field, or writes a function generic over
the row word, must spell that same bound. Today the contract traits are
reachable only by depending on `arvo-bits-contracts` directly: arvo-bitmask
re-exports the chassis types (`Mask`, `BitMatrix`, `cap_size`, `NodeId`,
`SetBitsIter`) but not the traits that bound them.

That gap forces a downstream consumer to reach past the L2 layer it is
meant to consume. A pipeline engine that carries its adjacency row word as
a generic-but-concrete-per-impl associated type (so the row width tracks a
capacity instead of being hardcoded) needs `W: BitSequence + BitAccess +
BitLogic + Copy + Default` on that associated type. It already consumes
arvo-bitmask for `BitMatrix` / `Mask` / `cap_size`; making it also depend on
arvo-bits-contracts to name the bound splits the dependency story across two
layers for one coherent need.

## The change

arvo-bitmask re-exports `BitSequence`, `BitAccess`, and `BitLogic` from
`arvo-bits-contracts`. The traits then resolve through the same L2 layer
that ships the chassis they bound. This is the bit-storage analogue of how
the chassis types already surface: the bound travels with the type it
bounds.

No behaviour change, no new code, no new trait. arvo-bitmask already imports
all three (`matrix.rs`, `mask.rs`); the re-export only widens what the crate
root re-publishes.

## Rationale (why L2, not a direct L0.5 consumer dep)

The layering intent is that L3+ consumers reach the bit contracts through the
L2 storage crate, not by reaching down to L0.5. arvo-bits-contracts is the
declaration home (orphan-rule correct: the traits live with the lowest layer
that defines them). arvo-bitmask is the layer a graph/engine consumer already
pulls in. Re-exporting keeps the consumer's dependency surface at L2 for the
whole `BitMatrix<W, C>` story: the type, its constructors, and the bound on
its row word.

## Non-goals

- No change to `BitMatrix` / `Mask` / `propagate_dirty` signatures.
- No new trait, no widening of any existing trait's surface.
- Does not address a capacity-generic row word (`Dim<N> -> Bits<{N}>`),
  which walls on arvo's per-concrete-N container projection and is a
  separate, larger arvo-bitmask effort (array-of-words row representation).
  This round only makes the existing bound nameable from L2.
