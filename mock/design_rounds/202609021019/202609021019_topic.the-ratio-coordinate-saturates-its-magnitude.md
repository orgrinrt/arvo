# Topic: the ratio coordinate saturates its magnitude instead of dropping it

**Date:** 2026-09-02
**Phase:** TOPIC
**Scope:** `mock/crates/arvo-format/DESIGN.md.tmpl`, `mock/crates/arvo-format/src/apply.rs`

## Current state

`Fraction::of` normalises a negative denominator by moving the sign to the numerator, and sends two
families of input somewhere else:

```rust
} else if den == i64::MIN || num == i64::MIN {
    Self { num, den: 1 }
}
```

Its rustdoc gives the reason: those pairs "would need a magnitude one past what the type carries",
so neither the sign nor the magnitude survives, "and they are the only inputs on which this is lossy
at all". A test pins both, so this is declared rather than hidden.

**The reason is false on the larger part of the family it fires on.** `of(i64::MIN, -2)` is exactly
`2^62` over one: both operands are even, the shared factor of two cancels inside the type, and the
exact form was there the whole time. Measured over the whole matrix at eight widths, the shipped rule
throws away an exact answer that exists on `2^(W-1) + 2^(W-2) - 2` pairs. That closed form reproduces
the exhaustive counts at three, four, eight and sixteen bits exactly, so reading it at sixty-four is
arithmetic rather than extrapolation: `13835058055282163710` pairs.

**And it changes the sign.** `of(3, i64::MIN)` names a tiny negative and answers a positive three.
`of(i64::MIN, -7)` names a large positive and answers a large negative. `2^W + 2^(W-1) - 2` pairs come
back with the wrong sign, which at sixty-four is `27670116110564327422`. The sign is what
`Exact::between` reads to decide which slot a position sits on, so this is not a precision matter.

The evidence, its controls and the two instruments are in
`mock/research/sketches/202609021019_the-fraction-decision/`.

## The phase repair does not transfer, and that is measured rather than assumed

`Phase::of` reached the same wall and got past it by dropping the normalisation entirely: it holds
the pair as it was written, and `Format::ADMITTED` refuses the one denominator that names no position.
The reasoning was that the invariant had no buyer, because divisibility and the quotient are both
independent of the denominator's sign and nothing else read it.

`Fraction` has a buyer. `Exact::between` splits the ratio with `div_euclid` and `rem_euclid` and
stores the remainder over the denominator it was handed, and `rem_euclid` is non-negative whatever
the sign of the divisor, so a negative denominator stores a remainder that reads as negative. The
`[0, 1)` reading is what lets the six rounding modes be stated once rather than once per sign, and
`round_slot` compares `2 * num` against `den` directly.

Measured: `4477` of `4801` negative-denominator pairs store a remainder outside `[0, 1)`. The control
is the other side of the same sweep, where all `4704` positive-denominator pairs stay inside. Holding
the pair costs the invariant on `4900` of `9604` swept pairs while losing nothing, which is exactly
the trade the phase could make and this coordinate cannot.

So the invariant stays, and the question is only what the constructor does on the pairs where holding
it is not free.

## The constructor is an adaptation, and the crate already names what it should do

The ratified factoring says arithmetic on a format is an exact operation in the ambient domain
composed with a named total adaptation onto the representable set, and that the adaptation is a
first-class object with its own laws. `Fraction::of` is one: the exact operation is a ratio in the
ambient rationals, the representable set is the pairs with a positive denominator inside the type,
and the constructor is the map between them.

Read that way the shipped rule is an adaptation with no name and no law. It is not rounding, it is
not saturation, it is not wrapping, and it is not the identity anywhere near the region it applies to.
`adapt` one file over has two named regions and both are stated as laws.

The same two regions state this map:

| Region | What happens | When it applies |
|---|---|---|
| Exact normalisation | the sign moves to the numerator and the shared power of two cancels | an exact form exists inside the type |
| Magnitude saturation | the magnitude pins to the largest the type carries | it does not |

Saturation is the crate's own word for pinning to a bound the declaration carries, and
`complete_slot` already does it to a slot that leaves the range. This does it to a magnitude that
leaves the width, which is the same act one coordinate down.

## The rule, and what it holds

```rust
if den > 0                       -> (num, den)
if den == 0                      -> ZERO
if num != MIN and den != MIN     -> (-num, -den)
if num == 0                      -> ZERO
if num == MIN and den == MIN     -> (1, 1)
let k = the trailing zeros of whichever operand is not MIN
if k > 0                         -> (-(num >> k), -(den >> k))
if den == MIN                    -> (-num, MAX)
otherwise                        -> (MAX, -den)
```

Four properties, asserted over the whole matrix at widths three, four, five, six, seven, eight,
twelve and sixteen, with representability decided by exhaustive search up to eight bits and by a
derived family above it that agrees with the search at every width where both run:

- the denominator is positive;
- the sign of the answer is the sign of the named ratio;
- the answer is exact wherever an exact one exists in the width;
- where none exists, the relative error is at most `1 / MAX`, and the bound is attained rather than
  slack.

The residue is `2^63` pairs, those whose other operand is odd, and on those the answer is off by a
relative `1 / i64::MAX`. The shipped rule is off by up to `2^63` on a family half again as large, in
the wrong direction, with the sign gone.

**It costs nothing on the path anything walks.** The first branch is unchanged, every branch is const
and folds where the pair is written, and the two that were added run only where the shipped rule was
already taking its own branch. Nothing here is a check: there is no refusal, no panic, no verdict, and
one lowered path per const-known pair.

## Why not the three alternatives

**Keeping it.** Legitimate on its face, and it fails on its own terms rather than on taste: the
rustdoc justifies the branch with a claim about representability that is false on two fifths of it.
Keeping the behaviour means keeping that sentence or replacing it with one that admits the constructor
discards answers it could have given.

**Reading the two families as `ZERO`.** The answer for a zero denominator, which names no position.
These name one exactly. Over the sweep it scores a relative error of `1`, the whole of the value, on
the family where the true ratio is large.

**Widening the pair.** An `i128` numerator over a `u64` denominator makes every input exact. It also
puts a `__divti3` call inside `Exact::between` on every position that is not on the grid, to serve
`2^63` of `2^128` inputs, and it does not stop there: the remainder `Exact` stores would then be wider
than the coordinate the rest of the crate is written in. Accuracy is not bought with performance here,
and the rule above is the arm that is both.

## Two sentences in the design describe a constructor that was deleted

Found while reading the design for what it says about the ratio coordinates, and both are in this
round's scope because they sit in the paragraph that has to move.

`DESIGN.md.tmpl` says `Phase` "carries the pair, its constructors cannot produce a zero denominator,
and the condition is a property of the type rather than a sentence asking for one". `Phase::of`
produces a zero denominator on request, and the crate depends on it doing so: the compile-fail
doctest on `Format::ADMITTED` writes `Phase::of(1, 0)` and the refusal is the obligation's, not the
constructor's. The sentence describes the constructor the phase round replaced, and the half about
the condition being a property of the type is true of a different mechanism than the one it names.

The paragraph after it says a negative denominator "moves its sign to the numerator and keeps the
magnitude" and that "two pairs stay whole-numbered". It sits under the phase paragraph and reads as
being about the phase. `Phase::of(3, -7)` returns three over minus seven. The sentence is true of
`Fraction` alone, and is about to stop being true of that too.

Both landed in the commit that made the phase hold its pair, so the design edit that round declared
went in beside two paragraphs describing what it replaced.

## Two facts about the reader, which this round also carries

`Fraction`'s invariant exists for one reader, so what that reader does with it is the same question
rather than an adjacent one. Both of these are `i64` arithmetic where the neighbouring `round_slot`
is `i128`, and both are reachable from a `Fraction` the constructor is happy to build.

`Exact::is_tie` compares `self.part.num * 2` with `self.part.den`. The stored remainder can be up to
one below the denominator, so the doubling leaves `i64` on `233` of the swept remainders. In a debug
build that is an overflow panic inside a function whose whole contract is to return a verdict, in a
crate whose design says it "stays total" precisely so the panic is the caller's decision. In a release
build it wraps, and the wrapped value cannot equal a positive denominator, so the answer is right by
accident. `round_slot` makes the identical comparison four lines away in `i128`.

`Exact::between` adds the euclidean carry to the slot index in `i64`. `4637` of the swept combinations
leave the type. That one is not a carrier mistake: `Exact` stores a `Slot`, `Slot` stores an `i64`,
and a carry past the end has nowhere to go inside the coordinate. `round_slot` widens to `i128` on the
way out, so the map deliberately admits a slot one past the type after `Exact` has been built and
cannot admit one while it is being built. **This round does not answer it.** It is catalogued as a
test asserting the intended behaviour and left red, because deciding what a carry past the coordinate
means is a question about the slot coordinate rather than about the ratio, and answering it inside
this round would be the undeclared design change the phase round's topic named.

## Changes proposed

State the constructor as an adaptation with two regions in the design, replacing the paragraph that
says two pairs stay whole-numbered, and correct the two phase sentences beside it to describe the
constructor the crate has.

Then implement the rule, widen `is_tie` to the carrier its neighbour already uses, and pin all of it:
the four properties over a matrix that includes both `i64::MIN` families and both parities of the
other operand, the two pairs the old behaviour was pinned at, the exactly representable pairs it was
losing, and the slot carry as a catalogued red.
