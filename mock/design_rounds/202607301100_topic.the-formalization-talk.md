## How arvo works now, formalised from source

Recorded at op's instruction, because the walk had started borrowing shapes from SystemC and MATLAB
instead of deriving from the one already here. Everything below is read from source on this branch,
with `file:line` where it is load-bearing. This is the set the formalization is measured against.

### What a numeric type is today

`UFixed<const I: IBits, const F: FBits, S: Strategy = Warm>` at `arvo/src/ufixed.rs:35` is
`#[repr(transparent)]` over `Bits<{ ufixed_bits(I, F) }, S>`, carrying a where-clause
`S: BitsContainerFor<{ ufixed_bits(I, F) }, Unsigned>`. `IFixed` is the same shape over
`{ 1 + I + F }` bits with `Signed`.

So the type itself carries exactly three things: two const meta-newtypes for the radix split, and one
strategy marker. Everything else is projected out of those by traits. That is the whole surface, and
it is worth stating plainly, because the formalization has been discussed as though arvo currently has
a wide parameter list. It does not. It has a narrow one and a deep projection behind it.

### The six mechanisms arvo already uses

These are the conventions the new axes have to arrive inside. Each is shipped, not proposed.

**An axis is a sealed marker trait with ZST implementors.** `Strategy` (`arvo-strategy/src/lib.rs:95`,
with `Hot` / `Warm` / `Cold` / `Precise`), `Signedness` (`:183`, `Unsigned` / `Signed`),
`OverflowPolicy` (`axes.rs:41`, `Wrapping` / `Saturating`), `ContainerWidth` (`axes.rs:77`, `Min` /
`DoubleLogical`), `StorageLayout` (`axes.rs:114`, `Dense` / `Bitpacked`). Every one is a
`pub const trait`, sealed, with `ConstParamTy`-deriving zero-sized implementors.

**A preset is a marker that projects its axes as associated types.** `HasAxes` at `axes.rs:159`
declares `type Overflow: OverflowPolicy`, `type Width: ContainerWidth`, `type Layout: StorageLayout`,
and the four strategy markers implement it with the table at `axes.rs:153` through `:165`. This is
worth dwelling on: **"the strategy markers are presets over axes" is not a finding of this round, it
is a shipped mechanism with a documented table.** What the round adds is more axes, not the idea.

**A carrier is an associated type on a const trait keyed by a marker and a const.**
`BitsContainerFor<const N: u16, Sign: Signedness>` projects `type T`. Absence of an impl at a
(strategy, width) pair is how a combination is refused, carrying a
`#[diagnostic::on_unimplemented]` note that names the alternative.

**Two markers combine through a table trait, and the mismatch is warned rather than refused.**
`Resolve<Other: Strategy> { type Out: Strategy }` at `lib.rs:210`, sixteen macro-generated impls,
resolving to the higher `RANK` so `Precise > Cold > Warm > Hot`. Alongside it `CrossStrategyOp<S1, S2>`
at `cross_strategy.rs:49` is implemented only for same-strategy pairs, so bounding on it at an op site
surfaces a diagnostic when the strategies differ. The module doc states the discipline outright: the
substrate cannot refuse the op, but it can warn when resolution shifts overflow policy, container
width, or storage layout.

**A mathematical fact is carried by the presence or absence of an impl.** `Identity<Additive>` for
`UFixed` at `ufixed.rs:82` is unconditional, because zero is representable at every width.
`Identity<Multiplicative>` at `:96` carries the extra bound
`Picker: OneRepresentable<{ tag_one_representable(I.raw()) }>`, and no impl exists at the tag a purely
fractional type maps to, so naming `IDENTITY` for `UFixed<0, F, S>` is a trait-resolution error rather
than a wrong value. The comment at `:90` records why in full.

**Operations dispatch at the (marker, width) key, never on the container.** `UArith<const N: u16>` at
`arith.rs:42` has supertraits `[const] BitsContainerFor<N, Unsigned> + HasAxes`, and declares `u_add`,
`u_sub`, `u_mul`, `u_div`, plus `u_mul_fixed<const FRAC>` and `u_div_fixed<const FRAC>`.

### The scale is already in the source, as a hardcoded shift

`u_mul_fixed`'s own doc at `arith.rs:69` states it: "the product of two `FRAC`-scaled values is
`2^{2*FRAC}`-scaled, so it is shifted right by `FRAC` to return to `FRAC` scale". `fixed_scale.rs`
exists to carry that shift into turbofish position. So arvo already knows a fixed-point value has a
scale, already knows the scale is `2^-F`, and already hardcodes it as a shift amount at every multiply
and divide. A1 is therefore not "should arvo have a scale". It is "does the scale that is already
there become a projection like every other axis, or stay a hardcoded shift".

### Four findings that fall out of reading it

**The proposed axis set silently deletes an axis arvo already ships.** `202607300400`'s table lists
number system, format, underflow, signedness, rounding, overflow, growth, container. `StorageLayout`
(`Dense` / `Bitpacked`) appears nowhere in it. That axis is `Cold`'s entire identity, and
`arvo-toolbox-not-policer.md` states "Cold storage is not optional. It is the reason arvo exists" and
"Bitpacking is the common case for the substrate's primary downstream, not the edge case". Adopting
the proposed set as written would drop it by omission.

**`ContainerWidth` and the proposal's `Growth` are the same axis under two names.** `Min` versus
`DoubleLogical` is described as container width, but its documented meaning at `axes.rs:90` is that "a
single add / sub / mul of two values within their logical range cannot overflow the container", which
is a statement about intermediate results. That is growth. The carrier width is the consequence, not
the axis. This is why D34 (`202607291800`) had to prise the two apart by necessity to work out what
`Warm` means above 64 bits: they were never separated in the first place.

**The source's own recorded path forward is blocked by a feature the workspace has since forbidden.**
`axes.rs:20` promises "a follow-up round will refactor those impls to dispatch via the axis traits,
allowing future experimentation with mixed axes (saturating bitpacked, wrapping double-logical with
bitpacked, etc.)", and `arith.rs:38` names the blocker: axis-only dispatch waits on "Rust trait
specialisation". Specialization is forbidden (D1 of `202607282100`, and `unstable-features.md`'s
forbidden table). So the plan as recorded cannot execute. The replacement is already proven in this
round: `sketches/202607300600_law-markers-derived-over-composition/` conditions a blanket impl on a
type-level tuple and needs no specialization at all. **This round is the follow-up `axes.rs`
anticipated, arriving with a different mechanism than the one the source was waiting for.**

**One workspace rule is cited in source and in D52 to reach opposite conclusions.** `axes.rs:25` says
"Per the `arvo-toolbox-not-policer` workspace rule, the public surface is intentionally narrow: the
four markers stay as the consumer interface. The axis decomposition is internal." D52
(`202607300400`) cites the same rule for the opposite: "sealing the composition would be arvo choosing
which combinations a consumer may want." D52 is op's and newer, so it governs, but the source comment
inverts under it and has to be rewritten rather than left standing.

### What this settles about the walk

S1 as I posed it (SystemC against MATLAB) is not a live fork for arvo, and posing it that way was the
borrowing op objected to. Arvo's answer is already on the page: **policy lives in the type, carried by
a preset marker, projected to axes by a `HasAxes`-shaped trait, dispatched at the (marker, width) key,
reconciled by `Resolve`, and warned about by `CrossStrategyOp`.** Nothing in the formalization needs
to move policy anywhere. What it needs to do is widen the axis list and make the projection carry the
dispatch, which is what `axes.rs` already said the next round would do.

That leaves a real fork, and it is the one op named rather than the one I asked: **where does the line
fall between `Bits` and a mathematical contract above it.** `Bits<N, S, Sign>` is storage: which
carrier, how wide, how packed. The axes that answer storage questions (`ContainerWidth`,
`StorageLayout`, the container projection) are its business. The axes that answer mathematical
questions (format, scale, underflow, rounding, overflow, membership, laws) are not obviously its
business at all, and today they have no home other than the strategy marker and the `UFixed` wrapper.

### The downsides of hanging every axis on the strategy marker

Op leaned toward widening `HasAxes` and adding no contract, and asked whether that carries downsides.
It does. Two are structural and neither is visible from the option as I stated it, which was my fault
for stating it flatly.

**Floats cannot reach a strategy marker, so D50 becomes inexpressible.** `FastFloat<F: Ieee>` at
`float.rs:32` and `StrictFloat<F: Ieee>` at `:41` take one parameter, the IEEE width, and no strategy.
`markers.rs:60` states the reason as design rather than oversight: "These do not carry a `Strategy`
marker. Float precision is defined by the IEEE width, not by fixed-point container rules." So an axis
hung on the strategy marker is an axis no float can have. D50 (`202607300400`) decided the format
concept unifies fixed point and float as one thing at different exponent functions. If underflow and
the exponent function live on `Strategy`, there is no contract a float and a fixed-point value both
implement, and the unification the round exists to build cannot be written down. Underflow is the
sharpest case, because it is the axis FLX, FLT and FTZ differ on, and those are float formats.

**Two of the axes are not performance choices, so putting them on a performance preset is a category
error.** `Hot` / `Warm` / `Cold` / `Precise` mean one thing: where a consumer sits on the precision
against throughput trade. Rounding, overflow, growth, storage layout and container width are all
answers to that question, which is why widening `HasAxes` for them is right. Scale and underflow are
not. A scale of `1/(2^F - 1)` is what the number *means*, and it is orthogonal to how fast the
consumer wants it; `Warm` cannot also mean "my denominator is Mersenne" without the marker naming two
unrelated things. This is the same conflation D34 (`202607291800`) had to unpick when it found `Warm`
silently stopped meaning anything above 64 bits, and it would be reintroduced deliberately.

Two further consequences, both real but tractable.

**The `Resolve` table is closed-world and hand-written, and D52 opens it.** `lib.rs:215` generates
sixteen impls by macro, one per ordered pair of the four markers, resolving to the higher `RANK`. That
is fine for a sealed set of four. D52 says compositions are public and bindable by anyone, so a
consumer marker would arrive with no `Resolve` row against any existing marker, and every
cross-strategy op involving it fails to resolve. The fix is to resolve axis by axis and compose the
results rather than look up a marker pair, which is strictly better anyway, but it is work this option
hides rather than avoids.

**The marker family stops being dissolvable.** `202607300400` recorded that `IntegerLike` /
`FractionLike` / `FloatLike` / `BoolLike` become derivable from the format, which turns C5 from a
placement question into a question of whether they exist at all. With no format contract there is
nothing to derive them from, so they survive as hand-maintained markers and C5 closes the other way.

**What survives of the instinct.** The instinct is right and the downsides do not touch it. The axes
divide cleanly in two, and only one half has a problem:

| Axis | Kind | Home |
|---|---|---|
| rounding, overflow, growth, storage layout, container width | the precision against throughput trade | the strategy marker, via a widened `HasAxes` |
| scale, underflow, the exponent function | which values exist at all | a format contract both fixed point and float implement |

So the answer is not to pick between the two options. It is to widen `HasAxes` for the five policy
axes, exactly as op said, and to put the two format axes where a float can also reach them, which D50
requires independently of anything in this walk.

### Op's reading is right, and it goes further than stated

Op's answer to the downsides: give floats the strategy rather than routing around them, because
declaring intent is worth something even where it has no immediate effect, because `Ieee` is not the
only spec for floats, and because the lowering *result* is unchanged while the *surrounding* lowering
is exactly what the strategy decides. Checked against source, that is correct, my objection to it was
wrong, and the argument reaches one step past where op left it.

**My objection was wrong on its own terms.** I claimed `FastFloat<Binary32, Cold>` and its siblings
mean nothing. Each has a real reading. `Cold` is bitpacked minimum storage, and a column of
nineteen-bit floats is exactly the exact-width case arvo exists for; the ML formats (bf16, fp8, tf32)
are the field already doing this at non-standard widths. `Warm` is a doubled container, which for a
float means computing binary32 operations in binary64 and narrowing on store, the x87 eighty-bit
intermediate and the naive-accumulation fix, both real. `Precise` is saturating, and fp8 E4M3 has no
infinities and saturates by specification, so a saturating float is a shipped hardware format rather
than a hypothetical. The axis instances differ per format (`Wrap` is meaningless for a float, and
`ToInfinity` is meaningless for a fixed-point value), but an axis whose instance set varies by format
is the mechanism already in use, not a problem: which instances exist is which impls exist.

**The float strategy axis already exists. It is spelled as two types.** `FastFloat<F: Ieee>` at
`float.rs:32` documents itself as "Operations on `FastFloat<F>` may be reassociated, may use
reciprocal approximation, and do not guarantee NaN propagation. LLVM fast-math flags apply to
arithmetic through this type." `StrictFloat<F: Ieee>` at `:41` documents "Bit-exact, NaN-propagating,
order-preserving." Both are `#[repr(transparent)]` over the same `F`.

Identical representation, different arithmetic policy, different emitted instructions. That is the
same structure as `Warm` against `Precise`, which `lib.rs:135` describes as "Container is 2x the
logical width (same physical layout as Warm). Arithmetic is saturating." Arvo spells that distinction
as one type with two markers. It spells the float one as two types with no marker. The inconsistency
is the finding, and unifying it deletes a special case rather than adding a mechanism.

**The four existing markers already span the float trade, so no new markers are needed.** `Hot` is
throughput first, which for a float is fast-math. `Precise` is correctness first, which for a float is
strict IEEE. `Warm` is widened intermediates. `Cold` is packed minimum storage. So
`FastFloat<F>` is `Float<F, Hot>` and `StrictFloat<F>` is `Float<F, Precise>`, and the two wrappers
become semantic aliases of the kind D52 already made the documented default path, exactly as `Rect`
aliases rank 2 of `Orthotope` under D40.

**And fast-math turns out to be a law, which the round already has machinery for.** The permission
`FastFloat`'s doc grants first is reassociation. Reassociation is associativity. IEEE floating-point
addition is *not* associative, which is precisely why fast-math is unsafe in every compiler that
offers it. So under D51 the fast float has an `AddAssoc` impl and the strict float does not, and the
fold that silently reassociates is refused for `StrictFloat` by the same mechanism that refuses it for
signed saturating fixed point.

Better still, D16 (`202607290200`) already classifies it correctly without being asked. Associativity
for a fast float is not derived from anything; it is a promise by the consumer that their data will
not expose the difference, and its falsehood returns a wrong answer rather than a slow one. That is
D16's definition of an asserted property, which D16 says is an `unsafe impl` carrying a stated
contract. So fast-math stops being a safe type whose doc comment mentions a caveat and becomes an
unsafe promise visible at the declaration. No other numeric library states fast-math that honestly,
and arvo gets it as a consequence rather than as a feature.

**On the lowering question, op's statement is exactly right.** Every one of these lowers to the same
primitive, because `repr(transparent)` guarantees it and because arvo has never claimed otherwise.
What the strategy changes is the surrounding lowering: which instruction sequence, which fast-math
flags on the emitted `fadd`, whether FTZ and DAZ are set, whether the loop may be reassociated or
vectorised, whether the column is packed. For floats that is the whole of the difference, since both
wrappers already hold an identical `f32`. Declaring the intent has value even where nothing acts on it
yet, and notko's profile machinery is the stated mechanism for acting on it later.

### Calls: the type unifies, and the axes split on identity against policy

**D53. There is one numeric type, and every family arvo ships today becomes a semantic alias over a
composition of it.** Decision (op, 2026-07-30). The format parameter is what differentiates, which is
D50 carried to its conclusion. `UFixed`, `IFixed`, `FastFloat` and `StrictFloat` stop being four
types and become four names for four compositions, the relationship D52 already made the documented
default path and D40 already established for `Rect` over `Orthotope`. D48 and D31 are satisfied
without special handling, because an alias preserves a spelling exactly. The cost accepted with it is
wordier rustc diagnostics, since the expanded composition is what an error prints.

**D54. The axes split in two, on whether they say what the number is or how it is computed.**
Decision (op, 2026-07-30). Op's statement of the principle: what the number *is* does not change
through strategies. So the strategy marker carries only the compute policy, and a separate contract
carries the identity. This corrects the direction the walk was heading in three messages earlier,
where every axis was going onto one widened `HasAxes`.

| Axis | Side | Reason |
|---|---|---|
| scale | identity | `1/(2^F - 1)` is what the value means, not how fast it is |
| exponent function | identity | fixed against floating is what the number is |
| underflow | identity | which values exist at the bottom of the range |
| signedness | identity | whether negatives are in the set |
| rounding | policy | what happens to a result too precise for the set |
| overflow | policy | what happens to a result too large for the set |
| growth | policy | how much room an intermediate gets |
| storage layout | policy | dense against bitpacked |
| container width | policy | which carrier holds it |

The test that separates the two columns, stated so later additions sort themselves: change the axis
and ask whether the set of representable values changed. If it did, the axis is identity. If the same
values are still representable and only the arithmetic differs, it is policy. Every row above sorts
cleanly under it, and it is the same test that makes `Warm` against `Precise` one type at two
markers, since both hold identically the same values.

Both contracts are renamed as part of this: the identity one is new and needs a name, and `HasAxes`
is named after its mechanism rather than its subject, so it wants one too. That naming is the next
call.

### The num-systems objection does not hold, and the relationship is a derivation

I argued `Numeral` reads badly beside `arvo-num-systems`. Op's reply: would the number systems not use
the very same contracts rather than reinvent a parallel, and do they not derive from the numeral
identity. Both halves are right and the objection is withdrawn.

**They are one dependency, not two hierarchies.** D39 (`202607291900`) already fixed the direction:
`arvo-num-systems` depends on `arvo-algebra-contracts` and defines each set through its algebraic
structure, so ℝ is a complete ordered field and ℤ is an integral domain. Nothing in that declares a
representation. The numeral contract declares the representation. Membership is then the question of
which set a given representation's values fall in, which is a statement *about* a numeral, computed
from it.

**And A1's research already showed the computation is mechanical.** `202607291900`'s inhabitance table
was written by hand, one row per arvo type. With the scale carried in the numeral it is a handful of
blanket impls instead: fractional bits zero and unsigned gives ℕ, fractional bits zero and signed
gives ℤ, a power-of-two denominator with no bias gives the dyadic rationals ℤ[1/2], any other exact
denominator gives ℚ, and a floating numeral adds the specials that fall outside every set. So the
membership markers are derived properties in D16's sense, safe impls that cannot lie, rather than the
asserted per-type claims the table currently amounts to.

**The near-identical words are the point rather than the problem.** In mathematics a numeral system is
the notation (positional, binary, Roman) and a number system is the set (ℕ, ℤ, ℚ). The two terms sound
alike because one is how you write members of the other, which is exactly the relationship arvo would
be encoding. Two words that sound related, for two things that are related, in a fixed direction, is
accurate naming rather than a collision. My objection reduced to the words being similar, which is not
an argument once the relationship is stated.

### Calls: the two contracts, the type, and the naming convention

**D55. The identity contract is `Numeral`, the policy contract is `Policy`, and the type is
`Number<N: Numeral, P: Policy>`.** Decision (op, 2026-07-30). `Numeral` is the representation, the
notation a value is written in. `Policy` is the umbrella over the axes arvo already names in the
`*Policy` form, so it reads as the bundle rather than as a bare abstraction. `Number` is the value
itself, which is why it is the type and not either contract. The three read as one sentence at a call
site: a number, in this numeral, under this policy.

**D56. No gratuitous abbreviation. Full, legible, recognisable words for every member.** Decision (op,
2026-07-30). An abbreviation is acceptable only where it is the stable form nearly everyone in the
field already recognises. Coining short forms of words that were already a sensible length is not
arvo's style and has never been. This applies to the whole round's output, not to one draft: the
sketches and every option I put in this talk carried `Under`, `Total`, `Over`, `Round`, `Grow` and
`fexp`, and all six are the failure the rule names.

Applied, with the reason each short form was wrong:

| Was | Is | Why |
|---|---|---|
| `Under` | `Underflow` | the full word is the axis, and it is four characters longer |
| `Over` | `Overflow` | same, and `Over` reads as a comparison |
| `Round` | `Rounding` | `Round` is a verb; the axis is the discipline, not the act |
| `Grow` | `Growth` | same, a verb standing in for a noun |
| `Total` | `LogicalWidth` | `Total` names no quantity; arvo already ships this concept as `BitPresentation::LOGICAL_WIDTH` at `markers.rs:41` and the existing word is the right one |
| `fexp` | `canonical_exponent` | Flocq's own prose calls it the canonical exponent; `fexp` is its Coq identifier, not the concept's name |

`Scale`, `Sign` and `Layout` stay as they are, being complete words already, and `Sign` additionally
matches the parameter name shipped on `Bits<N, S, Sign>`.

**A consequence to settle rather than assume.** `ContainerWidth` (`Min` / `DoubleLogical`) and the
proposed `Growth` axis are the same axis under two names, as recorded above: `axes.rs:90` documents
`DoubleLogical` by what it does for intermediate results, which is growth, and the carrier width is
the consequence. If that reading holds, `Policy` carries four axes and not five. Marked as the agent's
derivation and put to op rather than applied, because collapsing two shipped names into one is a
change to the axis set rather than a rename.

### The concept has a standard name, and it is the quantum

Op could not place a name and said "exponent" felt wrong for what is being shortened. The instinct was
correct. The concept has a settled term in the standards and in the numerics literature, and it is not
"exponent".

**Quantum.** ISO/IEC JTC1 SC22 WG14 N1781 states it plainly: "The term quantum refers to the value of
a unit in the last place of the coefficient. Thus, the quantum of x is `b^q`." The companion paper
N1724 gives the exponent form: "The term quantum exponent refers to `q = e - p`". Muller and
colleagues' *Handbook of Floating-Point Arithmetic*, the standard reference for this field, uses
"quantum exponent (`q = e - p + 1`)" alongside "integer significand". The term is IEEE 754's own for
decimal formats, where `quantize` is a named operation, and it carries into the formal-verification
literature: Martin-Dorel's thesis on the formal verification of arithmetic has "Definition 2.3
(Integral significand, quantum exponent)", from the same tradition Flocq belongs to.

So the vocabulary resolves in both directions at once:

| Concept | Standard name | What arvo was calling it |
|---|---|---|
| the value of one unit in the last place | **quantum** | "scale", from MATLAB's slope |
| the exponent form of that value, `q` where quantum is `b^q` | **quantum exponent** | `fexp`, from Flocq's Coq identifier |

**This renames A1's axis, and states its question far better.** The A1 fork was put as "can a format
carry a scale whose denominator is `2^F - 1`". In the field's own words it is: **must the quantum be a
power of the radix, or may it be an arbitrary exact rational?** A binary fixed-point format has
quantum `2^-F`, which is a power of the radix. UNORM has quantum `1/(2^F - 1)`, which is not. That is
the whole of A1, said in one sentence, using the term the standards already use, and it makes clear
that the question is about the quantum rather than about some novel parameter.

It also improves on "scale" for a reason worth recording: "scale" is MATLAB's word inside the
slope-and-bias framing, so it drags a bias along with it and invites the reader to expect the affine
form. "Quantum" names only the unit, which is the thing actually under discussion.

One precision the term forces, and it is a useful one. The quantum of a floating value varies with its
magnitude, which is exactly why the numeral projects a function rather than a constant. For a
fixed-point numeral the function is constant and the quantum is one value. For a floating numeral it
is `b^(e - precision)` adjusted by the underflow policy. Same contract, both cases, which is the
unification D50 asked for stated in the standard's vocabulary rather than in Coq's.

**D57. The exponent method moves onto the `Quantum` bound, where it is `exponent`.** Decision (op,
2026-07-30). Every single-word candidate was ambiguous while the method hung on `Numeral`, because a
numeral has more than one exponent in play and the name had to carry the disambiguation on its own.
Scoping it to the quantum removes the ambiguity structurally: the receiver is the quantum, so its
exponent can only be the quantum exponent, and no adjective is needed. This is the type system doing
the work a longer name was being asked to do, which is the house idiom.

The relocation also settles the `exp` question that had blocked shortening. `exp` was rejected because
a numerics crate will ship an actual exponential, but a quantum is not a number and has no
exponential, so `Quantum::exp()` could not be misread. It is spelled `exponent` in full anyway, on
D56's rule that an abbreviation has to be the form nearly everyone already recognises, and `exp` reads
as the exponential function to most readers of numeric code regardless of what it is scoped to. Three
characters is not worth the second of doubt.

```rust
pub const trait Quantum {
    /// The `q` such that this quantum is `radix^q`, for a value whose
    /// magnitude exponent is `magnitude`.
    fn exponent(magnitude: Exponent) -> Exponent;
}

pub const trait Numeral {
    type Quantum: Quantum;
    type Underflow: Underflow;
    type Sign: Signedness;
}
```

The value side follows the same path rather than growing a name of its own. Flocq's `cexp x =
fexp (mag x)` is the composition, and in Rust it stays the composition:
`<N::Quantum>::exponent(value.logb())`, where `logb` is IEEE 754's own name for the magnitude
exponent. So the two Flocq identifiers that started this thread both disappear into structure: `fexp`
is `Quantum::exponent`, and `cexp` is what you get by handing it a value's `logb`.

### Correction: `ContainerWidth` and `Growth` are two axes, not one

D56 flagged, as the agent's derivation, that `ContainerWidth` and the proposed `Growth` looked like one
axis under two names. Checking it against `Cold` disproves it, and `Cold` is the case that makes the
distinction visible.

`lib.rs:128` documents `Cold` as "Minimum container, bitpacked for sub-byte values. Arithmetic widens
to 2x before operating, narrows back on store." So `Cold` stores at minimum width and computes at
double width. Its container width and its intermediate width are different numbers, deliberately.
`arith.rs:13` confirms the widen-narrow path is designed and not yet built ("Cross-op widen-narrow
logic lands with the Cold widening table in a later round"), which is why reading only the shipped
arithmetic makes the two look identical.

Laid out across the four markers, arvo already demonstrates three distinct arrangements:

| Marker | Stored width | Where the intermediate headroom comes from |
|---|---|---|
| `Hot` | minimum | nowhere, the op wraps in the stored width |
| `Warm` | double logical | the stored container is already wide enough |
| `Cold` | minimum | widening into registers for the op, narrowing on store |
| `Precise` | double logical | the stored container, as with `Warm` |

So the two axes answer different questions, and the sharper way to say it is by what changes when you
move each one:

**`Growth` changes the answer.** `FullPrecision` against `KeepLsb` against `KeepMsb` return different
numbers for the same operands, because they keep different parts of an exact product. It is a semantic
axis and it belongs in the law derivation, since multiplication's associativity depends on it.

**`ContainerWidth` changes only the cost.** Storing double-wide against storing minimum and widening
per operation give the same answer by construction; they differ in bytes held and instructions issued.
It is a lowering axis with no semantic consequence.

Both are policy under D54, since neither changes which values are representable. But only one of them
can affect a law, and that distinction matters for D51's derivation: conditioning a law marker on
`ContainerWidth` would be conditioning it on something that cannot change the result.

### Calls: three contracts, and the domain read op asked for

**D58. There are three contracts: `Numeral`, `Policy`, `Container`.** Decision (op, 2026-07-30). The
three storage and compute concerns (stored width, where widening happens, packing layout) come out of
`Policy` and become a `Container` contract of their own. `Numeral` is the mathematical
representation, `Policy` is what happens to a result that does not land in it, `Container` is how it
is physically held and computed.

**The domain read op asked for: yes, and it is the split IEEE 754 itself makes.** This is not a
convenient decomposition invented here, it is the standard's own structure, arrived at independently.

IEEE 754 distinguishes a **format** (which values are representable) from its **encoding** (how those
values are laid out in bits), and keeps **rounding-direction attributes** separate from both, as
properties governing operations rather than properties of a format. Three concerns, the same three.

The proof case is decimal. IEEE 754 specifies *two* distinct encodings for the same decimal formats,
binary integer decimal and densely packed decimal. `decimal64` under either encoding represents
exactly the same set of values; the bit layouts are unrelated. That is one numeral with two
containers, which is precisely the separation D58 draws, demonstrated by a standard rather than argued
from first principles.

Arvo's own vocabulary already agrees. `BitsContainerFor` is named for the container, the round has
been calling it "the container projection" throughout, and `ContainerWidth` is already an axis name.
`Container` is the house word for this concern and needs no introduction.

So the three read as one sentence with three clauses. A number is written in a numeral, computed under
a policy, and held in a container.

**Two things to watch, stated because they are the seams rather than objections.**

*`Layout` may be a property of a collection rather than of a number.* `axes.rs:109` defines
`StorageLayout` as "How multiple values pack in column storage", which is a statement about an array,
not about a value. A single bitpacked number in isolation is a strange object. Against that, packed
access is a load-and-mask sequence per value, so it genuinely does change how one value is read and
written. The concern is dual, and whether it sits on `Container` or on whatever holds many of them is
worth deciding rather than inheriting.

*`Policy` constrains `Container` and the constraint has to be expressible.* A growth of
`FullPrecision` requires a carrier wide enough to hold the exact product; a container that cannot
serve it makes the combination unsatisfiable. That is an ordinary type-level constraint between two
parameters rather than a flaw, but it is the one place the three contracts are not independent, and it
is where the combination has to be able to refuse.

**D59. The type is `Number<N: Numeral, S>` where `S` supplies both non-identity contracts.**
Decision (op, 2026-07-30). Reasoning: the strategy is exactly the set of choices that move while the
numeral identity stays fixed, so the strategy marker and the pair of non-identity contracts are the
same thing rather than one selecting the other. That makes the bundle trait of the alternative
unnecessary: `S` implements both contracts directly, and axes read with no projection hop.

```rust
pub struct Number<N: Numeral, S>(..)
where S: Policy + Container;

pub type UFixed<const I, const F, S = Warm>
    = Number<Fixed<I, F, Unsigned>, S>;
```

The consumer surface is unchanged, which D48 and D31 require, and the raw composition stays two
parameters rather than three. D52's arbitrary combinations arrive as a marker implementing both
contracts, which a consumer writes directly or composes.

**And this exposes a naming problem in the third contract.** Under D59 the marker *implements* the
contract, so the trait name has to read correctly as a predicate on `Warm`. "Warm is a container" is
false: `Container` already means something specific and different in arvo, namely the primitive that
holds the bits, which `BitsContainerFor` projects as `type T`. The third contract does not name that
primitive; it decides which one to use, how values pack, and where widening happens. Naming a
selector after the thing it selects is the error, and it only became visible once D59 made the marker
the implementor.

**D60. The third contract is `Lowering`.** Decision (op, 2026-07-30). It holds stored width, where
widening happens, and packing layout: the three choices that change what is emitted and what is held
without changing what is computed. It is the only candidate covering all three members, since stored
width and packing are layout questions while the widening site is a codegen one, and it restates op's
own reading of what a strategy does: the lowering result is unchanged, the surrounding lowering is
exactly what moves.

### The spine, as settled

```rust
pub const trait Numeral {          // what the number IS
    type Quantum:    Quantum;
    type Underflow:  Underflow;
    type Sign:       Signedness;
}

pub const trait Policy {           // what happens to a result that does not fit
    type Rounding: Rounding;
    type Overflow: OverflowPolicy;
    type Growth:   Growth;
}

pub const trait Lowering {         // what it costs to hold and compute
    type StoredWidth: StoredWidth;
    type Widening:    Widening;

pub struct Number<N: Numeral, S>(..) where S: Policy + Lowering;

```

Nine axes across three contracts, one type, one knob, and the public spelling unchanged. What remains
is which instances each axis has, which is where the walk started before the shape had to be settled
underneath it.

### The forks, in the order they have to be answered

**S1. Do the landing policies live in the type, or on the operation?** The two industrial systems that
have thought hardest about this disagree outright. SystemC (IEEE 1666) puts them in the type:
`sc_fixed<W, I, Q, O, N>` carries quantization and overflow as type parameters, so the policy travels
with the value. MATLAB splits them: `numerictype` carries width, scaling and signedness, while a
separate `fimath` object carries `RoundingMethod`, `OverflowAction`, `ProductMode` and `SumMode`, so
the policy travels with the arithmetic rather than the value. This is the fork with the widest blast
radius in the whole round, because it decides whether two values that round differently can be added
at all, how wide every signature is, and whether a preset is a property of a number or of a context.

**S2. Is there a composition type, or is the composition a set of bounds?** A struct
(`Whatever<A, B, C, ...>`) that the semantic names alias, against keeping `UFixed` / `IFixed` and the
float wrappers as the concrete types with the axes reaching them as trait bounds and associated types.
D52 says compositions are public and bindable, which needs them nameable, but nameable is satisfied by
either shape.

**S3. If a composition type exists: its name, its parameter list, its order, its defaults.** `Num` is
mine and carries no thought. The order matters because it is what a consumer reads.

**S4. Is signedness part of the format or a sibling axis?** Mathematically the format is the set of
representable values, and whether negatives are in that set is a statement about the set, which argues
signedness belongs inside the format. Structurally it sits on `Bits` today as its own marker, and the
law sketch conditions on the `(Overflow, Signedness)` pair, which reads more naturally if signedness is
a sibling. Both readings are defensible and they produce different types.

**S5. Does the container stay a projection, or become a parameter?** Today `BitsContainerFor` projects
(strategy, width, sign) onto a carrier, so the container is derived and invisible. Growth changes what
the projection has to serve, since an intermediate needs a wider carrier than the value.

**S6. Where does underflow sit?** Nested inside the floating format as the sketch has it, or a
top-level axis that fixed formats ignore. Nesting keeps fixed types from carrying a meaningless
parameter; a top-level axis keeps the axis list flat and uniform.

The per-axis instance questions follow these, in the order already tabled: the scale (A1), the format
decomposition (A2), rounding (A3), overflow (A4), growth (A5), then the set as a whole (A6).

**D61. The quantum is an adjustment times a power of the radix, and the adjustment is `Unit` for
every ordinary numeral.** Decision (op, 2026-07-30). `Quantum` projects `type Adjustment` alongside
`fn exponent`, so the quantum of a value is `Adjustment * radix^exponent`. This is MATLAB's
decomposition, where the slope is a slope adjustment factor in `[1, 2)` times a power of two, and it
is what lets one contract cover both a binary fixed-point quantum of `2^-F` and UNORM's `1/(2^F - 1)`,
which decomposes as `(256/255) * 2^-8` at eight bits.

The decisive property is that membership stops being asserted. Dyadic inhabitance is the structural
condition `Adjustment = Unit`, written as an associated-type equality bound, so it is a safe impl that
cannot lie in D16's sense. `FullRange` cannot satisfy that bound and therefore gets no `Dyadic` impl,
without anything having to gatekeep the outcome. Every earlier draft of this axis needed an
`unsafe impl` asserting mathematics per marker, which was op's objection to the whole first framing.

This also answers D36 with a mechanism rather than a restatement, and gives `202607291900`'s
hand-written inhabitance table a derivation: the rows follow from the adjustment, the sign, and
whether the fractional part is empty.

### Underflow does not belong beside overflow, and D54's own test says why

Op asked whether underflow, having been in the wrong place, is in the right place if it goes where
overflow is. It is not, and the two are less symmetric than their names suggest.

D54's test: change the axis, and ask whether the set of representable values changed.

**Overflow does not change the set.** `Wrap` against `Saturate` differ in what happens to a result
that does not fit. Exactly the same numbers are representable either way. It is policy.

**Underflow does change the set,** and this is Flocq's entire reason for treating FLX, FLT and FTZ as
three distinct formats rather than as one format with three behaviours. Under `Gradual` the subnormals
are representable and precision degrades toward zero. Under `Flushed` the exponent jumps at the
threshold, so nothing below it is representable except zero itself. Under `Unbounded` there is no
floor at all and the values continue downward forever at constant precision. Three different sets of
numbers, from one parameter.

So the names mislead. Overflow is about the behaviour at a boundary; underflow is about where the
boundary is, which is a statement about the set. They are not two ends of one axis, and putting them
together would place an identity question on the policy contract, the exact conflation D54 exists to
prevent.

Op's earlier reading was therefore right: underflow is identity, and it stays on that side. The only
open part is whether it sits beside the quantum or inside it, which is a narrower question than the
one it looked like.

### What `Constant` and `Varying` were, and why they do not survive checking

Op asked what these are, having never agreed to them. They are mine, they appeared in a preview
without being put as a question, and that is the same failure as `Num<>` earlier in this talk. Worse,
checking them properly shows the shape is wrong on its own terms.

**What they were for.** `Quantum` declares `fn exponent(magnitude) -> Exponent`. A function from a
magnitude to an exponent either uses its argument or ignores it, and there is no third possibility.
Ignoring it means the spacing between representable values is the same everywhere, which is what fixed
point *is*. Using it means the spacing scales with the value, which is what floating point *is*. So I
reached for two types naming those two behaviours. Flocq makes the same cut, with FIX on one side and
FLX, FLT and FTZ on the other.

I named them `Constant` and `Varying` rather than the obvious `Fixed` and `Floating` for a reason I
failed to state: `arvo/src/aliases.rs` already declares `pub type Fixed<I, F, S>`, which D31 keeps, so
the obvious name is taken.

**Why they do not survive.** A fixed-point numeral's quantum exponent is `-F`, derived from its
fractional bit count. Writing that as a type parameter means writing `Constant<{ -F }>`, a const
expression in type position, computed from a generic parameter. That is precisely the shape D1 and D2
of `202607282100` forbade and the shape `generic_const_exprs` was banned for. So the two types cannot
be projected from a numeral without reintroducing the feature this stack spent a round removing.

**And checking that reveals the simpler shape.** The `202607300500` sketch already recorded the
relevant fact and I did not carry it forward: the exponent function applies to a *value's* magnitude,
so it lives in value position and never reaches type position. Inside a function body, `-F` is
ordinary arithmetic on a const parameter and needs no feature at all. So the numeral can simply answer
the exponent question itself, and the two intermediate types have nothing left to do.

```rust
pub const trait Quantum {
    type Adjustment: Adjustment;
    fn exponent(magnitude: Exponent) -> Exponent;
}

// the numeral IS its own quantum. no intermediate type,
// no const expression in type position, nothing invented.
const impl<const I: IBits, const F: FBits, Sign> Quantum
    for Fixed<I, F, Sign>
{
    type Adjustment = Unit;
    fn exponent(_magnitude: Exponent) -> Exponent { -F }   // value position
}
```

Under that shape the fixed-against-floating distinction is carried by which numeral implements the
function and how, rather than by a pair of marker types standing between them. `Constant` and
`Varying` were an extra layer answering a question the numeral was already positioned to answer.

### No, and the mathematics names the missing piece

Op asked whether a numeral being its own quantum makes sense mathematically. It does not, and pushing
on why produces a better shape than either option I put.

**Why it fails.** A numeral is a representation scheme: it says which values can be written. A quantum
is a value, the spacing of the lattice that scheme generates. The representable set of a fixed-point
numeral is the cyclic group generated by its quantum, intersected with a range, so the quantum is a
distinguished *element* of the structure rather than the structure. `Fixed<I, F, Sign>: Quantum`
asserts that a scheme is a spacing, which is the same category error as "Warm is a container", and it
would have shipped for the same reason: convenience at the point where the type checker stopped
complaining.

**What the mathematics actually distinguishes.** The two behaviours of the exponent function have
standard names, and they are not "constant" and "varying". A scheme whose representable values are
evenly spaced is a **uniform** quantiser. A scheme whose spacing grows with magnitude is a
**logarithmic** one, floating point being the piecewise case that steps by powers of the radix at each
binade. Uniform against logarithmic quantisation is the textbook division in signal processing, and it
is exactly the division Flocq draws between FIX and the FLX family.

So the missing piece is not a quantum type, it is the **quantisation law**: which rule this numeral
uses to decide the spacing. The numeral has one. It is not one.

**And the law needs no parameters of its own, which removes the hazard.** The sketch's `Underflow`
already showed the pattern: `U::fexp(e, prec, emin)` takes the numeral's parameters as *values*. A
quantisation law can do the same, so `Uniform` and `Logarithmic<U>` carry no const generics computed
from anything, and `type Quantum = Uniform` is a plain type with no expression in type position. The
GCE hazard that killed `Constant<{ -F }>` does not arise, because nothing is computed to name the
type.

```rust
pub const trait Quantum {
    type Adjustment: Adjustment;
    /// The `q` for a value at `magnitude`, given the numeral's own parameters.
    fn exponent(magnitude: Exponent, of: Parameters) -> Exponent;
}

/// Evenly spaced: the spacing ignores magnitude.
pub struct Uniform;
/// Spacing grows with magnitude, stepping at each binade.
pub struct Logarithmic<U: Underflow>;

pub const trait Numeral {
    type Quantum: Quantum;
    type Sign:    Signedness;
}
```

`Uniform` and `Logarithmic` are free names: `Fixed` is taken by the alias D31 keeps, but neither of
these collides with anything in the workspace, and both say what they mean to a reader who has met
quantisation anywhere else.

This also answers A2 without a separate decision. Only a logarithmic quantiser has a bottom to fall
off, so `Underflow` nests inside `Logarithmic` and a uniform numeral has no place to put one and needs
none.

### What becomes of the quantum, and whether that is sound

Op asked whether the quantum survives as a concept under a `Quantisation` member, or folds into it,
and whether folding would be sound. The answer is that it survives, that only the type-level use of
the word moves, and that this is the arrangement that makes the pair correct rather than a compromise.

**A quantum is a quantity; a quantisation is a rule.** In signal processing this is the standard
relation and it has been for decades: a uniform quantiser is a map, and its step size is a parameter
of that map. For a non-uniform quantiser the step size varies with the input, so it is a function of
position rather than a constant, and the quantiser is still the map. Arvo's case is exactly that
sentence: `Uniform` and `Logarithmic<U>` are maps, and the quantum is the step size the map yields at
a given magnitude.

So nothing folds. The quantum is `Adjustment * radix^exponent(magnitude, parameters)`, it is computed
from the quantisation, and it is a *value*. What goes away is a *type* named `Quantum`, and it should
go away, because a quantum was never a type. That is the same correction as the previous two: a
numeral is not a spacing, a marker is not a container, and a rule is not the quantity it produces.

The quantum stays nameable in the two places it is needed. As a decomposition, its adjustment is the
member that carries dyadic inhabitance, so the derivation is unchanged. As a value, it is what a
consumer asks for when doing error analysis, and it has an obvious accessor: the quantum at a value is
the resolution there, which for a uniform numeral is the smallest positive representable value and for
a logarithmic one is the spacing within that binade.

```rust
impl<N: Numeral, S> Number<N, S> {
    /// The quantum at this value: the spacing of representable
    /// values here. IEEE 754 defines it as the value of a unit in
    /// the last place.
    pub const fn quantum(self) -> Self { .. }
}
```

**D62. The member is `type Quantisation`, and the quantum stays as the quantity it yields.** Decision
(op, 2026-07-30, on the domain answer above; overturnable in a word if the reasoning does not hold).
`Quantisation` is the law, `Uniform` and `Logarithmic<U>` are its implementors, `Adjustment` and the
exponent function sit on it, and the quantum is what it produces rather than something the type system
names.

### A1. The scale question, whether a format can have a denominator of `2^F - 1`

This row is not carried forward from any earlier file. It surfaced from reading
`sketches/202607300500_format-as-exponent-function/01_format_trait.rs` against D36, and it says a
question two files record as settled is not settled.

**The problem.** The sketched `Format` is Flocq's exponent function and nothing else: `Fixed<F>`
returns `-F`, `Floating<PREC, EMIN, U>` defers to an underflow policy, and a value is representable
when it equals an integer significand times the radix raised to that exponent. Every representable
value is therefore `m * 2^e`.

UNORM is not of that form. Its value is `k / (2^F - 1)`, and at `F = 8` the denominator is 255, which
is not a power of two and never will be. No exponent function produces it. So the format as sketched
cannot express UNORM at all.

That matters because two prior files record the question as answered. D36 (`202607291800`) decided
"arvo takes UNORM, or something to the same effect" on the reasoning that the encoding is a property
the type does not currently carry, and `202607300400` lists D36 under "answered rather than reopened
by this proposal", stating the encoding is a format parameter. It is a format parameter only if the
format has a parameter that can hold it, and the one sketched does not. The answer was recorded
against a mechanism that had not been checked.

**What the field calls the general form.** MATLAB's Fixed-Point Designer and Simulink both define
fixed point by a two-part scaling rather than a radix point. Quoted from the Simulink scaling page:
`real-world value = (slope * integer) + bias`, where `slope = slope adjustment factor * 2^fixed
exponent`, the adjustment factor is "a number greater than or equal to 1 and less than 2", the slope
"must be a positive number", and the bias "can be any number". The same page states the special case
directly: "A binary-point scaled number is equal to a slope-bias scaled number where the bias is 0 and
the slope adjustment factor is 1." The stated reason for the general form is "when you need non power
of two scaling, if your hardware uses a custom format, or when your real-world data doesn't start at
zero".

UNORM is exactly a slope-bias number. Its slope is `1 / (2^F - 1)`, which at `F = 8` decomposes as
`(256 / 255) * 2^-8`, with an adjustment factor of `256/255` sitting inside the required `[1, 2)`, and
a bias of zero. It is not an exotic encoding; it is one value of a parameter the field has had for
decades and arvo has never named.

So this is the same shape of gap `202607300200` already found for rounding. The axis exists in
industry, it is absent from arvo, and its absence was invisible because nothing in arvo could state
it. Flocq does not cover it either: `generic_format` fixes the scale at a power of the radix, so
adopting a general scale is going past the formalization rather than instantiating it, which is what
op asked for.

**What adopting a scale buys, beyond UNORM.** Three things, all of which the round already wants.

Number-system membership stops being a hand-written table and becomes derivable. `202607291900`'s
finding lists per-type inhabitance by hand: `UFixed<I, 0>` is natural, `UFixed<I, F>` with `F > 0` is
dyadic, and so on. With a scale in the type, the rule is one line: the values inhabit the dyadic
rationals when the adjustment factor is one, and the rationals otherwise. UNORM's row falls out rather
than being appended.

The MV-chain gets a home. `202607300300` identified `UFixed<0, F>` under the UNORM encoding as a
finite Łukasiewicz chain, the standard MV-algebra, and under arvo's own encoding as a half-open
interval with no name in the literature. With a scale parameter, the difference between the two is one
parameter value, and the structural consequence (one is an MV-chain, the other is not) is derived by
D51's mechanism rather than declared for a bespoke type.

D36 gets a mechanism rather than a restatement. `UFixed<0, F>` having no multiplicative identity
becomes a fact about a scale rather than a fact about the type, and `OneRepresentable` starts asking
the right question.

**What a bias costs, stated because it is the deciding factor.** Slope and bias are not equally
cheap. A scale is closed under addition: `S*qa + S*qb = S*(qa + qb)`, so the sum is a value of the
same format and every law the round derives survives untouched. A bias is not: `(S*qa + B) + (S*qb +
B) = S*(qa + qb) + 2B`, which carries twice the bias and is therefore a value of a different format.
Addition on a biased format does not close, so `Semigroup<Add>` would not resolve for it.

Read one way that is a defect. Read the other way it is the design working: the absence of an impl
carries a mathematical fact, exactly as `OneRepresentable`'s absence does, and a consumer who folds a
biased format learns at compile time that the operation they wrote is not the operation they meant.
The cost is real either way, because a type that cannot be folded is a type most of layer 1 does not
reach.

**Reframed, after op's steer on the first attempt.** The fork was first put with the scale carried as
integer associated consts (`SCALE_NUM`, `SCALE_DEN`). That framing was wrong on its own terms, and
wrong in a way this round has already corrected once elsewhere. D2 of `202607282100` moved the
container tag off exactly this shape: "the tag, currently an integer computed by a function, is a
closed vocabulary of slots and becomes an enum of types". Putting the scale back into integers repeats
the mistake the same round removed.

The shipped idiom is uniform and the fork has to be stated inside it. A policy axis is a ZST marker;
the marker implements a `pub const trait` that projects its answer as an associated type; the answer
is a type rather than a number; and a fact about the combination is carried by the presence or absence
of an impl rather than by a value anyone reads. `Capacity` does this (`type Array<T>`, with `Dim<N>`
as the marker and the capacity itself a type). `BitsContainerFor` does this (`type T`, the container).
`Underflow` in the format sketch already does this (`Unbounded` / `Gradual` / `Flushed` as markers).
`OneRepresentable` does the absence half. The law sketch does both at once, conditioning a blanket
impl on a type-level pair.

Const generics stay where they are already the right form. `Fixed<F>` keeps a const `F` because a
fractional-bit count is a number the consumer writes; what becomes typestate is the *choice of
scaling*, which is a policy and not a number. The two are different questions and the first framing
collapsed them.

Where a type-level number is genuinely needed, `Dim<N>` is the shipped type-form of one, and going
from a const parameter to it is the per-width impl table D2 already settled and
`arvo-compile-time-last.md` already licenses.

**Second steer, and the finding it produced.** Op's objection to the reframed fork: the typestate
proof was sitting in comments rather than in machinery. That is correct and it is the sharper of the
two objections, because it is not a presentation problem. Writing `impl Dyadic for Radix {}` by hand
is an **asserted** property in D16's sense (`202607290200`), and D16 says an asserted property is an
`unsafe impl` carrying a contract, because nothing stops it being wrong. Every option as first stated
had membership asserted per marker, which means the crate would ship a pile of unchecked promises
about mathematics and call it typestate.

What is wanted is a **derived** property in D16's sense: computed from the thing itself, unable to
lie, a plain safe impl. So the question stops being "which marker vocabulary" and becomes "what
representation makes the properties structural".

The answer is to carry the scale as **the constructor that built it** rather than as a number or as an
opaque pair. A denominator written `Pow2<F>` cannot be anything other than a power of two, because
that is what the constructor means; there is no inhabitant of the type that violates it. So
`impl PowerOfTwo for Pow2<F>` is not a claim about an opaque value, it is a restatement of the
constructor's definition, and everything conditioned on it is derived. A denominator written
`Mersenne<F>` is `2^F - 1` by construction, odd and greater than one for every `F > 1`, so it is
provably not a power of two and correctly gets no such impl. A consumer's arbitrary `Exact<N>` proves
nothing, gets no structural marker, and therefore gets no membership, which is the honest outcome and
requires no gatekeeping to arrange.

Everything downstream then stops being written per type. Membership, one-representability, the
MV-chain, and additive closure all become blanket impls conditioned on structural markers, so adding a
scale means adding a constructor and the facts that follow from its definition, and adding nothing
else. That is the same mechanism the law sketch already proved out, conditioning a blanket impl on a
type-level pair, applied one layer down.

This also settles the bias question rather than trading it off. Under a constructor-typed scheme a
bias parameter defaulting to `Zero` costs nothing when unused, and the additive-closure fact stops
being a caveat in prose: `AddClosed` is implemented for a zero bias and not otherwise, so folding a
biased format fails to resolve on its own merits.

### A3. The rounding instance set, and where `Stochastic` can live

**The unnamed axis is not merely unnamed, it is inconsistent.** `202607300200` found arvo has no
rounding axis and concluded every narrowing carries an implicit behaviour a consumer cannot select.
Checking which behaviour shows the situation is sharper than that.

Signed fixed-point multiply is `a.wrapping_mul(b) >> FRAC` at `arith_macros.rs:148`, an arithmetic
shift right, which on a negative value rounds toward negative infinity. The crate says so itself at
`arith_macros.rs:400`: "matches the `>> FRAC` floor". Signed fixed-point divide documents the opposite
at `arith.rs:84`: "Truncates toward zero."

So one type today rounds toward negative infinity when multiplied and toward zero when divided. Both
are defensible choices; having both, unnamed, in one type is not one. Nothing is wrong with either
line of code, which is the point: with no axis to name, the two sites were written independently and
nothing could notice they disagreed.

**The instance set the field uses is two-dimensional, not a flat list.** IEEE 754 defines five
rounding-direction attributes: `roundTiesToEven`, `roundTiesToAway`, `roundTowardPositive`,
`roundTowardNegative`, `roundTowardZero`. SystemC defines seven quantization modes: `SC_RND`,
`SC_RND_ZERO`, `SC_RND_MIN_INF`, `SC_RND_INF`, `SC_RND_CONV`, `SC_TRN`, `SC_TRN_ZERO`. Reading them
together, both lists are points in the same two-axis space: a value either goes to the nearest
representable value, in which case a tie rule is needed, or it goes in a fixed direction, in which
case no tie can occur because the direction already decides.

That decomposition covers all twelve named modes across the two standards from two small
vocabularies, and it is what op asked for when asking for the highest granularity available rather
than the precedent's list.

**Correction, on op's push toward a uniform structure.** I said the twelve modes fall into two
dimensions. That was imprecise, and working it out properly gives a better shape than the one I
proposed.

An exact result falls somewhere in the interval between two representable values, and a rounding is a
rule for choosing an endpoint. There are exactly three positions it can fall in: below the midpoint,
exactly on it, above it. A rounding is therefore a *triple*, one choice per position, over a small
vocabulary of choices.

| Mode | below midpoint | at midpoint | above midpoint |
|---|---|---|---|
| toward negative infinity | down | down | down |
| toward positive infinity | up | up | up |
| toward zero | toward zero | toward zero | toward zero |
| away from zero | away | away | away |
| nearest, ties to even | down | to even | up |
| nearest, ties away | down | away | up |
| nearest, ties to zero | down | toward zero | up |
| nearest, ties to positive | down | up | up |
| nearest, ties to negative | down | down | up |

Every mode in IEEE 754 and every mode in SystemC is a row of that table, and the table has no gaps
that need naming: a mode is any triple. My `Directed<D>` against `Nearest<Tie>` split is precisely the
set of rows that are monotone, dressed up as if it were the structure rather than a constraint on it.

**On the hlist specifically.** `notko-hlist` is for heterogeneous lists of *variable* length, which is
what makes it the right shape for an access set or a command set. A rounding is a fixed triple, and
the shipped pattern for conditioning on a fixed tuple of axes is the type-level tuple the law sketch
already uses, `(Overflow, Signedness): AddAssoc`. So the uniform structure op is reaching for is real
and worth having; the machinery it wants is the tuple rather than the list.

**And the nonsense is better refused by a law than by the type.** The triple admits combinations no
standard names, such as choosing up below the midpoint and down above it, which is a rounding that
moves values away from the nearest representable one. Those are not meaningless, they are
non-monotone, and monotonicity is a property this round already derives rather than forbids. So the
uniform triple can be the structure, with `Monotone` derived over it, and the bad points exist but
cannot be used anywhere monotonicity is required.

**On const enums, which op asked about.** They would work. `adt_const_params` is enabled at
`arvo-strategy/src/lib.rs:2` and sits in the ALLOWED tier of `unstable-features.md`, a fieldless enum
derives `ConstParamTy` without difficulty, and arvo already derives it on every axis marker it ships.
So `Rounding<{Direction::Down}, {Direction::ToEven}, {Direction::Up}>` is expressible today.

It is still the wrong choice here, for one reason that outweighs the rest: **a const enum cannot be
blanket-implemented over.** With marker types, monotonicity for every nearest-mode is a single impl:

```rust
impl<T: Direction> Monotone for (TowardNegative, T, TowardPositive) {}
```

One line covering ties-to-even, ties-away, ties-to-zero, ties-to-positive, ties-to-negative, and any
tie rule a consumer adds later. With const enum values there is no `T` to quantify over, so the same
coverage is one impl per variant, written out, and re-written whenever a variant is added. That is
precisely the enumeration D51 exists to replace, and it would appear in the axis where the law
derivation matters most.

The benefit op identified is real but already available. Arvo's markers carry their integer form
alongside their type form: `OverflowPolicy` declares `const DISCRIMINANT: u16` at `axes.rs:43` and
every implementor sets it. So value-position work gets the integer, and type-position work gets the
blanket impl, without choosing between them. Adding an enum would trade the second for something the
first already provides.

**D63. Rounding is a triple over `Direction`, with the members named as IEEE names them.** Decision
(op, 2026-07-30). `Choice` was a placeholder; the field's own word is direction, since IEEE 754 calls
these its rounding-direction attributes. Members are spelled in full per D56.

```rust
pub const trait Direction {
    const DISCRIMINANT: u16;
}

pub struct TowardNegative;   pub struct TowardPositive;
pub struct TowardZero;       pub struct AwayFromZero;
pub struct ToEven;           pub struct ToOdd;

pub const trait Rounding {
    type Below: Direction;
    type At:    Direction;
    type Above: Direction;
}

// IEEE 754's five and SystemC's seven are all rows
pub type TiesToEven     = (TowardNegative, ToEven,       TowardPositive);
pub type TiesToAway     = (TowardNegative, AwayFromZero, TowardPositive);
pub type TowardZeroMode = (TowardZero,     TowardZero,   TowardZero);

// and the law is one blanket impl, not a table
impl<T: Direction> Monotone for (TowardNegative, T, TowardPositive) {}
```

### A4. The overflow instance set, and what `Trap` costs a signature

**Both of op's objections to the first draft hold, and the second is the load-bearing one.**

*The relation between the named rules and the recovery kinds was an invisible assertion.* Having
`Wrap` declare `type Recovery = Modular` moves the claim from the law table to the declaration; it
does not derive it. And if the entire content of `Wrap` is "I am modular", then `Wrap` and `Modular`
are two names for one thing, with a hand-written link between them that nothing checks. That is the
smell.

The fix is the one rounding already received. A named rule becomes an **alias over a structural
space**, not a marker with a declared kind. Overflow's space is a *pair*, since an out-of-range result
is either above the representable range or below it, and a rule says what happens at each end:

| Rule | above the range | below the range |
|---|---|---|
| wrap | reduce modulo | reduce modulo |
| saturate | clamp to the bound | clamp to the bound |
| saturate to zero | substitute zero | substitute zero |
| symmetric saturate | clamp to the bound | clamp to the negated bound |
| trap | refuse | refuse |

Asymmetric rules, which no standard names, fall out as other points rather than needing invention.

**And the associativity finding becomes derived rather than tabulated.** The sketch left this open
explicitly. The primitive property is whether a recovery leaves the operation faithful, meaning still
the operation of an algebraic structure on the representable set. Modular reduction does: wrapping
addition is the group operation of `ℤ/2ⁿℤ`. Clamping, substituting and refusing all do not.

Then the whole `(Overflow, Signedness)` table is two impls:

```rust
// unsigned addition can only leave the range above, so one end is
// unreachable and the rule is truncated addition whatever it does there
impl<A: Recovery, B: Recovery> AddAssoc for ((A, B), Unsigned) {}

// signed addition reaches both ends, so neither may deviate
impl<A: Faithful, B: Faithful> AddAssoc for ((A, B), Signed) {}
```

Checked against the cases: signed saturate has neither end faithful, gets no impl, which is the
sketch's refusal now derived. Symmetric saturate likewise, confirming by construction what the sketch
confirmed by experiment. Signed trap also fails, correctly: `(127 + 1) + (-1)` refuses while
`127 + (1 - 1)` returns 127, so the two groupings genuinely disagree. Hybrid points such as clamping
above and wrapping below fail too, which the hand-written table could not have predicted because
nobody would have written the row.

**On the fallible projection.** `notko::ConstTry` is the contract, declared at
`notko/src/consttry_const_path.rs:11` with `type Output`, `type Residual`, `from_output` and `branch`.
The projection should be bounded on it, and what it selects between is which tier of notko's
fallibility ladder the operation returns: `Just<T>` for the total rules, `Outcome<T, _>` for the
refusing one. So the member is naming the operation's fallibility, and `Fallibility<T>` says that
outright where `Result<T>` said nothing and collided with std.

### Why overflow looked like it needed different primitives, and why it does not

Op asked why overflow needs a different vocabulary from rounding. Working it through: it mostly does
not, and the round already knew that. `202607300300`'s Layer 3 groups rounding, overflow and growth as
**landing policies** and states outright that this is "one shape not two subjects". I split them into
a triple and a pair without noticing I was undoing the proposal's own finding.

**The unified frame.** Both axes answer one question: an exact result is not representable, so what is
returned. The cases are distinguished by *where* the exact value falls, and there are five:

| Situation | What is available |
|---|---|
| between two representable values, under the midpoint | two neighbours to choose between |
| exactly on the midpoint | two neighbours, equidistant |
| between two, over the midpoint | two neighbours to choose between |
| past the top of the range | only a lower neighbour exists |
| past the bottom of the range | only an upper neighbour exists |

The first three are what rounding names. The last two are what overflow names. One question, five
situations.

**And the vocabularies differ only where the situations differ.** In the first three cases every rule
is a choice between two existing values, which is exactly what a direction is. In the last two, one
neighbour does not exist, so a rule has three options rather than one: take the neighbour that does
exist, which is clamping and is *still* a direction; produce something unrelated to where the value
was, which is modular reduction or substituting zero; or decline, which is trapping.

So the out-of-range vocabulary is the in-range vocabulary plus three resolutions that are only
meaningful when there is nothing to choose between. That is why clamping never needed its own name:
clamping a value above the range is `TowardNegative`, the same marker rounding already uses.

```rust
/// What is returned when an exact value is not representable.
pub const trait Resolution {}

/// The subset available when two neighbours exist, so the rule is a
/// choice between them.
pub const trait Direction: [const] Resolution {}

pub struct TowardNegative;  pub struct TowardPositive;
pub struct TowardZero;      pub struct AwayFromZero;
pub struct ToEven;          pub struct ToOdd;
// Direction and Resolution

pub struct ReduceModulo;    pub struct SubstituteZero;
pub struct Refuse;
// Resolution only: meaningless where a neighbour exists

pub const trait Landing {
    type UnderMidpoint: Direction;
    type OnMidpoint:    Direction;
    type OverMidpoint:  Direction;
    type OverRange:     Resolution;
    type UnderRange:    Resolution;
}
```

Rounding and overflow become names for the first three members and the last two, rather than two axes
with unrelated vocabularies. `Saturate` is `(TowardNegative, TowardPositive)` at the range members,
which says what saturation *is* instead of asserting it. And the meaningless combinations are not
merely discouraged: `ReduceModulo` is not a `Direction`, so it cannot be written at a midpoint
position at all.

### The name is bad because the right word is on the other contract

Op's read is that the shape is right and the name is not. Checking the field's vocabulary says why:
the correct term exists, and D62 spent it one contract too early.

In signal processing a **quantizer** is the map from an exact value onto a discrete set of
representable ones, and that map includes clipping at the ends of its range. An analogue-to-digital
converter quantizes and clips, and both are quantization. So the five-situation map, rounding and
overflow together, is a quantization in the field's own sense. SystemC narrows the word to its `Q`
parameter, covering rounding only, but the general usage is the broader one.

What D62 named `Quantisation` is not the map. It is the shape of the grid the map targets: whether
representable values are evenly spaced or spaced by powers of the radix. In the same vocabulary that
is a property *of* a quantizer, described as uniform or non-uniform, not the quantizer itself. So the
Numeral's member is holding the adjective while the Policy's axis, which is the noun, has no name and
got a metaphor.

The swap puts each word where the field puts it:

| Contract | Member | What it is | Field's word |
|---|---|---|---|
| `Numeral` | the grid of representable values, evenly spaced or not | a property of a quantizer | spacing, or uniform against logarithmic |
| `Policy` | the map from an exact value onto that grid, including at the ends | the quantizer itself | quantization |

This is a reversal of D62 and is put as one rather than applied, since D62 is op's.

### The named-mode alias sets, and whether MATLAB is a third

Op asked whether MATLAB has a distinct naming and framing. It does, and it is genuinely a third
rather than a restatement. From this round's own research at `202607300200`:

| Source | Rounding names | Overflow names |
|---|---|---|
| IEEE 754 | `roundTiesToEven`, `roundTiesToAway`, `roundTowardPositive`, `roundTowardNegative`, `roundTowardZero` | not an axis; overflow raises an exception and delivers an infinity |
| SystemC (IEEE 1666) | `SC_RND`, `SC_RND_ZERO`, `SC_RND_MIN_INF`, `SC_RND_INF`, `SC_RND_CONV`, `SC_TRN`, `SC_TRN_ZERO` | `SC_SAT`, `SC_SAT_ZERO`, `SC_SAT_SYM`, `SC_WRAP`, `SC_WRAP_SM` |
| MATLAB | `Nearest`, `Ceiling`, `Convergent`, `Zero`, `Floor`, `Round` | `Saturate`, `Wrap` |

MATLAB is distinct in a way that matters: its `Nearest` breaks ties toward positive infinity, its
`Round` breaks them away from zero, and its `Convergent` breaks them to even. Three different modes
sharing the everyday word for the concept, and none of them is what IEEE calls `roundTiesToEven`
except the third. A consumer porting from MATLAB who assumes `Nearest` means the IEEE default gets a
different answer at every tie.

AMD Vitis `ap_fixed` uses `AP_RND*` and `AP_SAT*` names that mirror SystemC's almost exactly, being
derived from it, so it is the same set under a prefix rather than a fourth vocabulary.

Op's proposal is to ship these as optional feature-gated alias sets over the uniform structure, off by
default. That fits `arvo-toolbox-not-policer.md` directly: arvo ships one structure and does not
decide which vocabulary a consumer thinks in. It also has a property worth naming, which is that the
aliases are *checkable*. Each set is a table of definitions in terms of the five members, so writing
them down states what each vendor's mode actually does, and the MATLAB tie-breaking trap above becomes
visible in the alias table rather than surprising someone at runtime.

### The concept was wrong, and the naming difficulty was the symptom

Op took `Quantisation` for the policy axis and then said none of the candidates for the Numeral member
felt right, and that the difficulty might mean the concept is wrong. It did.

**What I had been naming was a consequence, not a cause.** `Uniform` against `Logarithmic` describes
how the spacing behaves. That is an observation about the numeral, not a statement of what the numeral
*is*, which is why every candidate name was either a metaphor or an adjective looking for its noun.

**The primitive underneath.** Fixed point and floating point differ in one place: where the exponent
lives. In a fixed-point numeral the exponent is a property of the type, known without reading the
value. In a floating-point numeral the exponent is stored in the value, in its own field. Everything
else follows from that one fact:

- The exponent is in the type, so it is the same for every value, so the spacing is constant. That is
  what "uniform" was describing.
- The exponent is in the value, so it varies per value, so the spacing varies with magnitude. That is
  what "logarithmic" was describing.
- A stored exponent occupies bits, so the width divides into an exponent field and a significand.
  An implicit exponent occupies none, so the whole width is significand.
- Only a stored exponent has a range it can fall out of, which is where underflow comes from.

**And the current framing was losing real information.** `Logarithmic<PRECISION, MINIMUM, U>` takes
precision and a minimum exponent as parameters. Physically, binary32 is one sign bit, eight exponent
bits and twenty-three significand bits, and both the precision and the minimum exponent are *derived*
from the exponent field's width. So the framing was carrying two derived numbers as primitives while
the actual primitive, the size of the exponent field, appeared nowhere. IEEE defines its interchange
formats the other way round, by the field widths.

So the member is the exponent's representation, and it needs no invented word:

```rust
pub const trait Numeral {
    /// Where this numeral's exponent lives, which decides whether the
    /// spacing is constant or varies with magnitude.
    type Exponent:   ExponentForm;
    /// The quantum's departure from a pure power of the radix. `Unit`
    /// for every ordinary numeral, per D61.
    type Adjustment: Adjustment;
    type Sign:       Signedness;
}

/// The exponent is a property of the type. Fixed point.
pub struct Implicit<const EXPONENT: Exponent>;

/// The exponent is stored in the value, in a field of this width.
/// Floating point. Only a stored exponent can underflow.
pub struct Stored<const BITS: Width, U: Underflow>;
```

`Implicit<-8>` is a fixed-point numeral with a quantum of `2^-8`. `Stored<8, Gradual>` with a
twenty-four bit significand is binary32. `Implicit<-8>` with `Adjustment = FullRange<8>` is UNORM8.
Three members, each a statement about the representation rather than about its consequences, and the
quantum falls out of the first two rather than being a member at all.
