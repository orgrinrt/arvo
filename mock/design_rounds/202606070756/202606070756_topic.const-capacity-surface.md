## What this round adds

A const-callable capacity surface in arvo-tensor: a new `ConstCapacity` trait,
the const analog of the existing `Capacity`, plus its `Dim<N>` impl. The
existing `Capacity` trait and every consumer of it are left untouched. This is
purely additive.

`ConstCapacity` carries the minimal surface a `const fn` needs to build and
index a fixed-capacity backing array in const context: a const `filled`
constructor and const indexed `get` / `set`. With it, a const fn generic over
`C: [const] ConstCapacity` can allocate and walk scratch arrays at compile
time, which is what compile-time DAG analysis (a const `waist_detect`, the next
round downstream) requires.

## Why a sibling trait and not an extension of `Capacity`

The existing `Capacity` cannot become a `const trait`. Its `from_fn` method
takes an `F: FnMut(USize) -> T` closure and its body calls
`core::array::from_fn`, neither of which is const-callable on the pinned
nightly. The `const_trait_impl` model requires that `impl const Trait` provide a
const body for every method, with no per-method opt-out. So making `Capacity`
const is blocked by `from_fn`, and rewriting `from_fn` to drop the closure would
break `Array::from_fn`, `Matrix::diagonal`, and the index-built algorithm
crates that depend on it.

A sibling const trait sidesteps all of that. `Capacity` keeps its `AsRef`/
`AsMut`/`from_fn` runtime surface verbatim; `ConstCapacity` adds the const
surface alongside. `Dim<N>` implements both. Consumers that need the runtime
surface bind `C: Capacity`; consumers that need the const surface bind
`C: [const] ConstCapacity`; a consumer needing both binds both (they share the
`Dim<N>` impl). This is the same additive-bridge shape arvo already uses for the
const predicate family (`ConstPartialEq` / `ConstOrd` / `ConstDefault` siblings
of the std traits, per the bridge-home rule).

This also matches the workspace directive driving the round: provide a const
version in arvo (others benefit too), make it additional rather than a rewrite,
and route the const access through an arvo contract rather than native arrays so
generic consumers do not reintroduce the `cap_size(N)` GCE surface.

## Shape

```rust
const trait ConstCapacity {
    // backing array for T at this capacity; [T; N] for Dim<N>. Copy is
    // required so the array is returnable and indexable by value in const
    // context (the const surface deals in Copy scalars: counts, bit-words).
    type Array<T: Copy>: Copy;
    const CAP: Cap;
    fn filled<T: Copy>(v: T) -> Self::Array<T>;
    fn get<T: Copy>(a: &Self::Array<T>, i: USize) -> T;
    fn set<T: Copy>(a: &mut Self::Array<T>, i: USize, v: T);
}

impl<const N: usize> const ConstCapacity for Dim<N> {
    type Array<T: Copy> = [T; N];
    const CAP: Cap = cap(N);
    fn filled<T: Copy>(v: T) -> [T; N] { [v; N] }
    fn get<T: Copy>(a: &[T; N], i: USize) -> T { a[i.0] }
    fn set<T: Copy>(a: &mut [T; N], i: USize, v: T) { a[i.0] = v; }
}
```

`ConstCapacity::Array` is a separate GAT from `Capacity::Array`, carrying the
`Copy` bound the const surface needs; for `Dim<N>` both resolve to `[T; N]`, so
a const consumer's `ConstCapacity::Array<USize>` is the same `[USize; N]` a
runtime consumer's `Capacity::Array<USize>` is. The const `get` / `set` take a
typed `USize` index and unwrap to the language-level array index inside the body
(the same array-length-grammar boundary `Array::get` / `Array::set` already
cross).

## Toolchain

Requires `#![feature(const_trait_impl)]` in arvo-tensor's lib.rs (WATCH-tier
ALLOWED per the unstable-feature sweep; already in use across arvo-bits,
arvo-bitmask, arvo-storage, and the contract crates). No other gate: the const
surface deals in `[T; N]` min-const-generics, never `cap_size(N)` in type
position, so `generic_const_exprs` does not run over it.
