# Topic: arvo takes a digest, FNV-1a below a measured length and XXH3 above it

**Date:** 2026-11-14
**Phase:** TOPIC
**Round:** `202611140014-l3t2`, job `arvo-digest`, ticket `arvo_takes_xxhash_rust_for_its_digest_and_allows_bsl_1_0`.
**Source topics:** none open on this branch.

arvo has had no digest since the canon work emptied the tree, and the consumers that hash content have
gone on spelling FNV-1a for themselves. The verdict on what to bind and what to take
(`.shared/research/2026-11-13-bind-and-take-verdict.md`, section 2.2, in clause-dev on `main`) put the
digest in arvo and recommended xxhash-rust for XXH3, and op chose it on 13 November. This round writes
the crate that shape describes and measures the one number the shape leaves open, the input length
where XXH3 overtakes FNV-1a.

## What the canon says, and where it is silent

The registry has one row that asks for a digest, `obligation::a_content_hash`: a hash of content stable
across sessions and machines, whose width the consumer names rather than inherits. Its `gap` field says
the width and the collision bound are not established, so the row asks for the stability and the named
width and nothing more. `proposal::the_old_hash_crate_returns_changed_in_slice_two` is a one-expert
proposal and binds nothing. No ruling places a digest crate in arvo, names it, or says which algorithm
it runs.

So the canon is silent on the crate's place, and this round builds on op's answer as the authority it
is, without citing it as a row. His words, verbatim, from `briefs/fixup/op-answers-35.md` on the kaski
channel: "Then I think we start with xxhash and backlog for later benching our own impls against its
using arvo and notko first party in there, so if we get some wins, we should roll our own then. But as
far as I understand, being const and no std is already a good match". The intent: arvo takes
xxhash-rust now, BSL-1.0 joins arvo's licence allow list, and a native XXH3 is benched against it later
(the next round). The options he chose among: [1] allow BSL-1.0, [2] no, use twox-hash, [3] no, arvo
or zig writes its own. He chose [1], with [3] as the measured follow-up.

## D1. The crate

`arvo-digest`, a leaf beside `arvo-bits`. It holds the digest and nothing else: two named algorithms,
the width-carrying result, and the one length-switched digest the stack reaches for when it has no
format to stay compatible with. It depends on `arvo-bits` for the one conversion the obligation asks
for, and on `xxhash-rust` with `default-features = false` and the `xxh3` and `const_xxh3` features.
`#![no_std]`, no `alloc`, no `dyn`, no `std` feature on xxhash-rust.

## D2. The result type

`Digest<const BITS: u16>` holds a digest at its algorithm's output width. The width admits a carrier
through a sealed trait on a marker, `Width<BITS>: Carrier`, so `Digest<32>`, `Digest<64>` and
`Digest<128>` exist and any other width is a compile error at the type, never a check at run time. The
raw value comes out through one declared door, `raw()`, the same shape `Bits::raw` has.

The obligation's named width is `Digest::bits::<N>()` on the 32 and 64 bit digests, a masked cast into
`arvo_bits::Bits<N>` for `N` up to the digest's own width; asking for more bits than the digest has is
refused at compile time. Low bits are kept. Both algorithms mix their output across every bit, so the
low bits of either are as good as any other choice and the cast stays the one masking `arvo-bits`
already owns.

The surface never implements or accepts `core::hash::Hash`, which feeds lengths as `usize` and so
differs between 32 and 64 bit targets (verdict 2.2). Input is explicit bytes, `&[u8]`, at the one door
where the host's byte image enters: the same declared unwrap door as `Bits::masked(u64)` and
`USize::from_host(usize)`, since arvo holds no byte-view type and a digest of the host's bytes is
exactly a function of them.

## D3. The algorithms

`Fnv1a<BITS>` at 32 and 64 bits, written here as `const fn`, with the reference offset bases and
primes. It is the digest a consumer names when its persisted values are already FNV-1a, which is what
the five spellings in hilavitkutin, kaski and muisti are.

`Xxh3<BITS>` at 64 and 128 bits through xxhash-rust. Two entry points, because one cannot be both:
`of` takes xxhash-rust's runtime path, whose SIMD is chosen by `cfg(target_feature)` at compile time,
and `of_const` takes its `const fn` path. Both return the same value for the same bytes, which a test
asserts over every length class the algorithm has.

## D4. The switched digest, and why its length is part of what it is

`Digest::<64>::of` and `Digest::<64>::of_const` digest bytes shorter than the crossover with FNV-1a and
the rest with XXH3. The rule is one rule on both paths, so a value computed at compile time equals the
value computed at run time for the same bytes. The crossover is therefore part of the digest's
definition: moving it changes what some inputs digest to, and that is a format change, so the
known-answer tests pin the lengths on both sides of it.

The crossover is measured, not assumed. A bench in arvo's harness, `digest-crossover`, times FNV-1a and
both XXH3 paths over the length sweep, with its CSV and findings committed under `mock/benches/` and a
findings note in `mock/research/`; the switch length is the first length where the runtime XXH3 path is
faster than FNV-1a with a confidence interval that excludes zero, and it stays there for every longer
length measured. The old bench (`fnv1a-vs-xxhash3_n*`) measured from 64 bytes up and found XXH3 faster
already at 64, so the sweep goes down to one byte. The bench is single-host and says so.

The 128 bit digest has no switch, because FNV-1a at 128 bits needs a 128 bit multiply per byte and
nothing in the stack asks for it.

## D5. The licence

BSL-1.0 joins `deny.toml`'s allow list. It is permissive, needs no notice in a binary, and is
compatible with MPL-2.0 and AGPL-3.0, which is the comparison op asked for before answering. kaski
already allows it.

## D6. What the round does not do

## Checks

`cargo test -p arvo-digest`: FNV-1a vectors from the reference test suite (Fowler, Noll and Vo), XXH3
vectors from xxHash's own sanity table (`tests/sanity_test_vectors.h` in the xxHash repository), each

## D7. The door where the host's bytes and words enter, in `arvo-format`

This section replaces the input and the carrier D2 records.

D2 above, as first recorded, took `&[u8]` and returned `u32`, `u64` and `u128`, and the round asked for
`arvo-digest` to join `[primitive-introductions]` so the numeric lints would skip it. The coordinator
refused that, in these words: "no, arvo-digest does not join [primitive-introductions]. arvo's own
comment there (mockspace.toml:1489-1493) says why it holds arvo-format alone: it is 'the one place the
stack's own primitives cannot be used to define themselves'. A digest defines no number, so listing it
would be an exemption, and none are kept. Instead: arvo-digest's surface and internals use arvo's types
(its words as arvo-format's carriers, its input as arvo's own byte carrier), and the one place host
bytes and host words meet those carriers is a door in arvo-format, the introducing crate, which the
xxhash-rust call goes through. Where arvo-format has no such door yet, add the minimal one on your
branch". The intent is that a digest names no host integer anywhere; the door is the vehicle. The canon
is silent on a byte or word carrier, so this rests on the coordinator's call, not on a row.

`arvo-format` has no such door, so this round adds the minimal one, in a new module `host` that touches
nothing else in the crate. `Byte` is one byte of the host's byte image and `Bytes<'a>` a borrowed run
of them, each with `of` taking the host value and `host` giving it back, the declared unwrap door the
shape `Width::bits` and `Bool::of` already have. `Bytes::split_first` walks a run without an index
type, and `Bytes::shorter_than::<N>()` compares its length against a const generic, which is the one
place a length is asked. `Word<const BITS: u32>` is a host word at 32, 64 or 128 bits, admitted through
a sealed `HostWord` on the marker `At<BITS>` so no other width exists, with `of` and `host` as the door
and, at 32 and 64 bits, the two operations FNV-1a is made of: `xor_byte`, and `wrapping_mul`, the
product reduced modulo two to the `BITS`. Each is `const fn`. Nothing more is added: XXH3's own
arithmetic stays inside xxhash-rust, whose call takes `Bytes::host` and whose result enters through
`Word::of`.

`Digest<BITS>` keeps its `u16` width parameter from verdict 2.2 and holds `Word<32>`, `Word<64>` or
`Word<128>` through `Carrier`. `arvo-digest` gains `arvo-format` as a dependency. The `arvo-format`
lane, which overhauls that crate, is told the exact signatures so it can keep or fold the module.

## D8. The door goes in `arvo-numeral`, not `arvo-format`

D7 keeps its intent and changes its vehicle. Read before writing, `arvo-format`'s summary says "There is
no machine container anywhere in this crate and you cannot reach one from here", and that "Where the
bits actually go is `arvo-placement`". A borrowed run of the host's bytes and a host word are machine
containers, so the door in `arvo-format` would put the crate against its own design. The coordinator's
reading that `[primitive-introductions]` holds `arvo-format` alone was also off: it holds `arvo-format`,
`arvo-bits` and `arvo-numeral`.

`arvo-numeral` is the introducing crate whose design is about this meeting. Its section `## Where the
host integers are named` says it "is where the containers the placement derives meet the host's
machine integers" and lists, by number, the surface the declaration covers, the doors `from_host` and
`host` on `USize` and `ISize` among them. The byte and word door joins that list as one more item, in a
new module `host` that touches nothing else in the crate. Its items, their signatures and their reasons
are the ones D7 names; only the crate changes. `arvo-digest` depends on `arvo-numeral` in place of
`arvo-format`. The coordinator was told the move and the reason, and can overturn it.
