# Topic: the const generic severed the binding, and the guard was never pinned

**Date:** 2026-09-01
**Phase:** TOPIC
**Scope:** how the objective reaches the derivation, and how the width bound is enforced
**Status:** both blockers reproduced; the first is a regression I introduced last round

## Blocker one, reproduced, and it is mine

Last round I moved `Objective` to a const generic parameter to get the branch erased at
monomorphisation. That worked and it **severed generic composition**, which I did not check.

```
error: generic parameters may not be used in const operations
   --> crates/arvo-strategy/src/tests.rs:185:28
    = help: add `#![feature(generic_const_exprs)]` to allow generic const expressions
```

A const generic argument may not depend on a generic type parameter, so
`derive_sole::<F, { S::OBJECTIVE }>()` cannot be written and a consumer generic over the strategy
cannot reach the ladder at all. Only a call site naming a concrete preset can derive anything. The
feature rustc suggests is on the forbidden list as op's call, so that route is closed.

**Every test passed because every test named a concrete preset.** `{ <Cold as Strategy>::OBJECTIVE }`
at `tests.rs:117` is the shape all of them use, so the breaking path was never entered. That is setup
that helps, in my own suite, one round after I deleted four tests for a neighbouring defect.

**And it made a shipped sentence false.** `arvo-strategy/src/lib.rs:53` says a consumer never has to
know which preset it holds. Under a const generic that is exactly what a consumer does have to know.

## The shape that fixes it, tested against the canon rather than taken on the report

The remedy offered was a type-level marker with `trait ObjectiveKind`, `Strategy::Objective` as an
associated type, and `derive_sole<F, O: ObjectiveKind>()`. **I checked it against what the binding has
to do and it holds on all three counts.**

**It composes generically**, because an associated type in a type position is not a const operation.
`derive_sole::<F, S::Objective>()` is an ordinary generic call.

**It keeps the erasure.** The arms branch on `O::OBJECTIVE`, an associated const of a generic
parameter, which is a constant after monomorphisation, so the branch folds exactly as the const
generic's did. `ruling::never_a_runtime_check_and_one_lowered_path` asks for branching erased by
monomorphisation, and this is that.

**It keeps the ladder keyed on the objective**, which is what
`ruling::the_derivation_is_a_placement_and_the_operation_set_is_an_admission_rule` states.

**And it removes an unstable feature rather than adding one.** The const generic needed
`adt_const_params`; the marker needs nothing. A remedy that subtracts from the feature set is worth
more than one that holds it constant, and that is the argument for taking this shape rather than
hunting for a cleverer one.

## Blocker two, and the finding under it is sharper than the fix

Deleting the upper-bound assertion from `checked_width` left the whole suite green. With it gone
`Signed<63>` inverts its range, `slot_count` goes negative, and `slot_in_range(0)` is false, silently,
in release.

The distinction the reviewer draws is the one to keep: **the width-recovery class is gone by
construction and the slot-range coherence class is guarded rather than constructed.** Half the claim
holds. A guard can be deleted; a construction cannot.

And `the_refusal_above_the_bound_is_recorded_where_it_can_be_reproduced` asserted
`MAX_DECLARED_WIDTH == 62`, a constant against the literal its own definition sets, which is the
tautology in its purest form and is mine from last round.

## So the answer is not a better guard, it is no guard

**The impls exist only for the widths the design admits.** `Slots` is implemented by macro for 1
through 62, and `Signed<63>` simply has no impl, so every use of it is a trait-bound error rather than
a const-eval panic in a function somebody can delete.

That is `harness-the-type-system`: make the illegal state unrepresentable rather than checked.

**And the list cannot be widened by accident.** An impl at 63 computes `(1i64 << 63) - 1` in its own
body, which overflows at the definition site, so adding 63 to the macro's list fails to compile there
rather than opening a hole at a use site. The thing that would have to go wrong is no longer a
deletion.

`#[diagnostic::on_unimplemented]` carries the message the assertion used to, so the error still names
the bound and the reason, and that attribute is stable rather than a feature.

**This also removes the non-blocking finding for free.** `checked_width` was `pub` and took a runtime
`u32`, so calling it at runtime in release panicked, which under I15 is a runtime check on the public
surface. It stops existing.

## What the tests have to become

**A generic consumer that must compile.** The pin for blocker one is not a compile-fail case, because
after the fix the generic consumer compiles. It is a test that exists permanently and stops compiling
if anyone re-severs the binding, which is the assertion.

**A compile-fail case for the width above the bound.** That one genuinely must not compile, and
`trybuild` is the mechanism `harness-the-type-system` and `a-hand-check-becomes-a-test-every-time`
name for it.

The tautological constant assertion goes, replaced by the properties the bound is about: that the
admitted set is coherent at every width in it, and that the count at the bound does not wrap.
