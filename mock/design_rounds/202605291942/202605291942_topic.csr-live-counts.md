# Live-count CSR: let a capacity-with-slack adjacency drive the sparse algorithms

arvo-sparse's `Csr` is a packed compressed-sparse-row matrix. The contract, stated in `csr.rs` and confirmed by every test, is that `NNZ` equals the real non-zero count: `row_end` of the last row returns `cap_size(NNZ)`, so the last row always runs to the end of the `col_idx` / `values` arrays, and `with_transpose`'s precondition requires `row_ptr` monotone with `row_ptr[ROWS - 1] <= NNZ` and every `col_idx[k] < ROWS`. The arvo tests bear this out: `round_trip_values` and `row_slice_views` both fill the arrays exactly, and the one empty-matrix test sets `row_ptr = [NNZ; ROWS]` to force every row empty.

That contract does not fit a consumer whose adjacency lives in a fixed-capacity buffer with a runtime live count. hilavitkutin's `DependencyGraph<MAX_UNITS, MAX_EDGES>` is exactly that: `unit_count <= MAX_UNITS` rows and `edge_count <= MAX_EDGES` edges are live, and the tail of each backing array is unused. Copying that graph element by element into a packed `Csr<{cap(MAX_UNITS)}, {cap(MAX_EDGES)}, W>` leaves the slack tail `col_idx[edge_count..cap_size(NNZ))` owned by the last CSR row (because `row_end(last)` is `cap_size(NNZ)`). The tail entries are the constructor's default `NodeId(0)`, so they read as edges to node 0. `with_transpose` then records those as incoming edges to node 0, and the spurious predecessors corrupt the real subgraph's analysis under RCM, block-diagonal, and Dulmage-Mendelsohn. The corruption reaches real nodes, not just the phantom tail rows, so it is not contained.

The fix belongs in arvo, not in the consumer. Forcing each consumer to pad, sentinel-fill, or otherwise bend the packed-CSR precondition reinvents a workaround for an arvo limitation at every call site, which is the failure mode the foundations exist to prevent. The `SparseAdjacency<N>` trait already names a live-node hook, `node_count()`, that every algorithm could honour; today every impl returns the cap. Honouring it as the live count, and teaching `Csr` to carry that count, is the minimal change that makes the existing abstraction do what its shape already promises.

This round parameterises the existing `Csr` / `CsrBidirectional` over the live counts rather than introducing a separate type. A separate loose-CSR type would duplicate the trait-impl surface and the algorithm-consumption path for no gain. The packed case stays the default, so `BitMatrix` and any existing packed-`Csr` consumer are unaffected.

## Current state

- `Csr<const ROWS: Cap, const NNZ: Cap, W: Copy>` (`csr.rs`): three arrays sized `cap_size(ROWS)` / `cap_size(NNZ)`. `new()` fills with defaults. `row_end(r)` returns `row_ptr[r + 1]` for non-last rows and `cap_size(NNZ)` for `r == cap_size(ROWS) - 1`. `node_count()` returns `ROWS.into()` (the cap). `SparseAdjacency<ROWS>` impl walks `col_idx[row_ptr[i]..row_end(i)]`.
- `CsrBidirectional<ROWS, NNZ, W>`: carries `forward: Csr` plus `transpose_row_ptr` / `transpose_col_idx`. `with_transpose` builds the transpose by count-prefix-scatter over `0..cap_size(NNZ)` and `0..cap_size(ROWS)`, using `cap_size(NNZ)` as the last row's end.
- `rcm_reorder_via` (`rcm.rs`), `block_diagonal_via` (`block.rs`), `dulmage_mendelsohn_via` (`dm.rs`): generic over `T: SparseAdjacency<N>` / `BidirectionalSparseAdjacency<N>`. Each iterates node seeds over `0..cap_size(N)` and sizes its visited / output arrays at `cap_size(N)`.
- Every node from `0..cap_size(N)` is therefore visited regardless of how many are live. A consumer with fewer live nodes than the cap has no way to express that.

## Changes proposed

1. `Csr` and `CsrBidirectional` gain two runtime fields, `live_rows: USize` and `live_nnz: USize`. `new()` defaults them to `cap_size(ROWS)` and `cap_size(NNZ)` respectively, so a freshly-constructed matrix is fully packed and behaves exactly as today. A `with_live_counts(rows, nnz)` constructor (or direct field assignment, the fields stay `pub` to match the existing direct-population style) sets a smaller live count.

2. `row_end(r)` returns `live_nnz` for the last live row (`r == live_rows - 1`) instead of `cap_size(NNZ)`. Rows at or beyond `live_rows` are empty. Storage arrays stay `cap_size(...)`-sized; only the iteration boundary moves.

3. `node_count()` returns `live_rows`.

4. `with_transpose` iterates `0..live_rows` (rows) and `0..live_nnz` (scatter), and writes the live counts through to the resulting `CsrBidirectional`. The slack tail is never read, so no phantom edge is ever counted.

5. The trait-driven algorithm bodies (`rcm_reorder_via`, `block_diagonal_via`, `dulmage_mendelsohn_via`) iterate node seeds over `0..node_count()` instead of `0..cap_size(N)`. Output and visited arrays stay sized at `cap_size(N)`; only the visitation bound changes. Slots for non-live nodes keep their default value and the consumer reads only the live prefix.

Backward compatibility: `BitMatrix::node_count()` returns `ROWS.into()` (the cap), and a packed `Csr` keeps `live_rows == cap_size(ROWS)`, so `0..node_count()` equals `0..cap_size(N)` for every existing consumer. The change is additive at the type level (two new fields with packed defaults) and behaviour-preserving for the packed case.

## Subtopics for the sketch phase

- **A. Transpose correctness under slack.** Live compile-and-run probe: build a `Csr` with `cap(4)` rows / `cap(8)` nnz but only 2 live rows and 2 live edges, call `with_transpose`, assert the transpose carries the reverse adjacency for the live nodes and that node 0 gains no spurious predecessor from the slack tail. This is the load-bearing correctness claim; it gets a live probe per `cl-claim-sketch-discipline`.
- **B. Algorithm visitation bound.** Confirm that switching the seed loop from `cap_size(N)` to `node_count()` leaves the packed-path results byte-identical (BitMatrix and packed Csr), and that the loose path visits only live nodes. Design-probe verified during SRC by running the existing test suite plus a new slack-input test.
- **C. Field-vs-constructor surface.** Whether the live counts are set via `pub` fields (matching the existing direct-population idiom) or a `with_live_counts` constructor, or both. Resolution leans toward both: pub fields keep the populate-by-assignment path, the constructor documents intent.
- **D. `successor_mask` and the `LinearOperator` / `SparseLaplacian` path.** Whether the spectral operator path needs the same live-count treatment. Likely yes for consistency, but spectral is out of this round's hot path (hilavitkutin's plan stage consumes rcm / block / dm first). Recorded; deferred unless the sketch shows a coupling.

## Why this is the right layer

`use-the-stack-not-reinvent.md` and the autonomous "fix the stack upstream, never reinvent in consumers" rule both point here: the engine hitting a packed-CSR wall is the same shape as the earlier arvo-graph 64-node cap, where the resolution was to widen arvo rather than hand-roll a parallel graph in the engine. arvo-sparse's own DESIGN states the intent: "any consumer that ships its own adjacency representation implements the trait once and reuses every algorithm." The live count is the missing piece that makes a capacity-with-slack consumer a first-class adjacency source.
