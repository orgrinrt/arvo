## Why

PR #40 merges the API additions for the bit-width refit family. The
reviewer surfaced four findings; this polish round closes them in
place before merge.

The headline finding is a contract clarity issue: `widen.rs` trait
doc and `arvo-bits-contracts/DESIGN.md.tmpl` claim the cross-Bits
Widen forwarder for `Bits<M, S, Signed>` "masks bits 0..M and
sign-extends bit M-1". The implementation does not. It calls
`raw.widen_to()` on the carrier, which sign-extends at the carrier's
high bit (i.e. preserves the carrier bit pattern). For sub-carrier-
width signed values where bits M..carrier_BITS may not match the
logical sign at bit M-1, the widening preserves the carrier bit
pattern, not the logical signed value.

This matches the existing signed `Narrow` macro (in
`arvo-bits-contracts/src/lib.rs:614`), which masks via the unsigned
shadow and `as`-casts, producing zeros in bits N..dest_carrier_BITS
regardless of the source's logical sign. So the substrate's actual
contract for signed sub-carrier-width Bits is **bit-pattern-
preserving across both narrow and widen**, not logical-value-
preserving. The implementation is internally consistent; the doc
prose was wrong.

The right fix is to retract the sign-extension claim in the docs
and explicitly document the bit-pattern contract. Consumers needing
logical-value-preserving signed conversion (rare, since the
substrate's signed Bits is mostly internal to `IFixed`) compose
narrow + widen with explicit sign-extension at the application
layer. This contract is a future-round concern if a real consumer
need surfaces.

## Decisions

### A. Signed sub-carrier-width Widen contract: bit-pattern-preserving

The existing signed `Narrow` macro produces a destination carrier
holding `(source as unsigned) & ((1 << N) - 1)` — bits 0..N from
the source, zeros above. This is bit-pattern-preserving, not
logical-value-preserving. Cross-Bits Narrow forwards through this
primitive impl, so signed cross-Bits Narrow is also bit-pattern-
preserving.

Cross-Bits Widen for signed sub-carrier-width Bits should match.
The implementation already does (it forwards through `raw.widen_to()`
on the carrier, which sign-extends at the carrier's high bit, i.e.
preserves the carrier bit pattern: zeros above N stay zero, ones
above N stay ones). The DESIGN.md prose claiming sign-extension at
bit M-1 was wrong; this round corrects it.

The contract is documented as:

> Cross-Bits refit for signed sub-carrier-width `Bits<M, S, Signed>`
> preserves the carrier bit pattern. Bits above the logical width
> M are taken from the source carrier as-is (typically zero for
> values constructed via `Narrow`, since the signed Narrow macro
> zero-pads above N). Consumers that need logical-value-preserving
> signed conversion (sign-extend at bit M-1) must compose `Narrow`,
> sign-extension, and `Widen` explicitly at the application layer.

This is a contract sharpening, not a behavior change. The
implementation already matches; the docs are catching up.
