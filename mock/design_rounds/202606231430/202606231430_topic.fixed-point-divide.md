# Topic: fixed-point divide (i_div_fixed / u_div_fixed)

**Date:** 2026-06-23
**Phase:** TOPIC
**Scope:** arvo-strategy (IArith/UArith + the arith macros), arvo (IFixed/UFixed Div rewire)

## The gap

`IFixed::div` / `UFixed::div` call `i_div` / `u_div`, which are plain integer `wrapping_div`. For F>0 that
is wrong: `0.5 / 2.0` (raw `0.5<<F` / `2.0<<F`) integer-divides to 0. Same bug class as the multiply that
round 202606231229 / PR #79 fixed. A fixed-point divide must rescale.

## The shape (mirrors i_mul_fixed)

For F-scaled raws `a`, `b`: `result_val = a_val / b_val = a / b` (the `2^F` cancels), and
`result_raw = result_val * 2^F = (a << F) / b`. So `i_div_fixed::<FRAC>(a, b) = (a << FRAC) / b`. The
numerator `a << FRAC` can exceed the container (needs up to N+F bits), so it is computed in a wider type,
exactly as the multiply widened its product.

Per-strategy (same container families as the multiply):

- **Hot / Cold 1..=64 (Min container N):** widen `a` to the native 2x (i128 / u128), `<< FRAC`, divide by
  the widened `b`, narrow. `Quantity = IFixed<31,16,Hot>` (N=48) uses this path, so the ikiuni decision-pass
  divide (Logistic) is unblocked by this round.
- **Warm 1..=64 (DoubleLogical container 2N):** the 2N container holds `a << FRAC` for F<=N, so
  `(a.wrapping_shl(FRAC)) / b` in-container, no extra widen.
- **Precise 1..=64 (DoubleLogical 2N):** same in-container shift+divide, then clamp the quotient to the
  logical bound (the Precise contract, round 202606231229).
- **Hot / Cold 65..=128 (container 128):** `a << FRAC` needs up to 256 bits, and dividing a 256-bit
  numerator by a 128-bit divisor needs 256/128 long division. There is no `carrying_div` intrinsic (unlike
  the multiply's `carrying_mul`), so this is a CATALOGUE RED this round: an `#[ignore]`d test pins the
  intended value, and the widen256 `*_div_fixed` arm uses the naive in-container `(a << FRAC) / b` (wrong
  when the numerator overflows i128). Tracked as a follow-up (256/128 long division). Not needed by sim #2.

## Div-by-zero

Mirror the existing convention: wrapping strategies (Hot / Cold / Warm) return the numerator `a`; Precise
clamps to the logical MAX.

## Rounding policy decision

Integer `/` truncates toward zero. The multiply floors toward minus infinity (an artifact of its arithmetic
`>> FRAC`). This round uses **truncate-toward-zero** for divide (the natural `/` behaviour, simplest, one
fewer remainder/correction step per arm). This leaves a documented asymmetry: `*` floors, `/` truncates.
Unifying the rounding policy across `*` and `/` is a separate tracked decision (it differs by at most one
raw unit on negative results, negligible for the sigmoid/ratio uses driving this round). Recorded so a
future reader does not mistake the asymmetry for a bug.

## Div rewire

`IFixed::div` / `UFixed::div` route through `i_div_fixed::<{frac(F)}>` / `u_div_fixed::<{frac(F)}>` with the
same `(): FracShift<{frac(F)}>` where-clause the `Mul` impls use (the const-generic shift carrier from
`arvo/src/fixed_scale.rs`). No public API shape change.

## Tests

- Hot/Cold 1..64 widen divide: `1.0 / 2.0 = 0.5`, `3.0 / 4.0 = 0.75`, a quotient whose numerator `a<<F`
  overflows the N-bit container but fits the i128 widen; negative signs; FRAC=0 reduces to integer divide.
- Warm / Precise divide; Precise quotient that exceeds the logical bound clamps.
- Logical-level `IFixed / IFixed` through the `Div` operator end to end.
- `#[ignore]`d catalogue red: Hot N=128 divide whose numerator `a<<FRAC` exceeds i128 (needs 256/128).
