# Topic: the gate over `mock/crates/` is untested, and two parts of it are broken

**Date:** 2026-08-31
**Phase:** TOPIC
**Scope:** `mock/lints/`, the imported lint pack, and the `undocumented-type` and `no-std` lints in
mockspace itself
**Status:** filed deliberately without doing it, so the next round has to address it

This is the re-filing that `202607270711_topic.the-lints-can-see-the-whole-crate-now.md` was owed. It
was consumed by round `202608311902` and archived with it, and the inheritance rule says a topic that
belongs to later work gets re-filed as a fresh flat topic after the round closes rather than being
carried inside a closed archive where nothing inherits it.

**What made it re-fileable is that a tree exists again.** That topic counted 128 lint findings across
a crate tree deleted on 2026-08-08, so the count is void: there are no files for those findings to sit
in. What survives is the fact underneath it, that the lints now read every source file rather than
only `src/lib.rs`, and that fact binds the three crates round `202608311902` wrote. Nobody has run the
count against them.

## Five lints gate this tree and none has a test

`no_std_enforcer`, `no_alloc_enforcer`, `no_dynamic_dispatch`, `no_runtime_grow` and
`arvo_bits_traits_only` in `mock/lints/` have zero test markers between them. Every canon-facing lint
in the same directory carries between eleven and twenty-three, so the habit exists in this repository
and these five are the ones that missed it. They are also exactly the five that read `mock/crates/`,
which is to say they are the gate over every line of source the canon will produce.

## Two of the five are measurably broken

Established rather than read off the source, in
`mock/research/sketches/base-primitives-gate/p4_the_untested_enforcers_have_holes.rs`, which
transcribes both predicates verbatim and carries a control that fails if the transcription is wrong.

`no_std_enforcer` matches `use std::` as a line prefix, so it never sees a qualified path expression.
`std::process::exit(0)` passes it, and so do `use std as platform`, a brace-first import, and an
import behind a `cfg` attribute on the same line. A qualified path is the ordinary way to reach the
platform without an import, so the hole is the common case rather than a corner.

`no_alloc_enforcer` matches the literal `" String"`, a space then the word, against the untrimmed
line. `String::from(..)` at column zero has no preceding space and passes, while the same expression
indented is caught, which makes the verdict depend on layout. An identifier beginning with the word
behind whitespace, `Stringify` or `StringBuilder`, is a false positive.

**The probe's first cut overstated that second class** and the probe refuted it: it claimed any
identifier ending in the word would fire, naming `CString`, which does not, because the token wants a
space then `S`. That wrong claim is kept in the file as a permanent negative so it cannot come back.

**The other three have not been examined at all.** That is a different statement from saying they are
sound, and it is the honest one.

## Two more defects, in mockspace's own lints rather than this repo's

Both were found by hitting them while writing the three crates, and neither is repaired.

**`undocumented-type` is unsatisfiable for a type whose name has no lowercase letter.** Its doc-side
extractor, `is_type_name` in `lint-rules/src/undocumented_type.rs`, accepts a word only if it contains
a lowercase letter. Its source-side collector takes every `pub struct` regardless. So `C8` is
collected from source, can never be collected from any design document however it is written, and is
reported as undocumented forever. Round `202608311902` renamed its carriers to `Carrier8` and
siblings, which satisfies the gate honestly and is a better name, and which is not a fix.

**`no-std` reads only the first thirty lines of a crate root.** A crate with a long module document
carries `#![no_std]` at line thirty-one and is reported as missing it. `arvo-format` hit this and
moved the attribute above the module document, which is also not a fix.

Both have the same shape as the two enforcer holes: the check demands something it cannot see, and it
fails in the direction that looks like the code is wrong.

## Why this is worth a round rather than a note

A gate with holes reporting green over source that violates the constraint is a fabricated claim of
correctness, and it fabricates it over exactly the source the canon is about to produce. The three
crates that landed are the first written from this canon and every crate after them goes through the
same five checks.

The work is bounded and unglamorous: five test suites with planted inputs in both directions, then the
fixes the tests make red. `mock/lints/canon_lint_testkit.rs` and the canon-facing lints beside it are
the worked example of the shape, so nothing here needs inventing.

## What a round on this should not do

**It should not lower a severity or reach for `lint:allow`.** Two of these lints let real violations
through, so the answer is a stricter check rather than a quieter one.

**It should not repair `[primitive-introductions]` again.** Round `202608311902` already replaced its
eight stale entries, seven of which named deleted crates and one of which silently exempted a new
crate that inherited a dead one's name. That is done and is recorded in that round's src changelist.
