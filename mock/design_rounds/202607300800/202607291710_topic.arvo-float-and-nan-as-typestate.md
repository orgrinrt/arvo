# Topic: `arvo-float`, and NaN as a typestate rather than a carve-out

**Date:** 2026-07-29
**Phase:** TOPIC
**Status:** one op call, and one op observation that reframes an existing workaround.

## D29. Floats get their own crate, and it takes the exceptions with them

**Decision (op, 2026-07-29).** `arvo-float` exists. It takes `FastFloat`, `StrictFloat`, the `Float`
alias, `Ieee`, the free helpers `abs_f32`, `abs_f64`, `sqrt_f32`, `sqrt_f64`, **and** the
float-specific carve-outs that exist only because a float breaks a contract fixed point satisfies,
such as `ConstSign`'s float impls.

**The reasoning is that the two are not the same kind of thing.** Fixed point is fractions in bits:
exact, and mathematics. An IEEE float is a hardware representation with its own rounding, its own
infinities and its own NaN. That difference is already load-bearing in the source rather than
theoretical, which is the argument for the split: floats cannot implement `ConstOrd` at all, because
NaN breaks reflexivity, and `ConstSign` exists precisely to give the ord-requiring predicates a path
that does not go through `ConstOrd`.

Taking the carve-outs too is the half that matters. Leaving them behind would keep every place a float
is an exception scattered through the crates that hold the rule, which is the state that prompted the
question.

## D30. NaN is a typestate question, and the carve-out is a workaround for not treating it as one

**Observation (op, 2026-07-29), recorded because it reframes work already scheduled.**

The current shape treats "floats have NaN" as a fact about the type, so the ordering contract is
withheld from every float and a parallel path (`ConstSign`) is built beside it. op's read: the
absence of NaN is a **property a value can be known not to have**, and this stack's whole idiom is to
carry such properties in the type.

Under that reading, a float known to be non-NaN satisfies reflexivity and can implement the ordering
contract like anything else, and a float that might be NaN **fails to compile** at the point it is
asked for an ordering, rather than being served by a separate trait. The refusal becomes a
trait-resolution error at the use site, which is the same mechanism `OneRepresentable` already uses to
remove `Identity<Multiplicative>` from a purely fractional type.

**So the carve-out is not a necessity, it is a workaround for a property that was never given a type.**
That is a design direction rather than a decision: nothing here says what the marker is called, where
the non-NaN obligation is discharged, or what it costs at a boundary where a float arrives from
outside and its NaN-ness is genuinely unknown.

It is recorded now because `arvo-float` is being created, and creating a crate around a workaround
without noting that the workaround may dissolve is how the workaround becomes permanent.
