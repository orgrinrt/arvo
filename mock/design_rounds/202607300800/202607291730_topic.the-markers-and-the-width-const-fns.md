# Topic: the marker family and the width const fns

**Date:** 2026-07-29
**Phase:** TOPIC
**Status:** op's call on the markers; the const fns derived from op's instruction that each is obvious
from its name.

## D32. The marker family splits on what it describes

**Decision (op, 2026-07-29).**

`IntegerLike`, `FractionLike`, `FloatLike` and `BoolLike` go to **`arvo-numeric-contracts`**. Each
names what kind of number a type is, which is a numeric contract and nothing else.

`BitPresentation` goes to **`arvo-bits-contracts`**. It describes how a value presents as bits, which
is the bit surface's question.

The split is on subject matter rather than on where they happen to sit together today, which is the
same correction D27 applies to `arvo-storage`.

## D33. The width const fns follow their subject

**Derived (agent), on op's instruction that the destination is obvious from each name.** Recorded
explicitly so that "obvious" is written down rather than re-derived by the next reader.

| Function | Subject | Destination |
|---|---|---|
| `ufixed_bits`, `ifixed_bits` | total container width of a `UFixed` / `IFixed` | `arvo-numeric` |
| `logical_width_unsigned`, `logical_width_signed` | logical width from I and F | `arvo-numeric` |
| `is_fractional` | whether `I == 0`, a property of the fixed-point shape | `arvo-numeric` |
| `width_le_64` | a width predicate read by container selection | `arvo-strategy` |

`width_le_64` is the one that goes elsewhere, and the reason is that it asks a question about
*container dispatch* rather than about a fixed-point value: it is the strategy crate's business which
widths fit which carrier. The other four are statements about `UFixed` and `IFixed` and travel with
them.

**`is_fractional` carries a second obligation.** It is one of the three GCE sites, appearing as
`[(); 1 / is_fractional(F)]:` at `ufixed.rs:274` and `ifixed.rs:308`. D3 already settled the cure
(`const { assert!(...) }`, stable, no feature), so it moves and is rewritten in the same pass rather
than being carried across as-is.

## Still to settle, carried here rather than into four more files

These were drafted as questions and not put, because the round was producing a file per answer and
that is the habit being corrected. They are the remaining open calls in this round.

**`BitMatrix`'s axes.** `rows: C::Array<Mask<W>>` makes W the per-row bit width and C the row count,
so a 64-bit row with 100 rows is 64 by 100 while the names suggest square. The release-blockers round
documented the asymmetry and explicitly deferred renaming it, and that renaming is still owed. D8
separately left open whether bits take the shape abstraction at all, and its own example argues they
should not: a bit shape wants `[Mask<4>; 3]` rather than `[[bool; 4]; 3]`. So the question is whether
to land the rename alone, or adopt the shape and let per-axis extents settle the naming as a side
effect.

**D10's projective-geometric-algebra fork.** D10 grounds rotation on rotors citing "Gunn's plane-based
PGA, with Dorst and Lasenby". The research pass found that lands on one side of a live unresolved
split: the bivector.net convention against Eric Lengyel's rigid geometric algebra, differing on
dimensional assignment, on what wedge and antiwedge mean, and on normalisation. Both ship code and
have consumers, and ikiuni needs the same machinery, so picking wrong is expensive across two repos.
Either stay with the cited lineage and record that a fork exists, evaluate Lengyel's convention
against the requirement first, or bench them the way D11 resolves the curve question.

**The UNORM encoding.** kirjo's colour pass found Direct3D divides by `2^n - 1` so all-ones lands
exactly on 1.0, while the same specification separately defines ordinary `i.f` fixed point for
subpixel positions. arvo's reasoning that `UFixed<0, F>` has no multiplicative identity is correct for
arvo's encoding; UNORM is a different encoding at the same width, and it does have an exact one. The
research flagged explicitly that this should not fall between the arvo and kirjo rounds. Either arvo
takes it as another fixed-point encoding, kirjo takes it as a colour concern, or the difference is
recorded and the first round that needs an exact one places it.

**`Natural`.** D6 left it "available to arvo" and nobody claimed it. `arvo-algebra-contracts` now
exists, which is where a mathematical primitive would sit.

**`ConstDefault`.** D27 could not place it. It is neither comparison nor bits, but the const-callable
form of `Default`. Candidates are the container crate, since `Bits` is its main implementor, or the
algebra crate, on the reading that a default is identity-shaped. Filing it by proximity is what
created the `arvo-storage` problem, so it stays open until argued.

**D18's band value.** What `Warm` and `Precise` resolve to between 65 and 128 bits, decided inside the
container-projection migration rather than before it. This is the one that blocks the changelist.
