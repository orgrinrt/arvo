# Topic: rank spans both element domains, and saturation stops borrowing the lattice

**Date:** 2026-07-29
**Phase:** TOPIC
**Status:** two op calls, one recording of something already decided, and one note about a question
that should never have been asked.

## D43. One rank abstraction over both element domains, and bits are not a special projection

**Decision (op, 2026-07-29).** Rank and extent are declared once, in `arvo-shape`, and both the value
domain and the bit domain implement them. `202607281126` called this the most consequential open
question in the design and it resolves toward one abstraction.

**op's correction to how the bit half was framed, which matters more than the call itself.** The
question was put with the bit projection described as packing the innermost axis into words, citing
D8's `[Mask<4>; 3]` against `[[bool; 4]; 3]`. The word framing is wrong and imports exactly the
assumption arvo exists to reject.

arvo's whole spirit is exact-bit definition. A consumer writes `Uint<7>` and means seven bits, rather
than being pushed to 8 or 16 because that is the ladder every other framework offers. Rounding to a
word buys nothing here: it is traditional rather than motivated, and the tradition exists because
other frameworks have no mechanism for the exact case. arvo goes n plus one all the way and uses only
what is needed.

The machine container is already chosen for it. `BitsContainerFor<N, Sign>` projects strategy, width
and sign onto a native primitive or a wide byte sequence, every one of them `repr(transparent)`, so
the lowering to a traditional width still happens and costs nothing. What that buys on top is the
strategy axis, bit packing without extra machinery, and optimisations that are not viable at all when
the width has already been rounded away.

**So the bit domain is not a projection needing an exemption.** A bit shape is a shape whose element
is one bit and whose extents are exact. Which primitive holds those bits is a question the container
projection already answers, one layer down, and the shape abstraction never sees it. D8's example was
always consistent with this: `Mask<4>` is four bits, not a word.

### The consequences, since op flagged not being able to see them all

Named here rather than discovered later.

| Consequence | Effect |
|---|---|
| `Mask<W>` | a rank-1 shape of bits with extent W |
| `BitMatrix` | rank-2, per-axis extents, which is D44 below |
| rank-generic algorithms | work over both domains when written against the element contract rather than against a container |
| `arvo-tensor`'s stated division | survives as a statement about storage and operations, and stops being load-bearing for the rank question |

**The one real risk, and why it is not a blocker.** Bitwise operations over a whole row are naturally
whole-container operations, while a shape contract presents elements. A per-element surface could
therefore look like it forfeits the cheap path. It does not, because
`arvo-always-optimal-internals.md` already separates these: the contract is per-element at the
boundary, and the implementation does whole-container AND, OR, XOR and popcount underneath. The trait
holds the meaning, the body does whatever the target makes fastest.

**The mask contract is not absorbed.** `arvo-mask-contracts` keeps set, clear, test and count. The
shape abstraction supplies rank and extent and nothing else, so a bit container implements both and
neither one grows the other's surface.

## D44. Per-axis extents were already the design, and square is an alias

**Recording, not deciding.** `202607281220` D2 already assigns `arvo-shape` "rank, per-axis extent
sequences, generic over rank". Per-axis extents are therefore settled and have been since that round.

What remains is a migration rather than a decision. `Matrix<W, C>` is square today because one
capacity parameter serves both axes, which `202607281126` correctly called fine for adjacency
matrices and Laplacians and fatal for anything spatial. It is an unfinished piece of the design, not a
position to overturn.

**op's addition:** nothing stops a bespoke `Matrix<N>` aliasing the square case of the general form,
in the same way `Rect` aliases rank 2 in D40. The name of the general ndim primitive it aliases is not
fixed yet and is settled with the rest of the shape vocabulary.

## D45. Saturation gets its own representational-limits contract

**Decision (op, 2026-07-29).** The second reader of `Bounded` gets a contract of its own rather than
continuing to borrow the lattice.

Saturating arithmetic clamps to what the container can physically hold. That is a fact about storage.
`Identity<Min>` and `Identity<Max>` are facts about a lattice. For every arvo numeric type today the
two coincide, which is the only reason the conflation survived long enough to reach this round.

Reading saturation through `Identity<Max>` names a lattice in order to ask a container a question, and
it produces a wrong answer the first time a type's representable range and its lattice bounds differ.
That is precisely the case where the answer matters, so the distinction is drawn now rather than when
the divergent type arrives and consumers have already built on the wrong reading.

**Placement follows the bridge-home reasoning.** The contract asks a container what it can hold, so it
lives with the container crate that D27 and D28 leave behind, alongside `Bits` and the width
conversions.

**D26 is untouched.** `Bounded` still dissolves into two `Identity` impls on the algebraic reading.
What changes is that the saturating path stops being one of `Bounded`'s readers, which is what made
dissolving it look lossy.

## A question that was already answered, recorded so it is not asked a third time

Whether `arvo-shape` is a new crate or what `arvo-tensor` becomes was put to op in this batch. It was
settled in `202607281220`, D1 and D2: the dimensional foundation "becomes its own crate below
`arvo-tensor` and `arvo-bitmask`", and `arvo-capacity` and `arvo-shape` are both listed as new, with
`arvo-tensor` surviving as a container peer over them.

**The mechanism is worth naming because it has now produced two wasted questions in one sitting.** The
question list was assembled from `202607281127`'s "Open questions for the talk" and `202607290600`'s
eighteen-item agenda. Both are stale by construction: they are lists of things written down in order
to be answered, and `202607281220` is the file that answered several of them. Trusting a recorded
agenda as the current open list inverts the order of authority between a question and its answer.

The corrective is to grep the round for the subject before drafting any question, and never to treat
an agenda as the open list. `202607292000_research.round-state-summary.md` now exists for exactly this
reason: one file carrying every topic's result, so the current state is readable without reassembling
it from stale lists.
