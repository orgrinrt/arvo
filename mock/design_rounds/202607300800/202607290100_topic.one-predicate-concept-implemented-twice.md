# Topic: arvo has one predicate concept, implemented twice, at the wrong level in both places

**Date:** 2026-07-29
**Phase:** TOPIC
**Status:** described and evidenced. The decision is op's and has not been made.

This began as a narrow question about whether `Pred`/`Pred2`/`Pred3` earn their place. Answering it
surfaced a second predicate family in a different crate, built on a different mechanism, unaware of
the first. Neither is complete on its own, and the completion of each is the other. That is a larger
finding than the question that produced it, so it is recorded separately rather than folded into the
restructure topic.

The supporting work is `mock/research/202607290030_predicates-arity-and-typestate-selection.md` and
the two sketches it points at.

## The two families

**Family 1 lives in `arvo/src/predicate.rs`.** `Pred<A>`, `Pred2<A, B>` and `Pred3<A, B, C>` are trait
aliases over `Fn(..) -> Bool`, each with a `Fn` supertrait and an empty blanket impl. Two callers,
both in `arvo-comb`: `greedy.rs:37` and `dp.rs:38`, each taking `feasible: impl Pred2<..>`. This is
the runtime family: the predicate arrives as a closure and is called per item.

**Family 2 lives in `arvo-numeric-contracts`.** `Predicate` is declared at `src/lib.rs:97` as
`pub const trait Predicate { fn test(self) -> Bool; }`, with five marker subtraits (`IsZero`,
`IsPositive`, `IsNonZero`, `IsNonNegative`, `IsZeroOrPositive`) and five wrapper types in
`src/predicates.rs` (`IsZeroOf<T>` and siblings). This is the type-level family: the predicate is the
type and the value is the receiver.

Both spell the method `test`. Family 1's receiver is the predicate with values passed in; Family 2's
is the value with the predicate in the type. The same word, inverted, in one crate graph.

## Family 2 already built the mechanism, and nothing reads it

`predicates.rs:36` states the purpose of the markers outright:

> the marker still gates which algorithms accept the wrapper

It gates nothing. Grepping `IsZero|IsPositive|IsNonZero|IsNonNegative|IsZeroOrPositive` across every
crate in the workspace returns hits in exactly three places: the trait declarations in
`arvo-numeric-contracts/src/lib.rs`, their own impls in `src/predicates.rs`, and the test file
`arvo/tests/predicate_family_const_probe.rs`. **No algorithm anywhere bounds on a marker.**

The clearest tell is internal to the family. `IsNonNegative` and `IsZeroOrPositive` have identical
bodies, and `predicates.rs:33` says they are kept distinct so a consumer can name the semantic it
means. A distinction whose entire value is being read by a bound, with no bound reading it, is a
mechanism built one step short of its purpose.

## What the typestate work establishes about why a typed predicate exists at all

From `sketches/202607290030_typestate-algorithm-selection/`, verified from emitted assembly rather
than from reasoning:

- A closure type carries no properties. A named type can, and a library can select an algorithm from
  one with no runtime branch, the discarded algorithm being **absent** rather than cold.
- The value is not codegen. At a single choice, typestate, a const-generic `bool` and a `const fn` are
  byte-identical and LLVM aliases them. The value is that the property **cannot desync** from the
  thing it describes.
- A `const fn` cannot discriminate on a type at all. An associated const is the only construct that
  makes a compile-time constant vary by type, which is what typestate is.

Family 1 cannot carry a property, because a closure is not a type a marker can be hung on. Family 2
can, and does, and is not asked. So the mechanism the sketches derived is already shipped here,
unpopulated.

## The consequence in shipped code, which is a correctness matter rather than a speed one

`impl Pred2<A, T>` is monomorphised, not `dyn`, so the predicate call already inlines. There is no
dispatch cost to remove and there never was.

What the missing property costs is defensive branching. In `greedy_group`:

```rust
// greedy.rs:58
if !open.0 {
    // greedy.rs:62
    if !feasible.test(&acc, item).0 {
        i = i + IDENTITY;
        continue;          // skip the item so the walk terminates
    }
```

That is an extra predicate call and a branch on every group-open. `greedy.rs:33` says why it is there:

> If a just-reset accumulator still reports an item as infeasible, that item is skipped to avoid an
> infinite loop. A well-formed predicate should always accept the first item of a fresh group.

**A required property, stated as prose in a doc comment, with no way for a caller to say it holds and
no way for the library to act on it.** A predicate carrying that guarantee as an associated const
makes lines 62 to 65 unreachable and the sketches show unreachable branches are removed rather than
predicted. A predicate that cannot promise it keeps the guard. `dp.rs:38` takes the same shape and
wants the same treatment.

## The inversion, which is the actual finding

Family 2 hangs the property on the **value**: `IsPositiveOf<T>` is a `T` about to be tested. The
typestate work says hang it on the **predicate**: a named predicate type carrying what it guarantees.

Those are not two flavours of one design. The second subsumes the first, because `IsPositiveOf` is the
degenerate case where the predicate has exactly one body and the property is its name. Family 1 can be
called but can promise nothing. Family 2 can promise but is asked nothing. Neither is worth having
alone.

## What this round has to decide

1. Whether the two families unify, and if so which shape survives. The candidates are recorded in
   `sketches/202607282230_hlist-arity-dissolution/FINDINGS.md`: Shape F (a `Deref` wrapper carrying an
   hlist as typestate, ordinary `f(a, b)` call syntax, no feature gates) is complete and enforced, and
   is the semantically correct one for both existing callers because `feasible(&acc, item)` is a joint
   atomic test rather than a chain.
2. Which properties are real. `MONOTONE`, `SORTED_OK` and `CHEAP` were invented to exercise the
   mechanism. The one with a named consequence in shipped source is the fresh-accumulator guarantee
   above. Anything beyond that is a bench question and belongs in `mock/benches/` per
   `bench-in-bench-harness-never-sketches.md`.
3. Whether asserted properties are admissible at all. A derived property (`N % 4 == 0`) is computed
   and cannot lie. An asserted one (`MONOTONE = true`) is an unchecked promise whose falsehood
   produces a wrong answer rather than a slow one, which is closer to an `unsafe` contract than to a
   tuning knob. From a call site the two look identical.
4. Where the unified concept lives. See below.

## Where it lives, and the constraint on moving it

The concept is not numeric. Family 1 is generic over arbitrary `A` and `T`; the hlist machinery the
sketches use is `notko-hlist` (D5 and D9 of the ndim round); `sketches/202607282230/FINDINGS.md`
already flagged that neither shape has numeric content. On subject matter it belongs in notko.

**The constraint is the return type.** `Predicate::test(self) -> Bool`, and `Bool` is declared in
`arvo-storage`, which depends on notko. A trait returning `Bool` cannot live below the crate that
declares `Bool`, by the same reasoning as `arvo-bridge-home-rule.md`. notko's own idiom at these
positions is bare `bool` (`Maybe::is`, `Outcome::is_ok`, `Maybe::filter<P: FnOnce(&T) -> bool>`),
which is its floor as the zero-dependency foundation.

So the placement question is really: does the general predicate concept return notko's `bool`, or an
abstract output, or does the numeric family keep a separate `Bool`-returning surface layered above a
notko core? That is a real fork and it is recorded in notko as a pending obligation at
`docs/202607290100_design.the-predicate-concept-may-belong-here.md` rather than settled here.
