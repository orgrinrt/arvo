# Topic: `Identity<Op>` already exists, and what algebra still needs

**Date:** 2026-07-28
**Phase:** TOPIC
**Scope:** correcting D13 of `202607281220_topic.the-ndim-and-shape-design.md`, and stating the actual
algebra gap and where it lands.
**Corrects:** D13, which described a missing mechanism that arvo already ships in a better form.

## The correction

D13 recorded that arvo lacks first-class monoids, and proposed parameterising by ZST operation marker
so that `Monoid<Add>` and `Monoid<Mul>` could coexist without Haskell's `Sum` and `Product` wrappers.

**arvo already does exactly that, and did before this round opened.** The agent had the context and
failed to connect it. `arvo-strategy/src/identity.rs` ships:

```rust
pub struct Additive;
pub struct Multiplicative;

pub const trait Identity<Op>: Sized {
    const IDENTITY: Self;
}

pub const trait Bounded: Sized {
    const MIN: Self;
    const MAX: Self;
}
```

exported from `arvo-strategy` as `Additive, Bounded, Identity, Multiplicative, OneRepresentable,
SignedIdentity, tag_one_representable`.

## What the existing design carries that the proposal did not

**One constant, not two, with the operation as the parameter.** The crate's own reasoning:

> An identity is only ever an identity with respect to an operation, so the operation is a parameter
> and there is one constant. The earlier shape carried `ZERO` and `ONE` together, which named two
> instances of one concept after their values and forced a type to have both or neither.

**Absence is a statement.** This is the part the proposal had no equivalent for:

> An identity element must be a value of the type it is an identity for, so where an operation has no
> identity in the type there is no impl, and naming `IDENTITY` for it fails to resolve rather than
> returning something plausible. `UFixed<0, F, S>` spans `[0, 1)`, which contains zero and does not
> contain one: it impls `Identity<Additive>` and no `Identity<Multiplicative>`.

The mechanism is a sealed witness. `tag_one_representable(int_bits)` maps the const space onto two
tags, and `OneRepresentable<TAG>` is implemented only at tag 0. **There is no `impl
OneRepresentable<1>`, and that absence is what removes `Identity<Multiplicative>` from a purely
fractional type.** The `#[diagnostic::on_unimplemented]` note explains it at the point of failure.

This is also the resolution of the `UFixed<0, 8>::ONE` defect, where the raw encoding of one is
`1 << F` and at `I == 0` the container is exactly `F` bits wide, so one is not representable at all.

**It already generalises past two operations**, by the crate's own statement:

> `Identity<Min>`, `Identity<Max>` and `Identity<BitOr>` each have their own correct element and
> arrive as new impls rather than as a third and fourth constant on this trait.

## The actual gap, which is narrow

A monoid is an identity plus an associative binary operation. **arvo has the identity half in full and
does not name the other half.** Addition and multiplication arrive through `UArith`, `IArith`,
`CrossStrategyOp` and core's operator traits; nothing pairs an associative combine with the
`Identity<Op>` that belongs to it.

So what is owed is a `Combine<Op>` sibling (name not settled) carrying the associative operation under
the same operation parameter. With that, the structures above it are supertrait lines rather than
designs:

- `Semigroup<Op>` is the combine alone.
- `Monoid<Op>: Identity<Op> + Combine<Op>`.
- A group adds an inverse; a ring pairs two monoids with a distributivity law.

**Folding then has something to fold with.** A fold over a shape, and a cascade folding across ranks,
both reduce to an identity and a combine, which is why the gap matters beyond tidiness.

## Where it lives

**Decision (op).** Monoids are **not** notko's. Semantically this is numerics and mathematics
territory, and notko is foundation primitives. The agent's earlier argument, that the fold needs the
monoid and the fold belongs in notko, does not override the semantic placement. Folding may be
notko's; the algebra is not.

**`arvo-algebra-contracts`** takes the structures, with **`arvo-algebra`** as the concrete sibling if
there are concretes to ship, following arvo's existing contracts-plus-sibling convention.

**`arvo-numeric-contracts` and `arvo-numeric` are tidied and redistributed** as part of the same
work. `Identity`, `Bounded` and `SignedIdentity` currently sit in `arvo-strategy`, which is the
strategy-marker crate, and whether they stay there or move to the algebra crates is open. This
interacts with the crate moves already settled in `202607281220`, D2, where `arvo-numeric` is created
to hold `UFixed`, `IFixed`, the float wrappers and the default contract impls that today sit in the
facade.

## Method note, recorded because it caused this correction

The agent proposed a mechanism arvo had already built, in a weaker form, having previously cited the
`UFixed<0, 8>` case in the same session without connecting it. **Before any further design work here,
the existing arvo, hilavitkutin and notko designs are to be read properly**, and the prior art
researched, rather than reasoned about from summaries. That reading is the next step for this round.
