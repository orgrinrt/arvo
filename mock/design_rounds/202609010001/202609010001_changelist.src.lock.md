## What lands

`Slots` gains `ADMITTED`, a defaulted associated const forced by every function in this crate that
reads the range, and `is_admissible`, the same question as a verdict.

**The trait is not sealed.** `proposal::the_concept_is_closed_and_the_inventory_is_open` is ratified
and a numeral wanting a third slot-range shape has to be able to supply one. The same proposition is
why prose was not enough: a new instance earns admission by supplying obligations, and closing the
concept while opening the inventory is "what makes admission a check rather than a negotiation".

## CHANGE: the obligation FROM three assertions TO five, computed in `i128`
File: `mock/crates/arvo-format/src/slots.rs`
Verification: `is_admissible::<SpanTooWide>()` is false, and a consumer using it does not build in
either setting of `overflow-checks`.

**My first obligation was insufficient and the panel's binding-time material is what found it.**

A range with `MIN = -2^62`, `MAX = 2^62 - 1`, `WIDTH = 62` passes every assertion I first wrote:
nothing is inverted and the width is in range. Its span is `2^63`, which is exactly what `slot_count`
cannot carry. Measured on a real consumer:

```
overflow-checks = true   ->  builds, then panics at runtime: attempt to add with overflow
overflow-checks = false  ->  builds, returns -9223372036854775808
```

**Both are wrong and in opposite directions.** One is a runtime check, which
`ruling::never_a_runtime_check_and_one_lowered_path` forbids outright. The other is the silent wrong
value the whole arc has been closing.

The obligation now also requires that the span fits a count and that the declared width can address
the range, **computed in `i128` so the obligation cannot overflow while checking that the thing it is
about does not**. Both are refused in both settings with a named message.

## Answering the three questions put to this round

**One: yes, the obligation is checkable in the profile arvo ships**, and it is measured rather than
assumed. `ADMITTED` refuses in all four cells of the `debug-assertions` by `overflow-checks` matrix,
because it is an explicit assertion rather than arithmetic, so the flag that governs arm C does not
govern it.

**The control is what makes that mean anything.** The same harness was run on arm C's shape in this
tree: `const fn add(a: u8, b: u8) -> u8 { a + b }` called at `200 + 100` refuses at
`overflow-checks = true` and produces `C = 44` at `false`. So the harness distinguishes, and four
identical cells is a result rather than an instrument that cannot vary.

**Two: arm E's property is what the guard needs and arm E's construction is not the only way to get
it.** Arm E works because the refusal is a value the const body inspects rather than a check the
backend may elide. `ADMITTED` gets the same property differently: it compares rather than computes, so
there is no arithmetic to be checked or elided, and the `i128` widening keeps it that way as the
obligation grew. Where the obligation does arithmetic it does it in a type the operands cannot
overflow, which is the same idea as inspecting a `checked_` result and is cheaper to read.

**Three: the three `apply.rs` sites are a separate round, and not because they are unimportant.** They
are on the adaptation map rather than the slot contract, this round's locked doc changelist does not
cover them, and `complete_slot` being `pub` with raw `i64` parameters raises the same question
`checked_width` raised two rounds ago about what a public const fn owes. That is a design question
needing its own doc changelist rather than a source edit smuggled in under this one. **Filed as a flat
topic after this round closes so the next round inherits it**, with the measurement, rather than named
here and forgotten.
