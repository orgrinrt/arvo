## Decisions sealed (from doc CL)

- D1: Hot strategy = single marker, align(16) baseline only.
- D2: N <= 128 → native primitives (u8/u16/u32/u64/u128 or signed); N > 128 → WideBits<bytes_for(N)>.
- D3: Delete `UContainerFor` + `IContainerFor`; unified `BitsContainerFor<const N: Width, Sign: Signedness>` only. No deprecation shims.
- D4: `const N: Width` in every projection trait. Width newtype relocates from arvo-storage to arvo-strategy.
- D5: Single per-Strategy impl via Pattern C const-tag dispatch through `Project<TAG, Sign, BYTES, S>` helper trait. 22 impls total.
- D6: `MultiContainer<HiT, LoT>` + `MultiContainerHalf` deleted entirely.
- C1: Byte-ordering convention: bit 0 = LSB of byte 0; lo-first cascade matching u128 semantics.
- C3: 128-bit boundary defended as rustc primitive ladder.

## Apply-time findings (post-stash-pop, 2026-05-03)

Two findings surfaced during the mechanical sweep of consumer call sites
after the parametric WideBits + Pattern C cascade landed.

### Finding 1: redundant `[(); ...]:` where-clauses caused E0275 trait-solver overflow

The user-facing `BitsContainerFor` impls originally carried both
`[(); tag_hot_cold(N)]:` / `[(); bytes_for_u16(N)]:` and
`Picker: Project<{ tag_hot_cold(N) }, Sign, { bytes_for_u16(N) }, Hot>`
where-clauses. The two are redundant: the const exprs in the Picker
bound's trait-arg position implicitly carry the WF requirement. Together
they recursed in the trait solver and produced ~74 E0275 errors at every
UFixed / IFixed call site.

Fix: drop the redundant `[(); ...]:` clauses, keep only the Picker bound.
Trait solver overflow eliminated; const-expr evaluation still anchors
through the Picker bound's trait-arg slots.

### Finding 2: `.hash()` blanket-impl chain fails cross-crate

`HasherExt::hash` (provided by blanket impl on `H: Hasher<N>`) cannot
satisfy `Hot: BitsContainerFor<N, Unsigned>` cross-crate via the
const-impl plus Pattern C chain. The bound is provable inside arvo-hash
(verified via probe `_probe()` with the bound declared as a function
where-clause; the probe compiled cleanly), but rustc method dispatch
over the blanket impl plus const-eval of `tag_hot_cold(64) = 3` and
`bytes_for_u16(64) = 8` cannot navigate the chain when called from a
downstream crate (`benches/variants/fnv1a` and `xxhash3`).

Fix: bench shims switched from `Fnv1a::<64>::new().hash(input)` to
`Fnv1a::<64>::hash_const(input)`. The per-N inherent `hash_const` is a
direct method, no blanket-impl chain. xxh3's streaming buffers up to
256 bytes anyway, so `hash_const` is also semantically more correct
for the larger 1024 / 4096 input sizes (streaming would only hash the
first 256 bytes; `hash_const` hashes the full input).

This is a rustc nightly trait-solver limitation, not an arvo design
issue. Revisit when the trait solver matures; the public `.hash()`
ergonomic should work cross-crate eventually. Until then, consumers
reach for `hash_const` for the one-shot path.
