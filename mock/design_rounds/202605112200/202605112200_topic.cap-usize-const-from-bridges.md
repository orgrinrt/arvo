# Cap / USize const-From bridges

The arvo primitive type-surface ships `USize` (newtype over `usize`) and `Cap` (newtype over `USize`) as the typed escape from raw integer counts at L0. Consumers that need to project a `Cap` to a `USize` (typed slot count, length, index bound) currently have three paths:

1. `USize(cap_size(N))` where `cap_size: Cap -> usize` is the canonical const fn in arvo-tensor and `USize(...)` is tuple-struct construction. Two steps; reads as "unwrap then re-wrap".
2. `Transparent::raw(N)` returns `USize` directly via the const unsafe trait. Verbose, plus exposes Transparent at the call site which is more of an internal implementation detail than an idiomatic typed projection.
3. `N.0` raw field-access. Workspace `PRINCIPLES.md.tmpl` already flags this as a smell; the workspace lint to forbid it is filed as a follow-up.

None of the three is what consumers actually reach for ergonomically. The idiomatic Rust path is `From<Cap> for USize` so `let n: USize = N.into()` works in returns, expression positions, and trait-bound calls. The existing `From<bool> for Bool` / `From<Bool> for bool` impls at `arvo-storage/src/platform.rs:318-330` are the precedent (non-const today; lifted to const in the same sweep).

## Subtopic A. Direction of the bridge family

`From<Cap> for USize` is the demanded direction (Cap → USize for counts / lengths / bounds). The reverse `From<USize> for Cap` is symmetric and useful for `array[i.into()]`-style consumer-side construction of capacity bounds from an index value, though less commonly reached for.

Decision: ship both directions in the same round to keep the symmetry clean. Both are const. Tests cover the round trip.

## Subtopic B. Scope of conversions

The full lattice of From / Into pairs between `Cap`, `USize`, and bare `usize` is six edges:

| From | To | Status |
|---|---|---|
| `Cap` | `USize` | THIS ROUND (primary ask) |
| `USize` | `Cap` | THIS ROUND (symmetric) |
| `USize` | `usize` | already covered by `Deref<Target = usize>` on USize plus `Transparent::raw`; `From` would shadow Deref ergonomics |
| `usize` | `USize` | already covered by `USize(n)` tuple-struct construction; `From` is the canonical form |
| `Cap` | `usize` | already covered by `cap_size(c)` const fn |
| `usize` | `Cap` | covered by `Cap(USize(n))` two-step; could be added |

Round 202605112200 scope: the two arvo-internal newtype edges (`Cap` ↔ `USize`). The `usize` edges stay through existing paths (Deref / Transparent / cap_size / construction); adding more `From` impls touching bare `usize` widens scope into ergonomic territory the next round addresses if a consumer demand surfaces.

Decision: just `Cap ↔ USize` this round.

## Subtopic C. `impl const` vs plain `impl`

The arvo workspace `pub const trait` framework treats const-callable as the default where the body can be const. The `Bool` precedent at lines 318-330 is plain `impl From`. For Cap / USize bridges:

- Body is trivial: tuple-struct construction + Transparent::raw (or equivalent). All const-callable on the underlying newtype layout.
- The `Transparent::raw(x)` const fn is already `const` (line 51 `unsafe impl const Transparent for USize`).
- Tuple-struct construction is const.

Decision: `impl const From<Cap> for USize` and `impl const From<USize> for Cap`. Const-callable at call sites including the new `.into()` form. Per `arvo-always-optimal-internals` and `arvo-compile-time-last`, runtime cost is zero (repr-transparent layout, monomorphisation collapses to a copy).

Side effect: `From<bool> for Bool` and `From<Bool> for bool` at the same file should also lift to const for consistency. Tracked as part of this round's src CL.

## Subtopic D. Lint that forbids `.0` field-access on arvo primitives

PRINCIPLES.md.tmpl lines 104-106 commit to a workspace lint forbidding `.0` on arvo primitives outside the implementing crate. That lint is not part of this round; it's tracked as a follow-up in `mockspace-hilavitkutin-stack-lints` once this round ships the `From` impls (without the `From` path the lint would over-fire on legitimate consumer code that has no other typed projection).

Decision: defer the lint to a follow-up round that lands in the stack-lints crate. This round only ships the From impls.

## Subtopic E. Field-pub status

`Cap(pub USize)` and `USize(pub usize)` keep their `pub` inner fields. Dropping `pub` is a follow-up audit (intersects with the workspace `.0`-forbidding lint). Risk: dropping `pub` is a breaking change for any consumer that did `Cap(USize(0))` or `USize(0)` construction — those would need to switch to `From::from(0)` or `0.into()`, which only works after this round lands.

Decision: this round keeps `pub` inner fields. The follow-up round drops `pub` together with the lint, once consumer construction sites are sweeped to `.into()`.
