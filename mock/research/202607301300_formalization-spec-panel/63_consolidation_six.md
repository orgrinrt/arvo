## The two rules

Two design rules are the review's real product, named once by the persona checkpoint at `48b` and
restated by every file since as the frame it works inside. Both keep firing, at positions further from
the numeral tower with each stretch.

**The spine rule.** A quantity that is computed and then has to appear in a type is a type; a quantity
that only ever has to be read is a const. Files 55 and 56 disagreed on the ordinal count of the rule's
own firings, one calling its finding "a fourth time" and the other calling its own finding "the fifth
reachable position" in one sentence and "a sixth time" in another, an inconsistency the fifth
consolidation left unresolved. This document counts once, from the founding instances the rule was
extracted from. Two founding instances, both op's, both at `44b`: the width chain and the biased-product
formula. Seven firings since the rule was named, in order: the fold's `Grade` (files 47/48); the
`Ranged` exponent bounds (reasoned by file 48, compiled by file 50); `Implicit`'s single exponent
(compiled by file 54, overturning file 36's own contrary claim); `Capacity`'s size (file 55, the first
firing outside the `Numeral` contract entirely, at a different crate and a different layer); the
notation macro's own const-struct face, sealing a computed reduced-fraction condition (file 56); the
notation macro's magnitude itself, a second and structurally distinct wall inside the same macro,
compiled separately by file 61 (a value-to-type escape for a literal's digits, refused identically to
the exponent case); and the shipped `arvo-strategy` container dispatch and its facade, where file 59's
reduced probe and file 62's whole-crate compile (sixteen refusal sites in `arvo-strategy`, four hundred
seventy-eight in the facade) confirm the wall is not a design-surface curiosity but the reason two live
crates carry a forbidden feature gate today. Nine occurrences in total, two founding and seven since.
What every file that has hit this wall agrees on is the shape, independent of which number a given file
happened to be counting: it is not a numeral-specific fact, it is a fact about `generic_const_exprs`-
shaped positions and the forbidden-feature list, and it now has one instance in the shipped tree as well
as eight in the review's own design surface.

**The carrier-at-birth rule.** A closed vocabulary that a guarantee quantifies over owes its seal and
its adversary at birth, not after three passes. Unchanged in mechanism this stretch; file 62 added a
fifth compiled route to `Rad<P>`'s own four-route seal (the `AtLeastTwo` predicate trait itself refuses

whole space") now covers five rather than silently becoming a stronger claim. File 61 found the same

## 1. The agreed shape

### 1.1 What a number is

Unchanged from file 40 and every consolidation since. A value of `Number<N: Numeral, S>` is an integer
k, drawn from a finite interval, together with a type-level rule injecting k into a set of rationals
(plus, for floats, a handful of data that are not rationals at all: `Specials`, section 1.16). The
numeral names the representable set and the indexing; D69 (op, `30b`) put them on two sides of the
design, identity parameterised in mathematical coordinates, not encoding coordinates.

### 1.2 The identity contract

```rust
pub const trait Numeral {
    type Radix:     Radix;        // Rad<P>, one constructor family over sealed Pos
    type Precision: Precision;    // significand digit count, primitive (D69), a Nat
    type Exponent:  ExponentForm; // where the exponent lives; nests the rest
    type Domain:    SignDomain;   // NonNegative | Symmetric | AsymmetricLow, a value fact
}

pub struct Implicit<E: Exponent, A: Adjustment, B: Bias>;
pub struct Ranged<EMIN: Exponent, EMAX: Exponent, U: Underflow, S: Specials>;
```

Every exponent position is a type. Both `Implicit`'s own `E` and `Ranged`'s `EMIN`/`EMAX` are computed
by `mulnum` and both have to appear in the result numeral's type, the spine rule firing on exactly the
shape it was stated for. `Exponent` itself is `EZero | EPos<P> | ENeg<P>` over the sealed `Pos`, sealed
at birth. No const route survives at any position this rule reaches; every permitted door (bare const
arithmetic, `min_generic_const_args`, a `const { }` block) is closed, compiled shut, and file 61 this
stretch confirmed the identical closure for a fourth and now fifth quantity (the notation macro's own
literal magnitude), stated in "The two rules" above.

`Radix` is a sealed carrier, `Rad<P>` the sole constructor over the sealed `Pos` bounded by
`AtLeastTwo`, exhaustive by construction. `Bias` and `Adjustment` are signed, gcd-normalised rationals,
value-unique and sealed, as ratified at `44b`.

### 1.3 Encoding, nested inside Lowering

Unchanged. `Lowering` changes no value; `Encoding`, nested inside it, may change which datum carries a
value. No law may read `Lowering`; a law's key is a `const fn` parameter list and `Lowering` is not a
parameter. File 59 gives this split its sharpest use yet: the float lowering door (section 1.21) is
safe precisely because it is a `Lowering` member and nothing else, derived rather than asserted.

### 1.4 The crossing contract

Three statements over the finite datum set of a numeral, unchanged in form:

1. `decode ∘ encode = id` on values, always.
2. `encode ∘ decode` is idempotent on data, always (canonicalisation).
3. `encode ∘ decode = id` on data iff the encoding is injective, a derived boolean.

The derivation, checked exhaustively by file 54 over the whole configuration matrix, stands unchanged.
File 60 gives statement 3 its first use as an operational tool rather than a classification: the
datum-versus-value order fork (section 1.20) is not a design-wide question at all, it is a per-numeral
question whose answer is exactly this boolean. `UFixed`/`IFixed`'s encoding is injective by
construction (no signed zero to repurpose, no NaN, no unnormalised-significand cohort, which needs a
radix above two); a float's is not. The fork lives wherever the boolean is false and is moot wherever
it is true, compiled at both ends by file 60.

### 1.5 The quantiser

Round-first, classify second, unchanged in mechanism, confirmed against binary32 on 41,380,159
operations with zero mismatches (file 50). For a `Ranged` numeral the quantiser gains a grid-selection
step in front of rounding, stated in full at `58:220-224` and unchanged this stretch. The overflow
band's closed form (lattice clause plus reachability clause) stands as file 50 built it.

**The quantiser's own statement was already radix-general; only its arithmetic kernel was radix-two
shaped, and that gap is closed.** File 59 found the design's own sentence for the quantiser (`radix^(e
- p + 1)`, `radix^e`) never named two, only its own file-50 model did, in exactly three places: grid
selection (`floor_log2` versus `floor_log_r`), alignment and rounding (`<<`/`>>` versus multiply or
divide by `R^k`), and carry-out renormalisation (`m >>= 1` versus `m /= R`). The repair, `R` as a const
generic so each instantiation monomorphises to its own radix, needed no change to the exponent function
at all, which is the finding worth keeping: the part of the quantiser that carries the design was
already radix-general before anyone checked. Checked at radix two against silicon (bit-for-bit,
32,768 operations, zero mismatches, the regression that confirms generalising did not break file 50's
own validated path) and at radix ten against an independent exact-integer oracle (same coverage; the
oracle itself panicked once on near-total cancellation dropping a result below either operand's own
grid, a defect in the check rather than the kernel, recorded because a reader should know the decimal
oracle was wrong once before it was right).

**A tie is reachable only at an even radix, checked rather than asserted.** `2 * lost == R^s` has no
solution for odd `R` at any `s`, since `R^s` is odd and the left side is even; the tie-breaking rule the
`Quantisation` axis offers is vacuous over half the radix axis's own domain. Radix ten keeps its ties.

### 1.16 The float model: absorbed with no new mechanism

Unchanged in its own content. `Underflow`'s two instances, flush-to-zero as a `Quantisation` resolution
rather than a `Numeral` fact, `Specials` as a four-point product, `TotalOrd`'s level fork: all stand as

**`Specials`' `NanOnly` witness confirms verbatim against the OCP specification's own text, and the
primary source itself carries a defect the review's secondary citation could not have shown.** File 62
read the OCP 8-bit Floating Point Specification, Revision 1.0, at Table 1 (page 13) and the prose at

### 1.17 Radix ten: the chain, the section, and the standard's own text

**The chain, unchanged.** Radix two normalises for free and stores a hidden bit; no radix above two has
a constant leading digit to hide, so its significand is stored unnormalised and a value has one datum
per representable exponent shift, a cohort. The remaining links are already named by the design's own
`Encoding::Fields` and `Encoding::Canonical` axes.

**Where the design and the standard part company is now stated more narrowly than the fifth
consolidation had it, and the narrowing is a genuine convergence rather than a concession.** File 62
read IEEE 754-2019 clause 5.2 at the paragraph and found the review's own characterisation had silently
generalised the standard's own two-branch rule. The standard's inexact branch selects the cohort member
of least possible exponent, which is a function of the result's value alone, exactly one of the two
natural cohort rules file 54 already compiled as a `Canonical` candidate. Three sharpenings follow. The
deviation is confined to **exact** results whose preferred exponent differs from the least-possible-
exponent choice, plus the two operations (`quantize`, `roundToIntegralExact`) that the standard's own
text carves out as datum-dependent by definition, never merely a `Canonical` reading. Multiplication on
`Implicit` decimal numerals delivers the standard's own preferred exponent by construction, because
`mulnum` computes exactly the exponent sum `Q(x) + Q(y)` at the type level; the same holds for
division's `Q(x) - Q(y)` on the held `divnum` shape. So "not conformant to the standard's preferred-
exponent rules," the fifth consolidation's own sentence, becomes "conformant by construction exactly
where the exponent is a type, and conformant for every inexact result under a least-possible-exponent
`Canonical`," which is a stronger and more precise position than the one it replaces.

**`Canonical = least possible exponent` becomes the stated default for decimal `Ranged` numerals,
marked reasoned rather than compiled.** File 62 declined to make this call; the `62b` checkpoint makes
it presumptively, on the ground that it is a default meeting op's own standard (representability
against MATLAB, IEEE 754 and SystemC) at zero new mechanism, and it is a default rather than a policed
choice since the other cohort rule stays available. One line for op to reverse; a second read is owed
before it hardens.

**The radix-ten quantiser's cost is now a real measurement rather than an open item.** Decimal costs
roughly twice binary, in software, at every point of a spread sweep (1.7x to 1.9x, file 59, harness-
run, comparable operand streams). Against a native `fadd` the ratio widens to 24x to 35x, using the
strategy-door bench's own hardware anchor, a consistency check rather than a second reproduction of
that number. Stated as an upper bound, not a floor: the dominant term is a division by a compile-time-
bounded constant (`R^s`, at most `P` distinct values for a given format) that nothing has yet strength-
reduced, and section 1.18's staging discipline names the same shape of win available here, an attempt
named rather than built.

### 1.18 The numeral notation: closed

**Closed this stretch, not merely narrowed.** The vehicle question `48b` left sketch-decidable is
answered: a proc-macro, adopted, with no external dependency.

**The declarative form does not fail because it is hairy. It cannot start, compiled twice over.** A
decimal literal is one atomic token to the lexer; no fragment specifier, no restringify-and-rematch
trick reaches its digits (file 61, section 1). The value-to-type escape (a `const fn` over the
literal's text driving a recursive type-level peel) fails identically to the exponent case, at the
identical wall, confirming this is a fact about the position rather than about the exponent
specifically (section "The two rules" above). One partial split is real and does not compromise the
refusal: a leading sign and an explicit `NUM / DEN` rational are each their own token and macro_rules!
*can* see them, which is not the ratified intent's "a consumer writes any number as a literal" and is
not proposed as a compromise notation.

**The vehicle: two entry points, connected to the sealed tower by an unsealed bridge trait declared in
the tower crate, and this shape is a structural necessity rather than a preference.** `raw_bias!(EXPR)`
emits a type expression; `numeral_face!(Name = EXPR)` emits an item, a concrete newtype implementing
`NumeralFace { type Encoding: Bias; const DISPLAY: &'static str; }`, itself deliberately unsealed since
it is an unbounded, per-literal vocabulary rather than a closed carrier. File 61 compiled why no other
shape is available: a macro-minted type cannot implement `Bias` directly, because the seal's private
supertrait is unreachable from a different crate, and a proc-macro's expansion crate is structurally
forced to be a different crate by Cargo's own `proc-macro = true` constraint. This sharpens file 56's
own recommendation (which framed the bridge as one legibility-preserving option) into a structural fact
about what a macro can and cannot do once the trait on the other side is sealed. The proc-macro needs no
external dependency at all (`extern crate proc_macro;` alone, lighter than the workspace's own
`notko-macros-core` precedent, not a departure from it): text parsing, digit extraction, decimal-point
folding into a rational, gcd reduction and bit decomposition are all ordinary host-side arithmetic, none
of it visible to the type checker because none of it produces a type-level obligation.

**Both ceilings, bisected to the exact bit, replacing the fifth consolidation's disagreeing figures.**
A `Pos` is nameable structurally through **128 bits**, refused at 129 (`E0275`, overflow evaluating the
`Pos` requirement). `Pos::VAL` reads back through exactly **`2^64 - 1`** (64 bits), refused at 65 bits
(`E0080`, a `u64` multiplication overflow at const-eval time), the exact boundary a `u64` implies rather
than an approximation of it. The two walls are independent, and the tighter one bites first: any
magnitude between 65 and 128 bits produces a `Pos` type that compiles, composes, and satisfies ordinary
bounds, and then panics the moment anything tries to read it back, which a ceiling guard set at the
looser figure would let through silently. The `10^20` figure from the fifth consolidation is not folded
into either bisected number; it stays open, plausibly a separate fact about a radix-ten accumulation
pattern (`10 * P::VAL + digit` rather than doubling; `10^19 < u64::MAX < 10^20` would make `10^20` a
reasonable just-past-the-ceiling figure for that specific pattern), unbuilt and unchecked.

**The vehicle's own refusal is two-tiered, adopted as the design recommendation.** Refuse at the
tighter, mechanism-specific readout threshold, print the actual decimal magnitude the macro has known
since before any type token existed, and name the refusal as the open widening question rather than a
notation defect. A vehicle refusing only at the looser structural figure defers an identical failure
into a worse, later, less legible position, for every magnitude in the sixty-four-bit-wide band between
the two walls.

**The whole-matrix test, and the bug it caught before this file existed.** 923 assertions: hand-picked
boundary and near-miss cases plus an exhaustive block over every three-digit magnitude. The first run
failed on the brief's own near-miss family, `37/53`, an explicit-denominator combination that silently
produced a valid but wrong `Bias` (`37/1` instead of `37/53`) through a one-character copy error in the
reduction arithmetic. All 923 pass after the one-line fix. This is the discipline "red is the lifeblood"
names working as designed: a strict test caught a real defect in the vehicle before any reviewer would
have.

### 1.21 The strategy door: compiled, replacing the presumptive table

**The door belongs to `Lowering`, derived rather than placed.** File 59's core result: the property that
makes a hardware lowering safe (it changes no value, under a pinned environment) and the property that
defines `Lowering` (the axis no law may read) are the same property, so the door is a `Lowering` member
and there is no fourth axis and no `Policy` member to mint. The rule is enforced by the language rather
than by discipline: a law trait keyed on the numeral alone leaves any lowering type parameter
unconstrained (`E0207`), unconditionally, and the receipt's own const face is walled a second,
independent time behind the forbidden feature.

```rust
pub trait LoweringDoor: Sealed { }
pub struct Quantised;
pub struct HostFloat<E: FloatEnv>(core::marker::PhantomData<E>);

pub trait Lowering { type Door: LoweringDoor; /* Encoding, StoredWidth, Layout unchanged */ }
pub trait HostImplemented: Numeral { }              // sealed, cfg-gated per target, a target fact
pub trait DefaultLowering<N: Numeral>: Strategy { type L: Lowering; }

impl<N: Numeral + HostImplemented> DefaultLowering<N> for Hot     { type L = HostLowering<N, IeeeDefault>; }
impl<N: Numeral>                   DefaultLowering<N> for Warm    { type L = SoftwareLowering<N>; }
impl<N: Numeral>                   DefaultLowering<N> for Cold    { type L = SoftwareLowering<N>; }
impl<N: Numeral>                   DefaultLowering<N> for Precise { type L = SoftwareLowering<N>; }
```

A door projected from the strategy alone, with a software fallback refined where the numeral is
host-implemented, is refused twice over: once by coherence (`E0119`, the identical structural-theorem
shape section 1.10's `Growth`-in-`Policy` closure already established, confirmed at a second position),
and once by `min_specialization`, the workspace's only permitted specialisation door, which reaches
neither an associated type nor an ordinary trait bound in the shape the fallback would need. The shape
that compiles needs no feature gate at all: one impl per strategy, `Hot`'s partiality living in a bound
(`HostImplemented`) rather than in a competing impl, refusing with the exhaustive "the following other
types implement" listing rustc prints unprompted because the marker is sealed.

**The corrected per-preset table, and the reading that makes all four rows fall out at once.** Every row
is derived from what the preset already means for fixed-point arithmetic in the shipped tree, carried
across to float by the same reading, rather than assigned by preference.

| preset | shipped fixed-point meaning | door | is it a choice |
|---|---|---|---|
| `Hot` | wrapping arithmetic, single instruction per op | `HostFloat<E>` where host-implemented, refusal otherwise | The only genuine choice, and it is `Hot`'s identity: one instruction per op. |
| `Warm` | container twice the logical width, exact-then-narrow | `Quantised` | Forced. No hardware `fadd` rounds outside the format; `Warm`'s whole identity needs a wider intermediate. |
| `Cold` | widens to 2x before operating, narrows on store | `Quantised` | Forced. Widen, operate exactly, narrow back is the round-first quantiser in miniature, `Cold`'s own doc comment giving the reason directly. |
| `Precise` | saturating, clamps rather than wraps | `Quantised` | Forced, and measured: `f32::MAX * 2.0` delivers hardware `inf`, where `Precise` owes the largest finite magnitude. |

**`Hot` is the only preset whose meaning is about the instruction; the other three are about the
intermediate, and an operation whose meaning is its intermediate cannot lower to an instruction that
has none.** The door assignment was never a table of preferences; it is what the four markers already
said, read at a numeral that happens to be a float, and three of the four rows stop being choices once
read this way. `Cold`'s presumptive justification ("follows the semantics-first side") is replaced: it
reached the right answer from a storage fact that does not imply it, where `Cold`'s own doc comment
derives the identical answer from something that does.

**The hardware door is reachable only in a uniformly-`Hot` expression, a property the shipped rank
ordering already delivered before the door question existed.** `Strategy::RANK` resolves cross-strategy
operations toward the more conservative side, `Precise > Cold > Warm > Hot`; `Hot` is the lowest rank
and the only preset whose door is hardware, so a mixed expression cannot silently acquire hardware
semantics. Compiled over the whole sixteen-cell matrix, one cell reaches hardware.

**Three build-layer obligations, stated so they are designed rather than noticed later.** Verifying the
declared control state against the deployment, invalidating it process-wide on any write to the FP
control register, and refusing rather than falling back when the first fails are all whole-program
properties a build layer owns; arvo ships a `const fn` receipt (four scalars off the door type) and
nothing downstream of it. The one thing arvo may cheaply offer is a debug-build assertion comparing live
control state against the declared one, three instructions of cfg-gated inline assembly.

**The printed number is corrected, and the mechanism it supports is unchanged by the correction.** The
software quantiser's cost against a native `fadd`, re-measured after `mock/benches/.gitignore` was found
discarding every artifact this review's benches had ever produced: the software column reproduces
