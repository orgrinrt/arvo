### 2.1 The domain-preservation equation guards a region the same checkpoint forecloses

That sentence is the tell. Under the ratified entry-level refusal, `Bounded<8192>` paired

anywhere in the program**. The cohort disjunct needs no equation either: a declared many-to-one
decode is total over inhabitants by its own definition, so no store can orphan. Both legal
disjuncts, one conclusion.

So file 95's probe_1 case B, the compiled evidence for the amendment, is constructible only in a

to survive". It does not survive **as spec text**, because a fact stated in two organs is the

And the pin: file 95's door-side refusal, kept as a **compile-fail test** when the real vocabulary

### 2.2 The terminating clause survives, with its one undefined term keyed on a term it already defines

My independent reading of `95:269-272` looked for the definition of "the outermost level arvo
constructs", and did not find one, and the gap is not pedantry: under the workspace's own no-heap
rule every byte in every consumer ultimately lives in a consumer-lent allocation, so "constructs"
either means nothing (arvo constructs values in consumer memory everywhere, so the clause
terminates at level zero) or means something the clause does not say. The repair is already in the
same statement: file 95's own section 4 defines "byte owner" (via `92`: the type whose safe
surface can reach a level's bits without `unsafe`). Key the termination on that:

> The per-level statement runs over every level whose byte owner is a type this design ships, and
> terminates at the first level whose byte owner is a consumer type. Beyond it the postcondition
> is a trusted-base entry stated once at the hand-over.

That is decidable from the API surface, where "constructs" is not. One further sentence makes the
entry's scope honest, and it is my one addition rather than a repair: the entry governs the

arena reality (columns resident in consumer arenas, read in place) is the common case, not the
corner. Stating that keeps the trusted base's perimeter exact: one entry, scope named, and the
provable half not silently annexed into it. With those two sentences the clause is, in my
judgement, correct and correctly tiered: it is the same cut CompCert makes at its last theorem,
and the design is right to refuse to state theorems about code it did not write.

### 3.3 The linked-library test is right, and its key is the lowering, not the fact

My independent reading asked the separation question: instantiate the test where its verdict could
go both ways for one candidate. The candidate exists and is the design's most important
environment fact. **Rounding mode is ambient for some operations and instruction-encoded for
others, on the same target.** Compiled and executed on this host
(`97_probes/probe_4_rmode_locus.rs`): with FPCR.RMode written to round-toward-plus-infinity, the
addition `1.0 + 1e-300` moves from `1.0` to the next float up, and `2.7 as i64` / `-2.7 as i64`
do not move at all, because the cast lowers to `fcvtzs`, whose round-toward-zero is in the opcode
(emitted body: `fcvtzs x0, d0; ret`, one instruction, asm committed). A linked library can change
the addition's rounding at runtime and cannot change the cast's. External corroboration, marked
external with its primary read owed to the ISA bundle file 93 opened: RISC-V encodes a rounding
mode per instruction with a dynamic escape (`rm = DYN` selects `fcsr`), so on that target even the
arithmetic operations classify either way **depending on which encoding the lowering emits**.

So the test survives with its key corrected: it is applied to **a fact as lowered**, not to a fact.
"Can a linked library change it at runtime" has no answer for "rounding mode"; it has an answer
for "the rounding of this operation under this lowering". Two consequences follow, both cheap.
First, the environment type's field set (file 94's fold) is keyed on the lowering, not on the
target alone: a lowering that emits static-rounding encodings has no RMode field in its bundle,
and the receipt correctly shrinks. That harmonises with where the environment parameter already
lives. Second, the clause "if no it is a lowering decision and gets a type, checked by the
compiler, with nothing in the trusted base at all" (`95b:93-94`) overstates by one word. Nothing
**new** in the trusted base is right; nothing at all is not, because the claim that the decision
was faithfully emitted rests on the toolchain, which is the standing trusted base every compiled
claim in this review already rides on. The distinction matters precisely because this stretch
watched the toolchain take back what a target gave (file 93's probe 3); the design's text should
not imply the compile-time tier is trust-free, only that it adds no deployment entry. One word:
"with no new trusted-base entry".

### 3.4 The receipt's refusal finisher converts an honest assumption into a refusal, and the defect it repairs lives at the verdict

This is my second substantive disagreement, and it is squarely in my subject. The adopted clause
(`95b:96-97`, from `95:437-446`): a zero mask declares the target cannot check the field, "and a
numeral whose correctness depends on an uncheckable field refuses at declaration rather than
passing a receipt."

The defect file 95 found is real: a boolean receipt returns `true` on a target that checked
nothing, which is a verifier structurally incapable of failing, the exact shape file 94 struck the
parity suite for. But walk the tiers. The environment parameter is ratified as **an assumption,
never a witness** (`91:854-855`). The receipt is not the guarantee; it is a debug-tier spot check
against the assumption, one artifact on the trusted entry's list. In a release build no field is
runtime-checked anywhere, on any target, and the design does not refuse those declarations; the
assumption stands, honestly listed, and the consumer who controls their deployment carries it
knowingly. A field the target cannot check is in **exactly that position**, minus one artifact: the
assumption's list has no receipt row on that target. The honest accounting is a trusted entry
whose artifact list says so. Refusing the declaration instead does two wrong things at once. It
polices: by file 95's own boundary sentence (`95:199-206`), policing refuses a choice whose cost
the consumer pays, and an unchecked-but-true environment assumption in a deployment the consumer
controls costs the consumer nothing and is theirs to sign. And it blurs the tier line from the
other side: where the review has spent two stretches stopping trusted facts from dressing as
provable ones, this clause makes an honest trusted fact **illegal**, as if unverifiable and false
were the same thing. They are not, and a design that treats them as the same has stopped keeping
the list this whole exercise exists to keep.

There is a case that deserves the refusal, and the clause conflates it with the one that does not:
a target that cannot **provide** the semantics (no gradual-underflow path at any cost, no software
fallback shipped). That is not an unverifiable assumption; it is a false one, statically known,
and refusal at declaration is correct there. The two cases are distinguishable at compile time and
the text must name them apart: **cannot-check enters the trusted base with its artifact gap
declared; cannot-provide refuses.**

The verdict-side repair is compiled (`97_probes/probe_2_receipt_verdict_split.rs`), and it costs
nothing. One per-field flag joins file 94's field set; `CHECKED_MASK`, `EXPECTED`, and
`UNCHECKED_IDS` (a bitset of field identities) all fold in const position with no feature gates;
the consumer's acknowledgment of the unchecked residue is a `const` assertion that refuses if the
bundle later grows a new unchecked field; and the emitted aarch64 receipt body is **four
instructions, identical to file 94's probe 5**, because the residue never reaches value position.
The boolean lie is gone: the split verdict reports "checked fields hold, one field unchecked"
where the boolean reported "true". A perturbation arm (file 95's own addition, adopted, and right)
completes the list.

One definitional gap rides with the clause whichever way it goes, and I name it open rather than
resolve it: **"depends on" is undefined.** The refusal (or the acknowledgment) needs a
required-field set per numeral, and nothing in the corpus derives it. It is plausibly derivable
from the numeral's own axes (an `Underflow::Gradual` binary16 numeral requires FZ16 clear; the
preset's rounding row requires RMode; a fixed-point numeral requires nothing), which would make it
provable-tier and const-computable, but that derivation is a proposal of one sentence's standing,
mine, unwritten. Until it is written, the clause quantifies over a relation nobody has defined,
which the completeness line does not permit a ratifying text to do silently.

*Grounded on: ratified (`91:854-855`, `91:620-626`, `95b:96-99`), settled shapes (`95:437-446`,

## 4. The division repairs

### 4.1 The two-arity fallback, confirmed, and its slot domain is the sentence still missing

The arity correction is right: one fallback for two cells collapses the distinction the
solution-set derivation established, and file 95's collision (a total `div_or` against clause 3's
partiality at `0/0` for NaN-less numerals) is real. Second read confirms both.

What the adopted text does not say is **what the directional slot does where the preset's own
resolution row already answers the cell.** Under the adopted derivation, `x/0` with a direction
borrows the range row: clamp goes to the far point, `Specials` deliver infinity, refuse refuses
(`93:293-301`, adopted at `95b:50-64`). So at `Warm`/`Cold`/`Precise` the directional cell **has**
an answer, and only `Hot`'s `ReduceModulo` (and the NaN-less `0/0`) are genuinely holes. A
consumer's directional fallback at a clamp preset either overrides the ratified row or is dead.
Both readings implement cleanly, and they diverge observably
(`97_probes/probe_3_fallback_slot_domain.rs`, executed): at a clamp-rowed model, `5/0` with
`f_dir = 7` returns 7 under the always-applies reading and the far point under the
holes-only reading; at the Hot-shaped model the two coincide, which is exactly why a fork argued
entirely at `Hot` never saw the question. The separation requirement, applied to the fallback's
own domain.

My suggestion, offered with its ground: **the slots fill holes; they do not shadow rows.** The
hole set is a function of the numeral and preset (which cells the resolution row leaves
unanswered), const-derivable, and a fallback slot exists exactly over it. The ground is the
two-organs discipline again: a per-call fallback that silently overrides a ratified resolution row
is a second home for resolution policy, reachable without reading the table, and the review has
now paid three times for two homes. A consumer who wants a different resolution at a rowed cell
has the resolution axis itself, where the choice is declared once and every law sees it. The
ratifying text needs one sentence either way; a signature alone cannot carry the answer, which is
the compiled point.

*Grounded on: ratified (`95b:50-64`), settled shapes (`93:288-335`, `95:344-381`), compiled and
run (`97_probes/probe_3`), reasoned (the hole-set proposal and its ground, mine, offered as a
suggestion, owed its own read).*

The admissible-remainder list ("a resolution-vocabulary member, a constant derived from the

## 5. The requirement-performance clause, second-read by first performance

The clause (`95:592-600`, adopted `95b:9-25`, itself on the working list at `95b:136-137`) says
both requirements are performed by the author of the ratifying text, on that text, before it
stands, and the performance is reported rather than cited. I am the first file dispatched under
it, so the honest second read is to perform it and report what performing it was like. The
performances are in section 7. What performing it taught, three things:

It is cheap. The term list for this file took minutes; the separation statements were already
written into each probe header because the probes were designed under the requirement, which is
the intended effect: the check moved from hindsight to design time.

It is not fully mechanical, and the clause should say so plainly. The grep finds whether a term
occurs; whether an occurrence **defines** is a judgement (file 92 defined "byte owner" without the
word "define" anywhere near it). File 95's own named attack surface (the author is the person
least able to see their own undefined terms) is real but aims at the wrong half: the fourteen/
fifteen discrepancy in section 1 shows the failure lives in **unre-run commands**, not in blind
spots about terms, and the performance clause is exactly the mechanism that forces the re-run.
A performance is a fresh execution; a citation is a memory. That distinction held up under use.

And it composes with the two-read discipline rather than replacing it: my performance below is
still one author checking one author's text, and the next reader re-running the two greps in
