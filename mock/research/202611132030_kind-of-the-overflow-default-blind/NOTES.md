# The kind of the overflow default ruling, read blind

This note reads one registry row, `ruling::a_shipped_overflow_default_is_a_generic_overridable_per_case`, and asks which value of the `ruling` namespace's `kind` field it carries. The row stands at `kind = "intent"` in the tree read here. The reading was done without opening the earlier double check, any review of `work/registry-repairs`, the arvo ticket file, or the log messages touching this field, so it is one independent reader's verdict and not a consolidation.

The field is declared in `mockspace.toml` (the `ruling` namespace, `name = "kind"`): `intent` for a want stated with no question in front of it; `ruling` for a question answered; `refusal` for an answer that a thing will not be done, which owes what happens instead; `deferral` for a question he declines to answer and hands back, which owes who it goes to; `process` for a call about how the work is conducted rather than about what arvo is. The declaration keys four of the five values on whether a question stood in front of the words and what the words did to it, so that is the first fact to settle.

## What stood in front of the words

The capture, `mock/research/202611130950_canon-double-check/OPS-WORDS.md` section "The overflow default", records that he was asked, with the priced page and the second plan in hand, what a `Warm` value becomes when it overflows in a release build, among four options: a, wraps everywhere; b, saturates everywhere; c, integers and indices wrap and fixed point saturates; d, `Warm` names no overflow behaviour and every alias keeps naming its adaptation. The row's own `note` repeats the same question and options. So a question was in front of the words, put to him with options, and this is a fact about the capture, not an inference.

His answer takes none of the four as put. It says the behaviour is not called one way, that arvo ships a default which is easy to override per case, that the default is a generic with a default, perhaps following a parity standard such as MATLAB's, floats `Saturating<Foo>` or `Wrapping<Foo>` as a possible mechanism, and adds a hedged remark that downstream users might primarily use the standard-paired implementations. Read against the question, this is an answer: what a `Warm` value becomes on overflow is whatever the shipped default generic parameter says, and the consumer overrides it per case. It is closest to option d with a shipped default added above it, which is how the row's `because` itself describes it ("declined to close it that way, which leaves the axis open and adds a shipped default above it").

## The five values

`intent` does not fit by the declaration's own words. The want is real, but it was not stated with no question in front of it; it was stated as the reply to a question with four options. The declaration makes the absence of a question the defining condition of `intent`, so a reply to a put question falls outside it. The tree does hold intent rows that were answers to put questions, `ruling::the_debug_abort_is_configured_by_the_consumer` being the nearest, asked with options and answered with a configurability want whose vehicle is left open, so the classification in the registry is not uniform; but that row is evidence of how the field has been applied, and it disagrees with the declaration in the same way this row does.

`ruling` fits. A question was put and the answer settles its subject: the overflow behaviour of `Warm` is a shipped, overridable default carried as a generic parameter, not one fixed behaviour and not no behaviour at all. That an answer cuts across the options does not stop it being an answer; the same day's sibling capture, `ruling::every_family_of_the_old_arvo_returns_and_the_shape_is_open`, is a reply that "took none of the three as put" and "cuts across them", and it carries `kind = "ruling"`. Nor does `ruling` require an `answers` edge to a registry `question` row: eighteen of the thirty `ruling`-kind rows in `mock/registry/ruling.toml` carry none (counted here by an awk pass over the file). So the row's statement that it narrows `question::does_warm_wrap_or_clamp` rather than answering it is consistent with `ruling`: the question it answers is the one put on 13 November, not Q6.

`refusal` fits only the first clause, "this shouldn't be called one way", which declines to fix one behaviour. But the declaration's refusal is an answer that a thing will not be done, and the rest of the answer is not about something withheld; it says what will be done, a shipped default generic. If one forced `refusal`, the `instead` would read: arvo ships a default overflow behaviour as a generic parameter with a default, overridable per case, the default following a parity standard. That an `instead` this full is the bulk of the answer is the sign that the answer is a ruling with a negative opening, not a refusal. The two refusal rows in the file are the comparison: in both, the substance is the declining, with `instead` the remainder.

`deferral` fits the residue only. He leaves which standard the default follows to "whatever would be the sensible default to use", and leaves the mechanism as a question ("Perhaps"). Those are handed back, and the row says the panel inherits them. But the question as put, what `Warm` becomes on overflow, is not declined; its shape is answered and a sub-choice inside it is left open. A deferral is a question he declines to answer, and this one he answered with a narrower question left over. Compare `ruling::wrap_or_clamp_stays_open_and_both_get_priced`, a true deferral: there he settles nothing about the behaviour and sends it to the bench.

`process` does not fit. The words are about what arvo is, its overflow behaviour and its shipped defaults, not about how the work is conducted. The parenthetical about the canon double check is a remark about process, but it is an aside to the answer, not its subject, and it would be its own row if it were anything.

## Verdict

`kind = "ruling"`. Confidence moderate, about two in three. Against it stands the registry's own uneven practice, where an answer to a put question that states a want and leaves the vehicle open has been filed as `intent` at least once; for it stand the declaration's wording, which makes a question in front of the words decisive, and the sibling row from the same capture day filed as `ruling` in the same shape.

The single fact that would change the answer: if the field's author intended "a question" in the `intent` and `ruling` clauses to mean a registry `question` row rather than any question put to him, then this row, which by its own note answers no registry question and only narrows Q6, would be `intent`. The eighteen `ruling` rows without an `answers` edge argue against that reading, but whether each of them answers a put question outside the registry was not checked row by row here.
